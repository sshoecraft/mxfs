## D-0133 — SB counter staleness on quiesce
Root cause (chain 116 s474c, 0.64.26, 2/2 reproduced): `xfs_log_quiesce`'s `P30-QUIESCE-RECOUNT` sums `pag->pagi_count/pagi_freecount/pagf_*`, which are rebuilt only on first AG header read or a fresh tenure. AGs a node never acquired stay mount-time-stale in its `pag` summary even though the underlying buffers ARE FUA-refreshed — so idle nodes recompute from stale cached headers (64/61) while workers compute the true totals (128/89, 128/125); 32 near-simultaneous unmounts (~300ms each, spread ~1s) race the whole-sector SB write, and whichever idle node's write lands last wins with the wrong numbers (regressors test9/test11/test28: PRE durable=128, wrote 64). `docs/history/docs/history/docs/history/compiled-sess474-475-d0133-sb-counter-campaign.md` `docs/history/docs/history/docs/history/compiled-sess474-475-d0133-sb-counter-campaign.md`

GPT design ruling (fix shape A+, preferred over "last member only" [rejected: unlocked RMW still races, membership==1 isn't a safe finalizer election] and a non-serializing variant): a dedicated `SB_SUMMARY` DLM EX lock (never AG0 — lock-order hazard) held across (1) draining local AG metadata first (log force + AIL push + buftarg wait, already done pre-P30), (2) an uncached-coherent recount (plain synchronous bio via `xfs_buf_read_uncached`, not a SCSI-FUA read which pierces to a lagging platter on this rig), (3) the cover, (4) the SB home write, (5) a flush, held until all of that completes. Never acquire SB_SUMMARY inside a metadata transaction; no inode/AG grant may be held when acquiring it. `docs/rulings/d0133-design-aplus-sb-summary-lock-uncached-recount.md`

Implemented as 0.64.28: `mxfs_sb_summary_key` = reserved slot 65 (beyond per-node pw keys and the samenode slot 64); `mxfs_sb_summary_lock/unlock` via `mxfs_v5_dlm_inode_lock(EX)`; `mxfs_sb_summary_recount_uncached`; `xfs_log_quiesce` sequenced LOCK -> recount -> RECOUNT-DONE -> WRITE -> cover -> buftarg wait+flush -> POST -> UNLOCK. First measurement (chain 116 s474c, 0.64.26 precursor) showed the mechanism working per-node but chk still failed — the lock itself was inert. `docs/history/docs/history/docs/history/compiled-sess474-475-d0133-sb-counter-campaign.md`

**Lock-inert discovery (sess475 MID1):** every node returned `P-SB-SUMMARY-LOCK rc=-19` (96/96) on 0.64.28. Cause: `xfs_fs_put_super` (`pal/linux/xfs_super.c`) sets `mp->m_mxfs_dlm = NULL` and runs `mxfs_v5_dlm_shutdown_defer_release` BEFORE `xfs_unmountfs` -> `xfs_log_clean` -> `xfs_log_quiesce`, where the locked recount lives — so the lock call always no-ops. Laps still passed by luck (uncached recount alone was correct absent real concurrency) — benign ordering, not real serialization. `docs/history/docs/history/docs/history/compiled-sess474-475-d0133-sb-counter-campaign.md`

GPT placement ruling: moving the locked section earlier in `put_super` (shape 9, DLM still alive) is **GO only** with: (a) every potentially log-producing work/cleanup path cancelled *synchronously* before the locked cover; (b) a "sealed" phase after lock release with assertions at every trans-alloc / `xfs_sync_sb` / SB-buffer-submission / cover-state-change site; (c) verify `!need_covered`, zero trans allocs, zero SB writes, no runnable work before destroying the DLM; (d) later `xfs_log_quiesce` becomes a guarded no-op under that invariant. Cleaner shape: split `xfs_unmountfs` into logging-capable prep (DLM alive) -> locked final cover -> strictly non-logging tail. An uncached re-read right before an unavoidable late unlocked write is explicitly **not acceptable** (read/write race undoes serialization) — late-dirty-after-DLM-gone must refuse the clean departure (mark `XFS_SICK_FS_COUNTERS`, loud report, recovery required), not silently re-write. Also flagged: the runtime `xfs_log_worker` SB cover (every 30s, unlocked) means the lock is **not** exclusive vs all SB writers generally (freeze/remount-ro/mixed-departure/crash weaker) — do not describe it as exclusive; opened as a follow-up defect. `docs/rulings/d0133-lock-inert-put-super-teardown-shape9-hardened.md`

## Rig trap — chain-gate collision (sess474, 17:58-18:02Z)
Four related traps discovered when a chain was gate-launched against a log that had *already* printed DONE:
1. A gate check must `grep -q '^DONE' $GATE` **before** launching — if already DONE, the launch starts immediately and can race a sibling gated on the same log (here: two `run.sh 32 caw prep_cluster` ran concurrently, both raced `install_ko` into the same tree `mxfs.ko` within a second; one got an empty/mismatched `sv=` and the harness did not abort on it — install_ko should hard-fail on empty/mismatched sv).
2. A harness's DONE-on-exit trap fires even on `kill` — killing one chain can cascade-start the next waiter (observed: kill -> DONE -> next chain started with rc=3 run-lock collision -> its own DONE -> the one after that started too). Aborting a chain requires immediately checking whether it just opened a downstream gate, and killing/relaunching that too; archive the polluted logs (`*.aborted_...`) since a relaunch appends to the same log name.
3. `timeout 300 ./run.sh ...` runs in its own process group (GNU timeout) — killing the `timeout` pid does not kill `run.sh`; kill both explicitly, then settle ~90-100s (one prep wall) for ssh fan-out remnants before the next prep.
4. A kill loop matching `/proc/*/cmdline` can match its own shell's cmdline (the search pattern appears literally in the command line) — exclude `$$`/`$PPID`/`*shell-snapshots*` or the Bash call kills itself.
