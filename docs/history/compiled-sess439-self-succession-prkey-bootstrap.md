## GPT ruling: bootstrap record + self-succession scope (04:xxZ)

``docs/rulings/bootstrap-record-self-succession-intent.md``

Question was how a rebooting whole cluster (all 64 slots dead) establishes recovery authority. Verdicts:
- Self-succession via REGISTER -EEXIST + ledger, then REGISTER-IGNORE + ledger FENCED-by-successor: UNSAFE. Concrete hazard: peer P wins the predecessor slot's fence-intent CAS; successor S REGISTER-IGNOREs old_key; P's prove-and-abort sees KEY_ABSENT_UNPROVEN; S crashes before its ledger write hits FENCED → unprovable residue (reintroduces the sess93 bug).
- No bootstrap record, rebooter claims a free slot ACTIVE and runs the existing pre-mountfs barrier over all dead records: UNSAFE for total outage — slot descriptors don't give a closed recovery manifest for the outage term, durable provisional identities for slotless actors, a mountfs gate before global completion, global completion evidence, or registrant-set closure for keys with no slot.
- A dedicated slotless bootstrap record: SAFE and recommended. Claiming one's own predecessor slot into GUARD is a conditional fallback only (replacement hardware), not the general path.
- 63-node cap is unnecessary once the dedicated bootstrap record exists.

REGISTER-IGNORE is permitted only by the owner of a durable CAS fence intent on the predecessor slot's descriptor, method=SELF_SUCCESSION, naming {victim tuple, old_key, old_key_gen, old_boot_uuid, successor provisional identity, transport-ID digest, bootstrap term, nonce}. Peer-owned intent always wins — successor waits for/consumes the peer's PREEMPT_ABORT_DONE rather than writing SELF_SUCCESSION_DONE itself. Certificate kind SELF_SUCCESSION_DONE requires: differing boot_uuid, confirmed nexus reinstatement on every predecessor path, old_key absent / new_key present on READ FULL STATUS across all transport IDs, no unclassified registrant, CAS'd under the owning intent. Unknown absence always stays KEY_ABSENT_UNPROVEN — never inferred.

Bootstrap record fields: state IDLE|CLAIMED|MANIFEST_SEALED|RECOVERING|RECOVERY_COMPLETE, bootstrap_term, owner provisional identity, heartbeat, fs_uuid, sealed victim-slot bitmap, ledger generation/hash, manifest hash, completion bitmap, crc. 5-phase order: (1) acquire bootstrap identity + seal manifest, (2) successor registration (self-succession per above), (3) fence every manifest registrant, (4) recover every slice via GUARD, (5) verify all complete → CAS RECOVERY_COMPLETE → convert to ACTIVE → mountfs. Long refusal list for cross-checks (key/host/boot ambiguity, multipath disagreement, stale term, unclassifiable transport, etc.) is enumerated in the ruling body — treat any of those as hard refusal, not retry-with-guess.

Design landed in `docs/whole-cluster-restart.md` §5.

## GPT ruling: PR-key register-before-ledger reorder (04:50Z)

``docs/rulings/prkey-register-before-ledger-derived-key.md``

MEASURED on 0.43.0 (chain 17, sv 7B7247CB): first node mounts and takes WE-AR; every later node's ledger CAS is a *write*, and under WE-AR only registrants may write any on-LUN metadata — so the ledger-before-REGISTER order from item 2 is unimplementable. Result: `P-PRKEY-PREPARE-FAILED rc=-52` (RESERVATION CONFLICT) → 31/32 mounts ENOTCONN. This is ``docs/history/docs/history/docs/history/compiled-sess439-self-succession-prkey-bootstrap.md``'s root cause.

Ruling: only permitted order is derive key → establish/replace **only our own** registration → verify → durably publish → only then any op touching other registrations. Derived key stays domain-separated hash(host_uuid‖boot_uuid‖fs_uuid[‖LU id]); collision against PR registrations or non-retired ledger entries is a hard refusal with no redraw (~63-64 bits of entropy after forcing bits — document, don't fix). Full order: derive K → generation-consistent READ FULL STATUS/READ KEYS → classify (K on our TID = reuse; K on foreign TID = collision refuse; predecessor key on our nexus = self-succession; unregistered = REGISTER(RK=0,SARK=K)) → verify K present → CAW ledger entry to REGISTERED directly (no PREPARED stage) → re-verify → claim. Crash between REGISTER and ledger write leaves an explicit UNCLASSIFIABLE orphan registration; same-boot retry repairs it via the same derived key, a different boot fails closed — peers must never guess-and-delete it.

Self-succession mechanism (supersedes the REGISTER-IGNORE path banned above): ordinary REGISTER(RK=Kold, SARK=Knew) on each nexus holding Kold — a target-side compare, changes only that nexus, no on-LUN intent needed — then verify Knew present/Kold cleared via FULL STATUS, then CAW a successor ledger entry `REGISTERED{Knew, succeeds={Kold, old_boot, old descriptor generation}}`. If Kold survives elsewhere, CAS the predecessor descriptor to SELF_SUCCESSION_INTENT and only the intent holder issues P&A. A peer may certify an absent Kold as REPLACED_BY_SELF_SUCCESSOR only if it holds the exact intent generation, sees stable global absence, and finds a durable CAW'd successor record naming the exact Kold+boot+generation plus Knew present on the expected TIDs — any other absence stays KEY_ABSENT_UNPROVEN.
