sess381 root-caused and closed two criticals in the SCSI-PR fencing lifetime: a single-holder reservation type that a routine clean unmount silently disarms cluster-wide, and a fence precondition failure that gets published as a permanent terminal guard with no retry path. Build 0.15.10 -> 0.17.0, `MXFS_PROTO_GEN` 4 -> 5, board 27/0/1-policy at 32/caw twice.

## Root cause, fully measured (answers `#379` step 0)

MXFS reserved the shared LUN with type 0x05 **WE-RO — a single-holder type** (`pal/linux/user.c:1317`). `mxfs_scsipr_reserve()`'s return value was discarded at all four call sites (`dlm/v5_mount.c:4320`, `:4031`, `dlm/mount.c:1980`, `:2191`), so a RESERVATION CONFLICT read as "someone else holds it, fine." `pal/linux/xfs_super.c:~1727` unregisters the node's key unconditionally at `put_super` (made mandatory by the sess377 PR-leak fix, `D-CLEAN-UNMOUNT-LEAKS-PR-REGISTRATION-377`). SPC-4 releases a `*_REGISTRANTS_ONLY` reservation the instant the holder's registration is removed.

MEASURED: `umount /mnt/shared` on test1 alone — `real 0m0.056s`, 0.49s wall — took the LUN from `holder_key=0x524c049d keys=64 distinct=32` to **`NONE HELD keys=62 distinct=31`**, with 31 nodes still mounted and registered. Nothing re-reserves; still NONE HELD after a 30s poll. ~30 minutes later, `virsh destroy test3`: elected prover logged `P236-FENCEKIND ... kind=NO_RESERVATION(8) proves_excl=0`, `P238-FENCE-UNPROVEN ... Recovery is BLOCKED on unproven exclusion`. The filesystem then became permanently unmountable — remounting test1 produced repeated `P236-CLAIM-UNCERTIFIED` then ABORT. No mass departure, no dirty slice, no crash: one routine unmount, 30 minutes later a routine kill, total brick. `docs/history/docs/history/docs/history/compiled-sess381-we-ar-fencing-lifetime.md`

The admission gate (`mxfs_scsipr_validate_admission()`, the sess378 `P303-FENCECAP` gate) is structurally blind to this: it validates the reservation it just created on the immediately-preceding line (`dlm/v5_mount.c:4320`), so it always reads OK even while independent observers see NONE HELD. There is no periodic reservation-health check anywhere in the tree — 31 nodes believed fencing was armed for 30 minutes it was not. Second root: `dlm/scsipr.c:437` returns `NO_RESERVATION` *before* the PROUT PREEMPT AND ABORT at `:459` — a pure precondition failure, nothing submitted, victim key untouched — yet it was published as a durable stage=1 guard nothing ever reopened. `docs/history/docs/history/docs/history/compiled-sess381-we-ar-fencing-lifetime.md`

Fix property proven directly against the target with a scratch key (no MXFS registration touched): under WE-AR (type 7, "Write Exclusive, all registrants"), unregistering the holder key leaves the reservation intact (`READ RESERVATION` still reports the WE-AR type), a second registrant's `RESERVE type=7` returns GOOD not CONFLICT, and RELEASE by any registrant works. Target confirmed to support it: `P303-FENCECAP type_mask=0xea01`, bit7 (WR_EX_AR) set. Two behavioral quirks to code around: under WE-AR, READ RESERVATION reports `Key=0x0` (no single holder key), and RELEASE/preempt raises a Unit Attention the next PRIN on other initiators will see as a failure. Harnesses: `tests/pr_reservation_ownership_probe.sh`, `tests/pr_all_registrants_semantics.sh`. `docs/history/docs/history/docs/history/compiled-sess381-we-ar-fencing-lifetime.md`

## Ruling 1: WE-AR is the right primary lever, plus new hazards it exposes

the design-consult rule verdict: switch to WE-AR (all registrants) behind the `MXFS_PROTO_GEN` bump. Confirmed independently on the rig: WE-AR survives removal of any single registration while ≥1 registrant remains; a holder-issued RESERVE with matching scope/type on an already-WE-AR reservation is a successful no-op (rc=0 from a second nexus); WE-AR beats EX_AC_AR (which also blocks reads by non-registrants — no extra write-safety, but outages during pre-registration reads, failover, diagnostics); PREEMPT AND ABORT under WE-AR removes the victim's registrations and aborts its task set while the reservation stays in force since the prover remains a registrant — no "transfer to A" concept needed. `docs/rulings/we-ar-fencing-lifetime.md`

New hazards WE-AR introduces:
- **`SARK == own_key` is not a self-fence.** The issuing nexus's own registration is protected from its own PREEMPT while *other* registrations carrying the same key are removed — under MXFS's one-key-across-two-nexuses scheme this silently kills sibling paths without fencing the issuer. Reject `victim_key == own_key` before issuing. Ties to `D-PR-KEY-32BIT-NODE-ID-COLLISION-RISK-377` (from sess377).
- No single holder key under WE-AR (READ RESERVATION returns `Key=0x0`, measured) — audit every parser/log line/certificate field/"one holder" assumption, not just `resv.type ==` comparisons.
- Stop reading RESERVATION CONFLICT as success. Under WE-AR a conflict from a correctly-registered requester means wrong type/scope or a lost registration — read back and classify (GOOD / conflict / transport-timeout-so-UNKNOWN / unsupported / unit attention).
- Admission gate needs a bootstrap branch: no reservation + no registrations = bootstrap and establish; correct WE-AR present = join; registrations present but reservation absent = degraded invariant, alert and repair under serialization; wrong type/scope = fail closed; incomplete PR view = do not admit.
- Do not PRIN from 32 heartbeat threads — one elected PR-health maintainer plus event-triggered checks (mount, unmount anomaly, target reset/unit attention, immediately before fencing) plus a slow jittered audit; the fencing path must verify/establish WE-AR itself rather than wait on a periodic thread.
- Re-reserving after a gap is not self-heal: "WE-AR absent while registrants live" is a high-severity safety event on its own — restoring it fixes future exclusion but does not prove the unprotected interval was harmless. `docs/rulings/we-ar-fencing-lifetime.md`

Fencing state machine (defect #2), phase encodes the **command-submission boundary**, not the reason: `PRECOMMAND_RETRYABLE` (nothing submitted, safe to retry) -> `COMMAND_MAY_HAVE_BEEN_SUBMITTED` (issued, outcome unobserved — timeout/path-failure/reset — must never be labelled "attempted nothing") -> `EXCLUSION_VERIFIED` (post-command verification passed) -> `TERMINAL_INCOMPATIBLE`. Do not derive retryability from `fence_kind` for new records — a future refactor could detect reservation loss after submission and the reason would lie; encode the phase directly. Keep the durable intent (slice still unreplayable) but make the guard reopenable under a fresh term via term/epoch-CAS'd updates, only current lease owner may advance. `GOOD` status is not a certificate: before certifying, still holding the fencing lease, re-read and assert victim key absent from a complete key view, reservation still held and right type, own registration present, PR generation consistent, all victim nexuses covered. Repairing already-bricked guards: reopen only when guard version+stage+kind unambiguously mean "returned before P&A" and the old term is dead and no later certified result exists; then victim key present -> P&A and verify; victim key absent -> do NOT fabricate a certificate (absence is equally consistent with a clean unregister or a plain PREEMPT without ABORT). `docs/rulings/we-ar-fencing-lifetime.md`

Rollout: a mixed cluster is unsafe — old binaries hard-require `resv.type == WE_RO` in three places (`dlm/scsipr.c:427` fence, `:661` admission, `:740` certificate verify) and would misclassify WE-AR as NO_RESERVATION. Sequence: ship a bridge version that reads both types but still creates WE-RO -> upgrade everyone -> drain non-holders first, WE-RO holder last (so the reservation survives until the cluster is empty) -> bump `MXFS_PROTO_GEN` while offline -> first new mount establishes WE-AR -> reject old binaries on the new generation. A live conversion has an unprotected RELEASE->RESERVE gap — exactly the interval class the design exists to prevent — so it is not the initial fix. Biggest hazard beyond the original proposal: **registration happens before admission** — a node gets SCSI write access the moment it registers, before the on-disk guard rejects it, and PREEMPT is not sticky: a preempted node can simply re-register its key and reacquire write access during the exact recovery interval the guard is supposed to protect. Needs registration/admission and fencing serialized under a cluster-wide lease, plus a rule that a key/incarnation may not register while its old slot is under recovery, plus no filesystem write I/O before admission completes — under the same protocol-generation change. `docs/rulings/we-ar-fencing-lifetime.md`

## Ruling 2: the fence-retry / takeover state machine

`FENCING` was being treated as durable work ownership with neither a durable retry source nor a takeover path — a one-shot heartbeat callback can never provide either. `fire_dead` sets `ctx->monitored[slot] = false` immediately before firing `expire_cb`, so a death fires it exactly once ever; `ctx->blocked[]` is purely a reporting array, not a retry queue.

**The durable bit goes the OTHER WAY** from the session's own first design. Not `F_FENCE_PRECOMMAND` (set at intent, cleared before submit — needs a mutable bit among sticky ones, cleared on a path that must not fail). Use monotonic `MXFS_RECOV_F_FENCE_CMD_MAY_HAVE_RUN`, set durably immediately before handing the CDB to the transport and never casually cleared — clear-by-construction on every early return, and the name stops future code from reading it as proof submission *did* happen. Required order: install FENCING intent (bit clear) -> all pre-command checks -> set bit durably + stamp -> wait for durable completion -> revalidate ownership/term -> hand CDB to transport. Crash before the flag write = nothing submitted; crash after but before submission = conservatively ambiguous, and that is the correct failure mode. Three durable states suffice: `FENCING`+bit-clear (guaranteed nothing submitted), `FENCING`+bit-set (reconcile before assuming anything), `stage >= FENCED` (certificate). In-memory name the middle phase **MAY_HAVE_SUBMITTED** — a transport handoff does not prove target execution; `VERIFIED != FENCED`, certification is a separate step. `docs/rulings/2-fence-retry-mechanics.md`

Retry driver, evaluated and rejected two options before landing on the third: (a) re-arming the heartbeat monitor is ACTIVELY DANGEROUS — `expire_cb` means one-time dead-identity retirement, re-firing it repeats retirement/notifications/slice-recovery-creation/purge/successor-rebasing and wrongly couples fencing liveness to heartbeat sampling; (d) fencing from mount admission is ALSO DANGEROUS — the mounting node isn't yet a member, its own PR authority may be unestablished, repeated mount attempts become a fencing storm, and admission/recovery locks can invert. (b) is right but a pure in-memory latch is insufficient (prover crash after arming loses the retry request — same bug class); **`stage == FENCING` on disk IS the durable outstanding work**, the latch is only a wake-up accelerator; 64 slots is cheap to scan. Keep the worker out of the heartbeat monitor state machine. The elected replayer KICKS the worker, never fences inline (inlining couples the recovery-execution lease to the fencing-attempt lease, inviting lock inversion). Certification fires an explicit `v5_fence_certificate_ready(slot, victim, epoch)` to wake blocked recovery — it must NOT repeat `v5_note_dead_node()`. `docs/rulings/2-fence-retry-mechanics.md`

Retry policy: backoff is liveness policy not a correctness lease — immediate, 250ms, 500ms, 1s, 2s, 4s, 6s capped, ±20% jitter, plus a global PR-op limit so 32 survivors don't hammer the target; retry immediately on membership change, reservation restoration, local registration, recovery-owner change, replayer discovery, or admin retry; never give up on attempt count or elapsed time — a non-retryable invariant violation enters an explicit durable QUARANTINED+reason state, never silent stop-with-automatic-looking-log.

Stale-attempt takeover (`-EBUSY` forever is its own defect): pre-command takeover needs, atomically in one CAS, still-FENCING + unchanged observed fence_term/prover/victim/epoch + abandoned lease + the old prover **definitively ineligible** (absent from live membership or under a different incarnation) — elapsed time alone is not a correctness lease, since a paused-but-live prover can resume and submit after a time-based takeover, giving dual authority; if merely wedged, fail-safe blocking beats dual submission. Do not reuse `MXFS_RECOV_ABANDON_MS` unless its clock/pause assumptions genuinely apply here.

Takeover after MAY_HAVE_RUN is the highest-risk part: never reset to "safe precommand" by bumping the term. The successor must reconcile — obtain a coherent PR snapshot (complete untruncated READ KEYS, READ RESERVATION, own registration present, expected WE form, stable generation across the compound read; one truncated/changing response is never absence). Victim key ABSENT proves exclusion only if MXFS separately prevents the retired incarnation from re-registering (explicit anti-rejoin property required) — certify under a kind meaning "verified exclusion from a coherent PR state after an earlier command may have executed," never claim a P&A this node did not observe. Victim key PRESENT does not prove no old command is in flight — before another P&A, need a bound covering transport timeout, target completion, fabric error recovery, local abort/drain, and the dead prover's inability to submit; without that bound, stay in reconciliation. Inconclusive -> stay FENCING/MAY_HAVE_RUN and retry, never convert a transient PRIN failure into operator-only recovery. Post-PREEMPT verification should be stricter than PROUT GOOD, but only once the reconciliation worker exists; a verification I/O failure after submission stays FENCING+MAY_HAVE_RUN and retries verification (not resubmission) — today's `P238-FENCE-UNRECORDED` is too pessimistic, even a failed certificate write should retry rather than go operator-only. Caller shape: replace obscure `<0/1` with `V5_FENCE_CERTIFIED / PENDING / FATAL`; one-time retirement + one-time recovery enqueue may still happen on PENDING, but the DEATH TRANSITION must never be re-run to retry a fence. `docs/rulings/2-fence-retry-mechanics.md`

Landing sequence, risk-ranked (highest risk last, done first for coverage): Increment 1 (in-memory phase, durable `MAY_HAVE_RUN`, descriptor-driven fence worker, retry of locally-owned FENCING/MAY_HAVE_RUN=0, certificate-ready wakeup, messages) is the one landed and verified this session; Increment 2 (pre-command stale takeover, dead/incarnation-changed prover only); Increment 3 (MAY_HAVE_RUN reconciliation — needs the most adversarial rig fault injection); Increment 4 (mandatory post-PREEMPT verification). Explicit carry-forward warning: do not claim the general "permanently unmountable" outcome eliminated until Increment 3 and certificate-write retry also land — Increments 1+2 remove it only for PRE-COMMAND failures. `docs/rulings/2-fence-retry-mechanics.md`

## Both closures — FIXED AND VERIFIED, 0.17.0

**`D-PR-RESERVATION-SINGLE-HOLDER-UNMOUNT-DISARMS-FENCING-381`**: reserve WR_EX_AR (0x07) behind the proto-gen bump; `held` decided by TYPE not by key (SPC reports holder key as 0 under all-registrants, measured); RESERVE return values no longer discarded; conflict read back and classified; admission gate observes *before* it acts (`P304-PREOBSERVE`) instead of validating a reservation it just created; both Write Exclusive forms accepted in fence and cert paths; `SARK == own key` refused. Also fixed a latent `user.c` bug found along the way: `cdb[2] = (type & 0x0F) << 4` put the type in the SCOPE field on every PROUT.

**`D-FENCE-PRECONDITION-FAILURE-RECORDED-TERMINAL-381`**: Increment 1 of ruling 2 — `enum mxfs_fence_phase` in memory, `MXFS_RECOV_F_FENCE_CMD_MAY_HAVE_RUN` on disk, a fence-retry worker whose queue is the on-disk descriptor, a per-slot single-prover guard.

The rig caught what code review missed: nine WE-RO type tests exist, not seven — grep found seven and missed two in `dlm/disklock.c` (~5007, ~5261), the certificate minter and its verifier. On the first patched build the fence PROVED exclusion and the minter then refused to certify it (`P236-FENCE-NO-RESV resv_type=0x07` / `P238-FENCE-UNRECORDED`) — the worst available outcome, since the victim key is already consumed by then. Only a real fence on a real cluster surfaced it. A claim from earlier in the session was also retracted: "`-EBUSY` forever, no stale-attempt takeover exists" turned out wrong — `mxfs_disklock_recovery_fence_takeover()` was fully wired at `v5_mount.c:~3783` (gated on `v5_node_is_dead`); the earlier grep only searched inside `fence_intent`. The real gap there is narrower and stays filed separately. `docs/history/docs/history/docs/history/compiled-sess381-we-ar-fencing-lifetime.md`

Verification, both tests in-repo and re-runnable: `tests/fence_lifetime_ab.sh` replays the exact bricking sequence, PASS on three disjoint node sets. `tests/fence_precondition_retry.sh` removes the reservation out of band with a scratch key, kills a node, restores the reservation: fence hit `NO_RESERVATION(8)`, published `P238-FENCE-PENDING ... command_may_have_run=no retry=automatic next_retry_ms=277`, re-drove itself 4x with visible backoff, certified with zero operator action 9 seconds after the reservation returned. Harness lesson worth the same weight as the code fix: the first run of `fence_precondition_retry.sh` FAILED because `virsh destroy` left the domain wedged "in shutdown" with the guest still running and serving I/O — no node ever died, and the test scored the absent fence as a code defect. Harness now polls `virsh domstate` until "shut off" and aborts with an explicit HARNESS/HOST FAULT verdict instead of a false test failure. (clyde's `test5` was left stuck in that state, guest healthy and a working cluster member — do not retry the destroy, the unkillable-wedge rule.) `docs/history/docs/history/docs/history/compiled-sess381-we-ar-fencing-lifetime.md`
