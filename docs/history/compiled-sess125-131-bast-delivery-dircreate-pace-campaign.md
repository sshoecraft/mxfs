## sess125 — deploy drought ends, defect gets a recipe, first two hypotheses die

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: sess105-125 had landed 12 DLM-core versions (0.11.440->452) without ever deploying — fleet pinned at 0.11.440, so under the zero-defect bar nothing exercising the new code could close. sess125 deployed 0.11.452 and reran the full 32-node board: 26/26 functional PASS. Process lesson banked here: never land more than one version without deploying; an undeployed landing is worse than nothing because it can't close its defect and silently accumulates regression risk for the eventual bisect.

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: D-CRASH-CONSISTENCY-32-NOTERMINAL-354 had been open since 2026-08-02 as "unreproducible, unidentified trigger" across three prior sessions (43, 45, 90), each closing on "immediate re-run passed." That control was invalid: crash_consistency.sh never removes its test dir, so the first run after mkfs does 3200 new dirent insertions (sf->block->leaf->node growth, cluster-coordinated) while every re-run does 3200 O_TRUNC overwrites of existing inodes — zero dirent mutation. Deterministic recipe: `prep_cluster` then `crash_consistency` FAILs 90s/90s virgin, PASSes ~21s on re-run. Host load, board-chunk adjacency, mount-root dirent count, and host writeback backlog were all measured and refuted as confounds. Arithmetic: 3200 creates / ~70s = 22ms/create, matching the project's known structural CAW publish rate — the slowness is a fully-serialized cost, not a starvation state; the ledger's "contention/starvation" mechanism text was wrong. Structural theory at this point: the per-AG adaptive yield quantum (`pag_dlm_yield_remaining`) has no equivalent for the directory inode DLM lock, so every dirent insert pays a full cluster-wide EX handoff. Re-attributed 354 as a manifestation of D-32NODE-SHARED-DIR-CREATE-PACE inside crash_consistency's 90s budget — the two could not be dispositioned independently at this point.

`docs/rulings/dir-tenure-batching-design.md`: design consult on a directory-EX tenure-batching fix (op-quantum for the yield quantum theory above). GPT accepted the diagnosis but rejected the fix's causality: you cannot know a create is a one-shot until enough time has passed to see no second op arrives — that inter-arrival grace is what the existing MHT clamp was trying to bridge, so the fix must relocate WHERE/HOW the grace applies, not delete it. Required hybrid: post-BAST op budget, idle-grace measured from last completed op (not EX grant), hard deadline measured from BAST receipt (not grant), adaptation only from completed-tenure outcomes, N~4-8 not 512, cross-tenure state treated as disposable/generation-tagged. This design was never built — see next entry.

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: before building the batching fix, harvested probes to confirm the underlying "dir-EX ping-pongs once per create via the MHT 15ms clamp" mechanism. NOT confirmed: only 25 P70-BP events total on the shared dir's inode across the whole failing run — 3200 creates cannot be 25 lock tenures. Probe census instead pointed at P68-EVDECIDE (12069, ~4x create count) and the P150 ALLOC/FREE family (~2500-2750, matching 3200-create scale) as better-matching suspects, i.e. inode allocation, not directory locking. Lesson: do not patch a clamp on an unconfirmed mechanism; a probe not gated to the watched inode (P70-BP fires cluster-wide) will mislead an aggregate histogram.

## sess126-127 — two more roots die, the real one is found

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: new tool, wall-clock stack sampling at 20Hz (`mxfs_stackprof.py`/`cc_stackprof.sh`) — attributes ~100% of workload blocking wall to the CAW inode grant wait, on the **mount root inode 128**, not the test directory (all prior sessions chased the wrong inode). 202 PR grants >5ms cluster-wide, mean 3533ms, sum 713681ms. Root theorized as a read-side livelock: 7 nodes hold PR on root and don't drain under an EX BAST because new PR readers (continuous path-walks for dd/md5sum opens) arrive faster than `mxfs_drain_ilock_read` retires them; the EX waiter's yield ticket freezes for ~3s until the 5s `MXFS_CAW_YIELD_TIMEOUT_MS` stale-ticket valve fires and the cycle repeats — the system running on its safety valve. Two fix candidates proposed: (a) read-side barrier once a conflicting BAST is pending, (b) bounded PR patience clocked independent of ticket rotation.

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: hypothesis (a) from sess126 directly REFUTED — P132-ILOCK-STUCK/-TIMEOUT is 0 on all 32 nodes, and `mxfs_drain_ilock_read` stacks are only 0.55% of blocked wall. The real root, found via new holder-side census (`cc_bastcensus.sh`) plus a stack-sampling FOCUS mode isolating the BAST release path: `bast_recv_fn` is a single thread per node that calls `bast_cb` **synchronously inside its UDP recvfrom loop**, and that chain bottoms out in a synchronous shared-LUN SCSI slot READ (`mxfs_dlm_caw_held` -> `find_slot`) to answer "do I hold this resource?" — a question already answerable from the in-memory `ctx->held` list. Measured: only 145 release pipelines cluster-wide in 90s (~1.6 handoffs/s) against 19 queued waiters, and `/proc/net/snmp` showed `RcvbufErrors=8085` — every UDP receive error is a receive-buffer overflow, meaning BAST hints were being silently dropped despite an already-4MB-locked `sk_rcvbuf`. This is the second half of a fix sess35 only did for the grant-nudge path (`wake_mask` to skip the disk re-check on nudge receivers) — the BAST path never got the same treatment. Fix shape proposed: `bast_recv_fn` does zero device I/O, answers held-state from memory, coalesces duplicate hints per resource, and moves `mxfs_caw_orphan_forensic`'s full slot scan off the hot path.

## sess128-129 — the fix, designed then verified

`docs/rulings/bast-dispatch-queue-design.md`: design-consult ruling approves the dispatch-queue shape with mandatory amendments: route `bast_poll_fn`'s inline callback through the *same* queue (today recv and poll can run callbacks for the same resource concurrently — new serialization, not a relaxation); 1-2 workers only (matches today's concurrency, more needs a lock-order audit); queue-based coalescing not time-based debounce; keep `POLL_RELAX_MS=4000` question open — the "UDP is up so disk poll doesn't matter" premise is refuted by RcvbufErrors=8085; mode-merge must be the conservative lattice join (not numeric max — PR/CW are incomparable, `max(CW,PR)=PR` is wrong, correct join is PW); preallocated pool + hash chains, not a direct-mapped table; never hold the queue lock across `bast_cb`; requeue at tail not head; teardown order producers-then-workers-then-free. Explicitly deferred: in-memory held-list prefilter as a drop reason (memory may justify processing a BAST, never dropping one) and the orphan-forensic offload. Code landed in this session but not wired — nothing ran yet.

`docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: wired the sess128 machinery (init/free lifecycle, dispatcher startup ordering guaranteeing no submit lands on an undrained queue, bounded worker join, `P265-BASTQ-STATS` probe), built as **0.11.453**, deployed, and measured 3/3 on the exact deterministic recipe that failed 3/3 on 0.11.452: `RcvbufErrors` delta 0 (was 8085), crash_consistency PASS 32/32 in 77-79s (was FAIL 90/90). Full board rerun: 27 PASS/0 FAIL. Correction on mechanism: coalescing carries only ~6% of load (submitted/dispatched ratio 1.05-1.06x, hiwater never above 2) — the fix works by decoupling the UDP socket drain from the synchronous disk read, not by deduplicating hints. Do not tune the coalescing table expecting it to matter.

## sess130 — a harness confound, then a clean re-measurement that overturns the headline

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: found that `cc_grantwait.sh arm|mark` and `cc_bastcensus.sh mark` ran `dmesg -n 8` to stamp their kmsg boundary, which raises `console_loglevel` to 8 and pushes every mxfs pr_warn/pr_info to the console synchronously under `console_lock` — onto a host-file-backed emulated serial console. A/B on identical 0.11.453 virgin-fs recipe: loglevel 8 -> FAIL 90/90 NO_TERMINAL_RECORD=32 (7061 `mxfs:` lines to the host serial log); loglevel 1 (run.sh's own `printk='1 4 1 1'`) -> PASS 32/32 79s, at *lower* host load, ruling out load noise. This invalidates the magnitudes (not the direction) of sess126's numbers, which were measured under `arm` (instr=1 + loglevel 8 together) — the yield-ticket convoy finding stood, its 3533ms figure did not. Fixed via `tests/quiet_console.sh` (the source-tree rule), sourced by both harnesses instead of `dmesg -n 8`. General rule: this is a second, independent knob (fires even with instr=0) alongside the already-known `mxfs.instr=1` pace-perturbation trap — before trusting any pace number, check `cat /proc/sys/kernel/printk` reads `1 4 1 1` on every node.

`docs/history/docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: clean (loglevel-1) re-measurement. The yield-ticket convoy is confirmed gone: valve firings 0/567 (was dominant), ticket age at defer p50 10ms/p90 69ms (was 2873/4588ms), ino-128 grant-wait sum 502ms (was 713681ms), crash_consistency PASS 5/5 (79/79/77/79/82s). Queue conservation closes exactly per GPT's earlier demand. But the defect's own headline number was wrong: `create_scale_curve.sh` shows shared-vs-private pace at 32 nodes is now 1.62x, not the ledger's 42x — the shared-dirent term has largely collapsed. However PRIVATE per-node dirs, assumed flat in the original defect text, in fact degrade 24x from 1 to 32 participants — a false premise in the ledger. Grant waits are no longer where the wall is (19 waits >5ms totaling 2026ms against a 79s run), so the CAW inode lock is no longer the bottleneck; candidates for the next root: AG-DLM inode allocation, log/journal serialization, CAW transport bandwidth — unresolved at handoff. Same-session GPT review flagged code hazards in the queue: a claimed UAF on teardown-timeout (refuted next session, see below), `ctx->running` cleared before producers joined (a late hint can be lost with no backstop), an undisproven recursive-PR self-deadlock, and `FASTPOLL_MS=2000` as a fixed post-overflow window that may not drain 2048 entries through 2 workers in time.

## sess131 — 354 closes, and a second defect's mechanism surfaces as a side effect

`docs/history/docs/history/compiled-sess125-131-bast-delivery-dircreate-pace-campaign.md`: closes D-CRASH-CONSISTENCY-32-NOTERMINAL-354 FIXED AND VERIFIED against all four the zero-defect bar tests (cause proven sess126/127, patch targets that cause sess128/129, test exercising the cause passes under unchanged 90s criteria 5/5, discriminators flipped) — ledger 29->28. The prior "cannot be dispositioned independently of D-32NODE-SHARED-DIR-CREATE-PACE" claim is explicitly retired: the two symptoms shared the CAW-grant-wait mechanism and no longer do, since residual pace is now outside that path entirely (19 waits/2026ms vs a 79s run). Explicitly left open, folded into D-32NODE-SHARED-DIR-CREATE-PACE: the virgin-77-82s-vs-aged-15-21s gap, and margin risk — passing runs consume 86-91% of the 90s budget, one modest regression away from re-failing; budget must not be widened. Also refutes sess130's GPT UAF concern by code reading: `caw_join_bounded` never returns without a confirmed-exited thread (second bounded join + `mxfs_pal_failstop()` on a second timeout), and `mxfs_dlm_caw_destroy` gates the free behind `unsafe_to_free`. The producers-not-joined drop window is real but benign — the same phase-0 section that clears `running` also sets `ops_closed`, which gates every release entry point, so a delivered late hint could not have been acted on regardless; only two now-false teardown comments need correcting, not a lifecycle restructure. Separately, while auditing the ledger, sess131 found that D-MIXED-VERSION-UNGATED-REPLAY's mechanism already exists in the tree unused: the three-layer C7 protocol gate (mkfs incompat bit, `cluster_proto_gen` mount check, disklock HB feature block) is real, but `MXFS_PROTO_GEN` (currently 3) was never bumped when the 0.11.422 certified-replay gate landed, so a pre-0.11.422 binary is still admitted by all three layers and can perform exactly the ungated replay the defect describes.

`docs/rulings/protogen4-and-quarantine.md`: design-consult ruling on that finding. Bumping `MXFS_PROTO_GEN` 3->4 APPROVED as the correct mechanism (a certified-replay rule change is a protocol generation change even with byte-identical descriptor encoding) but gated on four mandatory blockers before closure: (1) audit that recovery/replay cannot start before envelope admission — needs an immutable `proto_admitted` mount-state bit asserted by every recovery entry point; (2) the bump must be an offline cluster transition with storage-level exclusion (stop every member, revoke PR registrations, invalidate old membership epoch), not merely an offline metadata write — a suspended gen-3 node can otherwise resume and replay before fencing catches it; (3) the generation write itself needs crash-safe activation-transaction semantics (FUA/flush all copies, fail closed on disagreement); (4) any unsafe build released as "gen 4" permanently defeats the gate, so gen-4 conformance needs its own mixed-build test suite. "Accept N and N-1 read-only" rejected — RO mounts still do journal recovery. Part (B), auto-quarantining legacy FENCED/NONE descriptors on write, REJECTED as written: a survivor lacks write ownership/exclusion proof over the victim's descriptor (a live victim or another survivor can be racing the same sector), so the correct default is refuse-and-alert, leaving the descriptor unchanged, with `chk_mxfs --upgrade-protogate` as an inventory/detection tool only, not an auto-quarantine mechanism — no generic "clear quarantine" operation either. Limitation banked for the ledger text: the bump is prospective only; it does not certify no ungated replay happened before the upgrade.

## Cross-cutting lessons

- A "not reproduced, immediate re-run passed" control is worthless whenever the re-run doesn't exercise the same workload as the original — three prior sessions (43/45/90) on D-354 were invalidated by exactly this.
- Two independent, non-obvious knobs inflate or invert pace measurements on this rig: `mxfs.instr=1` (already known) and `console_loglevel`/`dmesg -n 8` (found sess130). Check both before trusting any timing number; check `/proc/sys/kernel/printk` == `1 4 1 1`.
- Aggregate probe counts not gated to the watched resource mislead (sess125's P70-BP negative result); wall-clock stack sampling at fixed frequency, not event counting, was what actually found the true bottleneck twice (root-inode grant wait sess126, BAST-recv disk read sess127).
- The fix that worked (decoupling BAST-recv from disk I/O) was designed to fix coalescing/dedup, but measured afterward to work for a different reason (socket-drain rate) than the one it was designed around — verify the mechanism after the measurement, not just the pass/fail.
- Every non-trivial fix design in this campaign went through a the design-consult rule GPT consult that found a real defect the author's own design/A-B testing had missed: the tenure-batching causality gap, the bastq mode-merge/teardown-order/prefilter hazards, and the protogen ordering/transition/quarantine-ownership hazards.
- Headline defect numbers should be distrusted until re-measured after any structural fix: the "42x" shared-dir pace figure was a confound of the actual (now-fixed) grant-wait convoy, and collapsed to 1.62x once that was fixed — while a previously-assumed-flat baseline (private-dir creates) turned out to degrade 24x on its own, unmasked only after the dominant term was removed.
