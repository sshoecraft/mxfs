Campaign: the RETIRE_PENDING two-phase clean-departure state machine (disklock ACTIVE -> RETIRE_PENDING -> {EMPTY, WITHDRAWN}) and its SCSI-PR absence-proof/quiescence hardening, versions 0.59.0 through 0.60.0-UNBUILT, sess450-453. Same defect shape recurs three review cycles running: a value (image, PR key state, I/O-inflight count) is trusted past the moment it stopped being fresh.

## 0.59.0 (sess450) — first landing, STOP-SHIP
`docs/history/docs/history/docs/history/compiled-sess450-453-retire-pending.md` lands the base mechanism: `MXFS_DISKLOCK_FLAG_RETIRE_PENDING`, `hb_retire_settle` (FUA confirm, CAS to EMPTY on proven absence or WITHDRAWN after a 30s grace), wired at pending-victim/first-sight/dead-confirm call sites, `mxfs_disklock_retire_complete_self` for no-key departures, v5 + chk_mxfs + docs updated.

RULE-5 review (`docs/rulings/0590-retire-pending-stop-ship.md`) STOP-SHIPs it on 3 defects + 2 ordering issues:
1. `-EAGAIN` from a CAS mismatch returns CHANGED but leaves `*rhb` stale; every caller classifies the stale image (worst case: false death processing against a slot a new incarnation already owns).
2. RETIRE_PENDING is invisible to the mount/admission recovery barrier — a crashed departer can leave a write-capable registration while a new node mounts writable on another slot.
3. The key lookup is boolean (PRESENT/ABSENT) folding UNKNOWN and `-EOPNOTSUPP` into ABSENT — an invalid identity with no frozen observation must be UNKNOWN, and only authoritative ABSENT may produce EMPTY.
Plus: P305 same-boot remount is locked out by the departer's own unresolved record; absence is only a fence proof while a reservation is actively held (not after a possible last-registrant release). 10 merge criteria issued, the load-bearing ones being tri-state PR state, the recovery barrier, safe P305 settlement, reservation-verified absence, and prohibiting no-PR clustered mode.

## 0.59.1 (sess451) — second landing, STOP-SHIP #2
Before the fix: clyde double-crashed (GPU PCIe P2P, user-attributed, unrelated to mxfs) — ledgered DISPROVED, and chains 60-68 from the prior 9-day boot were harvested, producing D-0517 (ICLUS relmark postmark-crash leaves an inobt-allocated inode with FREE core on the unlinked bucket) among other findings (`docs/history/docs/history/docs/history/compiled-sess450-453-retire-pending.md`).

0.59.1 answers criteria 1/2 of the sess450 ruling: tri-state `mxfs_scsipr_key_state`/`mxfs_disklock_key_state_fn` (ABSENT/PRESENT/UNKNOWN/OWN) with a 1s snapshot, `hb_retire_reread` on `-EAGAIN`, UNKNOWN never settles, RETIRE_PENDING now blocks the admission barrier, host-wide `mxfs_v5_dlm_departure_lock`, P305 settlement path.

RULE-5 review #2 (`docs/rulings/0591-retire-settlement-stop-ship-2.md`): criteria 1/2/9 MET, but STOP-SHIP #2 on 5 new blockers, all instances of the same "stale proof" defect family:
1. Absence proof is not coherent — READ KEYS then READ RESERVATION then a 1s cache is not atomic; a preemption between commands or during the cache TTL still yields EMPTY off a snapshot that was never true at once. Fix shape: bracket KEYS-A / RESV / KEYS-B with equal PR generation, cache PRESENT only, never cache ABSENT, invalidate on every local PR mutation.
2. Clustered no-PR still unsafe: `-EOPNOTSUPP` self-clears, and pr_key==0 reads as ABSENT instead of UNKNOWN/invalid.
3. OWN is too broad — any generic PRESENT-for-our-key lookup can clear ANY pending record naming our key, including stale/duplicate/colliding ones; OWN must be a P305-only operation on one exact (slot,node,epoch,boot_uuid) tuple under the departure lock with a *fresh* proof.
4. HB starvation — synchronous PR discovery on the heartbeat thread; a time cache bounds count, not latency.
5. No enforced freeze before publishing RETIRE_PENDING — evidence (`xfs_unmountfs`+flush) is not the same as a mechanically asserted quiescence transition.

Design for 0.59.2 written up in the same session (`docs/history/docs/history/docs/history/compiled-sess450-453-retire-pending.md`): bracketed A/RESV/B absence proof with generation equality and snapshot invalidation on every PROUT; PR discovery moved off the heartbeat thread onto a dedicated probe thread with a request table, monitor only reads it; OWN removed from the generic callback, replaced by a P305-only `retire_settle_own` under the departure lock with fresh proof; key==0 always UNKNOWN, self-retire only permitted under single_node_exclusive/fence_capability_override; quiescence asserted via a percpu inflight-buf counter before the release stamp; new kern.c debug knobs (`dbg_pr_read_keys_fail/trunc/delay_ms`) and harness arms (unknown, trunc, slowpr, joiner-under-unknown, race, multi-pending).

That same session also hit an unrelated rig blocker: chain 70's `run.sh prep_cluster` hung 300s with zero output; password ssh to nodes hung while BatchMode ssh answered instantly with "Permission denied" — diagnosed as environmental (root-owned passfile, resolved next session) rather than an mxfs defect. Also noted in-session: `tools/mxfs_pgrep.sh '<pattern>'` can match its own invoking command line and kill the calling shell — exclude `$$` or make the pattern unable to self-match.

## Rig trap: root-owned sshpass passfile hangs fleet ssh (sess451→452)
Root cause resolved in `docs/history/docs/history/docs/history/compiled-sess450-453-retire-pending.md` and recorded standalone in [[trap-sudo-mpath-up-leaves-root-owned-passfile]]: any sudo'd harness step (rig-runner's `mpath_up.sh`) leaves `/tmp/.mxfs_pass` root:600. `tools/mxfs_sshpass.sh`'s old readability check (`[ -s ]`) passes for an unprivileged caller even though the file is unreadable to them; sshpass 1.09 then prints "Failed to open password file: Permission denied" to stderr and **hangs on the password prompt instead of exiting** — indistinguishable from a real network/VM hang except that BatchMode ssh, ping, and port 22 all work fine. Fix: `mxfs_sshpass.sh` now tests `-r`/`-s` and refuses with exit 96 instead of hanging if re-materialization doesn't fix it; `mxfs_secrets.sh secrets_passfile` falls back to a per-uid path (`.uid<N>`) when the canonical path exists, isn't owned by the caller, and isn't accessible. Diagnostic shortcut for next time: `ls -l /tmp/.mxfs_pass*` before assuming a VM/network wedge.

## D-0518 — PAL logger swallows the last line of every capture (sess453)
`docs/history/docs/history/docs/history/compiled-sess450-453-retire-pending.md`: chain 71 came back **all-FAIL**, traced entirely to 3 non-filesystem causes, the load-bearing one being D-0518: `pal/linux/kern.c: mxfs_pal_log` printed via `"mxfs: %pV"` with no trailing newline, so the final printk of any burst stayed LOG_CONT and was invisible to dmesg until a later, unrelated printk flushed it — every harness assertion reading "last line" saw a truncated capture and reported a vacuous FAIL. ## 0.60.0 design ruling — review #3's 9 conditions (sess453)
`docs/rulings/0600-design-d1-d9.md` rules on 9 proposals (D1-D9), all ACCEPT WITH CHANGES except D3 (REJECT — teardown order must be unmountfs+flush -> FROZEN -> drain admitted I/O -> free sb/workqueues/shutdown_devices (rejecting anything they submit) -> release CAW -> late unregister) and D7 (plain ACCEPT — delete every `-EOPNOTSUPP`-triggered FUA fallback in settlement, fail closed as P304-RETIRE-NOCAW, and prove CAW actually works against the real LUN/multipath stack at mount time). ## Recurring pattern across all three STOP-SHIP rulings
Every review cycle finds the same defect shape in a new location: a value is captured once, treated as still true at a later decision point, with no invalidation on the events that actually change it (PR mutation, reservation loss, unit attention, buffer completion). The fix is never "read it right before use" alone — it is bracket + generation/identity match + explicit invalidation hooks on every mutating event + fail-closed (UNKNOWN, not ABSENT/PRESENT) on any incoherence. This same shape recurs in the I/O-quiescence counter (D3/C3) and in the fence-visibility gap (D-0519): correctness depends on the *sequencing* of two independent lifecycles (PR state vs. disk record; peer's local heartbeat state vs. another peer's fence certificate), and every landing until 0.60.0 handled one lifecycle's freshness while leaving the other's implicit.
