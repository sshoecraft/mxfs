## D-376: quarantined slot exhausts cluster admission

design-consult ruling (consult 1) set the shape before any code landed: a quarantined slice stays UNASSIGNABLE until loss acceptance, slice invalidation, required consistency repair, and durable verification have ALL completed — only the final guarded transition may make it reusable. Rejected outright as substitutes: headroom, guard relocation, read-only admission. `docs/rulings/quarantine-slot-repair-design.md`

Chosen design:
- `chk_mxfs --accept-quarantine-loss <slice> --confirm <digest>` (not `--clear-slot` — name it for what it does). Confirmation digest is derived from the exact verdict so a generic "yes" can't clear the wrong victim/filesystem.
- Source slot keeps `flags == RECOVERY_GUARD` for the entire repair so every existing closure/admission gate keeps blocking; repair phase lives in a versioned repair-state field inside the still-guarded record.
- Archive the original verdict into a new ledger built on heartbeat records 32..63 (never claimable under the 32-slice hard cap), gated by a superblock INCOMPAT bit.
- Reinitialize the poisoned slice, run consistency repair, clear the source slot only as the FINAL atomic generation-checked commit.
- Domain closure is unproven for XFS transactions (superblock, per-AG counters, cross-AG inodes/dirs, quota, intents, free-space, realtime) — **treat every accepted quarantine as FSWIDE** until a closure proof exists and is tested.
- Exclusion requires more than "every node unmounted": an exclusive whole-volume maintenance lease/reservation, fencing/exclusion of every registered writer, held for the entire repair, plus O_EXCL on the block device.
- 9-step crash-safe order, each step durable before the next: validate+display+confirm -> acquire exclusive maintenance ownership -> settle all non-quarantined slices (never touch the quarantined one) -> archive+flush+read-back-verify -> record LOSS_ACCEPTED/SLICE_RESET_PENDING (point of no return, slice still blocked) -> reinit journal slice with a NEW generation (never rely on discard/TRIM) -> full consistency repair with a clean second-pass verification -> record CHECK_COMPLETE/RELEASE_READY -> single atomic generation-checked guard->EMPTY clear. No crash state may make the slot claimable before slice reset and final verification are durable.
- Out-of-range occupants (a valid-looking ACTIVE record at slot 40 on a 32-slice volume) are a separate hazard: never assign a slice, never replay, must be reported as a protocol violation, must not be auto-cleared.
- An 8-part test matrix (A-H) was specified: max-capacity repro, authorization/exclusion races, exhaustive crash-injection (including torn writes/reordered flushes), lost-log consistency (two clean checker passes, no multiply-allocated/unreachable blocks), admission race at the final clear, archive survival/export/prune, out-of-range occupant fencing, and full before/during/after reporting.
- Patch order: (1) fix the ENOSPC diagnostic now — done same session, see below; (2) critical: the crash-safe repair engine; (3) same-format change: the high-slot archive ledger + incompat bit; (4) hardening: classify out-of-range occupants; (5) later/optional: a true observer-only mount role; headroom/relocation-without-repair explicitly NOT accepted.

Landed this session (patch item 1 + repair step 1): `hb_report_claim_exhausted()` replaces the old unfollowable-and-destructive "reformat with more slices (mkfs_mxfs -n)" message with real classification (markers P300-CLAIM-EXHAUSTED/-QUARANTINE/-WITHDRAWN/-FULL/-OUTOFRANGE); `chk_mxfs --show-quarantine` (-Q) decodes the full verdict read-only via O_DIRECT and prints a stable 64-bit digest over {volume uuid, slot, guard sector}; fixed `check_disklock()` treating the ACTIVE flag as a bitmask test on what is actually an enum (a quarantined slot was reported as a LIVE MEMBER); new harness `tests/quarantine_admission.sh`. `docs/history/docs/history/docs/history/compiled-sess377-pr-leak-quarantine-repair.md`

Audit finding with reach beyond this defect: slots 32..63 are live protocol state, not spare capacity — `mxfs_unclaimed_bucket_scan()` walks AGI-unlinked-bucket index 0..63 as if it were the disklock slot index, so parking anything permanent there would make `guard_slot()` return -EBUSY forever and leak an AGI unlinked bucket permanently. Also: a RECOVERY_GUARD with a valid descriptor (MXFS_RECOV_DESC_MAGIC present) is a recovery lease/terminal verdict; an all-zero-body guard is a transient bucket-sweep guard — anything counting quarantines must check the descriptor, not the flag. Audited clean: every in-tree descriptor reader already requires the descriptor magic. `docs/history/docs/history/docs/history/compiled-sess377-pr-leak-quarantine-repair.md`

### Consult 2 (follow-up ruling): archive magic, log reinit, other-slices precondition

- Distinct archive sector MAGIC (MXAR) instead of a superblock INCOMPAT bit is APPROVED for correctness only, conditionally on a full old-writer audit (old claim code can't write outside range; every old reader rejects non-MXLK sectors before consuming other fields; no old repair/init/scrub/resize path rewrites unknown-magic sectors; archive plays no role in admission/fencing/recovery/reuse decisions; losing an archive after safe release can't make the fs unsafe). It does NOT guarantee preservation against old software after a geometry expansion — required invariant: never increase slice_count across an occupied archive slot without first exporting/relocating it. If archive is meant as tamper-resistant forensic evidence, add SHA-256 alongside the two-seed crc32c digest (detector-only, not tamper-resistant).
- Archive durability stays a hard release precondition: construct from source guard -> write -> flush -> independent read-back verify (identity+checksum+full guard) -> only then the first destructive op on the source. Archive-region-full: refuse by default, require export before pruning, with export/prune itself durability-verified (different domain, fsync file+dir, re-verify, explicit identity confirmation). `--export-archive` must never write onto the same damaged volume and call that independent preservation. Any break-glass bypass (`--release-without-archive`) must be conspicuously named, demand the verdict digest, and emit a permanent operator-visible warning — an ordinary `--force` is too weak.
- Log slice reinit: FULL physical overwrite (no gaps, discard/TRIM is not proof) + the canonical XFS empty-log formatter — a hand-rolled MXFS generation field protects nothing since upstream XFS doesn't validate it. Invariant: after repair, no pre-repair sector in the entire log slice can participate in discovery of a valid XFS log record. Crash boundaries tested: during overwrite, after overwrite before format, during format, after format before flush, after archive before source release — every incomplete case must leave the source guard QUARANTINED and force a full-slice retry, never an inferred-complete shortcut.
- Other dirty slices: REFUSE to build a second recovery engine inside chk_mxfs. Precondition is every non-quarantined slice settled and clean (via quarantine-aware normal mount/replay/clean-unmount) before the offline tool starts; the tool independently re-verifies this and reports exact blocking slots, not "filesystem busy". Read-only archive/export may run earlier since it touches no fs metadata. `docs/rulings/2-archive-magic-slice-reinit.md`

## D-377: clean-unmount leaks PR registration — found BY building 376's tooling

Writing a real exclusion proof for the offline repair ("no initiator may be registered on the LUN", read from the PR registration table) instead of the usual "no heartbeat is beating" check exposed a defect nothing else in the project could see: on a fully unmounted 32-node cluster the proof REFUSED, naming a still-registered key. Lesson generalized: an honest precondition check is a defect detector — the heartbeat table can't answer "who can still write this device," only the PR registration table can, and nothing read it before this session.

ROOT (code + measurement): register used `PR_FL_IGNORE_KEY` (SA 0x06), accepted unconditionally on every dm-multipath path, so both nexuses registered. Unregister used a PLAIN REGISTER (SA 0x00, old_key=key); a path whose nexus key doesn't match answers RESERVATION CONFLICT, dm's first pass runs with `fail_early`, iteration stopped, and the other nexus kept its registration — then `if (ret == 0x18 || ret == -EBUSY) return 0;` reported success anyway. Every clean unmount left the departing node able to write the shared LUN. `docs/history/docs/history/docs/history/compiled-sess377-pr-leak-quarantine-repair.md`

### Consult 4 ruling: fix shape for D-377

Central distinction: symmetric unregister is the corrective MECHANISM; read-back verification is the POSTCONDITION CHECK; neither is a complete fix without a defined FAIL-CLOSED outcome on failed verification — "verify and log" only makes a silent failure detectable, it doesn't restore the fencing invariant. Load-bearing invariant: once MXFS declares an incarnation's storage authority retired, no registration bearing that incarnation's PR key may remain; departure and PR retirement must be coupled by successful verification or an authorized fail-closed recovery action.

9-item approved shape: (1) serialize against future registration/replay of the departing key across path-add, multipath recovery, and userspace multipathd replay; (2) genuine attempt-all-nexuses unregister, preferably via a corrected dm abstraction — natural symmetric op is REGISTER-AND-IGNORE-EXISTING-KEY with SA key zero, but verify dm actually visits all paths for `new_key==0` rather than assuming a rollback contract; (3) remove the unconditional RESERVATION_CONFLICT->success mapping; (4) mandatory complete READ KEYS (or READ FULL STATUS) verification; (5) real bounded-deadline retry; (6) failed/incomplete verification = STORAGE AUTHORITY NOT RETIRED; (7) on failure, local isolation/self-fencing or hand a certified recovery descriptor to the existing fencing protocol; (8) survivor cleanup only under normal fencing authority (never a casual "remove keys I don't recognize" reaper — that's an uncontrolled second fencing implementation; needs committed fresh membership/quorum, a durable key->cluster/host/incarnation mapping, proof of exclusion/handoff, serialization against key reassignment, a fence certificate, and post-PREEMPT verification); (9) keep per-incarnation PR keys (a stable per-host key is actively dangerous — a PREEMPT meant for an old incarnation would remove a new one sharing the same key) but widen from a 32-bit node_id to a collision-resistant 64-bit incarnation identifier, with a durable key->{cluster, host, incarnation, term} mapping recorded separately.

Result-mapping table for unregister+read-back: success+absent=success; success+present=failure; conflict+absent=success (already gone); conflict+present=failure; any+read-back-failed/incomplete=UNKNOWN=failure. A conflict from one nexus never means "globally absent." READ KEYS truncation must be handled via ADDITIONAL LENGTH; PR generation can change mid-read (retry). Two-phase departure recommended: publish a "storage authority retirement pending" record before the final unmount steps, do unregister+verify at the safe late point, mark complete if absent, else leave the record for authorized recovery/fencing and apply local fail-closed policy — avoids trying to rejoin DLM or resurrect a superblock after late cleanup fails. Liveness hazard flagged explicitly: a synchronous PR request can block far longer than any retry loop implies (multipath queue_if_no_path, SCSI timeouts/error-handler, path failover) — use both a bounded attempt count AND an absolute wall-clock deadline enforced below the loop. `docs/rulings/3-pr-unregister-leak-fix-shape.md`

### D-377 FIXED AND VERIFIED — 0.14.11

Symmetric all-nexus unregister (`pr_register(bdev, key, 0, PR_FL_IGNORE_KEY)`), the conflict->success mapping deleted, mandatory READ KEYS read-back that grows its buffer while the target's reported total exceeds capacity (a truncated view can never read as absence), bounded by both 6 attempts and a 20s wall-clock deadline. The `mxfs_bdev_t` form now calls the bdev form instead of open-coding a second copy — two copies is how the asymmetry existed on two paths undetected. Markers P301-PR-UNREG-*, P301-PR-AUTHORITY-NOT-RETIRED, P301-DEPARTURE-INCOMPLETE. Verified by new `tests/pr_departure.sh` (refuses to pass on a single-path device, since the leak is a per-nexus asymmetry): from an empty table, arm A 3/3 round trips 0->2->0, arm B 31 nodes mounted 0->62 then all unmounted 62->0 — table EMPTY. Pre-fix baseline on 0.14.10 same session: leaked 2/2. `docs/history/docs/history/docs/history/compiled-sess377-pr-leak-quarantine-repair.md`

Two residuals filed because the ruling asked for more than was built this session: D-PR-RETIREMENT-FAILURE-NOT-FAIL-CLOSED-377 (critical — no fail-closed action yet when retirement can't be proved, no serialization against re-registration/multipathd replay, no authorized survivor reaper); D-PR-KEY-32BIT-NODE-ID-COLLISION-RISK-377 (high — PR key is still a 32-bit node_id in a 64-bit field with no durable key->incarnation mapping).
