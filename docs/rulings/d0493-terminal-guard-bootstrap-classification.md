# D-0493 bootstrap classification ruling (GPT, sess493)

Reproduction: 32 nodes, one fail-stop victim (slot 0) under a refused AG (terminal AG-MASK verdict published after the fence certificate), clean mass unmount (31 peers -> RETIRE_PENDING), remount one node -> survivor scan says total outage, the only member-shaped record is slot 0 = RECOVERY_GUARD + terminal QUARANTINED desc; `mxfs_hb_identity_valid` fails on it -> noident -> `P-BOOT-KEY-UNCLASSIFIED ... bootstrap refused` (dlm/v5_mount.c ~4358; scan in dlm/bootstrap.c ~1118-1153).

## Ruling
1. TERMINAL guard = new manifest type (TERMINAL_GUARD): validate guard/desc/terminal stage/outcome crc/victim tuple/fs_gen; import the quarantine; never replay; require NO victim identity; issue NO PR op merely because it exists. It is evidence the incarnation was fenced and refused, NOT evidence that any registered key is the victim's.
2. Fail-closed key rule: every non-owner key in the accepted READ KEYS snapshot must classify EXACTLY once from durable evidence: ordinary replay victim key (fence then replay) / valid RETIRE_PENDING identity key (fence, no replay) / allowed slotless registrant / valid self-successor / key attributed to a terminal-guard victim ONLY through an authoritative PR-ledger binding (exact (node,epoch), exact key, fs_gen, unambiguous) / else REFUSE before replay. "Could be the terminal victim's key" is not enough. A terminal victim's key reappearing after a certified P&A = re-registration, stale/multipath PR state, or a fence-certification defect — never waved away by the guard.
3. Do NOT repurpose the guard's identity block to mean "victim" (writer identity semantics; readers, tools, self-successor logic). If victim-key attribution is wanted, add a separately named versioned `victim_identity_snapshot` to the recovery descriptor, bound to victim tuple + slot + fs_gen + descriptor. Premise check: a writer identity correctly crc-rebound to the guard tuple should be structurally valid as the WRITER's — if the scan calls it noident because it validates against the victim tuple, that is a validation bug in itself; an absent identity is allowed by the "never consulted" design. (MEASURE which: does slot 0's guard carry a writer ident that fails crc, or a zeroed block?)
4. RETIRE_PENDING must participate: attribution-only entry (CLEAN_RETIRE_REGISTRANT): if its exact validated identity key is in READ KEYS -> P&A that key and verify removal; absent -> no op; never replay. Safe only if the RETIRE_PENDING transition is durably ordered after clean journal shutdown (check). A malformed RETIRE_PENDING record authorizes fencing nothing. The observed second registrant at the remount matters: fixing only the guard may move the refusal to "unclassified key" if it is a RETIRE_PENDING peer's.
5. Minimal change: split RECOVERY_GUARD by descriptor stage in the scan (nonterminal = existing; terminal = TERMINAL_GUARD); add RETIRE_PENDING identities to an attribution-only map; classify ALL observed keys before replay; P&A only keys present in the snapshot with PR-generation re-read; verify each.
6. Verification bar: the reproduction with PR tracing: bootstrap accepts the terminal guard without identity; AG 7 quarantine imported before the fs is available; slot 0 never replayed; no P&A for the terminal victim when its key is absent; every observed RETIRE_PENDING key P&A'd and verified gone; no key absent from READ KEYS fenced; unexplained keys refuse; first mount succeeds; all 32 remount and see the quarantine. Negative arms: guard with absent writer identity; writer identity not describing the victim; corrupt desc/outcome crc; nonterminal guard without identity; lingering RETIRE_PENDING key; injected unknown key; ambiguous ledger mapping; crash after P&A before completion + retry.
