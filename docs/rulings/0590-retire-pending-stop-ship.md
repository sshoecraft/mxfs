# sess450 RULE-5 ruling — 0.59.0 RETIRE_PENDING implementation: **STOP-SHIP**

Reviewed: the as-landed 0.59.0 code (tree /src/mxfs, UNBUILT, scratch sv `1D966649DDAA5C735AE647F` compiles clean). GPT's earlier sess449 ruling required the state; this reviews the implementation of it. Core `RETIRE_PENDING -> {EMPTY, WITHDRAWN}` transition and the CAW serialization between competing settlers are judged SOUND. Five holes make it unsafe to ship as written.

## The three STOP-SHIP defects

**1. `-EAGAIN` returns CHANGED without refreshing the image.** `hb_retire_settle` returns `HB_RETIRE_CHANGED` on a CAW mismatch but leaves `*rhb` holding the stale RETIRE_PENDING image; all three call sites then "fall through and classify" that stale image. Worst case is the dead-confirm arm: peer A settles the record (or a claimant takes the now-EMPTY slot ACTIVE), peer B loses its CAW, falls through with the pending image and `WITHDRAWN/other -> fire_dead` — false death processing, fence and replay against a slot a new incarnation already owns. FIX: on `-EAGAIN` do a FUA re-read into `*rhb` before returning CHANGED, or return a RETRY code that no caller may classify. Audit every CAW-mismatch path in disklock.c, not just this one.

**2. `RETIRE_PENDING` is not in the mount/admission recovery barrier.** `mxfs_disklock_get_recovery_pending_slots` counts WITHDRAWN + descriptors only. Sequence: old node writes RETIRE_PENDING, crashes before unregister, key stays present; a new node mounts on a different slot; admission sees no victim and goes writable while the old registration is still write-capable for at least the grace. RETIRE_PENDING must BLOCK admission until it is either settled to EMPTY under active PR protection, or converted to WITHDRAWN + fenced + recovered + purged. This is the defect that makes 0.59.0 arguably no better than what it replaced.

**3. The key lookup is not fail-closed.** `key = ident_valid ? ident.pr_key : frozen_obs_or_0; if (key==0) absent;` — an invalid identity with no frozen observation means UNKNOWN, not "no key", and clearing to EMPTY there destroys the only fencing evidence. Also `mxfs_scsipr_key_present()` is a bool that folds error into PRESENT and `-EOPNOTSUPP` into ABSENT. Required: tri-state PRESENT / ABSENT / UNKNOWN. Only an authoritative ABSENT may produce EMPTY; UNKNOWN must never publish EMPTY, never age into a recovery action that assumes a usable PR context, and must block admission / degrade the mount. The local `known` flag currently has no effect — after 30 s an UNKNOWN still converts to WITHDRAWN. Additionally: a valid pending identity whose key disagrees with an existing frozen observation for the same exact incarnation is a protocol violation, not something to accept silently.

## The two functional/ordering defects

**4. P305 locks out the lone-node clean remount (confirmed regression).** Unregister rc==0 means the departing node cannot write EMPTY; on a same-host remount the P305 same-boot scan finds its own RETIRE_PENDING record and refuses forever. P305 must settle it, in this order: establish the remounting node's PR context and WE-RO protection FIRST; FUA read; validate generation/state/exact incarnation/ident crc; authoritative tri-state READ KEYS; ABSENT -> CAW the exact image to provenance-preserving EMPTY; CAW mismatch -> FUA re-read and restart classification; PRESENT -> refuse or fence, never clear; UNKNOWN -> refuse/defer, never clear. Serialize against any old shutdown/re-registration worker (same I_T nexus re-registered under a new key can let old queued commands pass PR checks).

**5. Absence is only a fence proof while a reservation is in force.** "A de-registered initiator cannot write the WE-RO LUN" holds only while the reservation exists; if the departing node was the last registrant/holder, unregistering can release the reservation and the gap has no protection. A peer may use absence as proof only after it has (i) registered its own key, (ii) established/verified the expected WE-RO reservation, (iii) verified the victim key absent under that reservation. Matters most in the last-node / next-mounter case.

## Minimum merge criteria (GPT's list, verbatim intent)
1. Fix stale-image use after every `-EAGAIN`. 2. Tri-state PR lookup; unknown identity fails closed. 3. RETIRE_PENDING in the mount/admission barrier. 4. Safe P305 settlement. 5. Active-reservation verification before absence permits EMPTY. 6. Unique/non-reused keys + complete authoritative READ KEYS parsing (truncated key list != absent; UA/path failure/conflict/timeout/partial -> UNKNOWN). 7. Prohibit clustered no-PR mode (`-EOPNOTSUPP` self-clearing pending is unsafe on a shared LUN; only independently-enforced single_node_exclusive). 8. Verify I/O freeze/drain and PR command serialization before pending is published. 9. Require a successful fence before replay/purge; test the newly reachable CLEAN-WITHDRAWN recovery case (clean unmount record + flushed log + released leases — replay must be a no-op or a clean-retirement path, and must be proven idempotent). 10. Prevent monitor PR work from starving heartbeat processing.

## Secondary findings
- **PR IN load:** up to 64 PR INs per 2 s lap. Prefer ONE READ KEYS snapshot per lap shared by all pending slots, async/deadline-bounded so heartbeat sampling is never blocked behind PR commands. Cache PRESENT/UNKNOWN within a lap; never cache ABSENT across the transition to EMPTY.
- **`rs < 0` treated as WAITING forever:** tolerable as transient retry, unsafe post-admission. Needs rate-limited diagnostics, health escalation, admission block, possibly RO/shutdown.
- **Grace:** 30 s is operational, not a correctness constant (fencing a present key is the safe operation). Per-peer first sight is acceptable ONLY if RETIRE_PENDING blocks admission; otherwise it is an unsafe writable window. Use wrap-safe monotonic arithmetic; clear the timer when the slot no longer holds that incarnation. At mount, do not admit-and-wait — get authoritative ABSENT or fence PRESENT.
- **EMPTY identity:** the claim "nothing trusts an EMPTY record's identity" is wrong — `hb_clean_empty_match` matches node+epoch on it and claim lineage uses provenance. Retaining it is fine but the invariant must be written down and enforced: only clean-retirement logic may consume identity from EMPTY; fencing, frozen-key observation, same-host predecessor detection, recovery-victim creation and membership must all reject it; a claimant must replace all identity fields atomically (no carried-forward `pr_key`).
- **Doc inconsistency to resolve:** identity crc covers `flags` (so every transition must rebind — we do) but the provenance crc does not; the on-disk format doc and tests must say which is which and not describe prov as protecting the state transition.
- **Departure error handling:** failure of ACTIVE->RETIRE_PENDING must not continue as a clean release; failure to flush pending before the unregister must not proceed to unregister; failure of RETIRE_PENDING->WITHDRAWN must report an unresolved departure locally rather than imply success.
- **State-machine audit:** recovery_begin/fence_intent/purge/find_node_slot accepting only ACTIVE|WITHDRAWN is safe only because RETIRE_PENDING is unreachable there — add assertions. The pending-victim call site defers a newly produced WITHDRAWN by one lap; enter the WITHDRAWN path immediately or document+test the latency.
