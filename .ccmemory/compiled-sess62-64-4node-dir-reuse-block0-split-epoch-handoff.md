## Compiled: sess62-64 — dir_reuse_coherency 4/tcp `node1_f1` loss, block0-split root, handoff→epoch design

Single criterion in view across all three sessions: **`dir_reuse_coherency` at 4 nodes / TCP transport**. 1/tcp and 2/tcp PASS throughout (16/16, 17/17); 4/tcp fails only this one test; 8/tcp never run. The test rm-rf's and recreates the SAME shared dir inode (ino 131, later 138) every round (24 rounds), so the dir inode is constantly freed + reallocated — **cross-incarnation reuse** is intrinsic. Failure signature: `node1_f1` (rank1's FIRST dirent in the reused dir) is **durably absent on disk** ~every round at sess62, driven down to 1-2/24 by sess63-64. rank1 (the dir creator) never loses its own entry; only peers cold-reading disk miss it. Marker never written in any session; criterion NOT met.

### sess62 — proving the root (build chain F3342B5D / F57039C0 / 9559A8F7 / 37F6F9A6 / 83C634AD, all baseline-equivalent, probes only)

Root proven at two coupled levels, both reducing to "the converter's pre-conversion dir state is not cluster-coherent":

- **Content level** [[sess62-FINAL-content-level-stale-shortform-base-at-conversion]] [[sess62-PROVEN-ROOT-4way-logical-block0-split-divergent-extent-map]]: the `xfs_dir2_sf_to_block` converter freezes an in-core SHORTFORM base MISSING `node1_f1`, even though `node1_f1` is committed in the disk shortform for the SAME incarnation. Probe P62-CRCONV (xfs_inode.c ~1504): when a node is in-core LOCAL at the converting create, DISK is ALSO LOCAL (P61-ADOPT-DISK fired 0×) — so it is a CONTENT gap, not a format gap. Converter's shortform and disk shortform are DISJOINT same-incarnation sets of SIMILAR COUNT (~11 dirents each) → a `disk_cnt > incore_cnt` count-based adopt CANNOT detect the missing name (fired ~0×, REFUTED).
- **Extent-map level** [[sess62-REFINED-block0-split-extent0-flipflop-orphans-node1f1]] [[sess62-PROVEN-ROOT-4way-logical-block0-split-divergent-extent-map]]: **4-way logical-block0 SPLIT**. Probe P62-DATAINIT-BLK0 (xfs/libxfs/xfs_dir2_data.c, always-on) shows each of the 4 nodes calls `xfs_dir3_data_init` for logical block 0 of the same inode at a DIFFERENT physical daddr (test1@120/AG0, test2@102568048, test3@18839088/4186520/62796792, test4@75356136 — different AGs from per-node AG affinity), 2-5×/incarnation, `buf_done=0` (fresh get_buf each time). P62-DWR-N1F1 confirms `node1_f1`'s whole block is written intact to daddr=120, but verify resolves logical-block0 to a different daddr with zero node1 entries. P62-REL-DIREXT (release-path decode of on-disk data-fork extent[0]) proves test1's RELEASE publishes `ext0_daddr` = a PEER's daddr (75356136, 4186520, 6279744, 98381600, 87915480), not 120 — i.e. test1 ADOPTED a peer's block0 and ORPHANED its own block0@120 holding `node1_f1`. Mechanism: EX is serialized but the sf→block CONVERSIONS are not serialized to a single block0; multiple nodes each allocate their own physical block0; inode's extent[0] flip-flops to whoever iflushes last; orphans the block holding `node1_f1`.

**REFUTED at sess62** (all with evidence): DLM double-grant (P-DOUBLEGRANT=0, P-STALEMASTER-GRANT=0 — EX serialized); `force_block=1` at 4 nodes (split persists, 4 different block0 daddrs — it only affects the creating node's mkdir); `mxfs_dir_modify_adopt_disk_format` (compares FORMAT/nextents/size only — invisible to a LOCAL-vs-LOCAL content gap; also added a per-create FUA dinode read = RULE-0 hit; re-disabled `if(0)` at xfs_inode.c ~1504); the prelock format-adopt serializer `mxfs_dir_adopt_block` (runs BEFORE EX acquire = racy snapshot, fired 0×, default set 0); shortform-reconversion-only (P42-SFCONV fires ~2×/24, reused dir treated as already-block via cache-hit P128-REARM-UNPUB).

**The gated-off fix that WAS the answer** [[sess62-SURGICAL-leadP-SFMERGE-dead-no-same-incarnation-shortform-union]]: `mxfs_dir_sf_merge_into` (xfs_mxfs_dlm.c:6754) / `mxfs_dir_sf_3way_merge` (:8948) is a base/ours/theirs 3-way UNION merge — keeps names WE changed, adopts peer's untouched (`node1_f1`), no delete-resurrection. It fired 0× (P-SFMERGE=0) because its gate at xfs_mxfs_dlm.c:8054 requires `i_dlm_dir_sf_base != NULL` (set :8735/:8723 after a coherent disk read; declared xfs_inode.h:140) AND disk still LOCAL AND nlink match — never all-true for the converter: most reloads are cross-incarnation (handled by P103-RELOAD-REUSE-ADOPT ~8000 first, new incarnation has no sf_base) or hit P116-SELFCLOBBER-SKIP / P33-FROMDISK-DIRSHRINK early-return, or disk has already converted to EXTENTS (merge is shortform↔shortform only).

**The signal the merge needs — found in dg_shadow** [[sess62-FIXDESIGN-master-exposes-prior-EX-owner-then-3way-merge]]: the 3-way merge is safe ONLY on a GENUINE cross-node handoff (else it merges against a stale/own base and resurrects deletes — the sess53 regression). `grant_gen` is NOT that signal (sess61 REFUTED: bumps on every same-node re-grant, over-fires 2/24→16/24). The reliable signal ALREADY EXISTS: `dlm.c` maintains `dg_shadow[]` per inode resource recording the current EX `{owner, gen}` (`dg_grant_ex` @2344 sets, `dg_release` @2403 clears). At the master, at grant time, `prior_owner != grantee` ⇒ a peer held EX since the grantee last did ⇒ GENUINE HANDOFF ⇒ must merge; `prior_owner == grantee` ⇒ no peer modified ⇒ no merge, no resurrection. **EPOCH/TENURE scoping is mandatory** [[sess62-HANDOFF-next-fix-is-namesetset-union-merge-epoch-scoped]]: a blanket union merge resurrects deletes on delete-heavy 4/tcp tests (dlm_fairness, tcp_dlm_scaling — currently passing); must distinguish "peer ADDED node1_f1" from "we DELETED an entry not yet published". Fix must be a NAME-SET union (not count) before sf→block, plus serialize block0 materialization so only ONE block0 ever exists per dir incarnation. GPT-5.5 (RULE 5 consult, justified) diagnosed a stale in-core data-fork EXTENT MAP with two equivalent gaps: (B) release side does not iflush the dir inode fork to the on-disk cluster before granting EX away → peers FUA-read stale cluster; (C) EX-acquire reload adopts scalar dinode fields but does NOT destroy+rebuild the i_df extent cache. GPT fix: force-iflush dir inode+blocks before release; on epoch-advanced EX grant fully rebuild i_df (`xfs_idestroy_fork`+`xfs_inode_from_disk`, not just scalars); restrict FASTEX self-dirty skip to continuous-EX + unchanged epoch. Adopt at the DLM EX-acquire path BEFORE XFS takes ILOCK_EXCL — never inside `sf_to_block`/`grow_inode` (too late, can't reload under ILOCK).

### sess63 — handoff signal built and validated; 24× improvement, 1-2/24 residual (build 503078E1 → 5E78DEE0, KEEP)

The master prior-EX-owner handoff signal was implemented end-to-end [[sess63-handoff-signal-works-1of24-residual-writeside-block0]]:
- `dlm/dlm.c`: `dg_shadow_ent` += `last_owner` (RETAINED across `dg_release`) + `used`; `dg_grant_ex()` returns `handoff = (last_owner!=0 && last_owner!=owner)`, sets `lk->handoff`, delivered to remote grantee via `mxfs_dlm_lock_resp.handoff` (reused `pad[0]`, wire size unchanged) at all send_grant GRANT sites (DENY sites pass 0); new query `mxfs_dlm_grant_was_handoff()`.
- `dlm/v5_mount.{c,h}`: `mxfs_v5_dlm_inode_grant_handoff()` (CAW→false). `xfs_inode.h`: `i_dlm_handoff_acted_gen` (consume once/episode).
- `xfs_mxfs_dlm.c mxfs_dlm_reload_inode`: compute `genuine_handoff = handoff && gg!=acted_gen` at top, fold into `peer_modified_since_load`, bypass P33 dir-grow-revert + P43/P43B fmt-revert keep-stale guards (`&& !genuine_handoff`), set `acted_gen` at the actual adopt. Fast-path EX serve ~9854 replaced the DISABLED sess61 grant_gen check with the handoff trigger (P63-FASTEX-HANDOFF).

VALIDATED: 1/tcp 16/16, 2/tcp 17/17 (DLM grant-protocol change does NOT regress). 4/tcp `dir_reuse_coherency` 17-24/24 failing → **1-2/24** (24× improvement). Evidence it works: P63-HANDOFF fires 23-24×/node cross-node post_release=1; P56-RELOAD-MERGE shows clean disk-superset adopt `clean=1 disk=[node1_f1..node1_f8]`; read-side staleness FIXED.

Residual root PROVEN [[sess63-residual-root-crossnode-gen-divergence-reused-dir]]: DIRID probe (`stat -c %i` every round) shows on a failing round ALL peers resolve the SAME dir inode ⇒ NOT cross-incarnation divergence but an **INTRA-INODE single-dirent lost-update**. P-DE-ENTER probe: `mxfs_dir_drain_evict_data_blocks` runs with `gen==loaded` on EVERY call (the lossy DIR_MODIFY evict-ring never bumps gen for a peer mod on TCP, AND the handoff reload sets `loaded=gen`), so the coherence-forcing `xfs_log_force` (gated `any_pinned || gen!=loaded`, ~3960) NEVER fires on a handoff. Mechanism: node C re-acquires EX; its cached dir block B is a STALE prior-tenure buffer that is PIN-tailed (CIL unpin pending); `drain_evict` cannot evict a pinned buffer (clearing XBF_DONE on pinned corrupts — sess64) and the `any_pinned` TRYLOCK scan misses a momentarily-locked B → no log_force → bounded per-block drain (50 iters/100ms) times out → B SKIPPED → C RMWs stale B → clobbers a peer's just-committed dirent. Note SF2BLK name-dump also showed cross-node incarnation divergence (same reused ino, different di_gen, disjoint same-node-only shortforms) as a contributing face; d_revalidate is DISABLED (sess38) so reused-dir dentry/iget coherence is unenforced.

**Acquire-side fix = RULE-0 dead-end** [[sess63-residual-root-crossnode-gen-divergence-reused-dir]] [[sess63-NEXT-FIX-handoff-gated-block-union-merge]] (all reverted to 5E78DEE0):

Conclusion: cannot cheaply distinguish the rare harmful pin from common benign ones at acquire; CIL-pinned (not in AIL) has no LSN-targeted force. Acquire-side log_force is the wrong layer.
- ATTEMPT 2 — handoff-gated block-union-merge `mxfs_dir_merge_peer_into_tp` (FUA-reads peer dirents into the create tp = the ideal force-FREE cost): `Corruption of in-memory data (0x8) at mxfs_dlm_ilock_begin xfs_mxfs_dlm.c:10364` SHUTDOWN at round 1. Still the ONLY force-free mechanism — debugging its corruption flagged a top next lead.
- ATTEMPT 3 (STRONGEST) — release-side durable-signal flush: `mxfs_dlm_dir_durable_signal` (xfs_mxfs_dlm.c:13287, post-commit per modify) already does `xfs_log_force(SYNC)+mxfs_dir_flush_data_blocks` but gated on the LOSSY `dir_gen>0`; adding `|| i_dlm_handoff_acted_gen!=0` made test1/test2/test4 run ALL 24 rounds CLEAN (single-dirent loss GONE — direction CONFIRMED) but test3 FROZE its view at 340/400 from round 18 (~60 missing peer .md5 entries, no shutdown, no timeout, mount up). ### sess64 — edge→level: per-dir monotonic epoch; adopt surfaces coupled bnobt corruption (builds A5554054 → 1035BDC5 / 8E168717 → 04E74E78 / 22F1D7BE, plumbing KEEP, adopt DISABLED)

Decisive quantification [[sess64-GPT-design-per-dir-monotonic-epoch-replaces-handoff]]: master computes **~270 handoffs but grantees act on only ~58 (P64-MASTER-HANDOFF ~270 vs P63-HANDOFF ~58 = ~80% LOST)**. The edge-triggered handoff bit + one-shot `acted_gen` consumption + EX-only + fast-path-bypass loses most cross-node dir-base-change signals. Also refuted this session: attempt-3 publish-side SYNC flush gated on handoff (2/24, reverted); dg_shadow 512-slot table-overflow (P64-SHADOW-EVICT=0, never fills). All point detectors CLEAN on failing runs: P106-STALE-EX=0, P-SF-DURABLE-FAIL=0 (release fence sess97 ALWAYS durable+unpinned before handoff), P58-SELFSKIP-STALE-DIR=0, P-DOUBLEGRANT=0, no shutdown ⇒ release side IS durable; the gap is reliable ACQUIRER refresh + READER invalidation. **TWO failure modes**: Mode A = single-dirent loss (EX RMW of stale cached dir DATA block, usually nodeX_f1); Mode B = whole-node frozen view (e.g. 300/400 or 340/400 stuck rounds 18-21 — a PR reader latched stale cached dir `xfs_buf`s; `drop_caches` frees pagecache/dentries but NOT the `xfs_buf` metadata cache, so stale dir blocks survive drop_caches+rm-rf).

**GPT-5.5 design (RULE 5, saved)** [[sess64-GPT-design-per-dir-monotonic-epoch-replaces-handoff]]: replace the edge-triggered handoff bit with a LEVEL-TRIGGERED per-dir monotonic EPOCH. (1) Master keeps per-dir-inode `dir_epoch` + `last_writer`, incremented ONLY after a dirty EX holder completes the release fence (one EX tenure = one bump), built on dg_shadow. (2) Every LOCK_GRANTED (PR or EX, remote or local) carries `dir_epoch`+`last_writer`. (3) Client `i_dlm_dir_valid_epoch`: on EVERY grant-authorization point, `if (grant_epoch > valid_epoch) { invalidate CLEAN dir bufs; if EX reload_inode disk-superset; valid_epoch = grant_epoch; }` — MONOTONIC compare cures the 80% under-fire (missed intermediate epochs fine, 10→20 in one refresh; no one-shot consumption). NO `xfs_log_force` on acquire (release fence already durable — this is what keeps it RULE-0 safe: SYNC force stays on the async release-side kworker; acquirer does only epoch-compare + cache-invalidate + on-demand FUA reread). (4) Buffer-level epoch stamp `b_mxfs_dir_epoch` on DATA/LEAF/NODE bufs, checked in `xfs_da_read_buf` (coherency domain = whole dir block set). (5) PR readers must be REAL DLM holders, BAST'd to NL before a peer EX grant, on recall drain readdir + invalidate clean bufs (fixes Mode B). (6) Fast path legal ONLY if `held_mode>=req && !recall_pending && valid_epoch==granted_epoch`. (7) Disk-heartbeat DIR_MODIFY ring → best-effort HINT only.

**Epoch plumbing IMPLEMENTED (build 22F1D7BE / 04E74E78, harmless, KEEP)** [[sess64-epoch-plumbing-done-adopt-surfaces-bnobt-corruption]]: `dlm.h struct mxfs_lock += uint32_t dir_epoch`; wire `mxfs_dlm_lock_resp += uint32_t dir_epoch` (all nodes rebuild together = safe wire growth); `dg_shadow_ent += epoch`; `dg_grant_ex(...,uint32_t *epoch_out)` bumps on every cross-node handoff, ALL call sites updated (1229 local, wk-grant 1613/1972/3173, reaffirm 2672, upgrade 2714, remote-immediate 2870; deny=0); `send_grant`/`process_remote_grant` carry+store `lk->dir_epoch` (monotonic max); query `mxfs_dlm_grant_dir_epoch()` + bridge `mxfs_v5_dlm_inode_dir_epoch()` (v5_mount.c/.h); both grant-recv callers (mount.c:487, v5_mount.c:217) pass `resp->dir_epoch`; `xfs_inode.h += i_dlm_dir_valid_epoch` (init 0 ~11617). P64-EPOCH-OBS confirms epoch fires 21-25×/node **EXCLUSIVELY post_release=1** (slow-path acquire reload at ~10432) — the slow-path reload IS the right adopt site.

**Enabling the adopt = DEAD END (bnobt double-free)** [[sess64-WIN-incarnation-gated-epoch-adopt-1of24-no-corruption]] [[sess64-NEXT-epoch-adopt-must-respect-incarnation-guards]] [[sess64-epoch-plumbing-done-adopt-surfaces-bnobt-corruption]]: driving the disk-superset adopt by having the epoch BYPASS the P33/P43 keep-stale guards (~7564/7663/8017), gated post_release=1 + same-incarnation: ungated (1035BDC5) → `xfs_create`/`xfs_dabuf_map HOLE` trans_cancel shutdown (post_release=0 adopt rolls back in-flight mods onto a freed block); gated post_release=1 (8E168717 / drc_s64i) → `bno+len>gtbno xfs_alloc.c:2428 xfs_free_ag_extent` = **bnobt DOUBLE-FREE during rm-rf** (HIGH VARIANCE — drc_s64h 1/24 fail shutdown=0, identical drc_s64i shut down 3×). Mechanism: P33/P43 are SHRINK/revert INCARNATION guards; dir_reuse rm-rf recreates the SAME inode (dirino 131/138 stable) so the dir inode is constantly freed+realloc'd = cross-incarnation; the disk-superset invariant holds ONLY within one incarnation — a handoff across a free+realloc is NOT a superset. The monotonic epoch fires the adopt ~270×/run (vs ~58 for the edge bit) so it bypasses the incarnation guards far more often → adopts a stale-incarnation extent map inconsistent with in-core bnobt/cntbt → rm-rf double-frees. This is the sess42-47 bnobt double-free family, now COUPLED to the dirent-coherence fix. **DECISIVE logic**: the `node1_f1` loss is a SAME-SIZE missing-one-entry loss, NOT a shrink, so it does NOT flow through the P33/P43 shrink guards at all — bypassing them CORRUPTS WITHOUT FIXING THE LOSS. The epoch-via-reload-adopt path is the wrong mechanism.

**Next-session directions (sess64 close)**: (1) KEEP epoch plumbing; do NOT re-try the P33/P43 bypass. (2) Make the epoch-adopt INCARNATION-AWARE: require disk `di_gen`/`i_generation` to match/supersede in-core before bypassing guards; OR adopt only DATA-BLOCK CONTENT (invalidate+FUA-reread clean dir bufs, NO `xfs_idestroy_fork` rebuild) when disk nextents == in-core nextents (the single-dirent-loss case) — sidesteps bnobt/AG churn. Keep gated post_release=true. (3) Pursue GPT's design: don't adopt in-place on the fast path — on stale epoch DISABLE fast-path serve, force a clean slow-path NL→EX re-acquire that atomically reloads the WHOLE coherent set (dinode + dir data/leaf blocks + AG free-space meta), avoiding the partial in-place adopt that desyncs inode-vs-AG state. (4) `node1_f1` publish-durability probe: confirm at rank1's BAST-release fence the dinode/block holding node1_f1 is actually bwritten before handoff, and whether the clobbering peer's first-create base for that block contained node1_f1 (P-SF-DURABLE-FAIL=0 claims durability yet node1_f1 still drops — a hole in that claim for the first-entry/sf→block case). **≥2 coupled failure modes must ALL be fixed for 100%**: single-dirent content loss (Mode A) + AG-free bnobt/dabuf corruption under rm-rf reuse + PR-reader frozen view (Mode B).
