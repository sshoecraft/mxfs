# dir_reuse 8/tcp — data-block re-read wedge, DLM starvation, and the AIL-destage clobber (sess24–25)

Central topic: the lone ship blocker `dir_reuse_coherency` at 8 nodes/tcp. 1/2/4 tcp PASS; 8/tcp = 16/17 with dir_reuse losing ~1–2 entries/run. Two sessions converged on: (a) the "just re-read the dir DATA block" family of fixes is a dead end (each variant hard-WEDGES nodes and/or starves the DLM), and (b) the actual clobber is a background xfsaild/AIL-push destage of a stale in-core dir DATA block by the EX holder itself. Keeper across both sessions: **EF6000F0** (≡ 8A437A71 rebuild), the sess23 keeper byte-identical.

## The failure signature
Durable single-entry lost-update: `readdir=799/800`, `lookup_fail=0`, LOOKUP_ENOENT + REREAD_MISS (durable, not a cache miss). `dirino=131` identical on all nodes → intra-inode dir-block lost-update, NOT dentry/iget reuse. The dangerous face is `kind=data` EQUAL-count / DIFFERENT-fingerprint: two nodes fill the same free slot from divergent bases, one entry replaces the other → global −1. See [[sess25-PROVEN-clobber-is-background-aild-destage-of-stale-incore-dirblock]].

## Decisive environment fact (ends a ~20-session false assumption)
The shared LUN `/dev/sda` is qemu `<disk device='lun'><driver type='raw' cache='none'/>...<shareable/>`: **cache=none (O_DIRECT, no host page cache) + guest write-through + shareable = STORAGE IS COHERENT.** A completed+synced write from one node is immediately visible to another node's read. The old "torn-read = FUA reads the platter which lags the write-back cache" story (sess13/sess20, which forced `dir_postread_leaf_only=1`) is WRONG for this stack. So data-block re-read is *sound* in principle. (Note: userspace `tools/fua_verify` SCSI CDB is rejected by qemu virtio-scsi with INVALID FIELD 0x24, but in-kernel REQ_FUA bios work.) See [[sess24-BREAKTHROUGH-storage-coherent-datablock-reread-safe-residual-dlm-starvation]].

## sess24 — the re-read family is a dead end (all variants wedge)
With storage proven coherent, `dir_postread_reread=1 dir_postread_leaf_only=0` (re-read every stale dir DATA block before RMW) ELIMINATES both corruption faces: DABUF-HOLE (stale leaf → freed block, EFSCORRUPTED) → **0** (was 60→shutdown), and `xfs_dir2_data_use_free` stale/torn-RMW-base corruption (`xfs_dir2_data.c:1740`) → **0**. The coherency fix is real. But every re-read implementation HARD-WEDGES nodes (network-dark, requires reboot):

1. **Bulk** `leaf_only=0` (postread hook re-reads every stale data block, `xfs_da_btree.c ~3796-3906`): uf=0/hole=0; wedges at 4 AND 8 nodes.
2. **Targeted postread (Patch5)** — per-inode `i_dlm_dir_rmw_reread` flag scopes the re-read to addname's one block: PASSED 8/8 ONCE, then wedged 0/8; wedges at 4 too.
3. **Targeted pre-read grant_stale** — moved staleness invalidation into the wedge-free pre-read path with TRYLOCK on the incore buffer (never relse a trans-joined buffer): STILL wedged 0/8 run 1.

Because even the TRYLOCK pre-read (no relse, no blocking lock) wedges, the wedge is NOT the relse-of-trans-buffer ABBA originally hypothesized. It is intrinsic to **serving the peer's fresh dir image under multi-node reuse churn**: re-reading the coherent block exposes the peer's REUSED inode numbers, and processing them (iget / reload / inactivate ghost incarnations) storms. At default (serve stale own block) there is no fresh-peer-inode exposure → no storm → no wedge (but corruption). See [[sess24-PATCH5-fixes-corruption-passes-8of8-once-but-intermittent-reread-wedge-remains]], [[sess24-leafonly0-wedges-at-4-nodes-too-fundamental-reread-deadlock]], [[sess24-CONFIRMED-leafonly0-wedges-pristine-keeper-need-serial-console]].

### The wedge, characterized
HARD hang (CPU stuck / IRQs-off): hung_task & NMI-watchdog print NO stack; node goes fully network-dark. Serial capture caught the moment: all of test2/3/4 froze at ts ~72–73s mid-FLOOD of `P103-RELOAD-REUSE-ADOPT` — hundreds of inode-cluster reload adoptions across AG-spaced inode numbers (2M,4M,…14M) in ~5s, then serial output STOPS with no Call-Trace → a livelock/hard freeze during the mass inode-reload sweep, not a clean D-state cycle. **P103 is a CORRELATE of the reuse churn, not the cause** (3727 P103 lines occur at DEFAULT 4/tcp which PASSES). P103 path = `xfs/xfs_mxfs_dlm.c:9113-9136`: reloading an in-core REG inode whose disk dinode has di_size==0 and di_gen≠incore i_generation (genuine inode-number REUSE, disk_mode=00 = free slot) → adopts peer's reused incarnation via `xfs_inode_from_disk`. See [[sess24-leafonly0-wedge-correlates-p103-reload-storm-serial-setup-done]].

### Confound correction (methodology lesson)
Early "leaf_only=0 wedges at 8" runs were confounded: they carried sess24's own (independently wedge-causing) DLM changes. Those 3 DLM changes — (1) `dlm/dlm.c` queued_at-preserve across retry, (2) `dlm/dlm.c` FAIR-GRANT queueing behind older incompatible waiter, (3) `xfs/xfs_mxfs_dlm.c` ASYMMETRIC MHT `mxfs_dlm_mht_defer_bast(ip, requested_mode)` honoring PR BAST immediately — PASS 2/tcp but REGRESS 4/tcp dir_reuse 4/4→0/4 (nodes wedge, rc=-110, no corruption). Prime suspect: asymmetric MHT is load-bearing (MHT batching both masks the leaf/btree coherency bug AND prevents a release-timing deadlock; honoring PR BAST immediately breaks it). LESSON: GPT's "honor PR BAST immediately / fair-grant" is NOT safe to bolt onto this DLM as-is. All reverted; only `prep_node.sh blockdev --flushbufs` kept. The wedge was then RE-CONFIRMED on the PRISTINE keeper (zero code changes) at both 4 and 8 nodes → the leaf_only=0 wedge is genuine and independent of those DLM changes. See [[sess24-FINAL-state-leafonly0-wedges-need-demand-reread-patch5]], [[sess24-CONFIRMED-leafonly0-wedges-pristine-keeper-need-serial-console]].

### Residual after corruption is gone: DLM acquire STARVATION
Once the coherency faces are eliminated, the run dies differently: a dir-lock acquire on the hot dir ino=131 retries 60× (P36-RETRY) and times out after **184535 ms** (exactly 60 × ACQUIRE_WAIT) → `DLM inode lock unrecoverable: rc=-110` → `xfs_force_shutdown(SHUTDOWN_CORRUPT_INCORE)` at `xfs_mxfs_dlm.c:12394` (later `:12392`). Observed for mode=3 (PR reader/cold-verify readdir) starved by the EX-writer storm; 8 nodes hammering one dir → EX ping-pong (grant_gen hit 52 round 1) starves PR waiters. leaf_only=0 WORSENS this: synchronous FUA per stale block → longer tenures → more staleness → worse starvation. Per RULE 0, 184s is itself a FAIL, and shutdown-on-acquire-timeout is wrong (rc=-110/ETIMEDOUT ≠ in-core corruption).

## sess24 GPT-5.5 design (converging 6-patch series)
GPT confirmed TWO separate bugs: DLM fairness isn't real (retries lose queue position + REAFFIRM bypasses fairness), and dir coherency is too coarse (leaf_only=0 ≈ 8.7s/handoff ≈ 10× budget). Ordered patch series ([[sess24-gpt5.5-dlm-fairness-and-demand-reread-design]]):
- **Patch 4 (do FIRST, easy):** don't `xfs_force_shutdown` on DLM wait timeout at `xfs_mxfs_dlm.c:12394`; retry/refresh + keep waiting (optional deadman). Stops the cluster cascade by itself.
- **Patch 1:** persistent idempotent master waiters — a timed-out remote retry must NOT remove+recreate the WAITING entry (resets queued_at → FIFO loss + absence window); refresh last_seen, PRESERVE queued_at, remove only on grant/cancel/death/unmount/destroy.
- **Patch 2 (the key missing piece):** REAFFIRM must obey the fairness barrier. Today a remote re-request of an already-held sufficient mode bumps grant_gen + re-grants + fires BAST but BYPASSES compat/queue, so an EX holder keeps cached EX while a PR waiter starves. Fix: if an incompatible waiter from another node exists → mark holder `revoking`, send BAST, reply "revoke-pending/wait", do NOT bump grant_gen, do NOT re-grant, but KEEP the GRANTED entry visible. REAFFIRM at `dlm/dlm.c ~2759-2856`; fresh compat path + (non-firing) FAIRGRANT ~2936; local check_compat ~1223.
- **Patch 3:** local BAST disables the cached fast-path — on BAST set `lock->revoke_pending=1`; acquire fast-path grants only `if (cached_mode>=req && !revoke_pending)`, else drain → EX durability fence (log_force+iflush+blkdev_flush) → RELEASE → recompete.
- **Patch 5:** demand-driven data-block reread — keep `leaf_only=1` (cheap leaf/node/freeindex reread), do NOT reread every stale DATA block; reread the SPECIFIC block on demand at authoritative sites (`mxfs_dir_buf_ensure_current(dp,bp,ctx)`): before use_free/addname RMW/removename RMW, before returning readdir/lookup results from a stale block, before using freeindex to choose a block. Correctness hole to avoid: readers must not return stale RESULTS (a stale negative lookup after a peer create is wrong) — lazy reread OK, stale results not. Call site `xfs/libxfs/xfs_dir2_node.c:1959` (`xfs_dir3_data_read`) right before use_free at `xfs_dir2_data.c:1740`.
- **Patch 6 (perf, later):** bounded EX batching quantum (max_ops=16 / max_ms=10) only when solely EX waiters; hard PR barrier if a PR waiter is oldest.
- **(d) big architecture, not now:** dir delegation/combining (one node owns the hot dir, peers forward create intents) or hash/range-partitioned dir locking.

## sess25 — PROVEN: the clobber is a background xfsaild destage of a stale in-core dir block
Probes settled it. Refuted first: `tenure_evict=1 + dir_evict_prior_tenure=1` still FAILS (acquire/modify-path evict is not the issue); P68-EVDECIDE showed ZERO `undurable=1 done=1` for ino=131 → the evict never keeps a stale DONE base ("stale RMW base kept by evict" theory WRONG).

`dataclobber=1` detect-only run + per-node dmesg PROVED: the clobbering write is ALWAYS `in_txn=0` (0 with in_txn=1 across all 8 nodes) — but in_txn=0 is NOT a discriminator (XFS writes ALL metadata outside transactions: log→CIL→AIL→xfsaild destage). The clobber is the **EX holder's own background AIL-push destage**: `mode=5 real_mode=5` (real DLM grant = EX), `in_ail=1`, `bdirty=0 pin=0`, comm=dd/bash (AIL-push in app context, NOT the kworker release-drain). Critically `stale=0` (bufgen==dirgen) → gen/epoch guards are BLIND (matches "count guards blind"). `ex_write_guard` (default ON) only suppresses non-EX writes (dir_not_held_ex); this clobber is EX-held so it slips through. `dir_stale_incarn_skip` needs dc_stale (bufgen<dirgen) → blind to stale=0. See [[sess25-PROVEN-clobber-is-background-aild-destage-of-stale-incore-dirblock]].

**Root (feedback loop):** EX holder's in-core dir block becomes stale (loses a peer's entry) → background AIL-push destages that stale block over the peer's fuller disk → disk now stale → next acquirer's evict+reread fetches now-stale disk → stale RMW base → repeats.

### RELVERIFY probe: the release fence is COHERENT — loss is MODIFY-time
P25-RELVERIFY (`mxfs_dir_data_release_verify`, param `dir_relverify` default OFF, build **5954F53F**): at EX release fence, plain-read each dir DATA block from disk, compare active-dirent fingerprint to in-core. Result: mismatches fire (incore_cnt<disk_cnt, e.g. 55 vs 134) but ALL are `done=0` (XBF_DONE clear = evict-invalidated, will refetch coherent disk on next access); `in_ail=0 undest=0`; ZERO `done=1` mismatches. So the release NEVER hands off a harmful XBF_DONE-stale block — Inv-1 (RELEASE) holds; the in-core/disk divergence at release is benign lazy-evict. Therefore the readdir=799 loss is NOT a release-fence gap and NOT an EX-held-served-stale-DONE block; it is a **MODIFY-TIME stale-base RMW** (addname reads a refetched-but-still-stale or evict-skipped block and allocates a slot occupied on disk → background destage clobbers a peer's dirent). See [[sess25-DECISIVE-exheld-stale-cached-dirblock-subset-of-disk]].

Narrow open question → next decisive probe: at addname, after `xfs_dir3_data_read` of the target block, plain-read disk and compare, AND log the freeindex block incore-vs-disk. If the DATA block matches disk but the chosen free offset is occupied on disk → **freeindex staleness** (freeindex/leaf drives slot choice, refetch it too before allocation). If the DATA block itself differs from disk → refetch race (concurrent destage between coherent release and this read, or a non-FUA per-initiator stale cache).

### The GFS2 invariant (the intended fix) and the AIL-defer attempt
Correct direction (GPT-5.5 confirmed): a multi-node dir DATA/LEAF block's on-disk image must change ONLY via the EX holder's synchronous release-drain (Inv-1 handoff fence), NEVER via background xfsaild/AIL-push destage. Then between acquire(read coherent disk)→release, disk is FROZEN; holder's view = acquire-disk + own-mods = coherent superset; handles ADD and REMOVE (release-drain writes current post-remove in-core) with no legit-remove resurrection (the trap that made dir_stale_incarn_skip catastrophic in sess22 and write-suppression a corruptor in sess23).

Implementation attempt (build **C2F02FF6**, all KEPT in tree gated OFF by default): `mxfs_dir_ail_push_defer(bp)` (defers iff multi-node + dir-namespace buf + owner in-core + `i_dlm_mode==EX` + (`i_dlm_dir_gen!=0 || i_dlm_dir_contended`)); `xfs_buf_item_push` (`pal/linux/xfs_buf_item.c`) returns `XFS_ITEM_LOCKED` + unlock (keep BLI in AIL, no I/O); sticky `i_dlm_dir_contended` set on ANY dir BAST (covers the create-phase cold window since create never bumps dir_gen); module param `dir_ail_defer` (DEFAULT 0). Results: 8/tcp dir_reuse loss 3 rounds → 1 round, but it **REGRESSES** — 4/tcp full suite defer-ON lost node2's ENTIRE 49-file batch (readdir=351/400) at round14. Two failure modes: (1) whole-batch loss — deferring WITHHOLDS background writes the release-drain does NOT reliably make up (the "lands only at release-drain" premise is FALSE as-is: coverage/timing gap); (2) starvation-shutdown — deferred blocks pin the AIL/log tail → EX holder can't release promptly → peer acquire times out 184s → the same shutdown wall as the re-read path. So `dir_ail_defer` DEFAULT 0; C2F02FF6 ≡ keeper. See [[sess25-FIX-ail-defer-reduces-dir_reuse-loss-residual-remains]]. Also refuted (modarg, no build): `tenure_evict=1+evict_prior_tenure=1`, `force_evict=0`, `inode_mht_ms=50` (fewer defers → less coverage) — all still lose.

### To make the GFS2/defer path viable (next-session TODO)
1. Make the release-drain PROVABLY flush EVERY deferred dir block — add an assertion that no dir DATA/LEAF AIL item survives EX release; if one does, the fence is false. The whole-batch loss = release-drain missing deferred blocks.
2. Add a liveness valve: on contention/BAST run the quiesced checkpoint+release PROMPTLY (cancel MHT); on AIL/log pressure schedule the release worker — NEVER let a deferred block be written async behind the release path's back.
3. Only then re-enable `dir_ail_defer` and re-test 4 AND 8 tcp.
Alternative if defer stays unviable: a bio-chokepoint backstop needs a real SUBSET check (our entries ⊆ disk) to safely suppress — fingerprint (count+sum+xor) CANNOT prove subset.

## Cross-cutting lessons / recurring failure modes
- **`dataclobber=1` / detect-only "PASS" is an ARTIFACT.** The extra detection latency masks the race; a detect run that "passes" is not a real fix.
- **Flakiness discipline.** dir_reuse 8/tcp is ~50% on fresh boot and ~always-fails on a 2nd consecutive run (bdev buffer cache survives rmmod → peers read stale run-A pages after test1 re-mkfs). ALWAYS `virsh destroy+start test1..N` between trusted runs; single-run PASS is not proof. `blockdev --flushbufs $DEV` added in `tests/setup/prep_node.sh` (hygiene, not root).
- **Validate every DLM change at 4/tcp first** — the wedge/regression first appears at 4 nodes, before spending an 8/tcp run.
- **184s (60 × ACQUIRE_WAIT) shutdown is itself a FAIL** (RULE 0); do not treat rc=-110 acquire timeout as SHUTDOWN_CORRUPT_INCORE.
- **stale=0 defeats all gen/epoch guards** — the harmful clobber has bufgen==dirgen; count/gen guards are blind; the true discriminator is EQUAL-count DIFFERENT-fingerprint (content-divergent).
