## dir_reuse single-dirent loss (sess50-52, ccloop): a TCP-DLM phantom-EX / grant-ordering hole, not cache staleness

Central topic: the ~130-session `dir_reuse` 8-node/TCP failure — a **count-preserving single-dirent durable loss** (readdir=799/800; one node's `.md5` sidecar vanishes, e.g. `node1_f9.md5`, `node4_f15.md5`, `node6_f43.md5`; all 8 nodes agree; LOOKUP_ENOENT + REREAD_MISS = durable). Storm dir = shared, EX-serialized, ino **131**, daddr **120** (block 0), incarn reused across rm-rf+recreate. Storage confirmed **LIO-ORG, write-through, FUA reads required+ON** (NOT SCST; FUA-platter-lag is not the mechanism). Across sess50-52 the loss was decisively re-cast from a cache-coherency bug into a **DLM mutual-exclusion / grant-ordering hole** — a dir-block modify performed WITHOUT a currently-held exclusive grant. A second, **flaky mass-loss / readdir=0 cascade mode** (700-722/800) is build-independent, correlated with a slow/wedged node under storm load and the D-state `[mxfs-worker]` teardown wedge — distinct from the primary single-dirent bug.

### Cross-cutting invariant / infra facts (all three sessions)
- **Base is coherent at modify.** Re-proven many ways: P28-PLATTER FUA-compare in-core-vs-platter = MATCH overwhelmingly (only own dirty in-flight adds DIFFER); sess50 `b_mxfs_relepoch == dp->i_dlm_epoch` at every read; i_dlm_epoch does advance. So stale-read and stale-modify-base are OUT.
- **Master serializes correctly.** Single stable master per resource (test7/test3 depending on run); `mxfs_dlm_audit_double_grant` = 0; epoch monotonic, no reset/eviction. The hole is timing/ordering, not a static double-grant.
- **Loss is count-preserving:** no write ever lowers a block's count (P-COUNTREGRESS 0×). Two nodes RMW the same block from the same base K→K+1 with different entries; last writer durable, the other's entry gone.
- **Infra:** every run wedges 1-2 nodes on teardown (D-state `[mxfs-worker]` pins module refcount, rmmod fails); recover with `virsh -c qemu:///system destroy testN; start testN`; do a FULL 8-node clean reboot before trusting any result (partial-reboot gives mass-isolation false cascades). Decisive tool = `dirwr` content fingerprints (`MXFS_EXTRA_MODARGS=dirwr=1 + DRC_STREAM=1`, P50-WR/P50-RD by daddr+incarn+realns → `/src/mxfs/tests/tcp/drc_cap/stream_rank*.log`). CAVEAT: cross-node `realns` (ktime_get_real_ns) is NOT clock-synced (no chrony); absolute dt (3-26ms) can't alone prove overlapping critical sections — need a clock-independent proof (owner-cookie).

### sess50 (ccloop 4cb2d0a2) — coherency theories exhausted; localized to grantee phantom-EX
Builds: instrumentation-only progression `4115969B` → `5362F91E` → `F6E61BD7` → `A9C02659` → baseline-equiv `4E3733D0`/`3B0EB406` (epoch_adopt=0). No functional fix baked.

Full **refutation map** (each measured, do NOT retry) [[sess50-FINAL-all-coherency-refuted-prime-suspect-dlm-serialization-hole]] [[sess50-REFUTED-grantgen-and-tenure-counters-unreliable-handoff-underfires]]:
- **relepoch cross-node writeback gate** (GPT "Fix 4/5": skip clean dir buffer where `b_mxfs_relepoch < ip->i_dlm_epoch`): REFUTED, reliability loop PASS=0/FAIL=4, and 2/4 losses had **0 skips** → the loss does NOT go through an xfsaild reflush of a pre-release stale buffer; **loss is at MODIFY time, not writeback** [[sess50-relepoch-writeback-gate-REFUTED-loss-is-at-modify-not-writeback]].
- **grant_gen writeback gate** (sess49 GPT): `gg_mismatch=0` on every clobber; grant_gen inert for the contended inode.
- **dir_refresh_inplace=1**: regresses to whole-batch loss.
- **Case A allocator-overwrites-live-dirent**: ruled out (`xfs_dir2_data_check_free` would EFSCORRUPT; loss is silent).
- **i_mxfs_ex_grant_seq tenure counter (Case B)**: unreliable (only bumps on slow-path EX upgrade @15172, not fast-path serves), prior_tenure=0 is a false negative.
- **stale read / ABA writeback / acquire LOCKED-SKIP hole**: all refuted.

Handoff-bit root-and-refinement chain:
- **Handoff bit `ho` under-fires** [[sess50-ROOT-handoff-underfire-last_owner-immediate-prior-only-use-dg_shadow-epoch]]: P51-HANDOFF-UNDERFIRE (build `5362F91E`) proved a fast-path EX serve where `hgg` jumps (e.g. 862→1071) with `ho=FALSE`. Cause: `dg_grant_ex` (dlm.c ~2732-2756) sets `handoff = (last_owner != owner)` and overwrites `last_owner` every grant (dlm.c:2753) → true only if the IMMEDIATELY-prior grant was another node; in a same-node re-grab burst `ho=FALSE`. sess63 gated on `ho` (not raw grant_gen) to avoid same-node over-fire — trading over-fire for under-fire.
- **The reliable signal exists but isn't consumed on the fast path**: monotonic `dg_shadow.epoch` (dlm.c:2744, P64-MASTER-HANDOFF), surfaced as `i_dlm_dir_valid_epoch` via `mxfs_v5_dlm_inode_dir_epoch`. The READ gate (xfs_da_btree.c:3959) consumes it; the fast-path dir-EX SERVE (xfs_mxfs_dlm.c:14373) does NOT.
- **But propagation is broken** [[sess50-NEXT-fix-dir_epoch-propagation-some-grant-path-delivers-0]]: sess44 already proved (P44-GRANTDIREPOCH, dlm.c:2514) the modifying node's local `lk->dir_epoch=0` while the master computes epoch→515. Suspect paths delivering 0: **self-grant (master grants itself, dlm.c:1720-1722)** uses `pending_signal_resource` not `send_grant`, never stores `wk->dir_epoch` into the master's own lk; local-insert dlm.c:1334 only assigns `handoff`, not epoch_out. Remote-promote path (dlm.c:1714-1727) is correct.
- **Localized to the grantee** [[sess50-LOCALIZED-grantee-phantom-cached-EX-stale-local-dir_epoch-master-sends-correctly]] (build `C69E3475`, P51-SENDGRANT+P44+P64): master computes AND sends epoch correctly (up to 662); EVERY grantee stores a STALE local `lk->dir_epoch` (max 57-189, many 0). ⇒ loss is at the grantee: a node serves a fast-path cached `i_dlm_mode=EX` with an OLD dir_epoch while the master advanced the epoch by granting peers — the prior holder's local EX was never downgraded (lost/unprocessed BAST on TCP, or MHT held through it). **PHANTOM CACHED-EX after an unprocessed revoke.**

Two fix directions named: **(A)** reliable revoke/downgrade of the prior holder before the new grant commits; **(B)** grantee-side per-epoch ownership-validation RPC (master-authoritative held-check). Prime remaining suspect stated explicitly: a DLM serialization hole / phantom-EX where `i_dlm_mode=EX` (mode=5) but `mxfs_dlm_grant_gen=0` (dlm.c:2406, no granted local lock) — XFS holds a cached/phantom EX not backed by a current local grant. GPT-5.5 owner-cookie variant proposed (write `{node,epoch}` to a debug sector with FUA on EX acquire, verify at every modify). Tools added: `tests/drc_grantgen_probe.sh`, `tests/drc_timeline.sh`, `tests/drc_reliability_relepoch.sh`.

### sess51 (ccloop) — root PROVEN via content fingerprints; both fixes reverted; master-authoritative revalidate candidate
Build progression: `C69E3475` (baseline) → `B3957326` (grant_gen fix) → `65E74628`/`AED21CF5` (probes/evict, both inert/reverted) → `CBE2E8D9` (dir_ex_revalidate, gated).

- **Content-fingerprint proof** [[sess51-PROVEN-loss-is-count-preserving-divergent-RMW-phantom-cached-ex]] (build `B3957326`, dirwr=1): loss round2 = `node4_f15.md5`. Ruled out master handoff-miss (sole stable master test7, epoch monotonic 1→616, P-DOUBLEGRANT=0, P-STALEMASTER-GRANT=0), stale-base RMW (no create write below running max), ABA writeback. PROVEN mechanism = **count-preserving block-level divergent RMW**: two nodes serve dir-EX and RMW the same block from the same base concurrently. Master never sees a double-grant because the PHANTOM node serves the fast-path (cached `i_dlm_mode=EX`) without consulting the master. The local held-check (`mxfs_dlm_held_mode`, xfs_mxfs_dlm.c:13965) reads the same stale local mirror → cannot detect it. **Note: P51-HANDOFF-UNDERFIRE / grant_gen is NOISE** — grant_gen is a GLOBAL counter (`dlm_next_gen`), so `hgg` jumps ~200/grant from the 800 file-inode grants, not ino-131 handoffs.
- **grant_gen=0 self-grant root + fix (Attempt 1)** [[sess51-ROOT-local-immediate-grant-gen-zero-evades-fastpath-gates]]: fresh-dir round1 lost 4 tail `.md5` entries (NOT about inode reuse — refutes sess50's phantom-across-reuse framing as the *primary* mechanism). Master's local-immediate EX self-grant (`mxfs_dlm_lock` compat path, dlm.c:1321-1368) does `lock_alloc(GRANTED)` (zeroes grant_gen) then `dg_grant_ex` WITHOUT `dlm_next_gen` — unlike every sibling path (remote-immediate 3141, reaffirm 2947, upgrade 3015, promote_waiters 707). So the master's own EX grants carry grant_gen=0; fast-path staleness gates all guard `hgg != 0` (xfs_mxfs_dlm.c:14391) → master SKIPS the handoff refresh even when a peer held EX → RMWs a stale base. FIX (`B3957326`): stamp `newlk->grant_gen = dlm_next_gen(ctx)` at dlm.c:1346. Secondary anomaly: P-DOUBLEGRANT owner ids (garbage, appear nowhere else in dmesg) pair with grant_gen=0. **Attempt 1 REFUTED** — single-dirent loss persisted identically; reverted [[sess51-FIX-epoch-triggered-wholedir-evict-build-AED21CF5]].
- **Attempt 2 (GPT epoch-triggered whole-dir evict, `AED21CF5`): REGRESSED HARD** — round7 722/800, round8/9 700/800 mass loss. Cause: under the storm handoffs fire on nearly every op → constant eviction → cold re-read fetches the on-disk image LACKING peers' committed-but-not-durable entries (each node syncs only at end of its wave) → RMW+writeback of the short image clobbers many. **"Force the reader to re-read more" is the WRONG direction — it amplifies loss.** Revealed lead: the loss is fundamentally a **release-side durability/ordering gap**, not reader-side staleness — for a post-handoff cold read to lose a peer's entry, that entry must not be durable at handoff time (Invariant #1 drain-before-release). Both attempts reverted; tree byte-identical to `C69E3475`.
- **Correction** [[sess51-CORRECTION-epoch-evict-was-inert-force-evict-already-1]]: the epoch-evict gate change was **INERT** — `mxfs_dir_force_evict=1` is the compile-time default (xfs_mxfs_dlm.c:3957), so `mxfs_dir_evict_data_blocks` ALREADY runs every modify; adding `!epoch_advanced` to an already-false AND-chain is a no-op (`AED21CF5` compiled byte-identical to baseline). ⇒ the repro7 mass loss was the FLAKY second mode, build-independent, not the change. Key implication: **whole-dir clean-block evict already runs every modify and the single-dirent loss still happens** — eviction machinery is NOT the fix.
- **Refuted the dirty-AND-epoch-stale-block hypothesis** [[sess51-REFUTED-dirty-stale-block-hypothesis-P51-zero-fires]]: P51-KEEPSTALE-DIRTY (build `65E74628`) fired **0×** at a round-11 single-dirent loss → the clobbered block is NOT dirty-and-epoch-stale; blocks are NOT epoch-stale at RMW (matches sess50 base-always-fresh). This directly REFUTES the sharpest merge hypothesis below.
- **Sharpest (later refuted) mechanism** [[sess51-SHARPEST-mechanism-in-AIL-stale-block-needs-merge-or-drain-on-acquire]]: proposed the clobbered block is BOTH locally-dirty/in-AIL (our adds) AND stale (missing a peer's drained entry) — the evict keep-guard prevents refresh → block needs a UNION/MERGE not evict-or-keep; fixes were (1) drain-own-in-AIL-before-refresh on handoff, or (2) block-level 3-way merge. Refuted by P51-KEEPSTALE-DIRTY=0×.
- **BREAKTHROUGH candidate (build `CBE2E8D9`, `mxfs_dir_ex_revalidate=1`, gated default-OFF)** [[sess51-BREAKTHROUGH-dir-ex-revalidate-master-authoritative-fix]]: in `mxfs_dlm_ilock_begin`, a PUBLISHED peer-reachable dir EX-modify (`!i_mxfs_self_created && !i_dlm_unpublished`) falls through to slow-path master re-acquire instead of serving cached EX. On a non-master node the slow path always round-trips the master (dlm.c:1026 has no local short-circuit) → master reaffirms (cheap, dlm.c:2919) or serializes (BAST peer, grant fresh). Kills the proven phantom; the TCP analog of CAW's on-disk slot-bit check (sess106/107). Result: rounds 1-15+ clean vs baseline failing by round 2/6/11. **⚠️ REFUTED IN sess52** (see below) — a ~25% flaky fluke.

### Convergent FIX direction (open at end of sess52)
Guarantee the DLM EX grant is HELD continuously from first dir-block read through txn commit; no bast_process/dwork/demoter/entry-removal path may release the dir grant while a create modify is in flight. Concretely: (1) gate the dir modify/serve on `mxfs_v5_dlm_inode_held()>=EX` (DLM = source of truth) — NOT on `(mode==EX && state==CACHED)`; the slow path must not publish EX unless `held==1` (a plain `dir_ex_revalidate` divert is insufficient — the slow path itself yields the state=ACQUIRING held=0 case); (2) fix revoke→demote propagation (GPT#2 handshake: master revoke → holder demotes+ACKs → master grants) and grant-after-drain ordering (master must not grant peer B until holder A confirms drain-complete, seq-numbered); (3) block local-entry removal while `ex_holders>0`. Validate: **P51-MOD/P51-PHANTOM held=0 count == 0 AND dir_reuse 8/tcp PASS**, holding perf (RULE 0 — keep MHT; `mht=0` worsens phantoms and is 260-410s). Clock-independent proof still owed: shared-disk OWNER-COOKIE (`{node,grant_gen}` FUA sector, verify at every block-0 modify) or a master-side grant_gen-vs-current-granted total-order check. Write-side residual (sess28 stale-in-AIL destage of a coherently-read block) may be a parallel contributor; the reacquire-site transactional 3-way merge sess28 named was never landed.
