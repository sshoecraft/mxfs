Two families of trap, folded from nine notes: (1) MXFS is a fork of upstream XFS built for several kernels (6.8 rig, Debian 6.12, PVE 6.17, 7.0, RHEL 5.14), so anything behind a kernel-version gate can be wrong, deleted or never compiled; (2) PAL block I/O has hard constraints on buffer memory, length and size that only fail on particular paths. Plus one C-language trap that passes silently. The topic is the last-listed group; the grouping is by shared failure mode, not one subsystem.

## 1. Kernel-version gates

- **A hook behind one arm of a version `#if` is deleted, not just unreached.** The authority gate's `data` arm sat in `xfs_writeback_submit`, referenced only by the 6.17+ iomap ops. On the 6.8 build nothing referenced it, gcc dropped it, and `strings -a mxfs.ko | grep -c P290-AUTH-REFUSED-DATA` was 0 while the log/dio/meta probes were 1. Source reading concluded the arm existed for weeks. A "VACUOUS" lap (class `data` never reached the gate) was the module reporting accurately that the path was not in the binary. Ask the BUILT module (`strings -a`, `nm <obj>`), not the tree; when a lap says class X never reached the gate, check the arm is in the binary before blaming the workload. Sibling trap: do not reuse a site->oracle map as a site->workload map (`SITE=data` ran the O_DIRECT writer and entered as `dio`). [[trap-a-hook-wired-only-into-one-arm-of-a-kernel-version-if-is-deleted-by-the-compiler-not-merely-unreached]]
- **A backported fork loses whole hooks.** Four mechanisms were installed only in the newer kernel's ops struct: buffered-data authority arm (`xfs_writeback_submit`, 6.17+), iomap mapping revalidation (`iomap_write_ops`, 6.15+; 6.8 uses `iomap->folio_ops`), lazytime completion (`sync_lazytime`, 6.19+; 6.8 uses `dirty_inode`), delalloc release scan (a compat macro reduced the function to an unconditional punch). Three were integrity defects. Find them with `tools/warn_sweep.sh` (`defined but not used` = a dropped function; replays compile commands with `-o /dev/null`, safe on a live rig). Grep reference counts mislead (four `.sync_lazytime =` lines, all inside the same guard); a compat struct defined only to compile stays empty and the macro expands the argument away; half a pair (`validity_cookie` stamped, never read) means the wired half does nothing. Audit every `#if LINUX_VERSION_CODE` around an ops-struct member and every `xfs_platform.h` shim that replaces a function rather than renaming it. [[trap-a-backported-fork-loses-whole-hooks-because-the-newer-kernels-ops-struct-is-the-only-place-they-are-installed]]
- **A stable kernel carries some newer APIs, so gates pick wrong branches, some silently.** Debian 13 6.12.107 has embedded ioend `io_bio`, `->map_blocks(len)`, `iomap_file_buffered_write(..., private)`, 3-arg `kvrealloc`, `mapping_max_folio_size_supported`, yet keeps `io_type`/`IOMAP_F_SHARED`. Version gates at 6.13/6.15/6.17 chose wrong; worst one compiled cleanly (`xfs_end_bio` read `bi_private` as the ioend, no longer set once the bio is embedded). Compile errors are not a complete guide: audit every gate above the target against its real headers. Fix: one probe per API in `pal/linux/kcompat_probe.sh` (split bundled gates), export-check called functions (6.12 declares but does not export `generic_atomic_write_valid`, giving a modpost undefined), then tabulate each probe's answer on every shipping kernel (6.8, RHEL 5.14, PVE 6.17, 7.0) and confirm it equals the old gate's choice. A gate leaving a feature flag OFF can hide a missing check (enabling `fop_flags` would have exposed MAP_SYNC acceptance, already live on 6.17). [[trap-a-stable-kernel-carries-some-newer-apis-so-version-gates-pick-wrong-branches-some-silently]]
- **A clean rig build on Ubuntu 6.8 says nothing about Proxmox.** 0.89.77 passed every rig gate and shipped; DKMS failed on every PVE 9 node because gated newer-kernel code had never been compiled (`>= 6.19` `mmap_prepare` branch used `desc->vm_flags`, gone in 7.0). Run `scripts/pve_kbuild_check.sh [KREL ...]` (Debian 13 container, ~2 min; `scripts/release.sh` runs it first) after any change calling a kernel API not used before. Container gotchas handled: host network, `libelf1t64` and `libdw1t64` (else `Error 127` with no compiler message), `make -k` (else make stops after the first failed object). Drift found: `d_hash_and_lookup` -> `try_lookup_noperm(q, dir)` (6.16, args reversed); `destroy_timer_on_stack` -> `timer_destroy_on_stack`; `inode->i_state` a struct from 6.19/7.0 (read via `mxfs_istate()`, write `inode_state_assign_raw()`; a struct in `pr_warn` varargs compiles, so grep every read); `iomap_read_folio`/`readahead` ctx in 7.0 -> `iomap_bio_*`; `vm_area_desc.vm_flags` -> `vma_flags` + `vma_desc_set_flags`; `kernel_bind`/`kernel_connect` take `sockaddr_unsized *` in 7.0. 6.18/6.19 headers are unavailable (no kernel downloads), so 7.0 gates are proven only at 6.17 and 7.0. [[trap-a-clean-rig-build-on-ubuntu-6-8-says-nothing-about-the-proxmox-kernel-run-pve-kbuild-check]]

## 2. PAL I/O constraints

- **Sub-sector bio hangs dm.** `mxfs_pal_bdev_write(dev, off, ents, 96)` hung in `submit_bio_wait` (D-state) on `/dev/mapper/mpatha` on 6 of 30 nodes, on the disklock heartbeat thread via `v5_pr_fence_prove_locked`; heartbeat stalled (P-HB-MONSLOW 64 s) until peers fenced the prover, bio returned -52 after ~64 s, cascade needed virsh destroy/start of 7 VMs. Rule: every bio through `mxfs_pal_bdev_write/_fua/read` is a whole multiple of the logical block size (round to 4 KiB, `MXFS_RMAN_IO_ALIGN`; zero-pad, crc over the real length). SCSI paths reject sub-sector with -EINVAL; the plain bio path does not fail fast on dm, it hangs. Anything slow in `v5_pr_fence_prove` runs on the heartbeat thread; a stall beyond the lease makes the prover the next victim. [[trap-pal-bdev-write-must-be-sector-aligned-subsector-bio-hangs-dm]]
- **Bulk FUA read is not a bulk bio read.** `mxfs_pal_bdev_read_prio` is a READ(16) passthrough (`scsi_execute_cmd`); `blk_rq_map_kern` refuses transfers over `max_hw_sectors` (512 KiB on the 2-node LUN), so 1 MiB gives -EINVAL, and the fallback only fires on -EOPNOTSUPP, which would have refused every mount. `mxfs_pal_alloc` is `vzalloc` above 16 KiB and the passthrough maps by `virt_to_page`, silently yielding wrong pages (the bio path handles vmalloc via `kaddr_to_page`). Rule: FUA-read buffers are `mxfs_pal_alloc_io` (kzalloc), at most the LUN's hardware limit (64 KiB is reliable order-4); the FUA write path may use any chunk size. Check `max_hw_sectors_kb` before choosing a passthrough size on a new rig. [[trap-a-bulk-fua-read-through-the-scsi-passthrough-is-bounded-by-max-hw-sectors-and-must-not-use-vmalloc-memory]]
- **An emulated compare-and-write must bounce the caller's buffer.** The DRBD CAS emulator built its write bio on the caller's buffer; `mxfs_pal_bio_sync_bdev` refuses vmalloc with -EINVAL and kernel stacks are vmalloc'd (`VMAP_STACK`). `mxfs_bootstrap_claim` passes a stack `&want`, so the pair-outage claim failed `P-BOOT-CLAIM rc=-22`; normal operation passes heap buffers and never showed it. Rule: a software replacement for a device command must accept every buffer the device path accepts; bounce through its own kmalloc memory. [[trap-an-emulated-compare-and-write-must-bounce-the-callers-buffer-a-kernel-stack-is-vmalloc]]
- **A bound that admits the only write is defeated by large-folio writeback bios.** 0.90.70's DRBD write bound (4 MiB / 64 requests per mount) admitted an oversized write when nothing else was in flight. On 6.17, iomap large-folio writeback built a 392 MiB bio (`P-DRBD-IOQ-DONE peak_kib=401408`), admitted alone; everything behind waited (coordination swaps up to 0.97 s on NVMe, O_DIRECT at 1.4-1.8 MiB/s with 8-10 s median completion vs buffered 80-115 MiB/s), because DRBD splits to 1 MiB only after queueing the whole bio. Rule: split before admission (0.90.71: `bio_split` from the front to <= 1 MiB, `bio_chain` the remainder, admit and submit each); judge a bound by peak in-flight bytes, not request count. Never split REQ_NOWAIT (cannot retry whole after a piece went out) or REQ_ATOMIC (`bio_split` returns -EINVAL). Pre-6.9 iomap chains and submits its own writeback bios, so a filesystem hook never sees them. [[trap-a-write-bound-that-admits-the-only-write-is-defeated-by-large-folio-writeback-bios]]

## 3. C declaration trap

- **A block-scope `extern` with the wrong parameter list compiles cleanly.** `xfs/xfs_icache.c` P99-IGET probes declared `mxfs_inode_disk_di_size(ip, modep)`; the definition in `xfs_mxfs_dlm.c` takes `(ip, modep, genp)` and writes through `genp`, so the callee wrote via whatever was in the third argument register (only with `mxfs.instr=1`). The sole symptom was one `-Wmissing-prototypes` among 236 unread warnings. Fix: declare cross-file functions once in a header the defining file includes (block in `xfs/xfs_mxfs_dlm.h` since 0.89.88) so a wrong local extern is a hard "conflicting types" error; run `scripts/extern_decl_audit.py` (exit 1 on disagreement) after adding any local extern; keep the 6.8 build warning-free and count from a CLEAN build (incremental builds hide warnings in unrebuilt files); grep assembler `Warning:` case-insensitively. Same pass: `xfs/xfs_stubs.c` stubs had wrong signatures (the zone stub treated `struct xfs_open_zone **` as a bio); compile stubs against their real headers. [[trap-a-block-scope-extern-with-the-wrong-parameter-list-compiles-cleanly-and-passes-garbage]]

## Common thread

Compiling and running on the rig proves only the arm the rig takes. For each of these, the instrument is the compiler or built artifact (`warn_sweep.sh`, `strings`/`nm`, `pve_kbuild_check.sh`, probe tabulation, `extern_decl_audit.py`), and for each I/O path the check is what the lowest layer accepts (alignment, `max_hw_sectors`, non-vmalloc memory, bio size) rather than what the caller usually passes.
