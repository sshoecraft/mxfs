One arc of MXFS design-consult rulings (Astra, sessions 80, 81, 83, 87, 88; defect D-381; builds 0.89.12 → 0.89.21) about what "this victim is fenced" is allowed to mean, who gets to certify it, and how the certifying state is held. Read in order — each ruling closes a gap the previous one's fix exposed.

## 1. Reachability, not proof, was the first bug (0.89.12)

Before any of the proof-contract work: a PREEMPT AND ABORT whose response is lost leaves the prover holding a durable "may have run" arm with no proving response, and *nothing ever revisited the slot* — not the retry worker (slot deliberately unarmed for retry), not takeover (refused, holder is alive), not any proof mechanism (all reachable only from `KEY_ABSENT_UNPROVEN`, never from `MAY_HAVE_SUBMITTED`-turned-ERROR). Consequence worth remembering: the lockout blocked not just a successor recovering the victim, but the *returning victim mounting itself*.

Fix shape: a **read-only same-owner resume** — fires only when the holder is this node's own current incarnation, descriptor still FENCING/durable-armed/blocked/unarmed; issues no state-changing command; cannot reach the sole-survivor gate (admission without retirement); tries only self- and boot-succession (pure observation); returns *before* the point that would arm a retry. Re-laying intent is idempotent (`mxfs_disklock_recovery_fence_intent` returns 0 for "our own attempt, resume it"). Must be bounded well inside the peer's mount barrier — first build polled 68x in one 790s lap against a 30s barrier. Verified `flr_s75e`, fails=0. See [[design-an-ambiguous-fencing-attempt-needs-a-read-only-revisit-not-a-retry-and-not-a-takeover]].

## 2. What counts as a retirement witness, at all (Astra s80, 0.89.13)

D-BOOT-SUCCESSION-NO-TASK-RETIREMENT-WITNESS: 0.89.12 had documented the unwitnessed premise (comments, log line, `rigs.json` declaration, a harness abort-on-undeclared-rig accessor) instead of fixing it. Ruling: **harness gating does not constrain a mounted filesystem.** The defect wasn't "module doesn't read rigs.json," it was that the production recovery path could authorize replay without establishing retirement of the victim's previously accepted writes.

Rules that came out of it: default to refusal (an integrity fix may sacrifice availability without owing a replacement first); scope any trust to a per-LUN qualified profile, never a global flag; an assertion is not a witness — record *which basis* was used (target-op vs. deployment-contract), never collapse to "proved"; the contract must state an *ordering* (every command from the lost nexus completed/aborted, ordered before the registration-absence event, before that event's *cause* is checked — arbitrary absence isn't nexus-loss evidence); a negative workload measurement characterizes, it doesn't establish a boundary; LOGICAL UNIT RESET is the one standard active retirement primitive but it aborts survivors' I/O too and needs full quiescence machinery around it, not a drop-in call.

Implemented as `enum mxfs_retire_basis {NONE, TARGET_OP, QUALIFIED_CONTRACT}`, a five-field contract string checked against LUN identity, module param `target_retire_contract` defaulting empty (refuse), refusal counter `P238-BOOTSUCC-NO-RETIRE-BASIS`. Explicitly NOT closed: the module still can't detect a target that violates its own contract — enforcement of the boundary is verified, truth of the assertion is not. See [[design-a-fence-kind-that-proves-only-admission-needs-a-declared-retirement-basis-and-refusal-is-the-default]].

## 3. Publish the proof, don't re-derive it; separate three claims (Astra s80, D-381 remainder)

Three facts that don't imply each other: (1) victim can't submit new I/O, (2) victim's *already-admitted* I/O has retired, (3) the *predecessor prover* can't cause further PR side effects.

Half 1 (successor's second PREEMPT AND ABORT): not intrinsically dangerous under distinct non-reused per-boot keys — the target's state-transition order decides which command matches, the late one names no valid service-action key and certifies nothing. "WRITE retirement" (outstanding data can't reach media) does not imply "PROUT retirement" (an accepted PROUT from a dead nexus can't later touch PR state) unless the contract says both. Residual gaps: same-boot remount key reuse, key-derivation collisions, I_T nexus identity ≠ boot identity.

Half 2 (certificate publish failure): **retry the publication, not the fencing.** Keep the completed proof bound to an immutable attempt identity and re-CAS only. A non-`-EEXIST` error is an **unknown commit outcome**, not failure — publication must be idempotent and reconcile the actual descriptor, never rewrite from a stale in-memory copy. Read-back of bytes is not durability; use the metadata layer's commit-reconciliation. Blocking is operational, not a verdict ("no valid durable certificate exists now," never "can never be certified again") — reconciliation, a later independent proof, or the same prover retrying all remain valid routes back, gated by the same attempt identity so a late error handler can't block a slice another thread already certified. Proof decay: historical retirement doesn't decay; *admission observations* do (absence-at-T isn't durable if that incarnation can re-register).

Implemented in 0.89.13: five-attempt doubling backoff from 200ms (~6s, inside the 30s mount barrier), disklock-primitive-supplied reconciliation (0 if already certified under our lease, -EEXIST if sealed/taken over), injectors `dbg_cert_fail_n` / `dbg_cert_lost`. Half 1 not implemented at this point. See [[design-publish-the-proof-do-not-re-prove-it-and-a-failed-certificate-write-is-an-unknown-commit]].

## 4. CAS validates an image, it doesn't choose one; SEALED isn't a release condition (Astra s81, D-381)

Closes the remaining D-381 ambiguity items:

- The successor's second PREEMPT AND ABORT is **disposed**, not prevented: target state-transition order (not response arrival order) decides which command wins; the loser's inherited "may have run" marker is historical, not a successor submission. Do **not** route an inherited `PRIOR_TERM_MAY_HAVE_RUN` to the read-only proof path — that manufactures a lockout (victim still registered, predecessor dead, no independent proof, reads can't make exclusion true). Keep takeover / proof-resume / publication-retry as three distinct operations.
- **A CAS is not a commit predicate by itself** — it protects a validated expected image, it does not validate that image for you. Unsafe schedule: A resumes under term 7, B takes over at term 8, A reads B's term-8 image as its expected image and CASes its term-7 proof in — the CAS succeeds and is "correct" while being wrong, because nobody compared the expected image against A's *captured* authority first. MXFS avoids this because `fauth` is captured once at fence-intent and carried unchanged to fence-certify, which validates the captured token before CASing — do not "simplify" this into a fresh auth-issue before certify, that reintroduces exactly this defect. After a failed CAS, re-reading must reconcile an unknown outcome, never silently adopt a new owner/term.
- **SEALED is not a release condition** for a rejoining node. A software admission barrier legitimately serializes rejoin, but releasing on the seal by name is wrong if sealing only freezes the dead node's journal work list — a joiner can mount, modify block M, and the survivor then replays the dead node's older update over the newer state. Release only at recovery-complete or once recovery locks/exclusion are actually installed. Measured seal-to-complete window on the 2/tcp rig: ~8.6s, and seal strictly precedes replay dispatch. Also: under a registrants-only/all-registrants reservation, a joiner's *registration* confers write eligibility even though "the survivor holds the reservation" — that fact alone doesn't exclude the joiner. Sole-survivor gate (single-holder WE) excludes; boot succession (WE-AR) does not.
- A local timeout proves nothing about a target command's fate — a freed request, an EH return, or `DID_ABORT` is not target quiescence. There is no honest fixed timeout after which an unobservable target operation becomes known-dead; without termination evidence or a complete noninterference argument, stay blocked. A read-only resume must never issue an abort/reset to manufacture its own evidence.

See [[design-a-successors-own-keyed-preempt-is-safe-and-a-commit-predicate-is-the-captured-authority-not-the-local-identity]].

## 5. A durable enum value is a construction contract (Astra s83, 0.89.16)

Question: does a fence certificate need a new on-disk retirement-proof block? Answer, generalized: the requirement is durable unambiguous identification of a still-supported proof contract, not necessarily a new block — but **tightening the meaning of an existing, historically overloaded value does not repair its durable instances.** A value on disk identifies which code, under which rules, was allowed to write it.

Consequences: never widen or reassign a value's meaning (disable consumption if the rules turn out unsound; allocate a new code point if the rules change incompatibly — "stricter from now on" silently reclassifies every past record). If two producers can write the same value under different contracts, the value is **unclassifiable and must be retired** — MXFS fence kind 16 was written both by the fence path (after a completed PREEMPT AND ABORT) and by bootstrap-owner takeover (after reading its own PR ledger with no operation run at all). Diagnostic method: enumerate every *writer* of the constant (grep every assignment), not the readers — that's how kind 16's collision was actually found.

Reader rule that falls out: authorize an irreversible action only by classifying the record into an explicitly supported, still-sound contract, validating its required evidence/bindings, and establishing it authorizes *this* operation under the applicable authority history — else refuse. "An older build wrote it" is not evidence the older build was right; "never rejected" is not a whitelist criterion. Mint-support and consume-support are separable (a contract can stop being minted and stay consumable). Before declaring "no format change needed," check the record actually carries the needed bindings — a key must not ambiguously identify two incarnations of a subject, an actor's epoch isn't the subject's epoch, a timestamp/generation counter isn't an operation witness. See [[design-a-durable-enum-value-is-a-construction-contract-so-two-producers-make-it-unclassifiable-and-it-must-be-retired-not-tightened]].

## 6. An environmental assertion is not a witness (Astra s83, 0.89.16, same session)

A path minted a replay-authorizing certificate from a *deployment assertion* (a per-LUN clause about the target's ordering behavior) rather than a proof. Unfixable by strengthening the assertion because: the module cannot detect a target that breaks it (no error, no refusal, no log — just a replay silently overwriting live metadata), and its support was purely observational (four probe laps, no late write in 180s at 50ms) — more laps improve characterization, they never turn absence-of-counterexample into a guarantee.

**Removing the unsupported certificate-producing path IS the integrity fix**, not a relabeling; the resulting unavailability is a separate, separately-recorded limitation. Checklist for this shape of fix in general: withdraw in CODE not config (a default an admin can restore isn't a fix — gate it at the one choke point every replay-authorizing kind crosses); reject a configured value out loud, by name, on its own log line (not buried in a reason buffer that truncates); legacy authority must not survive the upgrade (a durable certificate that could only have been minted on the withdrawn basis is refused at consumption too, not just at minting); no override in any form — not waiting, retrying, a mount option, "I accept the risk," a replacement key, or read-only mount. Refusal itself has a bar: bounded real failure (never a timeout kill) at the dependent mount, a durable BLOCKED state reached after a bounded series so dependents fail fast, survivor stays up serving what it owns, nothing crashes or shuts down. See [[design-an-environmental-assertion-is-not-a-witness-so-withdraw-it-in-code-and-reject-configured-values-by-name]].

## 7. Storage authority is a lease to a deadline, not a loss you're told about (Astra s87, 0.89.20)

Structural gap: every containment path needed the LUN to *answer* (a bounced write, a PR poll finding the key gone) — pure detection. A quiet fenced node whose audit tick hasn't come round yet issues nothing, is fenced, and knows nothing; once the appliance purges the dead registration, nothing is left to bounce anything. Measured: the fenced incarnation's bytes read back off the raw LUN. **Eventual detection of ownership loss is insufficient if stale I/O can become admissible before detection**; polling more often is not a fix (a PR read isn't an atomic check bound to the writes that follow).

Three details that make a local lease sound (the idea is easy, these are where the obvious implementation is wrong):
1. Anchor the deadline **before** the heartbeat is issued, never at completion — a delayed/aged completion stamped "now" makes local authority look younger than what peers can observe.
2. Accept a renewal only while the previous authority is still valid — a heartbeat CAS can succeed against a target that already released its reservation. CLOSED is sticky; a heartbeat that starts working again is not a grant.
3. Check where authority is *used* (the submission path), not only in a timer — a timer/heartbeat thread can stall with the rest of the VM. The check must close its own epoch from whatever context finds it expired, reaching no lock the withdrawal needs, no allocation, no LUN.

Gate covers all four LUN-mutating producers (metadata buffer submission/xfsaild/delwri, journal, buffered writeback, direct I/O) and **coordination I/O itself** — an expired heartbeat worker must not refresh its slot, an expired reservation-health worker must not re-register (that would be an incarnation undoing its own fence). No journal exemption: a dirty log on forced shutdown is correct; a node whose authority expired must not look clean by writing more. Refusals route through each layer's existing error completion or the gate only produces hung tasks.

The lease number is derived from two directions, never as a ratio of the peer's timeout: availability (must outlast heartbeat cycle + scheduling/completion delay) and safety (must expire before a peer completes a conflicting handoff) — show the remaining budget covers closure lateness, clock error, in-flight drain.

Hard limit that no lease closes: completing a Linux request with an error is not proof the corresponding SCSI command can never execute later — a software check can't retract a command already handed below it. If worst-case command lifetime is unbounded, no finite timeout ratio completes the proof; that needs exclusion surviving the fencer's disappearance, proven target quiescence, or a handoff that keeps protection until quiescence is established. Say so rather than letting unallocated budget read as margin. See [[design-storage-authority-is-a-lease-held-to-a-deadline-not-a-loss-a-node-is-told-about]].

## 8. The authority object itself: mount-owned, refcounted, not context state (Astra s88, 0.89.21)

Given the lease design above, where does its state actually live? `struct mxfs_authority` is a separate refcounted allocation holding the one copy of `{state, deadline_ms, anchor_ms, closed_at_ms, last_ok_ms, close_reason, withdraw_pending, incarnation, node, slot}`. The **mount** allocates it in `xfs_fs_fill_super` before `mxfs_v5_dlm_init` (so the gate has an answer from the first instant a clustered mutation is possible) and drops its reference in `xfs_mount_free`, after every producer/workqueue/timer/I/O completion is gone. The v5 DLM context and the disklock context each hold their own reference and write through to it. `mp->m_mxfs_clustered` gates once, never cleared: `if (!clustered) return true; else mxfs_authority_ok(auth)` — a missing object on a clustered mount is refused and counted.

Why not the obvious alternatives: not state inside the disklock context, because teardown frees that context while the mount can still be submitting (and the reverse — mount outliving the context — also happens, per the P304 departure-quarantine leak-with-module-pinned path). Not two mirrored copies (one in disklock, one in mount) — races produce a renewal completion overwriting a close, an old renewal clobbering newer state, state and deadline read from different updates, shutdown closing one copy while producers use the other; `READ_ONCE()` gives neither a coherent snapshot nor a lifetime. Not a per-work-item epoch stamp — sound only as long as an incarnation IS a mount and work already retains a mount reference implicitly; breaks if authority resolution ever routes through "current context for this device/slot/node" instead.

Published counters, once per unmount: `P291-AUTH-TAIL tail_admit=… tail_refuse=… no_authority=… tail_blind=…`. `tail_admit` is the positive control (submissions after DLM detach, admitted because the lease was still live — an ordinary unmount produces exactly one). `no_authority` must always be zero. See [[design-the-incarnations-authority-is-a-refcounted-object-the-mount-owns-not-state-inside-the-context-that-teardown-frees]].

## Cross-cutting lessons across the whole arc

- Detection is not the same claim as exclusion, and exclusion is not the same claim as retirement — every ruling in this arc is ultimately about not letting one of those three stand in for another.
- "It hasn't been observed" (probe laps, workload measurement, read-back bytes, absence at time T) is never treated as proof in this codebase; only a target-confirmed, ordering-guaranteed primitive counts, and where none exists the ruling says so and blocks rather than inventing margin.
- The fix for an unsound authorization path is consistently: refuse by default, withdraw in code, no override — never "narrow the conditions" or "trust it a bit more."
