## 4/tcp `dir_reuse_coherency` durable single-dirent loss — sess10 (ccloop run 4cb2d0a2)

Central topic: at 4-node TCP-DLM, `./run.sh 4 tcp dir_reuse_coherency` fails ~80%+ with a **durable single-dirent loss** — one create's entry vanishes from the shared target. The whole session was a RULE-4 hunt for the clobber mechanism; every gen/epoch-gated fix was refuted, the leading root landed on a release→grant durability/visibility race, and the concrete probe to settle it was left for the next session. Criterion NOT met at handoff.

### Ground-truth failure shape (baseline build DE3A7E21)
- **1/2-node PASS, 4-node FAIL.** `./run.sh 2 tcp dir_reuse_coherency` = PASS 2/2 on DE3A7E21; 4-node = FAIL 0/4 on a **fresh virsh-reset clean cluster** (not a degraded-node artifact — reproducible). This is a concurrency-threshold bug [[sess10run-4tcp-clean-repro-dirty-block-clobber-mechanism]] [[sess10run-NEXT-real-fix-direction-concurrent-rmw-stale-base]].
- **All 4 nodes lose the SAME entry** (readdir=399/400, lookup_fail=0 everywhere) → gone from the shared TARGET, not a per-initiator read cache → some node RMW'd a dir data block from a stale base and wrote it durably [[sess10run-GPT-consult-durable-clobber-stale-inAIL-block-survives-release]].
- **Survives the test's `drop_caches`** → durable on-disk loss, not intra-node staleness. Losses are EARLY rounds (2,8,9 or round 15), NOT accumulation. Lost items are `.md5` sidecars or data files (e.g. `node4_f1.md5`, `node2_f16.md5`, `node1_f9`) [[sess10run-DISCRIMINATOR-clobber-stale_base0-invisible-to-gen]] [[sess10run-4tcp-clean-repro-dirty-block-clobber-mechanism]].
- **NO FS corruption/shutdown.** Earlier "shutdown" greps matched benign `scsipr: unregister on shutdown failed` + module unload; `xfs_imap_to_bp` stacks are the normal `mxfs_dlm_bast_process` P70 quiesce barrier, not EFSCORRUPTED. No `Internal error`/`EFSBADCRC` [[sess10run-4tcp-clean-repro-dirty-block-clobber-mechanism]]. Later rounds (19/20) degrade further (324/400, test1=0) + P36-RETRY acquire timeouts + forced-release = post-damage cascade, not the core bug.

### Mechanism (evidence-backed)
4 nodes concurrently create into ONE shared leaf-format dir spanning multiple data blocks. Two nodes' dirents hash to the SAME data block. Node A adds its entry to block X, flushes durable via `mxfs_dlm_dir_durable_signal` (xfs_bwrite + blkdev_flush, publish-before-notify, EXTENTS/BTREE only, gen>0). A peer holds block X cached **DIRTY** with its own adds (missing A's entry); on the peer's EX reacquire the read-path invalidation in `xfs_da_read_buf` (gated `b_mxfs_dir_gen < i_dlm_dir_gen`) **SKIPS the dirty block** — can't clear `XBF_DONE` on dirty/in-AIL without losing the peer's own committed work (sess61-DECISIVE "dirty bufgen=0 kept by dirty guard"). Peer RMWs the stale-dirty base and flushes → **clobbers A's entry**. The dir INODE EX serializes the RMWs correctly; the gap is dir-DATA-BLOCK coherency across the EX handoff [[sess10run-4tcp-clean-repro-dirty-block-clobber-mechanism]] [[sess10run-NEXT-real-fix-direction-concurrent-rmw-stale-base]].

### The decisive discriminator: clobber is `stale_base=0`
Grepped ALL 4 nodes' `dirwr=2` streams: **`stale_base=1` occurs ZERO times.** Every dir-EX RMW reports `stale_base=0` (`i_dlm_dir_gen <= i_dlm_dir_loaded_gen` — node believes its base is current), yet a durable entry is lost. The block's in-core gen was stamped FRESH while its content was STALE. **This rules out an entire class of fixes**: no write-side gate keyed on `dir_gen`/`loaded_gen`/`epoch-vs-valid_epoch` can catch it — they all read "fresh". The bug is UPSTREAM: a re-read STAMPED a stale image as fresh. The clean-stale backstop `dir_postread_reread` (default ON, xfs_da_btree.c:3651) only FUA-re-reads when `b_mxfs_dir_gen < i_dlm_dir_gen`, so since gen says fresh **it never fires at the clobber** [[sess10run-DISCRIMINATOR-clobber-stale_base0-invisible-to-gen]] [[sess10run-REFINED-handoff-read-stamps-fresh-over-stale-durability-race]].

### GPT-5.5 consult (RULE-5) — architectural verdict
Leading root = **release→grant ordering race (Rank 1)** or **release-drain coverage hole (Rank 2)**. The clobbering node B RMWs block X from a STALE base because either (Rank 1) the DLM master granted the next EX before the prior owner A's modified block was actually visible on the shared target, or (Rank 2) A's release drain skipped the block; a further variant is that X is B's OWN dirty/in-AIL committed-but-not-checkpointed block that survived B's prior release, and the slow-path drain_evict skips it to avoid resurrecting B's work. Guidance:
- In-core gen counters are UNSOUND here — freshness must mean "bytes read from the canonical device by an IO issued *after* this EX grant, or modified locally under this grant" → track `read_under_grant_gen`/`modified_under_grant_gen` **per buffer**, not `gen>=inode_gen`.
- RELEASE must be a true writeback fence: don't grant next EX until releaser has checkpointed its modified dir blocks home, using a **per-grant TOUCHED-SET of daddrs** (NOT an incore-buffer scan; the "uncached⇒assume durable, skip" at `mxfs_dir_flush_data_blocks`:~1290 is unsafe).
- ACQUIRE/RMW: on first RMW under a remote-acquired EX, force coherent device read ignoring gen; NEVER re-read a block modified under the CURRENT grant (avoids resurrecting own deletes). For a dirty/in-AIL block from a prior tenure: checkpoint it (disk gets our work) THEN adopt the disk superset.
- 2-node pass / 4-node ~80% fail ⇒ multi-party handoff race: with ≥1 queued waiter the master grants the next EX in a window where the prior owner's drain/AIL-removal isn't complete; 4 nodes almost always have a waiter ready [[sess10run-GPT-consult-durable-clobber-stale-inAIL-block-survives-release]] [[sess10run-REFINED-handoff-read-stamps-fresh-over-stale-durability-race]].

### FIX3 — per-buffer grant-gen validation (build 9527F28F, UNTESTED)
Implements the GPT "freshness = read under current grant" idea using the reliable acked-TCP grant gen. Also found: the pre-read dir-gen invalidation in `xfs_da_read_buf` is gated `!owned_ex` (SKIPPED on the modify/clobber path). Changes (3 files):
1. `xfs/xfs_buf.h`: added `uint32_t b_mxfs_grant_gen;` (grant gen at last coherent read of a dir block).
2. `xfs/libxfs/xfs_da_btree.c` `xfs_da_read_buf` postread_reread gate (~3673): ALSO re-read when `dp->i_dlm_mode == 5 (MXFS_LOCK_EX) && bp->b_mxfs_grant_gen != dp->i_dlm_cached_grant_gen` (block last read under an older grant → we lost+reacquired EX = peer modified = stale). Existing `clean` guard (destaged/!dirty/!in_ail/!pinned/!delwri/!undestaged) still wraps the actual re-read → no resurrection. Stamp `b_mxfs_grant_gen = i_dlm_cached_grant_gen` on genuine fresh disk read (gated `dir_stamp_fresh`, true only on `inc_rc==-ENOENT` real miss) and on postread re-read success. Net: each dir DATA block coherently re-read ONCE per EX grant tenure (when grant gen changes = handoff), independent of the unsound `i_dlm_dir_gen`; within a tenure no re-read (perf OK). ### CRITICAL test-harness fact (affects ALL validation)
After a dir_reuse FAIL at 4-node a node is left **WEDGED**: mxfs won't rmmod (D-state `mxfs-ino-bast`/flush kworker holding the LUN), so the NEXT run's `mkfs_mxfs -f /dev/sda` returns 1 (FS_PREP_FAIL). Consequence: running `./run.sh 4 tcp dir_reuse_coherency` N times in a row gives only ONE valid result (the first, post-reset); runs 2..N PREP-FAIL on the wedge → **all earlier "Nx flake-rate" batches were partly invalid.** MUST `virsh -c qemu:///system destroy+start test1..test4` (wait for boot) BEFORE EACH run. The wedge itself is a real teardown bug (a release/drain kworker never completes after the heavy concurrent storm) and may share a root with the durable loss [[sess10run-REFUTED-fua_disable0-and-test-harness-wedge]].
