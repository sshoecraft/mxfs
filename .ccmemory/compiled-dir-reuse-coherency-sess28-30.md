## dir_reuse_coherency 2/tcp — sess28-30 (ccloop 8ddb16a2)

Single ship criterion under investigation: `./run.sh 2 tcp dir_reuse_coherency` (2-node TCP cluster, test1=.186 / test2=.182). The test each round `rm-rf`s + `mkdir`s a shared dir, then both nodes concurrently create ~100 dirents each (a `dd` data-file wave `nodeN_fN`, then an `md5sum` wave `nodeN_fN.md5`). By sess30 16/17 suite tests pass; dir_reuse is the last failure. Three distinct faces were peeled off in order: **(A) inode-gen revert** (fixed sess28), **(B) dir DATA-block stale-base clobber**, **(C) leaf-hash lookup miss**. All three share one proven root: **DLM EX serializes the logical create, but xfsaild async writeback does not respect DLM tenure**, so a node RMWs or flushes a stale cached dir buffer over the peer's newer durable image.

### DECISIVE infra correction (sess30) — supersedes stale SCST assumptions
The 2-node TCP cluster's iSCSI target is **LIO fileio backstore `/home/steve/disk.img`, write-thru activated** (`/dev/sda` vendor=`LIO-ORG`; targetcli on clyde; NO SCST anywhere). Write-through = no target write-cache ⇒ **plain-bio cold-reads ARE coherent** (a written block is immediately visible to all initiators). Therefore `mxfs_fua_disable=1` (default) is SAFE here, and **evict+cold-read is a valid refresh mechanism**. The `project_test_cluster_scst` memory is STALE/wrong for THIS cluster (it describes the separate v5/.1 SCST cluster). The SCST "stale-reread" failure mode (the sess96/99 reverts) does NOT apply. FUA is dead on this LIO target. See [[sess30-LIO-coherent-and-acq-pin-drain-fix]].

### FACE A — inode-gen revert on create-reuse (FIXED sess28, build C887AFA3, KEEP)
The 27-session primary blocker `P26-IGET-FAIL`. Root PROVEN (RULE 4): node2 creates `node2_f10`=inode 2099081 with `incore_gen=919987021`, but disk shows it freed at `disk_gen=919987022` (one higher). The `P25-RESURRECT-SKIP` guard in `xfs_iflush` (xfs/xfs_inode.c ~4619) reads `disk_gen > incore_gen` as "peer freed this ahead of us" and SKIPS node2's flush of its OWN just-created file → alloc never reaches the platter → reader's dirent→iget returns a FREE inode → lookup_fail.

Why incore_gen was stale (disk−1): XFS randomizes gen only on the **cache-MISS** create path (xfs/xfs_icache.c ~1171, `xfs_has_v3inodes && XFS_IGET_CREATE`). The **cache-HIT/recycle** path (`xfs_reinit_inode` line 356) PRESERVES the in-core gen. Under MXFS a freed inode LINGERS in cache (held EX per Invariant 2 — peer inode ALLOCATION via AGI/inobt does NOT BAST the per-inode lock, so it is never reclaimed), so re-allocating the same inum cache-HITs the stale struct. The peer's `rm-rf` freed the prior incarnation on disk, bumping di_gen by 1 (xfs_inode_util.c ~866); our idle cache never saw it → in-core gen stuck 1 behind → RESURRECT-SKIP every round. Single-node never hits this (freed inode reclaimed → always cache-miss → fresh gen).

FIX: in `xfs_icreate()` (xfs/xfs_inode.c), right after `xfs_inode_init(tp, args, ip)`, for `xfs_has_v3inodes(mp)` set `VFS_I(ip)->i_generation = get_random_u32()` + `xfs_trans_log_inode(tp, ip, XFS_ILOG_CORE)`. The cache-HIT analogue of the cache-MISS randomize: every newly-allocated inode gets a fresh gen regardless of cache state. RESULT: RESURRECT-SKIP → 0, IGET-FAIL gone, lookup_fail=0. Also landed (KEEP, defensive, did NOT fix alone): `mxfs_submit_partial_inode_write` (pal/linux/xfs_buf.c) writes only owned|logged|bli_dirty slots, omits free/NL-not-logged co-resident slots; `iwr` module param gates decision probes. See [[sess28-ROOTFIX-inode-revert-fresh-gen-on-create-reuse]].

### FACE B — dir DATA-block stale-base content clobber (sess28 characterization)
After the gen fix, dir_reuse fails at ~round 11-15 (drifts, timing-dependent) with `readdir=184-188/200 lookup_fail=0` — ~12-16 dirents DURABLY MISSING from the dir's data blocks; every LISTED entry is lookup-able, both ranks agree (durable cross-node loss). New `RDMISS` logging (tests/suite/dir_reuse_coherency.sh, build 0270D870) pinned it: `missing=[node1_f1..node1_f12]` — EXACTLY node1's first-wave DATA files, NO `.md5`. Those 12 contiguous first-wave entries land in the dir's FIRST data block (block 0); they are durably lost while their later-created `.md5` siblings survive. Some rounds (e.g. 17) lose ~196 (worse incarnation/timing variant). This is the "writer's first-dir-block entries clobbered" pattern named at xfs/libxfs/xfs_da_btree.c:3055 — a node RMWs block 0 on a STALE cached base.

RULED OUT (decisive): inode-revert (P26-IGET-FAIL=0, gen fix holds); di_size WRITE-revert (`P133-DIRINO-REVERT`=0 on both nodes under `iwr` — no node writes a smaller di_size/nextents over a larger coherent disk image). So the di_size oscillation seen earlier is node-to-node DIVERGENCE or pure DATA-block content loss with di_size intact — a `xfs_dir3_data_buf_ops` block-0 lost-update, not inode-cluster (the sess28 inode-write skip doesn't cover dir blocks).

Strong suspect (sess28): the dir-block READ-time invalidation (xfs/libxfs/xfs_da_btree.c ~3047-3081, `b_mxfs_dir_gen < dp->i_dlm_dir_gen` → invalidate+re-read) is GATED OFF when `i_dlm_dir_gen == 0` (single-node optimization; xfs/xfs_mxfs_dlm.c:9972 also early-returns on gen==0). The per-round `rm-rf`+`mkdir` makes the dir a fresh incarnation with `i_dlm_dir_gen` RESET to 0 (mxfs_dlm_inode_init, xfs_mxfs_dlm.c:9681). There is a bump-0→1 on multi-node dir-block read (xfs_da_btree.c:3064-3081), but a WINDOW exists where gen==0 and a stale/ABA prior-incarnation block-0 buffer (same reused daddr, same i_dlm_dir_gen=1) is RMW'd before the bump — the gen-compare is blind to ABA reuse because each fresh dir starts 0→1 matching a prior incarnation's stamp. i_dlm_dir_gen++ sites to verify fire on dir EX acquire: xfs_mxfs_dlm.c:8604, 11408. See [[sess28-dir-data-block-RDMISS-first-block-clobber]], [[sess28-remaining-dir-disize-revert-after-genfix]].

### PROVEN ROOT (sess29) — xfsaild flushes STALE dir DATA/leaf blocks while EX-held
Built 75FD71CC = baseline 0270D870 + **P29-DATAWRITE** detector (pal/linux/xfs_buf.c, in the P56 block; helper `mxfs_dir3_data_fingerprint` counts live dirents + inumber sum/xor of buffer-being-written vs the coherent on-disk plain-read). Ran `MXFS_EXTRA_MODARGS="dirwr=1"`.

Decisive evidence (both nodes):
- `P29-DATAWRITE tag=CLOBBER` + `P-LEAFWRITE tag=CLOBBER` almost all `comm=xfsaild/sda` (async AIL flush) writing a dir DATA/leaf block that drops dirents/hashvals the COHERENT disk has (test1 daddr=2600 block-0 reverting 5→4→3→2→1; test2 leaf daddr=2096952 buf 126/disk 123).
- `P16-DIRBLK-SUBMIT` for the clobbered daddrs: `mode=5` (EX), `nl=0`, comm=xfsaild → the dir is EX-held by THIS node at flush time, so the existing NL-release chokepoint skip (`mxfs_buf_xfsaild_skip_dir_write`, xfs_mxfs_dlm.c:14895) does NOT apply. `dirskip=0` — that write-side skip is disabled anyway.
- `DIR-STALE-SKIP` read keep-guard: a PINNED+undestaged stale dir block (`pin=1 has_bli=1 buf_gen=0 inode_gen=8`) is KEPT (can't re-read a pinned buf without corrupting) — this is how the stale base survives re-acquire.
- `P106-MR-EVICT` 179/104, `P106-MR-SKIP: 0`: modify-refresh fires but only evicts CLEAN blocks; pinned/undestaged stay stale.
- bufincarn == cur i_generation on clobbers → NOT incarnation-ABA; it is WITHIN-incarnation async-flush staleness.

ROOT (== sess65 theme): DLM EX serializes the logical create, but xfsaild async writeback does NOT respect tenure. On a tenure boundary (node releases EX, peer modifies dir, node re-acquires), the cached dir DATA/leaf buffer is stale; the read-side keep-guard CANNOT refresh it while PINNED/undestaged → node RMWs a stale base and/or xfsaild later flushes the stale buffer over the peer's newer durable image → durable loss. Two faces: DATA-block dirent loss (node1_f1..f13) + LEAF-hash hole (node2_fNN.md5 readdir-yes/lookup-ENOENT). DETECTOR CAVEAT: "buf_cnt < disk_cnt" also fires on legit `rm-rf` removals (buffer shrinks, disk lags) — false positives; the real clobber signal is "disk has an inumber the buffer LACKS", not raw count. See [[sess29-PROVEN-root-xfsaild-stale-dirblock-flush-at-EX]].

### FACE C — leaf lookup miss (sess29)
The dirent is DURABLY present in the data block (readdir lists it) but `xfs_dir2_leaf_lookup` ENOENTs and the `mxfs_dir2_datascan_lookup` fallback MISSES it. Observed `P26-DSCAN-MISS ndb=1 scanned=128` = UNDER-SCAN (extent-map walk gave ndb=1 while dir has ~200/2 blocks) and/or a `cmpresult` skip. Fix written: at top of `mxfs_dir2_datascan_lookup` (xfs/xfs_dir2_leaf.c) set `args->cmpresult = XFS_CMP_DIFFERENT` — a failed leaf-lookup leaves cmpresult=EXACT, making the scan's `cmp != args->cmpresult` gate SKIP an exact match (sess27-FINAL prime suspect). Leaf face may additionally need leaf-rebuild (`MXFS_IF_DIR_LEAF_STALE` / `dir_leaf_rebuild=1`, default off) once DATA blocks are coherent.

### Fix attempts + decision tree (sess29)
`dir_merge=1` (`mxfs_dir_merge_peer_into_tp`, additive union-merge in xfs_create — re-adds peer's durable dirents before each create RMW so xfsaild flushes a union) FIXES the DATA face: readdir 187→**200**. This PROVES the data face is a write-side stale-base RMW. **BUT `dir_merge=1` causes an `rc=-110` DLM-timeout shutdown** at `mxfs_dlm_ilock_begin:8534` — the per-create full-dir plain-bio read slows create processing → delays BAST handling → peer's PR readdir times out 120s. Confirmed for BOTH per-create AND once-per-tenure variants (sess18 + sess29). KEY LESSON: **any non-trivial work while holding EX risks the peer-acquire timeout; the fix must NOT extend the EX hold.** Merge is therefore DEAD as a shipping path (dir_merge default OFF, inert).

Build progression: 0270D870 (sess28 baseline) → 75FD71CC (+P29 detector) → 5760A5E2 (+merge once-per-tenure) → **AB435ACC** (+datascan cmpresult reset; KEEP the cmpresult reset — real lookup-skip bug fix). AB435ACC also = baseline + P29 detector + merge-once-per-tenure (inert). See [[sess29-fix-progression-merge-and-leaf-decision-tree]].

### GPT-5.5 design (sess29, RULE 5) — epoch-driven tenure-local invalidation + purge-at-NL
Consulted because the merge class is dead (EX-hold-extending → peer timeout). Core invariant: **a dir DATA/leaf buffer must NEVER survive from one DLM tenure into a later tenure if a peer could have modified the dir between.** The expensive part (waiting for a pin to drain) happens at **NL (after demote, before next acquire)**, NOT during EX hold → no peer timeout. NEVER clear XBF_DONE on a pinned buffer (corruption, sess64). Six pieces, most machinery already in-tree:
1. **Dir content EPOCH** (cluster-shared; DLM LVB or reuse `i_dlm_dir_gen`+incarn): bump on EX release AFTER durable drain; peer sees newer epoch → cold-read returns committed image (LIO plain-bio coherent).
2. **Release-side triage** (extend `mxfs_dir_stale_data_blocks`, xfs_mxfs_dlm.c:3005): clean+unpinned → `xfs_buf_stale()` NOW; dirty/in_ail/delwri → keep draining (must finish before demote); **pin-ONLY clean** → do NOT stale (pin owns lifetime) → mark `MXBF_TENURE_POISONED` + queue post-release purge + set purge_pending, then DEMOTE (peer not blocked). Replaces today's P99-STALE-SKIP.
3. **Post-release purge worker @ NL**: `wait_event(!ispinned)` → revalidate + `xfs_buf_stale()` + clear poison. Replaces the in-release bounded log_force loop AND the acquire-side bounded 50-iter pin wait @3302 that GIVES UP.
4. **Acquire gate** (`mxfs_dlm_ilock_begin`, before DLM request): `wait_event(!purge_pending)`; after grant, if epoch changed, stale old clean buffers; unsafe pinned/dirty old-epoch buf → drop to NL, purge, retry `-EAGAIN`. NO full-dir read in grant path (that was the merge timeout).
5. **Buffer-lookup enforcement** (`xfs_da_read_buf` + modify path): a dir buf is usable for RMW only if tag `(ino, i_generation, dir_epoch)` matches AND not poisoned; ABA note — "daddr equality is NOT identity; identity = (daddr,ino,gen,epoch)"; existing `b_mxfs_dir_incarn` = the gen part.
6. **xfsaild guard** (`mxfs_buf_xfsaild_skip_dir_write`, xfs_mxfs_dlm.c:14895): a POISONED buf must NEVER be written (return XFS_ITEM_LOCKED/defer). Keep P29-DATAWRITE as a debug assert, not the primary fix.

GPT REJECTED: (A) naive stale pin-only at grant (pin owns lifetime — unsafe); (B) forbid all xfsaild writes of held dir bufs (pins log tail, perf); (C) write-side semantic guard (can't soundly distinguish stale-revert from legit-remove) — use C only as a detector. See [[sess29-GPT-design-tenure-local-poison-purge-at-NL]].

### sess30 baseline + shipped fix (build 72676B77, UNVALIDATED at write time)
Baseline AB435ACC signature: `./run.sh 2 tcp dir_reuse_coherency` → FAIL 0/2, round 15/24 `readdir=186/200 lookup_fail=0`, missing = `node1_f1..node1_f14` (contiguous create-order range = ONE dir DATA block), durably gone from BOTH nodes. NO shutdown, NO rc=-110, NO P35F/P99-STALE-SKIP (release-flush→stale loop not leaking). test1 had 334 `P21S-EVICTSKIP-LEAF` but lookup_fail=0 (read-time leaf heal covers it) ⇒ pure DATA-face stale-base clobber, NOT the leaf face.

Refined mechanism: a re-acquiring node keeps a PIN-ONLY stale dir DATA block (pinned, !dirty, !in_ail, DONE; content already PUBLISHED to disk via publish-before-notify, but CIL-pin-tailed). `mxfs_dir_drain_evict_data_blocks` (acquire-side; slow-path L8687 + fast-path L8249 when dir_gen>loaded_gen) does ONE pre-loop `xfs_log_force` then a 50-iter (~100ms) PASSIVE msleep; if still pinned it GIVES UP (`P-ACQ-DRAIN-SKIP`) → block stays stale → RMW onto stale base → durable dirent drop. The single force misses a block re-pinned by publish-before-notify's own re-log or pinned after the pre-scan; passive msleep can't unpin without a force.

FIX (build 72676B77): in the per-block pin-wait loop (`mxfs_dir_drain_evict_data_blocks` ~L3302) extend bound 50→`MXFS_DIR_ACQ_PIN_WAIT`=2000 (~4s wedge backstop, << 120s DLM timeout) AND re-issue `xfs_log_force(SYNC)` at w==50 (~100ms) then every 250 iters (~500ms). Gentle cadence avoids the sess97 log-force-storm (force/32ms → 5.5× unlink slowdown, reverted). SAFE: runs post-grant, NO ILOCK, NO peer blocked (peer just released to us) → only delays OUR RMW → no merge-class -110 timeout. A pin-only block is our own already-published work; forcing completes its CIL checkpoint → unpin → evict → cold-read peer's durable image. Secondary lead (NOT pursued): `i_mxfs_self_created` gate (xfs_inode.c:1221 set on create, cleared on peer BAST @dlm.c:5482) skips fast-path stale refresh for a self-created dir but clears on first peer contention → likely not primary. See [[sess30-LIO-coherent-and-acq-pin-drain-fix]].

### Recurring failure modes / rules to carry forward
- **EX-hold-extending work → peer BAST-handling delay → 120s DLM PR-acquire timeout → rc=-110 shutdown** (`mxfs_dlm_ilock_begin:8534`). Killed the merge class (sess18+29). Any coherency fix must do its expensive waiting at NL, never during EX hold.
- **Log-force storms are a perf trap**: force/32ms → 5.5× unlink slowdown (sess97 reverted). Gentle cadence only (per RULE 0).
- **i_dlm_dir_gen resets to 0 every incarnation** (per-round rm-rf+mkdir) → single-node gen==0 fast-paths bypass read-invalidation; ABA prior-incarnation buffers at reused daddrs share stamps. Identity must be `(daddr, ino, i_generation, epoch)`, not daddr alone.
- **Detector false-positive**: "buf dirent count < disk count" fires on legit rm-rf removals; trust "disk has an inumber the buffer lacks" instead.
- **Reboot the cluster before EVERY run** (`tests/reboot_cluster.sh 2`) — a shutdown leaves `/dev/sda` busy → "PREP FAIL (mkfs): device is busy" / test2 rmmod-wedge after kills. dnsmasq reservations keep test1=.186 / test2=.182.
