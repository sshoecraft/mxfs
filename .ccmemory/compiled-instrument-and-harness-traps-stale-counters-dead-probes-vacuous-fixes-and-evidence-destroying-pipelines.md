# Instrument and harness traps: a measurement that cannot see the thing reads as a finding

Assorted group: the clusterer could not fit these to one topic. What they share is that an instrument, probe, pipeline or harness step produced a confident null, a false FAIL, or a refusal that looks like a different cause than the real one. Organised by failure family.

## 1. A counter that measures something adjacent to the question

- `chk_mxfs -v <dev>` "Superblock icount" reads the platter superblock, which MXFS writes only at unmount (`sb_icount`, `sb_ifree`, `sb_fdblocks` are lazy; recomputed from AGF/AGI at mount; `sync` does not push them). Three live samples all said 64 while the run carved 187 chunks; the cold read after both unmounts said 12032. A live-mount superblock counter is historical: never gate a verdict on it, never subtract two of them. Gate on a number the workload produced (files created) or on the cold read. Same family: `df --output=itotal` reports `maxicount`, and `P133-ICLUSTER-SYNCINIT` / `P45-INIT` are print budgets, not counts. Ask what writes a counter and when. [[trap-chk-mxfs-superblock-icount-lags-a-live-mount-by-one-unmount]]
- A `pr_warn_ratelimited` count that lands exactly on 10 is `DEFAULT_RATELIMIT_BURST` (10 per 5 s), not a count. A 24-vs-10 gap between a plain and a ratelimited probe nearly became a false "persistent poison flag carried across laps" escalation. Never take a ratio between a ratelimited and an unratelimited probe. Use `static atomic_t n; if (atomic_inc_return(&n) <= CAP)` so printing is capped while the counter keeps the true total, and print the total. Comparing separate ratelimited call sites against each other is sound (independent state); the absolute count from one site is not. The same session also had a probe comparing fields that never move for the defect, and a harness grep for `[PASS]` against a bare leading word that recorded a genuine reproduction as `NO_TERMINAL_RECORD`. [[trap-a-ratelimited-pr-warn-count-is-not-a-measurement-burst-is-10-per-5s]]

## 2. A probe that exists but cannot fire on your path

- A probe guarded by the complement of its enclosing branch is dead code that reads as coverage: the chunk-delete branch in `xfs_difree_inobt` was entered under `!D || S` (not multi-node) and the `P103-CHUNKFREE` probe inside required `D && !S`. Every chunk deletion was silent. Check: conjoin the probe guard with every enclosing guard; if unsatisfiable, silence means nothing. A probe that has never appeared in any captured evidence though the path plausibly runs is a candidate; grep the evidence tree for the tag before believing a zero. [[trap-a-probe-whose-condition-is-the-complement-of-its-branch-never-fires]]
- "The probe exists" is not "the probe covers your path": `P132-CREATE` started its clock under `is_dir`, so file creates (every workload that sets the create ceiling) had no decomposition for ~350 sessions. Before believing a coverage claim, read: (1) the gate on the clock, not just on the print; (2) the threshold (`P138-ACQ` fires only above 5 ms, so a uniform 3 ms path is silent, identical to "fast" and "not measured"); (3) the print cap (`P291-EXWIN` 20000, `P138-ACQ` 4000, so a long run's tail can vanish). An absent measurement and a zero measurement look the same: `tools/p132_attribute.py` refuses to print when no input carried the probe, and `tests/suite/lib.sh` separates `notrun=` from `failed=`. [[trap-a-probe-exists-is-not-a-probe-that-covers-your-path-check-its-gate]]
- Fixing a vacuous probe can invert the vacuity instead of removing it. `P165-AFFINE-STALE` fired on 229,444/229,444 lines (`d_time=0`); narrowing to `d_time && d_time != epoch` removed log volume but is blind to the named population: `d_time` has one writer (the `ret == 1` tail of coordinated validation in `mxfs_drevalidate`), the affine fast path returns before it, and the conjuncts selecting that exit are constant for a positive dentry's life, so an affine regular-file dentry holds `d_time == 0` forever. A recorded "zero here is the first real evidence" would have been a confident wrong negative. A probe fix is verified only by demonstrating the new predicate CAN fire on the population at risk: which population does the branch sample, can every predicate field take a discriminating value there, is each field's writer reachable from this path. Claim blindness, not impossibility: `d_time` belongs to the dentry object and `d_splice_alias`, negative-to-positive reincarnation and `d_move` can carry nonzero values, so "unsatisfiable" was an overstatement a reviewer could refute. When the field cannot see the risk, measure the thing itself: `mxfs.affine_audit_pct` (0.66.0, default 0) diverts a sampled fraction into the skipped coordinated validation and compares. [[trap-fixing-a-vacuous-probe-can-invert-the-vacuity-not-remove-it]]

## 3. Harness and pipeline steps that destroy or fake evidence

- `grep -v authorized` as an ssh-banner filter also deletes kernel lines containing "unauthorized image(s)" (`P227-FR-ATOMIC-SKIP`), the one line naming the mechanism behind `refused=2`; an hour of code reading followed. Anchor the filter: `grep -av '^Unauthorized\|^Warning:\|^If you'`. Never filter pulled kernel logs by a bare substring that can occur in a kernel message (authorized, warning, error, failed). When a counter says N and the notices are absent, suspect the pipeline first: `grep -c` on the node with no filter. 22 sites across six scripts were switched. [[trap-grep-v-authorized-deletes-unauthorized-image-kernel-lines]]
- Under `set -u`, an env var read only inside conditional arms passes for months and then dies inside the one arm that matters. `tests/tcp_death_replay.sh` documented an `MXFS_DEV` default it never had; it died reading PR state, and two reservation assertions FAILed against the empty string, reading as a critical fencing regression on a run with 327/327 files verified. `ck "<claim>" "$(measurement)" "expected"` cannot distinguish "broken" from "could not look". Assert on emptiness first and report it as a harness fault naming itself. Fixed in 0.75.89 with a default plus a refusal to compare an empty reading. [[trap-set-u-unbound-var-inside-a-conditional-arm-turns-into-two-false-fencing-FAILs]]
- Never `grep -r` over `tests/`: `tests/evidence/` holds hundreds of run dirs with 13 MB journals each; the grep exceeded the 120 s Bash timeout and, run during a live rig lap, competes for the same disk that hosts the LUN, guest images and journal, which can invalidate the lap. Scope to source: `grep -rn PATTERN tests/suite tests/lib tests/*.sh` or `--include='*.sh'`. Same class as the ban on root-wide searches. [[trap-never-grep-r-over-tests-evidence-journals-are-13mb-each-and-starve-a-running-rig-lap]]
- Rebooted or destroyed nodes lose their kernel log: node journald is volatile (`/run/log/journal`; `/var/log/journal` files date from Jul 1), so `journalctl -k -b -1` after a `virsh destroy` returns 0 lines. Harnesses that power-cycle a node (lone_crash_replay, node_death_replay, tck) must capture `dmesg`/journalctl on the victim into `tests/evidence` BEFORE the destroy, or derive victim facts from the survivor's journal. The dmesg ring also wraps within minutes under a board. [[trap-node-journald-volatile-rebooted-node-kernel-log-gone]]

## 4. Harness setup traps that masquerade as product refusals

- Reusing a node id in a harness is a retired identity: `node_id_override` with an id that already departed in the peer's mount lifetime gets `P164-DEAD-NOTE` / `P164-DEAD-REJECT announce ... retired identity ignored`, active_count stays 1, the mount parks page requests and the harness's 40 s bound kills it. Not a filesystem defect (real ids are random 32-bit per incarnation). Pick a fresh id per rejoin or cycle the peer's mount between reuses (`tests/rejoin_residue.sh` arm 4 now uses ID_LOW+1 / ID_HIGH-1). [[trap-reused-node-id-override-is-a-retired-identity-p164-dead-reject-peer-never-admitted]]
- Bumping `MXFS_PROTO_GEN` (or any on-disk header the tools compile in) needs `make tools`; `make modules` does not rebuild `tools/`, so `mkfs_mxfs` stamps the old `cluster_proto_gen` and the first prep mount fails EPROTO ("Protocol not supported", dmesg `C7 gate: ... refusing mount`). EPROTO on the first mount after mkfs is this, not a transport-census refusal. [[trap-proto-gen-bump-needs-make-tools-or-every-mount-is-refused-eproto]]

## 5. Tooling side effects follow the tool, not the bytes

- The awareness `track` hook is PostToolUse on `Edit|Write|MultiEdit` only; `sync` (Stop) computes drift from that session ledger, not mtimes. Appending to `.claude/awareness/subsystems/*.md` with `cat >>` or a heredoc writes correct bytes but leaves the drift unresolved forever. Use Edit/Write on awareness docs. Generally which tool performed a file operation is semantic: `sed -i`, `cat >>` and heredocs are invisible to PostToolUse hooks, as are the ccmemory injection (on `Read`) and ledger guard. [[trap-awareness-track-hook-only-sees-edit-write-not-bash-heredoc]]

## Standing checks

Before trusting a null: what writes this number and when; can the probe's full guard chain be satisfied on my path; can the measurement come back empty and be mistaken for a result; did my own filter or search remove or starve the evidence.
