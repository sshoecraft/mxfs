Topic: running MXFS tests on the PVE pairs. The physical pair is pve1 192.168.1.80 / pve2 192.168.1.81 (old HP Z400-class workstations, no BMC). The disposable nested pair is pve9-1/pve9-2 (192.168.120.192 / .137). The notes below cover what not to do to the hardware, how to deploy and launch, and how to read results without being fooled.

## Hardware: never reset the physical pair

- The user first said "pve1 is old hw like pve2 dont break them" after a failover suite sysrq-reset pve1 three times in ten minutes. pve1 then stayed down about 37 min and came back about two minutes after Wake-on-LAN packets were sent (likely the wake, not proven). [[feedback-the-physical-pve-pair-is-old-hardware-so-minimize-hard-resets-and-restore-without-one]]
- This escalated to a hard prohibition. Resets "fried" the old pve2 and it no longer boots. Never reset, reboot, crash, sysrq or power-cycle pve1/pve2. That covers every crash/reset/power step of `tests/pve_pair_failover.sh` and `tools/pve_power.sh off|on`. Crash, reset and outage testing runs on the nested pair only. A defect record whose next step says "verify on the physical pair" with a crash step is verified on the nested pair, and the record says so. [[feedback-never-reset-reboot-or-power-cycle-the-physical-pve-pair]]
- Non-destructive work on the physical pair is still fine: installs that stop and start units, loads, tree walks, profiles. Announce anything that interrupts service first.
- If a host is left in a bad state, restore without a reset: `tools/pve_power.sh restore <addr>` lifts the isolation and starts mxfs-drbd-guard then mxfs-drbd@mxfs (pve2 was back Connected Primary/Primary UpToDate in 95 s). If a host does not answer, send `tools/wake_on_lan.py <mac> 192.168.1.255` before declaring it dead. A reset is the user's call. [[feedback-the-physical-pve-pair-is-old-hardware-so-minimize-hard-resets-and-restore-without-one]]
- The same applies to host power. clyde and both pve hosts share unprotected power (no UPS). When pve1 and pve2 both show a previous boot with no shutdown sequence within seconds of each other, run `journalctl --list-boots | tail -3` and `uptime` on clyde before blaming MXFS. A clyde restart in the same minute means power. A clyde restart also kills the netconsole listeners (restart them with `tools/pve_netconsole.sh start`), the nested pair VMs (not autostarted) and any lap driver waiting on them. pve1 does not reliably power on after AC loss, so use Wake-on-LAN. An unplanned outage is a free power-cut test: check the pair rejoined and run `chk_mxfs` while unmounted. [[trap-clyde-and-both-pve-hosts-share-unprotected-power-so-a-joint-crash-is-checked-against-clydes-boot-list-first]]

## Deploying and launching

- Test builds go to pve1/pve2 straight from the working tree. The user called commit, push and pull on the nodes "unnecessary churn". Rebuild the module on each host (`scripts/pve_dkms_rebuild.sh` reads clyde's NFS /src), then swap it in with `scripts/pve_pair_update.sh SKIP_INSTALL=1` (`CHECK=1` adds a cold `chk_mxfs`). Confirm the loaded srcversion equals the tree's (`modinfo -n mxfs`) before measuring. Run git only when the user says so. The clone/pull/`make install` path is tested when the user asks for a release. [[feedback-test-builds-go-to-the-physical-pve-pair-directly-never-by-commit-push-and-pull]]
- The pve_* harnesses disagree on their default pair. `tests/pve_cluster_write_authority.sh` defaults PVE_PAIR to nested pair A (192.168.120.137 / .192). `tests/pve_churn_fairness.sh`, `tests/pve_pair_profile.sh` and `scripts/pve_pair_update.sh` default to the physical pair. A "physical-pair verification" churn launched without PVE_PAIR ran on the nested pair, overlapped a fairness profile there, and the physical counters read 0. Always pass `PVE_PAIR="<addr> <addr>"`, check that the evidence's host lines name the intended pair, and never run two workloads on one pair at once. [[trap-pve-test-scripts-default-to-different-pairs-so-always-pass-pve-pair]]
- In bash, `a > f; echo rc >> f & b ...; wait` backgrounds only the `echo`, so job A ran in the foreground and job B started after it (about 8 min each, serially, and B's log did not exist while A ran). Group each job: `( job1 > l1 2>&1; echo "RC=$?" >> l1 ) & ( job2 > l2 2>&1; echo "RC=$?" >> l2 ) & wait`. Check that each log exists right after a parallel launch. [[trap-ampersand-after-a-semicolon-list-backgrounds-only-the-last-command-so-two-jobs-run-serially]]

## Reading results correctly

- Clock skew after a reset. A reset Z400 starts from the RTC and chrony only slews. pve1 ran 237 s fast, so wall-clock journal times misplaced a boot (network-online at 224 s vs 15.5 s monotonic), and a defect record was drafted on the wrong numbers. `tests/pve_pair_failover.sh` uses `journalctl --since @$t0` with t0 from clyde's clock, so the window reached into the previous step and answering-restart reported "recovered 2 s after its reset". Use `journalctl -b -o short-monotonic` (and `-k`) for boot timing. Compare `date +%s` on the host with clyde's before trusting a log-window verdict. Take t0 from the host being read. Fix the source with `chronyc makestep` then `hwclock --systohc`. [[trap-a-reset-pve-hosts-journal-runs-minutes-off-until-chrony-slews-so-time-a-boot-in-monotonic-seconds]]
- Rig kernel-log volume is not production. `tests/setup/prep_node.sh` loads mxfs with `dyndbg=+p` (1591 of 1593 sites on), so a rig node logged about 165k lines in 4 min of I/O (iomap addr, buf_io, P71/P239-P241). Never cite that as production log volume or compare rig latency/IOPS with a production node without saying so. Count flags with awk on field 3 of `/proc/dynamic_debug/control`, not `grep '=p'`. On the rig, a missing probe line is real absence. [[trap-rig-nodes-print-every-mxfs-debug-site-so-their-log-volume-and-latency-are-not-production]]
- Anything written to the kernel log with an `mxfs` prefix reads as MXFS spam to the user ("gonna piss off a lot of people"). pve1's steady 243 lines/h were `mxfs-diag-heat` from `tools/pve_crashdiag.sh on`, while the module logged 4 lines. Split by source before judging a rate: `journalctl -k --since -60min -o cat | grep mxfs | sed -E 's/[0-9]+/N/g' | sort | uniq -c`. Install kmsg-writing diagnostics only on the host under investigation and turn them off afterwards (`tools/pve_crashdiag.sh off <host>`). [[feedback-a-diagnostic-that-writes-mxfs-prefixed-lines-to-the-kernel-log-reads-as-mxfs-spam-to-the-user]]
- fio `--time_based --runtime=N` on a `--size` file lays the whole file out, writes only as far as N seconds reach, and a later `--verify_only` reads the unwritten tail as zeros ("got pattern '00'"). Before calling it corruption, compare the first bad offset with the job's `write.io_bytes`. They matched exactly on the nested pair. For a write load checked afterwards, make writers size-based (`--loops` for duration) or verify only `io_bytes`. `tests/pve_pair_write_bound.sh` does the former, with `verify_pattern=%o`. [[trap-a-time-limited-fio-writer-leaves-its-laid-out-tail-unwritten-and-verify-reads-zeros-there]]
- osimager proxmox builds that log `Using SSH communicator to connect: <no value>` never connect and die at packer's 45 min `ssh_timeout`, on any storage. The cause was `ssh_host` rendered as `{{ .Host }}` for platform proxmox, and the owner fixed it. Do not read such a build's rc as a verdict on storage. Check the step it died in, and judge storage by install time (`qm agent <id> get-host-name`, or `scripts/pve_pair_builds.sh` "installed after N s", `STOP_INSTALLED=1`). The 45 min bar is real for the owner's workflow. [[trap-osimager-proxmox-builds-never-connect-over-ssh-so-every-build-times-out-on-any-storage]]

## Kernel trap found on the PVE 6.17 kernel

- From Linux 6.17, iomap leaves the ended ioend in `wpc->wb_ctx` when `->writeback_submit` returns an error. An fsync pass resubmits it for every later folio and once more at the end, giving a double `bio_endio` and `BUG at mm/slub.c:563` in `iomap_finish_folio_write` (measured on the nested pair with `tests/pve_wb_refusal.sh`). The physical pair saw one ioend refused 11 times and an fsync hung on a folio lock. Any 6.17+ `->writeback_submit` must clear `wb_ctx` after handing off the ioend (`mxfs_ioend_hand_off` in `pal/linux/xfs_aops.c`), and every new error return in that hook goes through it. Before 6.17 the `->prepare_ioend` path was safe. [[trap-iomap-6-17-keeps-an-ended-ioend-in-wb-ctx-after-a-failed-writeback-submit]]
