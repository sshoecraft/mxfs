## 8/tcp: both remaining blockers reduce to ONE root — TCP-DLM acquire starvation on the hot shared dir

sess15 (ccloop) unified the two remaining 8-node/TCP ship blockers into a single root cause and landed one verified correctness fix. Baseline: 1/2/4 tcp PASS; 8/tcp full suite = 16/17 at TEST_TIMEOUT=900. The two 8/tcp failures — `dir_reuse_coherency` (slow) and `tcp_dlm_scaling` (60s window fail) — are the SAME TCP-DLM inode-acquire starvation on the hot shared test dir (ino=131), manifesting as `P36-RETRY` acquire churn. See [[sess15run-UNIFYING-both-8tcp-blockers-are-tcp-dlm-acquire-starvation]].

### The single root — TCP-DLM master-side queue-vs-grant race
Under 8-way contention, `mxfs_dlm_lock` → `mxfs_dlm_lock_retries` STARVES on ino=131. Per-attempt wait `MXFS_LOCK_ACQUIRE_WAIT_MS` (declared 6000 in stale dlm/dlm.c comments and include/mxfs/mxfs_dlm.h:279, but observed re-fire ≈ **1s**), 60 retries = **60s** budget. Mechanism (TCP is reliable — this is a LOGIC gap, not packet loss): a waiter queues in the instant the holder owns no grant → NO BAST captured; the holder re-acquires/upgrades and nothing re-fires the BAST → the waiter is stranded until its OWN ~1s ACQUIRE_WAIT retry re-fires the BAST. This is the sess35/sess36 queue-vs-grant race (documented mxfs_dlm.h:266-278), CONFIRMED still live at 8-way. sess35 added `collect_grantee_bast_if_waiters` (dlm/dlm.c:528) to direct-grant/upgrade/REAFFIRM paths (called @1119 local-upgrade, @1238 fresh-grant, @2913 remote) + `collect_post_promotion_basts` on release; sess36 lowered 6000→1000ms as a BANDAID (each stall ~1s not ~6s). Residual stalls accumulate across 8 nodes. `promote_waiters` (dlm/dlm.c:569/605-655) stops at first incompatible waiter to avoid starvation — under mixed PR+EX waiters this leaves a straggler un-granted until its own retry. See [[sess15run-PRECISE-ROOT-8tcp-dlm-acquire-starvation-ino131-P36-retry-60s]], [[sess15run-FIXPLAN-8tcp-dlm-queue-vs-grant-race-and-acquire-churn]].

### Two symptom faces of that one root
1. **dir_reuse_coherency = SLOWNESS only (CORRECT).** PASSES 8/8 at TEST_TIMEOUT=900, ROUNDS=24, no content failures, no shutdown, dirinos coherent across all 8 nodes. But ~630s (round1@607s → round24@1222s) vs native XFS ~12s = **~50× over → RULE 0 FAIL** at the default 300s budget. The -110 (ETIMEDOUT) acquire failures here are TOLERATED (file-op retries) and do not fail the test. Per-round time varies 12s..74s: a slow round = one node's verify-phase PR acquire on ino=131 stalled in P36-RETRY, and the coord_barrier (drc_rN_vr) makes all 8 nodes report the same ~62s. See [[sess15run-ROOT-8tcp-dir-reuse-is-SLOWNESS-hot-block-fua-restorm]], [[sess15run-8tcp-TWO-blockers-tcpdlmscaling-P58-DIRPIN-NONEX-and-dirreuse-slow]].

2. **tcp_dlm_scaling = the acquire EXHAUSTS 60 retries → rc=-110 (ETIMEDOUT).** PROVEN via dmesg `DLM inode lock failed: ino=... rc=-110` (ino=100665222 mode=PR on test4/test6). The caller then proceeds to modify+commit the DIRECTORY anyway → `P58-DIRPIN-NONEX ino=537968 dlm_mode=0(NL) state=3 ex_h=1 pr_h=0` at `xfs_inode_item_pin → xfs_cil_prepare_item → xlog_cil_commit → __xfs_trans_commit` (also `xfs_inode_item_precommit`) → durable dirent RESURRECTION → 1/8 PASS. The `ex_h=1 dlm_mode=NL` signature = ex_holders incremented but the EX grant never landed (-110), yet the op committed at NL. P58-DIRPIN-NONEX is the sess58 KEPT detector in xfs_inode_item.c (always-on). sess58 fixed this face for 2/tcp by acquiring the dir DLM grant in the `xfs_lock_two_inodes`/`xfs_lock_inodes` nowait paths (ILOCK via AIL-nowait had skipped the DLM grant); at 8 nodes ANOTHER modify+commit path (comm=bash, concurrent create/rename/remove) reaches commit with the dir at NL. Note: P108/P-TCPEX reconcile paths (xfs_mxfs_dlm.c:10735/10781) already guard ex_holders==0, so they are NOT the source — it's the acquire-failure-then-commit path.

### VERIFIED FIX this session — P58 rel-abort (build 48C6A95E, KEEP)
A SEPARATE resurrection face (P58-DIRPIN-NONEX from a released-during-drain race, not the -110 path) was root-caused and fixed. In `xfs/xfs_mxfs_dlm.c` `mxfs_dlm_bast_process`, right before `i_dlm_mode = MXFS_LOCK_NL` (~line 6375): re-check holders under `i_dlm_lock`. If `i_dlm_ex_holders>0 || i_dlm_pr_holders>0` (a fast-path acquire raced in DURING the async drain), **ABORT the release** — clear `MXFS_IF_DLM_RELFLUSH`, set `i_dlm_state=MXFS_DLM_ISTATE_BAST` (re-arm), `wake_up_all(&i_dlm_wait)`, RETURN — keep the grant, do NOT set NL, do NOT unlock. The holder's `mxfs_dlm_ilock_end` re-fires the BAST once ex_holders drops to 0 (established deferred-BAST pattern, P-NONE-HELD-DEFER). Logs `P15-REL-ABORT` (always-on, ratelimited). Safe: `bast_work_fn` sets/clears `i_dlm_demoter` and ireles around the call, so early return leaks nothing.

PROVEN (RULE 4): probe `P15-NL-WHILE-HOLDER` fired `ino=14680192 mode=EX ex=1 state=DEMOTING` on kworker `mxfs-ino-bast` — bast_process was queued when ex_holders==0 (bast_notify guards that) but a fast-path acquire re-incremented ex_holders during the drain; OLD code released to NL anyway → holder commits dir at NL → P58-DIRPIN-NONEX at xfs_inode_item_pin → durable dirent resurrection. AFTER fix (clean reboot, `./run.sh 8 tcp tcp_dlm_scaling`): P58=0, no `__xfs_trans_commit` corruption, no shutdown, no hung task on all 8 nodes (was 5 nodes trans_commit corruption). Resurrection ELIMINATED. tcp_dlm_scaling STILL fails 1/8 — but now PURELY on SLOWNESS: its PASS criterion (`tests/tcp/tcp_dlm_scaling.sh`) is `ck "tds node within window" elapsed <= WINDOW(=60s)` per node; all 8 completed 150 rounds CLEAN but elapsed 73-119s (only test8=24s ≤60s → 1/8). So after 48C6A95E, BOTH blockers are the same DLM-acquire-starvation slowness. See [[sess15run-FIX-P58-rel-abort-VERIFIED-tcpdlm-now-slowness-only]].

### The FUA re-read storm (secondary slowness amplifier)
P15-DIRFUA probe (`dir_perf_probe` module param, build 0BB72C83): single node cold 800-entry verify = 0.55s, **0 dir FUA reads** (no peers → no gen bump → dir blocks stay cached). 8 nodes: ALL 200 (capped) P15-DIRFUA reads hit the SAME block **daddr=120** (dir DATA block 0, touched by every lookup/readdir), each `rc=0 fresh_after=1` — FUA-re-read on EVERY access. `_XBF_FUA_FRESH` is set by the read but CLEARED before the next by the gen-invalidation in `xfs_da_read_buf` (~line 3351, clears XBF_DONE|_XBF_FUA_FRESH when `b_mxfs_dir_gen != i_dlm_dir_gen`). So i_dlm_dir_gen is ADVANCING on ~every dir op at 8 nodes (constant DLM re-acquire/BAST ping-pong), invalidating the hot block each time. 8 nodes × per-access real FUA SCSI read on the LIO target (cache-bypassing, serialized) = ~65s/round verify. This is a real but SECONDARY effect — the dominant cost is the P36-RETRY acquire stall itself. REFUTED: `fua_disable=1` did NOT fix slowness (rounds still 12-74s) → slowness is NOT FUA-read cost. REFUTED: predecessor gen-coupling hypothesis (P14 DABUF probe: `loaded_gen==dir_gen` at EVERY hole, never <). See [[sess15run-ROOT-8tcp-dir-reuse-is-SLOWNESS-hot-block-fua-restorm]].

### The inode_mht_ms tradeoff — one global knob can't satisfy both tests
`inode_mht_ms` (EX minimum-hold-time, default 300ms; `mxfs.inode_mht_ms=<N>` via MXFS_EXTRA_MODARGS) is the dominant speed/correctness knob, but the two tests need OPPOSITE values:
- **tcp_dlm_scaling wants LOW mht** (less per-handoff defer → less acquire churn): mht=300 → 73-119s/node, P36-RETRY ~25-45/node → FAIL 1/8; mht=50 → 5-22s/node, P36-RETRY ~1-3/node, P58=0, no corruption → **PASS 8/8**.
- **dir_reuse wants HIGH mht** (batch dir-EX modify, avoid stale-base RMW dir-block lost-update): mht=300 → CORRECT PASS 8/8 @900s but SLOW ~630s; mht=150 → FAIL 0/8 (~round 8, sh=0, content/coord); mht=50 → fast (fits 300s) but readdir=0/800 + Corruption-detected SHUTDOWN (sh=1, NOT P58) → FAIL 0/8.

A single global mht has a narrow/empty window (mht=150 already breaks dir_reuse; mht=300 too slow for tcp_dlm). dir_reuse's low-mht corruption is the SAME dir-block coherency family fought for ~90 sessions (sess69 cross-node stale-read-cache-hit RMW base poisoning is the known root; the P58 fix removed the resurrection face, this is the stale-base RMW face — fix belongs on the READ/invalidation side). See [[sess15run-MHT-tradeoff-tcpdlm-wants-low-dirreuse-wants-high]].

### Fix directions for next session
**Highest-value (fixes BOTH):** eliminate the queue-vs-grant missed-BAST so acquires succeed promptly under 8-way contention — audit dlm/dlm.c grant paths (FRESH local grant, remote-request grant `process_remote_request`, promote_waiters FIFO @605-655, `collect_grantee_bast_if_waiters` @528, `collect_post_promotion_basts` @674): after every release/convert, re-run promote_waiters AND collect BASTs for ALL newly-grantable waiters (not stop-at-first); verify ino=131 P36-RETRY count → ~0. Trace one stuck ino=131 acquire with DLM_TRACE (gated to ino==128 — edit to the hot ino).
**Independent correctness defense (do regardless):** when a dir EX acquire returns -110, the modifying op MUST abort the transaction (trans_cancel + error), NEVER fall through to modify+commit at NL. Fix at the acquire site (find the caller ignoring -110 from `mxfs_v5_dlm_inode_lock`/`mxfs_dlm_ilock_begin` on create/rename/remove), not by turning the P58 gate into an enforcement point (risks shutdown).
**Options to break the mht tradeoff:** (1) fix the underlying dir-block coherency so low mht is safe, then set mht low for everyone; (2) adaptive/scoped mht — high EX-hold only for dir DATA-modifying tenures, low otherwise.

**CONSTRAINT:** `MXFS_LOCK_ACQUIRE_WAIT_MS` is SHARED with the v5_mount ABBA-yield path (`mxfs_v5_dlm_inode_lock_retries`, v5_mount.c:1081) that sess58 tuned so inode-acquire returns every ~retries seconds to re-run the cooperative AG-yield (breaks the inode↔AG ABBA deadlock in tcp_dlm_scaling). DO NOT just raise the constant — it would slow that yield cadence and may regress tcp_dlm_scaling. Prefer FIXING the missed-BAST race (no timing change) OR thread a per-call wait_ms so only the full-budget dir path waits longer while the ABBA path keeps 1s.
