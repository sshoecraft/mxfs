# Fencing, recovery and lap-harness traps: who drives the work, and what the wait is really behind

Topic group of 12 notes. Two threads: (A) code that is supposed to make fencing/recovery progress but does not, because nobody owns the next step; (B) harness defects that make a fence lap vacuous or manufacture a verdict about the filesystem. Entries are grouped by thread, not strictly chronological.

## A. Progress ownership in fencing, recovery and the DLM

Common shape: a state change releases, clears or elects, and the action that the state change was meant to enable is triggered from a different event, a different thread, or a different node. Check every site that clears the last holder / arms a retry / elects an actor against the sites that actually perform the action.

- **Mount-time fence retry is not automatic.** `v5_fence_retry_worker_fn` (dlm/v5_mount.c) skips armed retries until `ctx->mounted`, so "retry=automatic" in a `P238-FENCE-PENDING` line means automatic only on a live mount. A whole-cluster bootstrap phase 3 waited 107 s on an armed PRECOMMAND attempt with no `P304-FENCE-RETRY`. Mount-time code waiting on a fence certificate must drive `v5_fence_retry_one` itself when `fence_retry[slot].next_ms` is due. When a retry certifies while `dead_node_notify_fn` is NULL, the slot must not be handed to the late-death dispatch (`P567-FENCE-RETRY-DEFER`) if a bootstrap term already owns it. Order phase-3 fences so a PRECOMMAND miss is deferred: another victim's PREEMPT may remove the registrant that refused it. [[trap-the-pr-worker-re-drives-a-fence-only-once-the-mount-is-live]]
- **A retry armed on a worker that takes locks waits behind what it should unblock.** The foreign-slice replay retry was scheduled on the reap delayed work; the worker's other duties take inode/AG grants, and a second node's death left it waiting on that node's grant, which only the replay ends. A delayed work armed while running fires only after the function returns, so six survivors hung and could not unmount. Rule: a retry that a lock-holder's progress depends on lives on its own work item that takes no lock. Before arming on an existing worker, list what it can block on. Proof used: `work_busy()` printed at the arm plus a per-duty line; a parameter (`dbg_reap_wait_dead_ms`) parks the worker to make the case on every lap (natural hit was ~1 in 10). The refusal itself was common (3 of 4 laps) and harmless only because the worker was usually free. [[trap-a-retry-armed-on-a-worker-that-takes-locks-waits-behind-the-thing-the-retry-would-unblock]]
- **A recorded block that releases a dependant must also drive what the dependant held.** The terminal refusal called `v5_gate_dep_clear(..., "refused-terminal")`, but gate restore was only called from recovery-complete publication and from the PR worker re-driving an already-due restore. Nothing lifted the gate: WE(1) stayed held for the survivor's lifetime and the returned victim was refused at PR-ledger publish (`P-PRKEY-PUBLISHED rc=-52`) on every mount. Fix (0.87.12): `v5_gate_terminal_release` marks the restore due under the gate lock first (progress never depends on the inline call), then runs the same checked primitive; the PR worker re-drives a due restore every 2 s. Two hazards from the design consult: (1) "key absent" proves nothing about a revived incarnation that re-registers under WE(1), so the restore re-checks quarantined gate-kind descriptors with a fresh synchronous bracket and converts only on proven ABSENT (`P-PR-GATE-RESTORE-VICTIM-PRESENT` otherwise); (2) the joiner must install the terminal refusal synchronously (mount barrier import, `P241-RECOV-TERMINAL-IMPORT`/`-SCAN`, `P240-QUAR-NSOP-REFUSE`). Audit method: grep all `*_clear`/`release` sites against the callers of the action. Harness: `MODE=terminal_rejoin tests/d_intents_2tcp_open_efi.sh` (EXPECT=refuse is the control); the LUN carries a quarantined slice afterwards, so `MXFS_FORCE_PREP=1 ./run.sh 2 tcp prep_cluster` first. [[trap-a-recorded-block-that-releases-a-dependant-must-also-drive-the-thing-the-dependant-was-holding]]
- **An election of the lowest live slot does no work when that node left.** `mxfs_disklock_lowest_live_slot()` gated WE-AR reservation repair on `elected = (low == local_slot)`, but the maintainer is exactly the node whose departure removes the repairer: its PR worker exits, yet its slot reads live after a clean teardown (`P304-RETIRE-PENDING-RELEASED`) until a successor proves the release (`P163-CLEAN-DEPART-LINEAGE`). Measured on 2-node TCP 0.86.1: test2 logged `P305-RESV-HEALTH state=ABSENT role=auditor` and never repaired until test1 remounted. Fix: the election is a head start, not an exclusive right; `mxfs_disklock_live_slot_rank()` uses the same liveness predicate, stand-ins act after `grace + rank*step` (measured exactly 20.50 s; with the maintainer present, repair at t+6 s as `role=maintainer rank=0`). Every other `lowest_live_slot` call site must answer "is this job still required when the elected node is absent?"; replay elections that pass a `skip_slot` are the other correct answer. "Must not be done by everyone" and "will be done by someone" are separate requirements. [[trap-an-election-that-elects-the-lowest-live-slot-does-no-work-when-that-node-is-the-one-that-left]]
- **A progress counter published only on success turns every refusal into a frozen-clock wait.** `ctx->takeover_pages_done++` (dlm/dlm.c:3558) moves only on `dlm_takeover_page`'s success return; the caller answers `-EINPROGRESS` on any refusal (dlm.c:2787); the retry loop (dlm.c:8001-8035) detects the frozen counter after `MXFS_DLM_TRANSITION_STALL_MS`, logs `P960-AUTH-TRANSITION-STALLED fallible=0`, resets `trans_t0` and waits again, and `retries++` at :8054 undoes its own decrement. Every refusal (recovery-judging guard, PREPARED page never consumed, unresolved owner incarnation, failed activate/import) is an unbounded wait for a non-fallible caller. Aggravations: the counter is global while the wait is per-object (unrelated progress resets a stuck waiter's clock); the counter is relayed in replies, so one stuck worker freezes other nodes' waiters. Ask separately which writes move the counter and what the exit is when it is legitimately static; a refusal that can persist by design needs a terminal answer, not a longer wait. A predicate comment saying "for as long as X stands" marks an unbounded wait. [[trap-a-progress-counter-published-only-on-the-success-path-turns-every-refusal-into-a-wait-with-a-frozen-clock]]
- **A lone fresh mount on two nodes is the whole-cluster bootstrap.** A prover that unmounts and mounts again with the peer dead runs the total-outage bootstrap (`mxfs_bootstrap_survivor_scan`, two 62 s windows in `v5_bootstrap_run`, then phase 3 fences and certifies every victim inline and replays its slice). Either the victim is recovered before the mount masters anything (no standing guard for the unmount), or recovery cannot complete and the mount is refused (`P-BOOT-FENCE-UNPROVEN`, `P-BOOT-MOUNT-REFUSED`); there is no in-between. A dead member keeps mastership until its recovery completes, so requests on its pages fail fast (`-ENOTCONN`), never a transition wait; the victim's rejoin is refused while its old incarnation is under recovery. A "REMOUNT arm" for a page-authority transition lap cannot work; if the shape needs a third identity it is a 3-node lap. Corollary: a refused bootstrap mount had started the fence-retry worker and freed the DLM context under it (guest panic at `v5_fence_retry_worker_fn+0x8f`), fixed in 0.89.70 (`v5_refused_mount_stop_workers`). [[trap-a-lone-fresh-mount-on-two-nodes-is-a-whole-cluster-bootstrap-that-recovers-the-victim-inline-or-refuses]]
- **Three refused latch firings are not a retry budget.** `P304-FENCE-RETRY attempt=1..3` plus `P304-FENCE-PROVE-BUSY` is the PR worker's latch (`v5_fence_retry_worker_fn`) refused by the single-prover guard because the node's own parked prover held it; `P304-RETIRE-WORKER exiting` is the separate settle worker. No retry budget exists on that path. Measured on 0.87.14: with the gate available the departing prover certifies and releases RETIRE_PENDING; with the gate refused (`fence_gate_inject_refuse=1`) the unmount waits ~110 s on the dead victim's grants until the recovery-blocked cutoff returns EIO, then departs DIRTY (no unmount record), so slot and key are retained by the ordinary dirty-departure rule. Attribute a probe line to the function that prints it before naming a mechanism (shared prefix means nothing). [[trap-three-latch-firings-refused-by-the-nodes-own-parked-prover-are-not-a-retry-budget-and-a-filtered-journal-capture-cannot-say-why-a-slot-stayed-active]]
- **A usermode DLM harness must mirror the kernel's phantom handling.** In `tests/tauth/formation_test` (12 in-process nodes, PR/unlock/EX/unlock on ino 128 at the engine level) 3 of 8 runs failed rc=-35 on EX. Each was an EX denied while local mode was NL; master `P-CONVBLK-DENY` count equalled failures; the engine returns -EDEADLK through the pass-through arm of `mxfs_dlm_lock_retries` (~dlm.c:7948) without spending retry budget, so "budget too small" was never a candidate. A ramp remaster leaves the node's PR holder bit at the new master (phantom upgrade deny; kernel names it `P109-EDEADLK-NL`). Unlock-and-retry made it worse (5 of 8): `mxfs_dlm_unlock` with nothing held locally is a local -ENOENT no-op. Only the gen-0 unconditional release (`mxfs_dlm_release_orphan_if_unheld`) clears it: 8 of 8 pass. Do not file the deny as an engine livelock without the first-failure trace (request, held mode, rc, call wall, deny count). [[trap-a-usermode-dlm-harness-that-releases-at-the-engine-holds-nl-so-a-phantom-upgrade-deny-cannot-be-cleared-by-unlock]]

## B. Ruling adherence and fence-lap design

- **A ruling's hazards are part of its procedure.** The design-consult ruling for the transient-refusal progress rule said: release locks the publication path needs before waiting, and do not hold the cluster AG grant across a synchronous flush (cluster-wide head-of-line blocking). `mxfs_pubob_drive_publication()` nevertheless did `xfs_log_force(XFS_LOG_SYNC)` + `xfs_ail_push_all()` + up to 200 ms of `msleep(2)` under the AG EX from `mxfs_dialloc_two_phase`, and `mxfs_pubob_flush_owed()` did an uncapped synchronous force per candidate. The board then showed `node_responsive` FAIL (inode-BAST worker blocked in `mxfs_dlm_ilock_begin`) and `soak` FAIL (`P36-STACK` first timeout). Correct shape: kick publication asynchronously (`xfs_log_force(mp, 0)`, `xfs_ail_push_all`), refuse the candidate transiently, and let the existing 500-1000 ms reservation cooldown be the retry delay. Re-read the hazard list against the diff line by line before building, not after a board row fails. [[trap-i-built-the-synchronous-flush-under-the-ag-grant-the-ruling-warned-against]]
- **The fence matrix has two different entries.** `tests/fence_crash_cuts.sh` cut 4 kills the prover after PREEMPT AND ABORT proved exclusion; the proof dies with it and a successor recovers across a boot boundary (banked 12/12 both victim arms). It says nothing about a prover that stays alive and deciding after a lost response (`docs/rulings/fence-lost-response-live-prover.md`): the target really performs the P&A, only the result is lost, the prover keeps a durable `MAY_HAVE_RUN` arm with no proof. The defect hunted is a shortcut that treats the victim key's absence as proof, or yields `BOOT_SUCCESSION_ABSENT` with no boot boundary. Injection point: `pal/linux/kern.c`, in `mxfs_pal_prout_preempt_abort`, after `scsi_execute_cmd` returns and before its status normalization and `P302-PROUT-ABORT-FAIL` reporting (before submission tests the weaker "never ran"; after reporting omits the log line a real loss emits). Substitute `-ETIMEDOUT`, which reaches `dlm/scsipr.c:2013` as `kind=ERROR, phase=MAY_HAVE_SUBMITTED`. No second P&A is issued (`fence_node` classifies `KEY_ABSENT_UNPROVEN`); resolution is only via the sole-survivor gate or boot succession, held with the non-sleeping knobs `fence_gate_inject_refuse` / `fence_bootsucc_inject_refuse` (a blocking hold would park the disklock heartbeat thread, a different lap). Verdict must be two-part: (A) alternatives refused, nothing certified/sealed/claimed/replayed/zeroed, durable arm intact, error path shown to have run; (B) released, a real certificate naming the mechanism actually used and completed recovery, bounded. "Certificate or a named block" passes an implementation that always blocks. [[technique-the-fence-matrix-splits-into-crash-cuts-and-lost-evidence-and-they-are-not-the-same-entry]]

## C. Harness mechanics that make a lap vacuous or hand back a false verdict

- **Key a VM kill on the node's own kernel line, never a fixed sleep.** `sleep 3; virsh destroy A` landed before A's REGISTER once a 1.5 s READ KEYS delay was injected (tell: empty `a_mount.txt` and `keys_after_kill.txt`). Poll A's ring over ssh for `P-PRKEY-REGISTERED 'mxfs' key=` after the kmsg mark, bounded, destroy on sight, report `registered_seen=1` and ms into the mount. [[technique-kill-a-vm-on-its-own-kernel-line-and-never-wait-on-the-corpses-ssh]]
- **Never `wait` on the ssh client talking to a dead VM**: it blocked 96 s until TCP gave up, by which time the state under test had moved (the QNAP target kept the dead session's registration for the 10 s grace and dropped it only when the peer's PREEMPT AND ABORT landed: last seen 11.1 s, absent 12.1 s, fence certified 11.6 s). Run the client under `setsid bash -c "..." &` and `kill -- -$apid` right after the destroy; the peer then mounts 0.7 s after the kill. Same note: count the worker's `P304-RETIRE-WORKER ... result=PRESENT` line, not `P304-RETIRE-PENDING-SEEN ... state=UNKNOWN`, which is logged before the table is read; and a rebooted test VM has no `/src` (NFS from 192.168.1.4), so mount with the retry loop first (shape at `tests/d0932_owner_depart_takeover.sh:193`) or `prep_node.sh` reads as a prep failure. [[technique-kill-a-vm-on-its-own-kernel-line-and-never-wait-on-the-corpses-ssh]]
- **`wait_for_into` bound is SECONDS** (`tests/lib/rig.sh:247`; it sleeps 2 and adds 2). `$(( PROGRESS_BOUND / 5 ))` gave 48 s against a 60 s re-drive sweep, which would have printed a liveness FAIL about a correct module. Derive every wait bound from the period of the mechanism producing the event (re-drive sweep 60 s, `fence_blocked_after_ms` 120 s) and state the derivation beside the wait; too short reads as a confident negative verdict. Caught by reading the helper; the lap was killed rather than measured. [[trap-a-poll-helper-whose-bound-is-in-seconds-read-as-a-poll-count-manufactures-a-liveness-fail]]
- **Evidence capture.** A VACUOUS/ABORT exit must save the full journal (`journalctl -k --since @MARK`), not a pattern-filtered tail: the lines that explain a negative are never the ones the pattern was written for (the filtered capture missed `P277-SLOT-RETAINED-UNMOUNT-DIRTY`, `P278-LATE-RELEASE`, `P236-RELINQ-*`, `P302`). A harness that virsh-destroys a node must power it on before any exit (`run.sh prep_cluster` aborts on a powered-off node). Do not edit a harness while a lap of it runs: bash reads the script incrementally from the current offset; kill first, then edit. [[trap-three-latch-firings-refused-by-the-nodes-own-parked-prover-are-not-a-retry-budget-and-a-filtered-journal-capture-cannot-say-why-a-slot-stayed-active]] [[trap-a-poll-helper-whose-bound-is-in-seconds-read-as-a-poll-count-manufactures-a-liveness-fail]]
