Compiled from sess14 (ccloop `4cb2d0a2`) TCP-transport full-suite work: getting the criterion `1/2/4/8 tcp FULL suite 100%` met. Two breakthroughs landed 1/2/4-tcp; 8-tcp remains blocked by three narrow causes (create/lookup DABUF holes, bnobt, dir-EX handoff throughput). Criterion NOT met at session end.

## The two root fixes that unblocked 1/2/4 tcp

**FIX 1 — cluster is a LIO target, not SCST → FUA-read source defaults required** [[sess14run-BREAKTHROUGH-LIO-fua-defaults-plus-barrier-perf-fix]]. `lsscsi` on test1 = `LIO-ORG mxfs`; host has `iscsi_target_mod`/`target_core_mod`, no `scst_tgt`. On LIO each initiator has its own read cache, so plain bio reads see STALE peer state; only SCSI-FUA reads pierce to the coherent backstore. The old sess63 default `fua_disable=1` (an SCST shared-write-cache assumption; the project memory `project_test_cluster_scst` describes an older cluster generation) is WRONG here → default dir_reuse 4/tcp = readdir 0/400, 322/400 coherency fail (no shutdown). Changed SOURCE DEFAULTS in `xfs/xfs_mxfs_dlm.c` (harness passes no modargs, so defaults must be right): `mxfs_fua_disable=0`, `mxfs_fua_always=1`, `mxfs_dir_epoch_adopt=1`, `mxfs_dir_epoch_convert_gate=1`. Note `fua_always=1` (force FUA on every coherency-metadata read) is REQUIRED because the `_XBF_FUA_FRESH` amortization gate does NOT invalidate on cross-node dir handoff — gated `fua_always=0` fails IDENTICALLY to no-FUA (0/400, 322/400 from round ~8). Confirmed later: a gated-defaults run = crash_consistency 3/4 + dir_reuse 0/4, so gated is not reliable. FUA costs NO extra wall vs gated (same round time) — FUA is NOT the perf bottleneck. First build with these: `83CAA038` → dir_reuse 4/tcp 24-round PASS 4/4, zero failrounds. [[sess14run-STATUS-2tcp-17of17-4tcp-16of17-tdscaling-marginal]]

**FIX 2 — coord_barrier polling latency was the budget blocker, NOT MXFS** [[sess14run-BREAKTHROUGH-LIO-fua-defaults-plus-barrier-perf-fix]]. Single-node FS ops for a whole dir_reuse round (50 files + sync + drop_caches + readdir + 50 stat + rm + sync) = 0.45s total, yet a round took ~18s. Root: `tests/suite/coord.sh` coord_barrier looped `mosquitto_sub -W $COORD_POLL --retained-only` with `COORD_POLL=2`, blocking the full 2s window every poll even after all nodes arrived — 5 barriers/round × 2s ≈ 10s/round of pure artificial latency masquerading as MXFS slowness. Fix: `mosquitto_sub -t "$base/r/+" -C "$MXFS_NODES" -W "$COORD_TIMEOUT"` exits the instant all node retained markers arrive. Same barrier semantics. dir_reuse 4/tcp wall 465s → 205s (~7s/round), well within the 300s TEST_TIMEOUT; speeds ALL coordinated tests. (Same bug-class as the fixed-`TEST_TIMEOUT` harness issue below.)

## The readdir DABUF_MAP_HOLE fix (real, but narrow)

[[sess14run-FIX-readdir-dabuf-map-hole-gen-bump-before-reload-bail]]. Symptom: full in-suite `./run.sh 4 tcp` (build `83CAA038`) = 16/17, only dir_reuse FAIL 0/4. test4 reached round 23/24, stalled ~124s at a barrier (peers grew the dir), then verify-phase readdir hit `Internal error !(flags & XFS_DABUF_MAP_HOLE_OK) at line 2817 of xfs_da_btree.c` in `xfs_dabuf_map` → EFSCORRUPTED whole-FS shutdown → test4 drops from barriers → all nodes NORESULT → 0/4 cascade.

Root (proven by code path): in `xfs_readdir` (`xfs/xfs_dir2_readdir.c` ~695) a non-EX reader with dir_gen>0 BUMPED `i_dlm_dir_gen` (forcing `xfs_da_read_buf` to re-fetch FRESH leaf/data blocks) and THEN called `mxfs_dlm_reload_inode` (refreshes the extent map). But reload uses a trylock and BAILS under contention (leaves `i_dlm_stale=true`). On bail: gen already bumped → getdents re-reads a fresh leaf referencing peer's grown block N, while the extent map stays stale (no mapping for N) → `xfs_bmapi_read` returns HOLE → `!HOLE_OK` → shutdown. The 124s stall maximized the fresh-leaf/stale-map gap.

FIX (`70F91E1B`): reorder — do the reload FIRST; bump `i_dlm_dir_gen` ONLY if reload SUCCEEDED (`i_dlm_stale` cleared). On bail, do NOT bump gen — keep leaf+extent map consistent-stale (at worst a transient readdir miss that self-heals next round; no hole, no shutdown). PROVEN: 4/tcp dir_reuse reliable after this. This eliminated ALL DABUF_MAP_HOLE shutdowns at 4 AND 8 nodes on the readdir path (test7/8 previously took 17-18 each) [[sess14run-8tcp-10of17-clean-run-bnobt-is-the-blocker-DABUF-gone]].

## 4/tcp tcp_dlm_scaling — flaky at the 60s window (measured, RULE 4)

The test has its OWN internal `WINDOW=60s` assertion (not `TEST_TIMEOUT`): 150 rounds × 3 ops × 4-way = ~1800 serialized cross-node dir-EX ops. Typical elapsed ~44-52s for the slow ranks; rank1 always finishes fast (~7-17s = DLM UNFAIRNESS, one node hogs). Standalone passes 4/4; in-suite (after soak) the extra contention tips 2/4 nodes >60s → FAIL. FUA vs gated makes NO difference (~44s both) → pure dir-EX handoff throughput, not a FUA cost.

Cost localized to the holder-side dir-EX release path `xfs_mxfs_dlm.c` ~5788-5818 (settle usleep loop + 2× log_force + `mxfs_dir_flush_data_blocks` + `mxfs_ail_drain_inode_sync` + `blkdev_issue_flush` ~25ms). A/B with the diagnostic params [[sess14run-tdscaling-cost-is-settle-loop-required-asynckick-minor-help]]: `relflush_skip=1` (skip per-release `blkdev_issue_flush`) → elapsed UNCHANGED ~44s (the flush is NOT the cost); `relsettle_skip=1` (skip the `while(pincount>0) usleep` settle loop) → max 45s → 29s (settle ≈ 35% of cost). BUT the settle is REQUIRED — defaulting `relsettle_skip=1` broke the suite (dir_reuse 0/4, fence/netpartition 3/4). The settle's pincount==0 wait protects the dir-DATA flush: `mxfs_dir_flush_data_blocks` runs BEFORE the inode drain `mxfs_ail_drain_inode_to`, and the drain only covers the dinode, not dir data blocks — so it is NOT redundant with the drain's own pin==0 loop (Invariant #1). The added async `xfs_log_force(mp,0)` CIL kick trims ~10% (45→41s, more balanced) and is safe. Remaining ~12s (41 vs 29) is genuine durability wait (log write + AIL insert before dir-data flush) — inherent. To get real margin: (a) FUA-write dir blocks so they are durable independent of inode pin, letting the settle be inode-only/shorter, or (b) reduce handoff COUNT via a longer hold quantum (worsens the fairness asymmetry). Both non-trivial; deferred.

## 8/tcp — three narrow blockers (coherency itself is SOLID)

Clean-start discipline is essential: the FIRST 8-node run scored ~1/17 (cache_coherency 0/8) but was CONTAMINATED (stale-build boot + post-4node state); a clean start did NOT reproduce those empty-content failures → contamination/variance, not a real 8-node coherency bug [[sess14run-8tcp-10of17-clean-run-bnobt-is-the-blocker-DABUF-gone]]. At TEST_TIMEOUT=600 the full map is 12/17 [[sess14run-8tcp-FULL-MAP-12of17-at-600s-remaining-DABUF-createlookup-iscsi-conn-tdscaling]]: 12 PASS 8/8 (precond, cache_coherency, strong_consistency, posix_multi, mmap_coherency, zero_silent_loss, dlm_fairness, dlm_membership, scaling_curve, dlm_scaling, rsync_paired, crash_consistency); 5 FAIL (dir_reuse, fence_during_write, fault_netpartition, soak, tcp_dlm_scaling). All coherency tests pass 8/8.

**Blocker 1 — DABUF_MAP_HOLE in CREATE (addname) and LOOKUP paths for large LEAF-format dirs.** The real remaining correctness bug and #1 priority [[sess14run-SESSION-SUMMARY-and-next-priority]]. The readdir fix only covers readdir; create/lookup also map dir blocks via `xfs_dabuf_map` against a stale data-fork extent map when `mxfs_dlm_dir_modify_reload_prelock` / `mxfs_dlm_dir_consumer_refresh` trylock-BAILS under 8-way contention → fresh leaf references a block absent from the stale map → hole → shutdown. In-suite (after crash_consistency's node-kills) test4 recorded 251-668 DABUF events → FS shutdown → downstream iSCSI conn-error-1020 recovery loop. FIX APPROACH: make the modify/lookup extent-map reload RELIABLE under contention — a bounded-retry of `mxfs_dlm_reload_inode` in the prelock (called pre-`xfs_trans_alloc`, only IOLOCK held, so bounded blocking is relatively safe), gated default-OFF first, validate (a) no 1/2/4-tcp regression, (b) cuts the 8-node storm, then default-on. Do NOT use the reverted in-hole EIO guard.

Instrumented signature (`1A0A8F9C`) [[sess14run-INSTRUMENTED-8node-DABUF-hole-signature-bno2-HOLE-plus-P103-reuse-adopt-flood]]: `xfs_dabuf_map: bno 2 inode 537965` / `br_startoff 2 br_startblock -2 (HOLE) br_blockcount 1` — logical dir block 2 is HOLESTARTBLOCK(-2) in this node's extent map while a leaf still references it; repeats hundreds of times (test4: 251-668). Surrounding P103-RELOAD-REUSE-ADOPT flood: files (high inos) with `disk_gen = incore_gen + 1`, `disk_size=0`, `disk_mode=00` — heavy ABA inode-reuse churn (rm-rf + recreate each round frees+reallocs all files AND the dir); the node adopts the peer's freshly-allocated incarnation.

CORRECTION on root [[sess14run-CORRECTION-8node-DABUF-NOT-modify-time-extent-staleness-instrument-next]]: the create/lookup hole is NOT modify-time extent-map staleness. The gated `dir_modify_extent_reload` branch (reload a non-SF dir when its DLM epoch advanced) fired `P14-MODEXT-RELOAD` 0× with dir_reuse still 0/8 and the storm unchanged — the `grant_epoch > valid_epoch` trigger never matched. Combined with sess68 P68-MAPDIVERGE=0 (per-block daddr compare found maps AGREE at every modify-prelock), the fresh-leaf/stale-map theory is REFUTED for create/lookup: the in-core extent map matches disk when the modify starts. The readdir ordering bug that WAS fixed is a different timing (bump-before-bailable-reload) and does not generalize. NEXT is pure instrumentation (RULE 4, do not guess again): at the invalid_mapping site (~line 2815, multi-node dir DATA fork, !HOLE_OK) log bno, `dp->i_df.if_format`, `if_nextents`, `i_disk_size`, `i_dlm_dir_gen`, `i_dlm_dir_evicted_incarn`, `i_dlm_mode`, `comm`, the returned irecs[], and the referencing LEAF block's `b_mxfs_dir_incarn` — to decide leaf-incarn-vs-map-incarn mismatch (stale leaf re-read via ABA daddr reuse) vs an in-txn `xfs_trans_roll` re-read vs a genuinely orphaned/double-mapped daddr. The `b_mxfs_dir_incarn` check at `xfs_da_btree.c` ~3246 may catch only data blocks, not the leaf. Build `61E384CC` carries this `P14-DABUF-HOLE` probe ready to run; the 8-node storm (test4 251-668 events) makes capture easy. `comm` distinguishes ls=readdir from create/lookup. If `loaded_gen < dir_gen` at the hole, the extent map was not reloaded for the gen the leaf refreshed to (decoupled evict-ring gen-bump vs extent-map reload) = root proven; fix = advance `i_dlm_dir_gen` only together with an extent-map reload, or arm `MXFS_IF_DIR_RELOAD` whenever the evict-ring bumps dir_gen.

**Blocker 2 — bnobt AG-free-space btree corruption** (crash_consistency, long-standing family sess42-47/81/88/90) [[sess14run-8tcp-10of17-clean-run-bnobt-is-the-blocker-DABUF-gone]]. On the clean 10/17 run this was THE blocker: 75 shutdowns on test1 (=rank1, does dir_reuse rm-rf + is coordinator → heaviest AG churn), 2 on test7. Because `fua_always=1` makes AG-meta READS coherent, this is a WRITE-side/RMW/release-ordering bug, amplified by 8-way AG free-space contention. crash_consistency 0/8 cascades to dir_reuse/fence/netpartition/soak. Reference prior fixes: sess43 (in-AIL AG-meta must not be discarded), sess47 (stale cached inode inactivation), sess42 (advance `b_mxfs_ag_gen` only when fresh). NOTE: on the later 600s run crash_consistency recovered to 8/8 — earlier bnobt/crash_consistency 0/8 was partly a 300s-timeout-induced incomplete-recovery artifact; the bnobt WRITE-side bug is still real but intermittent.

**Blocker 3 — 8-way dir-EX handoff throughput** (dominant on timeouts) [[sess14run-8tcp-CORRECTED-dominant-blocker-is-8way-handoff-throughput-plus-bnobt]]. Same root as tcp_dlm_scaling (2/8 → the 60s window with 8×150=1200 serialized ops) and dlm_scaling (7/8). The per-release Invariant-#1 settle (~22ms, required) × the 8-way handoff count is the cost. Highest-leverage single fix (helps dir_reuse timeout, tcp_dlm_scaling, dlm_scaling at once) but needs a genuinely cheaper handoff, which is hard given the mandatory settle.

## dir_reuse at 8 nodes — the O(N) budget reframe (RESOLVED as correct)

Successive isolations converged, with earlier hypotheses refuted along the way:
- First hypothesis: readdir=0/800 on ALL nodes (incl the creator, after drop_caches) for DRC_NFILES=50 (EXP=800) while DRC_NFILES=10 (EXP=160) PASSES 8/8 → "NODE/btree-format directory coherency" [[sess14run-8tcp-dir_reuse-root-is-NODE-format-dir-coherency-small-dir-passes]].
- REFUTED by P26-RDDIR evidence [[sess14run-8tcp-CORRECTED-dominant-blocker-is-8way-handoff-throughput-plus-bnobt]]: the 800-entry dir is fmt=2 (XFS_DINODE_FMT_EXTENTS), nextents=9, disk_size=24576 (6 data blocks) = LEAF format, NOT NODE/btree. Different DRC_ROUNDS/NFILES runs gave different outcomes (DRC_ROUNDS=4/NFILES=50 PASS; ROUNDS=24 run A real readdir=0/800 miss; ROUNDS=24 run B NORESULT = killed at 300s).
- RESOLVED [[sess14run-8tcp-dir_reuse-is-CORRECT-passes-at-600s-budget-not-coherency]]: `TEST_TIMEOUT=600 ./run.sh 8 tcp dir_reuse_coherency` (24 rounds, NFILES=50, EXP=800) = PASS 8/8, ZERO failrounds. 8-node dir_reuse coherency is CORRECT. The workload is O(N) — EXP = 2×T×NFILES (800 at 8 nodes vs 400 at 4); 8-node wall ~2× the 4-node wall (~400s vs ~205s) for 2× the work = MXFS scales ~LINEARLY. `run.sh` uses a FIXED `TEST_TIMEOUT=300` for ALL node counts, so an O(N) test inevitably times out at high N. Per CLAUDE.md RULE 0 (`budget = infra + workload(native×2)`), scaling the per-test budget to the workload is implementing RULE 0 CORRECTLY, NOT "widening to pass" — same class as the fixed coord_barrier `-W` bug. Many 8-node "failures" (dir_reuse, likely fence/netpartition/soak) are budget artifacts, not bugs. Action item: implement a node-count-scaled per-test budget in `run.sh` — but that does NOT fix the in-suite DABUF cascade (blocker 1), which is a real bug.

## Recurring operational lessons

- **INFRA — 8-node runs WEDGE mxfs modules** (rmmod-busy after FS-shutdown/heavy run) and leave nodes in iSCSI recovery. Clean between runs: `for n in test1..test8; do ssh $n 'umount /mnt/shared; sleep 0.3; rmmod mxfs; dmesg -c'; done`; if still WEDGED, `virsh -c qemu:///system destroy <node>; virsh -c qemu:///system start <node>`. Budget extra prep time at 8 nodes. A failed/killed run leaves nodes mounted → next `./run.sh` prep_fs mkfs hits "device busy" — always clean first.
- **Deploy**: `run.sh` prep rmmods+insmods `/src/mxfs/mxfs.ko` (NFS-shared `/mnt/mxfs-src`); boot auto-loads a stale ko but prep overrides it. Cluster is test1-8 via `virsh -c qemu:///system` (not the default session URI).
- Clean start is mandatory at 8 nodes — contaminated first runs produce false coherency failures.
