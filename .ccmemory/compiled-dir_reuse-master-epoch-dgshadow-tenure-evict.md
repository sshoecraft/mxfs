## sess23 (ccloop) — dir_reuse 8/tcp clobber: dg_shadow epoch, eviction-immunity, and the acquire-side racy residual

Central topic: the lone ship blocker at sess23 is `dir_reuse_coherency` at **8 nodes over TCP DLM** — a rare, durable, content-divergent dir-DATA-block dirent clobber under concurrent same-dir create. Everything below traces one bug through instrumentation, refuted levers, a master-epoch reliability fix, and a GPT-5.5 architectural design for the real fix.

### DEEPEST ROOT: the dg_shadow master dir-handoff epoch is unreliable (LRU evicts the hot dir)
`mxfs_v5_dlm_inode_dir_epoch()` returns the per-resource handoff epoch from `dg_shadow[DG_SHADOW_N=512]` — a file-global **LINEAR-SCAN** table in the DLM master (dlm/dlm.c). `dg_grant_ex()` increments epoch only if the resource slot is FOUND and it's a handoff (last_owner != new owner). If the slot was **LRU-evicted** (recycled for another inode), it's treated as first-grant → **epoch RESET to 0, handoff=false**. The dir_reuse workload creates ~800 file inodes/round churning the 512-slot table; the hot shared-dir inode goes briefly INACTIVE between its ~800 grants and in a window with 512 more-recent file-inode grants becomes the LRU victim → evicted → epoch resets to 0 → `tenure_stale`/P16/P-FASTEX-EPOCH CANNOT fire → stale RMW base → clobber. The rarity of that eviction window == the flakiness. Enlarging DG_SHADOW_N is REFUTED (dlm.c:2464, sess17): linear-scan per grant → O(N) acquire timeouts → DLM timeout → shutdown cascade at N=16384. [[sess23-ROOT-dg-shadow-epoch-unreliable-lru-evicts-hot-dir]]

### FIX (KEEP, default-ON, low-risk): dg_shadow eviction-immunity
dlm/dlm.c: added `grant_count` to `dg_shadow_ent`; eviction now recycles the COLDEST inactive slot (lowest grant_count, tie-break oldest seq) instead of oldest-seq. The hot shared-dir inode (granted ~800×/round) accrues a huge grant_count → NEVER LRU-evicted → its handoff epoch is preserved. VERIFIED: `P64-MASTER-HANDOFF` fired 570×, master epoch advanced to 41 (previously suspected stuck near 0). Strict improvement (worst case = old behavior; cannot cause false handoff/corruption). This is the load-bearing keeper gain. [[sess23-eviction-immunity-fixes-epoch-but-residual-is-acquire-side-racy]]

### But eviction-immunity + reliable epoch does NOT fix 8/tcp — the residual is acquire-side racy
With the reliable epoch AND `dir_tenure_evict=1` (modify-evict + master-sync + GPT-9.1 + read-path tenure_stale all firing), 8/tcp STILL FAILS flaky: r21 lost 15 SCATTERED .md5 entries across two nodes/multiple blocks (node5: f27,f39-42,f44,f45; node7: f6,f7,f12,f13,f15,f17,f25,f26), r24 lost 1. More invalidation did not converge it. Confirms the documented sess16 conclusion: acquire/read-side invalidation (invalidate+re-read the RMW base) is structurally racy — the re-read opens a TOCTOU window and the peer's newer write is often not yet on the LUN at the evict moment. The whole epoch/evict/read-invalidation family treats the SYMPTOM (stale cached base), not the cause. [[sess23-eviction-immunity-fixes-epoch-but-residual-is-acquire-side-racy]]

### FUA correction (do NOT pursue fua_disable)
The BREAKTHROUGH memo floated a "FUA reads stale platter" hypothesis for the residual — REFUTED/CORRECTED. `_XBF_FUA_FRESH` / `mxfs_pal_scsi_read_fua_bdev` (SCSI READ(16) FUA) exists precisely because it PIERCES the LIO target/initiator cache to get CURRENT data (CLAUDE.md "LIO drops FUA" tension). Proof: `fua_disable=1` alone = dir_reuse 0/400 catastrophic; `dir_tenure_evict=1 + fua_disable=1` = flaky then r21 loss + r22-24 got=0 CASCADE (per code comments xfs_mxfs_dlm.c:16996/17052 — plain bio reads are per-initiator-cached/stale across nodes on LIO; FUA is REQUIRED). So the evict's FUA re-read DOES get current shared-target data; do NOT change the evict to keep `_XBF_FUA_FRESH`, and do NOT pursue fua_disable. The stale-platter rationale was SCST-target, not this LIO cluster. Since FUA gets current data yet a single-holder still reads a base missing the peer's entry, the peer's just-committed write was NOT yet visible on the target when we FUA-re-read → GPT §5 "grant-before-durable" at the DLM serialization level. [[sess23-fua-disable-refuted-residual-needs-generalized-probe]] [[sess23-residual-race-correction-not-fua]]

### REFUTED levers (do not repeat)
- **`dir_evict_prior_tenure=1`** (both read+modify epoch sites): SHUTDOWN cascade (r20 loss → r21-24 got=0). The cause is the **read-path epoch_stale** (xfs_da_btree.c:3333-3401, clears XBF_DONE on in-AIL buffers during PR reads → trips XFS verifier/AIL/log-lifecycle assertions). The modify-evict half (runs under our own EX hold) is SAFE. This SPLIT is the actionable finding. [[sess23-tenure-evict-progress-and-gpt-grant-gen-design]] [[sess23-BREAKTHROUGH-master-epoch-sync-flaky-pass]]
- **`dir_bast_evict=1`** (release-side eager-evict clean dir blocks on cross-node BAST, post-drain, via `mxfs_dir_evict_data_blocks` under nowait ILOCK_SHARED): HARMFUL — 8/tcp r11 lost 2 (798), r12 lost 86 (714) + leaf-hash lookup_fail. It evicts DATA *and* LEAF blocks; evicting a leaf at the BAST moment (peer then rebuilds/RMWs it) corrupts the leaf hash index → readdir-present-but-lookup-ENOENT holes. [[sess23-REFUTED-eager-evict-on-bast-harmful]]
- **Conclusion from both:** buffer EVICTION/INVALIDATION (either side) is the wrong lever — the fix must be PROTOCOL-level. Acquire-side is racy; release-side eager-evict corrupts leaf.
- **`dir_tenure_evict=1 + dir_release_fua_write=1`**: WORSE (r7 loss, r8=663, r9=0 cascade) — FUA-write at release perturbs/cascades.
- **`b_tenure_id` reuse for dir blocks** (0EA92470 first attempt): cascade — `b_tenure_id` is shared with AG-meta (sess123) and bmbt; daddr reuse → AG-meta tenure logic misreads it. Use dir-specific `b_mxfs_dir_epoch`, NOT `b_tenure_id`.
- **`i_mxfs_ex_grant_seq` is 0 for dirs** (egseq=0 in 96% of P68-EVDECIDE) — unusable as a dir tenure counter. The maintained counter is `i_dlm_dir_valid_epoch` (master-authoritative, level-triggered, set in P-FASTEX-EPOCH at xfs_mxfs_dlm.c:11800).
- **P17-CLOBBER-DROP** (pal/linux/xfs_buf.c:3137) confirms dir DATA destaged with fewer live dirents than held (stale-base RMW), BUT its per-daddr max table keys on (daddr,owner-ino) which are REUSED across rounds → cross-round FALSE POSITIVES; not reliable alone.
- DLM release→grant ordering was INSPECTED SOUND at the code level (release fence drains before unlock-send before next grant; xfs_mxfs_dlm.c ~6981-7027/7840; dlm.c promote_waiters ~1623) — but see the residual evidence that a visibility gap persists in practice.

### GPT-5.5 architectural design (the recommended real fix — master-authoritative grant-generation)
Consulted GPT-5.5 (RULE-5 justified). Distilled: [[sess23-gpt5.5-grant-generation-coherency-design]]
- **Correct invariant:** a dir DATA buffer may be an RMW base only if its bytes correspond to the CURRENT DLM EX tenure, or it was dirtied during this same continuous EX tenure. A buffer from an OLDER tenure must not be an RMW base after any FOREIGN EX grant. Do NOT key KEEP on `in_AIL && logged_seq>written_seq` — AIL bookkeeping is NOT a durability/ownership oracle (that keying is the bug).
- **Why master grant-gen > in-core epoch:** the epoch is local cache state (can be stamped on stale bytes, re-stamped by a bad read path, encodes no cross-node happens-before). A master grant-gen is tied to serialized ownership transfer. Required properties: master-authoritative; monotonic per inode-lock resource; incremented on every EX ownership change; returned SYNCHRONOUSLY in the grant reply (not async BAST/AST); ORDERED AFTER the releasing node's drain; invalidated on DLM recovery (resource incarnation); resource key MUST include inode allocation incarnation (the test REUSES the dir inode#+daddrs).
- **Main failure mode (§5):** granting next EX BEFORE the previous owner's data is durable+VISIBLE on the LUN → acquirer reads pre-peer image → clobber. Release path must: stop new local dir mutations → commit+wait txns → wait unpin → write dirty/delwri dir blocks → wait write completion → flush bdev → STAMP release-gen/destaged → ONLY THEN complete the DLM unlock/downgrade. Also no future AIL push may write the old image after release (§9.5).
- **Why "different node held EX since" UNDER-FIRES on TCP (§6):** voluntary release (peer acquires with no BAST to us); only "previous owner" recorded (misses intermediate owners); TCP per-connection ordering ≠ global; cached EX→PR→EX / EX→NL→EX satisfied locally with no master round-trip. FIX: master keeps `ex_seq` + `last_ex_seq_by_node[]`; answer "did any node != me get EX after my last seen seq?"; return `(resource_incarnation, current_ex_seq, foreign_since)` synchronously. Prefer FALSE POSITIVES (extra reads) over false negatives (lost dirents).
- **Why release-side invalidation SHUT DOWN (§8):** clearing XBF_DONE / staling a buffer at release while XFS holds a live log item / AIL membership / callbacks / delwri refs trips verifier/AIL assertions. PREFER release-side durable STAMPING (set fields only) + acquire/RMW-side hard refresh under buffer lock keyed on grant-gen.
- **Why logged_seq>written_seq persists after a release drain (§9):** written_seq advanced on some write paths not all (9.1); iodone/unpin/delwri not fully waited (9.2); buffer RELOGGED after the drain scan (9.3 — drain isn't a true quiescence point); AIL membership ≠ non-durable (9.4); delayed AIL push of old image fires after release (9.5). FIX: at the durability fence, authoritatively `written_seq=logged_seq` + clear undestaged under buffer lock; prevent new mutations + wait all active dir txns BEFORE the scan.

### Late-session competing hypothesis — node-format freeindex staleness (HIGH-CONFIDENCE, not yet proven)
The 8-node threshold coincides EXACTLY with the XFS dir2 leaf→node format transition (≈ blocksize/8 ≈ 512 entries at 4K blocks): 4 nodes = 4×50×2 = 400 entries = LEAF format (no separate free block) → dir_reuse 4/tcp PASSES; 8 nodes = 800 entries = NODE format (separate `xfs_dir2_free` freeindex block with `bests[]` per-data-block free summary) → FAILS. **SMOKING GUN (grep, no run):** `b_mxfs_dir_epoch =` modify-time stamp sites exist ONLY in xfs_da_btree.c (read-time), xfs_dir2_data.c (data blocks), xfs_dir2_leaf.c (leaf) — **xfs_dir2_node.c has NONE.** The freeindex block (`xfs_dir2_free`, logged via xfs_dir2_free_log_bests @370/476/1210/2000/2068 and xfs_dir3_free_log_header @391/477/1238/1789) is NEVER stamped with the coherency epoch at modify. `xfs_dir2_node_addname_int` (~L1907) reads the freeindex to pick a data block with space; a stale freeindex across a cross-node handoff → addname targets a data-block slot a peer already filled → overwrites the peer's dirent. A coherent DATA-block re-read alone does NOT fix wrong SLOT SELECTION driven by the stale freeindex. This is the sess22 free-slot double-alloc; the residual cause would be FREE-block staleness. NOTE: the read-time stamp at xfs_da_btree.c:3739 already stamps the freeindex on READ, so the gap may be only the MODIFY stamp — verify. [[sess23-SMOKINGGUN-freeindex-not-epoch-stamped-node-format]] [[sess23-NEXT-hypothesis-node-format-freeblock-coherency]]
- **Experiment (RULE 4):** instrument `xfs_dir2_node_addname_int` to log freeindex `bests[]` vs the freshly-read data block's actual free space at the chosen findex/offset — free-block-said-free but data-block-occupied = PROVEN stale-freeindex clobber. Re-examine why the sess22 L3 free-slot guard (before `xfs_dir2_data_use_free`) fired 0× — it likely checked the data block's OWN bestfree, not the cross-block freeindex. Fix candidates: (A) add modify-time epoch/gen/incarn stamps to the freeindex at its log sites in xfs_dir2_node.c, mirroring xfs_dir2_data.c:887 / xfs_dir2_leaf.c:409; (B) coherently re-read the freeindex before slot selection on a cross-node node-format addname and re-validate the chosen data slot before `xfs_dir2_data_use_free`.
