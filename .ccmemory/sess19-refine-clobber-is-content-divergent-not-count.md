## sess19 (ccloop 8ddb16a2) — REFINEMENT after 3 detector iterations on the leaf-hash clobber.

## NEW DATA (build 8B8D7499, dirwr=1, cc_blockdir_probe 30 50, short iter14 193/200): .ccb_14 readdir=200, lookup-fail=7 on BOTH nodes (leaf-hash inconsistency mode), BUT:
- P-LEAFWRITECLOBBER (buf_cnt < coherent_disk_cnt at leaf submit) fired **0×** this run. So the clobber is NOT always a count shortfall — the leaf can reach the full 200 entries yet have 7 hash→data-offset mappings WRONG (lookup follows the hash to a stale/wrong data-block offset → name mismatch → ENOENT). i.e. the clobber is CONTENT-DIVERGENT at EQUAL count. A count-only detector/guard is INSUFFICIENT; need an entry-SET (hashval+address) compare.
- The leaf xfsaild/bash submits showed `dgen=2 lgen=2 pmp=0` (peer-modify-pending = dir_gen > loaded_gen = FALSE). So pmp is NOT a reliable discriminator for the safe-skip (refuted this session's hypothesis). (Note: ino=131 is REUSED every iter via rm-rf+mkdir, so i_dlm_dir_gen resets low (1-3) each incarnation — gen-based discriminators are weak under this ABA-reuse stress.)
- P16-DIRBLK-SUBMIT is pr_warn_RATELIMITED so most leaf writes are dropped from the log — do NOT rely on its counts for completeness; P-LEAFWRITECLOBBER (atomic ≤200, not ratelimited) is the reliable one but only catches count-shortfall.

## WHAT THIS MEANS: the leaf↔data-block coherency is broken across the DLM handoff. The leaf hash entry encodes (hashval, data-block ADDRESS/offset); concurrent creates land dirents at different data-block offsets on each node, and a leaf RMW from a base with a DIFFERENT data-block layout writes hash addresses that point to the wrong/stale data entries → lookup ENOENT even at full count. This CONFIRMS GPT's frame: the whole dir image (ALL data + leaf + free + node blocks together) is the coherency unit; piecemeal per-block gen-gated refresh is insufficient. Two manifestations seen this session: (1) leaf-hash inconsistency (readdir>lookup; iter2/14), (2) genuine readdir loss (iter9/16, data block lost entries). Same root.

## SHARPER FIX DIRECTION (sess20): authoritative WHOLE-DIR reload at dir-EX acquire (post-release OR peer-modified): evict ALL dir blocks (data+leaf+free+node, the entire data fork) and re-read the peer's durable image atomically BEFORE any RMW — NOT the current gen-gated per-block evict that SKIPS pinned/undestaged blocks. PREREQUISITE CHECK (RULE 4, do FIRST): at a failing iter, does the acquire-side evict (mxfs_dir_evict_data_blocks via modify_refresh) SKIP any dir block (P-EVICT-SKIP) at the FRESH-grant acquire? At a clean post-release acquire there should be NO undestaged/pinned dir blocks (release drained them, Invariant #1). If P-EVICT-SKIP fires at acquire, the release-drain is INCOMPLETE for dir blocks under this stress = the concrete Invariant-#1 hole to fix (strengthen the dir release to fully destage+unpin ALL data-fork blocks before unlock). If evict does NOT skip at acquire but the leaf is still stale, the re-read is returning stale (SCST coherence or restamp) — different fix. ALSO consider: leaf is deterministically rebuildable from data blocks — if data blocks are authoritative, rebuild the leaf rather than RMW a stale leaf base.
