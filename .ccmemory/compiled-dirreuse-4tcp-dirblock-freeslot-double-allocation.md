## 4/tcp dir_reuse_coherency durable single-dirent loss — ROOT PROVEN: cross-node dir-data-block free-slot double-allocation

Consolidated from the sess11 ccloop run (cluster test1-4, TCP DLM transport, `log_buf_len=16M` grub on all nodes). Criterion `dir_reuse_coherency` fails ONLY at 4/tcp; 2/tcp passes. Symptom: ~80% of 4-node rounds durably lose exactly ONE dirent — usually a 2nd-wave `.md5` sidecar (e.g. node3_f45.md5, node4_f22.md5, node2_f13.md5), sometimes a 1st-wave DATA file (node2_f38). Loss is `LOOKUP_ENOENT` + cold-readdir MISS on ALL 4 nodes incl. the creator (readdir 399/400). Always during the dir's 2→3 data-block GROWTH/rebalance window (size 8192→12288, fmt=2 EXTENTS, LEAF1).

### The proof (final root cause)
The lost entry is a **cross-node INTRA-BLOCK freespace DOUBLE-ALLOCATION** — two different nodes place two different dirents at the SAME physical byte slot of the shared dir data block. Decisive trace from `P11-DATALOG` probe with byte offset (build **C0290572**, dirwr=1), lost=node2_f1.md5 [[sess11run-ROOTCAUSE-PROVEN-cross-node-dirblock-freeslot-double-allocation]]:
- `123.404 test4: P11-DATALOG ino=131 daddr=2093296 off=2768 name=[node4_f4]`
- `124.609 test2: P11-DATALOG ino=131 daddr=2093296 off=2768 name=[node2_f1.md5]`

Same daddr, same off=2768, different names, 1.2s apart, different nodes. This is the DIRECTORY-level analog of the AG free-space double-allocation family (sess24/42/43) at the `xfs_dir2_data_hdr` bestfree[]/unused level: when a node acquires dir-EX and RMWs the block, its bestfree must reflect ALL peers' committed dirents; here test2 RMW'd block 2093296 from a stale base lacking test4's node4_f4 at off=2768, so test2's free-slot search saw off=2768 free and double-used it.

### Directionality (build C0290572) [[sess11run-DIRECTIONALITY-later-writer-stale-bestfree-loses-fix-coherent-refresh]]
The **LATER writer loses**. test4 wrote node4_f4 first (123.404, SURVIVED on disk); test2 wrote node2_f1.md5 +1.2s later to the same slot (LOST). The 1.2s gap rules out a durability race — node4_f4 was long durable. It is a READ/refresh-coherency gap on the later node: test2's EX-acquire evict+cold-read failed to refresh block 2093296's bestfree, so its dir2 addname double-allocated onto an occupied slot, then test2's in-core block was coherently re-read/reverted to the disk image (node4_f4 at 2768) before flush → node2_f1.md5 dropped.

### Investigation chronology — how the earlier "same-thread revert" framing was reconciled
Before the cross-node proof, probes showed the committed dirent (rval=0) vanishing from its in-core CACHED block within ~250us, same thread, under continuous ILOCK_EXCL, with no split/evict/reload in the window — which initially pointed INSIDE the create transaction:
- `P11-DATALOG` in `xfs_dir2_data_log_entry` (build **96931768**, KEEP; uses the tp-held bp, no fresh lock) caught the entry's BYTES logged to a daddr, then a precise ONE-ENTRY revert of just that entry within 325us, back to the pre-add on-disk image [[sess11run-SMOKINGGUN-datalog-entry-bytes-logged-then-vanish-no-evict-no-reload]].
- `PRELOGF` (`mxfs_dir_dump_block_names` at `mxfs_dlm_dir_durable_signal` ENTRY, before `xfs_log_force`; build **E5DFBB14**, KEEP) proved the entry ABSENT at durable_signal entry, only ~32us after rval=0 — before log_force. Ruled out: the 2→3 split (happens 0.6s later, a consequence not cause), cross-node daddr divergence (all 4 nodes agree block layout), uncached-skip, and concurrent peer-BAST evict (ILOCK_EXCL held continuously) [[sess11run-FINAL-entry-vanishes-in-addname-to-commit-window-not-split-not-evict]] [[sess11run-DECISIVE-dirent-absent-at-durable-signal-entry-handoff-during-create]].
- A DECISIVE detail: dir gen bumped (e.g. 4→5) DURING one create → the create's PR→EX path spanned a contended DLM handoff, and the EX-reacquire's P62-RELOAD/P106-MR-EVICT cold-read the peer image [[sess11run-DECISIVE-dirent-absent-at-durable-signal-entry-handoff-during-create]].

The `off=` proof unified all of this: the "entry vanishes from in-core before durable_signal, no evict/reload, ILOCK held" observation is explained because the slot it occupies is contested cross-node — the peer's overwrite / a bestfree-from-stale-base displaces it. The bytes were logged; the slot was double-allocated.

### Mechanism (GPT-5.5 RULE-5 consult) [[sess11run-ROOT-committed-dirent-reverted-by-evict-before-publish-GPT-fix]]
`log_force(SYNC)` does not revert memory; it lets a buffer look "clean" (not dirty/pinned, maybe not in_ail) so a concurrent evict heuristic `dirty||pinned||delwri||!DONE||(in_ail&&!incarn_aba&&undestaged)` FALSELY clears `XBF_DONE`; a normal dir read then cold-refills the SAME xfs_buf from the stale home block (entry not yet destaged). XFS buffer flags are NOT a valid proxy for "home block contains this committed dirent" — peers cold-read the device, so LOG durability ≠ HOME-block durability. Under EX-modify, `xfs_da_read_buf`'s pre-read gen-invalidation is gated `!owned_ex` → SKIPPED, and `b_mxfs_dir_gen` is lossy (stamped fresh over stale content), so the addname serves whatever is cached [[sess11run-REFUTED-dataclobber2-and-readside-gap-is-the-fix-target]].

### Fixes TRIED and REFUTED (do NOT re-apply)
- **FIX3 read-side gen-stale** (sess10 build **9527F28F**, P67-POSTREAD-REREAD, param `dir_postread_reread`): default-inert; flag ON REGRESSES to 14/400 (drops own committed work). Read-side gen-stale is the WRONG layer. `b_mxfs_grant_gen` harmless/inert [[sess11run-ROOT-committed-dirent-reverted-by-evict-before-publish-GPT-fix]] [[sess11run-HANDOFF-evict-fix-insufficient-revert-under-ilock-next-probe]].
- **Write-side clobber-enforce** `dataclobber=2` (build **C0290572**, `pal/linux/xfs_buf.c:2320` skip write when dc_stale): makes it WORSE — drc4 FAIL round 1, whole-dir readdir=0 (corrupt). Mis-classifies legit/coalescing writes (matches sess23 P122/P93 suppression-was-corruptor). Do NOT use dataclobber≥1 [[sess11run-REFUTED-dataclobber2-and-readside-gap-is-the-fix-target]].
- **memcpy-overwrite coherent-modify** (build **890C3B13**): overwriting in-core block with disk image REGRESSED to 345/400. "disk has more dirents" does NOT imply disk is a SUPERSET — it drops this node's own entries disk lacks. UNSOUND, reverted [[sess11run-FIX-ATTEMPT-coherent-modify-detection-works-remediation-hard]].
- **Invalidate coherent-modify** (build **F0D7B279**, `mxfs_dir_refresh_stale_data_blocks`, param `dir_coherent_modify` default 0): DETECTION works (P11-COHMOD fired 4x/node, confirms stale-cached-dir-block root) but remediation insufficient — the losing block often isn't cached at modify_refresh time (xfs_buf_incore miss), and even on re-read the addname's COLD-READ itself returns a stale (non-FUA) image [[sess11run-FIX-ATTEMPT-coherent-modify-detection-works-remediation-hard]].
- **in_ail-gate evict tweaks**: removing `in_ail &&` on the modify-path keep (`mxfs_dir_evict_data_blocks` ~2501, build **78B0C9B7**) pushed failure later (round 23 vs 5-15) but did NOT fix. Doing the same on the acquire-path drain_evict (~4663, build **A0D1A382**) HANGS the test (>280s dir-EX handoff STALL) — acquire-side suppression without a complementary guaranteed release-destage livelocks. Both REVERTED [[sess11run-HANDOFF-evict-fix-insufficient-revert-under-ilock-next-probe]].

### Fix direction (converged)
The pre-RMW read must use a COHERENT base that includes every peer's committed dirent, so bestfree never double-allocates — WITHOUT reverting own work and WITHOUT write-suppression. Two complementary halves:
1. **Coherent pre-addname READ**: on a contended dir (`i_dlm_dir_gen>0`) force the modify-path dir DATA-block read FUA-coherent so the addname's bestfree reflects peers' occupied slots. Signal must be CONTENT divergence (P29-DATAWRITE-style: dirent count + inumber sum/xor vs a coherent plain/FUA read), NOT lossy `b_mxfs_dir_gen`; guard with `mxfs_dir_buf_is_undestaged` to never revert own committed-unwritten work. One plain read per modify (RULE-0 timing) [[sess11run-FIX-ATTEMPT-coherent-modify-detection-works-remediation-hard]] [[sess11run-REFUTED-dataclobber2-and-readside-gap-is-the-fix-target]] [[sess11run-DIRECTIONALITY-later-writer-stale-bestfree-loses-fix-coherent-refresh]].
2. **Per-EX-grant TOUCHED-BUFFER writeback fence** (GPT-5.5 architectural): mark every dir DATA buffer logged under EX `b_mxfs_cluster_undestaged`+hold at the low-level dir-data log points (`xfs_dir2_data_log_entry/header/unused`, `xfs_da_log_buf`); NO evict/cold-read may clear `XBF_DONE` on it in ANY path (modify-evict 2501, acquire drain_evict 4663, read-side xfs_da_btree 3260, bmbt 836/12717); publish by force-writing every touched buffer HOME before DLM unlock even if it looks clean, THEN clear the flag; BAST must DEFER (schedule, not sync-IO) evict/reload while a local publisher is active — the missing half that stops (2) livelocking. Tie clean-block refresh to a PEER durable epoch (LVB), not grant churn. NEVER union-merge dir data blocks (corrupts variable-size entries/bestfree/tail/crc). Infra already exists: `b_mxfs_logged_seq`/`b_mxfs_written_seq` + `mxfs_dir_buf_is_undestaged()` [[sess11run-ROOT-committed-dirent-reverted-by-evict-before-publish-GPT-fix]] [[sess11run-HANDOFF-evict-fix-insufficient-revert-under-ilock-next-probe]].

### Tooling / harness lessons
- **POSTADD2 / P11-POSTADD are unusable heavy.** Calling `mxfs_dir_dump_block_names` with a fresh `xfs_buf_incore`+`xfs_buf_relse` from INSIDE `xfs_dir_createname` CORRUPTS the dir (readdir=0) — the live transaction holds those buffers locked and the relse drops the tp's hold. Dumping ALL blocks after every addname is O(n²)/perturbing → drc4 verify reads spurious `?` (heisenbug). Only inspect in-transaction buffers via the tp-held bp or by walking `tp->t_items`; PRELOGF (in durable_signal, after commit) is safe [[sess11run-P11-POSTADD-probe-too-heavy-need-lighter-targeted]] [[sess11run-FINAL-entry-vanishes-in-addname-to-commit-window-not-split-not-evict]]. Next-gen probe should be O(1): after createname, one lookup to resolve the entry's data-block daddr, then dump only that block.
- **Validation harness**: use standalone `drc4_repro` (exits at first fail, ~10s/round) for pass/fail; `tests/tcp/drc4_capture.sh N` (dirwr=2) PERTURBS timing (heisenbug) — forensics only. `run.sh`/`validate_drc4` (MQTT barrier suite, all 24 rounds) became unreliably slow — avoid for correctness. KEEP `log_buf_len=16M` (survives the storm).
- `mxfs_dir3_data_fingerprint` EXPORTED from `pal/linux/xfs_buf.c`; `mxfs_dir_dump_block_names` exported in `xfs/xfs_mxfs_dlm.c` ~1247.
