Central topic: how a rig run produces a false "absent / zero / PASS" because the instrument was off, mis-matched, read from the wrong window, or scored a filesystem nothing touched. Plus two stacked-device traps and one oops-decoding technique that surfaced in the same measurement work.

## Dynamic-debug probes: absence is not evidence until the site is known enabled

- Since 0.89.89 every instrumentation line (`P12-...`, `P-AGIFC-MOD`, `PW-...`, `tauth: P-TAUTH-...`, untagged tags like `EVICT-RING-FLAG`) is `pr_debug` via `mxfs_probe*` (`pal/mxfs_probe.h`) or `mxfs_pal_log(MXFS_LOG_DEBUG, ...)`. Nothing prints unless enabled. A harness that loads the module itself without `dyndbg=+p`, or checks a packaged node, greps 0 and reports "did not happen". [[trap-a-harness-that-loads-mxfs-without-dyndbg-sees-no-probe-lines-and-reads-them-as-absent]]
  - Enable: `insmod mxfs.ko dyndbg=+p` (prep_node.sh and the existing insmod harnesses do), `echo 'module mxfs +p' > /proc/dynamic_debug/control` at run time, or `options mxfs dyndbg=+p` in modprobe.d.
  - Confirm probes are on before trusting a zero: count enabled mxfs sites, or look for a high-volume probe (P-AGIFC-MOD fires on every AGI free-count change).
  - `dump_stack()`/`sched_show_task()` belonging to a probe are gated by `mxfs_probe_on()`, so "stack follows" prints no stack with probes off.
- Same failure at 0.90.48: `tests/mkdir_mutex_storm.sh` control runs reported relookup=0 flipwaits=0 three times and were read as "window not reached"; nothing could have been counted. The mpath path-fault rows (tests/mpath/lib.sh) turn all probes on; a from-scratch harness does not. [[trap-probe-lines-are-dynamic-debug-so-a-harness-that-counts-one-reads-zero-unless-it-turns-it-on]]
  - `nohup sh -c '... exec dmesg -w' | grep ... > file &` over ssh leaves the grep un-nohup'd; it dies with the session, file is 0 bytes. Follow the whole log (`nohup dmesg --follow < /dev/null > file &`, as `kmsg_follow_start` in tests/lib/rig.sh) and grep afterwards.
  - A path row deletes its followed kmsg log on PASS; anything to be counted from it must be counted inside `pf_done` first, as an INFO line.
  - A zero counter is evidence only after the same counter has been seen non-zero on a run known to contain the event. Type-flip events (INODE-REUSE-EVICT, P95B) accompany path-fault stalls; a plain mkdir/rmdir storm produced none in 600 s. `typeflip_force_unresolved=2` forces the P201-RELOOKUP path; value 1 does not.
- 0.90.64: `mxfs_pal_log(MXFS_LOG_DEBUG, "mxfs: P-TAUTH-IMPORT-RETAINED ...")` never appeared although `drbd_rig.sh` enabled `module mxfs format "P-TAUTH-IMPORT-RETAINED" +p`. `mxfs_pal_vlog` (pal/linux/kern.c) routes every DEBUG call through ONE `pr_debug("%s%pV\n", ...)`; dyndbg matches the call site's format, which is `"%s%pV\n"` for all, so a tag can never be enabled alone, and `+p` on that site is a flood. A tag a harness must switch on is written with `mxfs_probe()` / `mxfs_probe_ratelimited()`; `mxfs_pal_log(MXFS_LOG_DEBUG)` only for lines nobody selects by tag. If a line is absent, find which macro printed it first. [[trap-mxfs-pal-log-debug-lines-share-one-pr-debug-site-so-a-format-match-never-enables-them]]
- 0.90.55: `grep " \[mxfs\]" /proc/dynamic_debug/control | grep -c "=p"` counted 7 enabled sites on both PVE hosts; all were `=_`, the `=p` was inside format text (`at=put_super`, `site=pr_demote`, `via=pubob`). A defect record briefly carried "7 sites enabled" as flood evidence. Control line is `file:line [module]func =FLAGS "format"`; match the flags field only: `awk '$3 ~ /^=p/'` or `grep -E '\] *[^ ]+ =p[a-z]* "'`. Anchor every count to the field it means. [[trap-grep-equals-p-on-dynamic-debug-control-matches-format-text-not-the-flags]]

## Reading the log: window by build, not by boot

- 0.89.90: `journalctl -k -b -1` on test2 was a 2026-07-01 boot of a months-old module (P68-EVDECIDE 29,600 lines, tags that no longer exist). A node's current boot can also span several module loads. Window by time: `journalctl -k --since "<load time UTC>" -p info`; check `journalctl --list-boots` before any `-b -N`. `-p info` excludes pr_debug, so on a probes-on run it shows what prints by default, except `callbacks suppressed` lines and probe-gated stacks. A message with no matching format in current source may be a `%s`-built tag (`"P-PRKEY-%s idx="`); check before blaming an older build. [[trap-a-test-nodes-journal-since-boot-holds-older-builds-and-older-boots]]

## A chain's PASS can be vacuous

- 0.90.12, chain 116 at 4/tcp (tests/evidence/sess475_chain116_d0133_s4e_4tcp.log): the SB-dirtying workload `tests/dirshard_reuse_peer_list.sh` got `ENOTSUP MXFS_IOC_DIRSHARD_MKDIR` on every mkdir because `mxfs_dirshard_enabled(mp)` needs `mkfs_mxfs -D` and rig prep formats without it. The workload reported 110 failures per lap, yet the chain's own seal-ok / distinct-epochs / counters==chk verdicts PASSed on `icount=64 ifree=61`: a fleet unmount of a filesystem whose counters never moved verifies nothing. A second, stacked miss: the lock-line grep (`epoch=N at=put_super`) predated the `master_self=` field added in 0.89.66, so `lock_ok=0` every lap. Fixes: chain exports `MXFS_MKFS_OPTS="${MXFS_MKFS_OPTS:--D}"`; the pattern allows fields between `epoch=` and `at=`. Before trusting a chain PASS, read one lap's VERDICT/TERMINAL counters and the workload's own verdict; counters equal to fresh-format values (icount=64) mean nothing was exercised. [[trap-a-chain-whose-workload-needs-a-format-time-feature-scores-its-verdict-on-a-filesystem-nothing-touched]]

## Stacked block devices and SCSI PR

- 0.90.40: `mxfs_bdev_to_sdev` (pal/linux/kern.c) resolved any non-SCSI, non-partition device to "the SCSI disk whose LBA 0 matches" (built for dm-multipath). DRBD with internal metadata and md RAID1 with end-of-device metadata share LBA 0 with the backing disk, so `/dev/drbd0` resolved to its iSCSI LUN (`P-MPATH-RESOLVE stacked bdev 147:0 -> SCSI backing path 3:0:0:0`, measured on test1). Had the mount been admitted, `mxfs_pal_scsi_write_fua_bdev` (xfs_ialloc.c, xfs_mxfs_dir_data.c, xfs_buf.c), every FUA read and COMPARE AND WRITE would have hit one replica, unreplicated. Hidden only because PR admission refused first. Fix: content resolution only for disks named `dm-*`. For any new stacking layer (DRBD, md, others), look for P-MPATH-RESOLVE on its major before trusting passthrough; the defect record carries the verification step. [[trap-a-layer-whose-lba0-equals-its-backing-disk-is-resolved-to-that-disk-and-passthrough-skips-the-layer]]
- s147c/s57: `tests/delayed_write_across_fence.sh` remounted through `/dev/mapper/mxfsdelay` (`0 SZ delay 8:0 0 0`); the mount died with `P305-PR-SWAP-NOKEY ... RESERVATION CONFLICT` and `P305-PR-NEXUS-ALREADY-REGISTERED ...` on a nexus that held nothing. Cause: REGISTER goes through the stacked device's `pr_ops` (`mxfs_pal_scsi_pr_register` -> `dm_pr_register`), not to the resolved sdev (P-MPATH-RESOLVE is for passthroughs). `dm_pr_register` calls `__dm_pr_register` per `iterate_devices` entry and rolls back on first failure; `delay_iterate_devices` reports read, write and flush `dm_dev`, the SAME device three times. Register #1 succeeds, #2 conflicts, rollback removes the key, caller sees CONFLICT, and the module's "predecessor key" diagnosis is wrong. Earlier record/harness header wrongly claimed REGISTER goes to the sdev; read `get_pr_ops` first. Working substitute: single-path dm-multipath without the `mpath-` uuid prefix (`dmsetup create mxfsmp --table "0 $SZ multipath 1 queue_if_no_path 0 1 1 round-robin 0 1 1 8:0 1"`; `dmsetup message mxfsmp 0 fail_path 8:0` to hold, `reinstate_path` to release). Verified: a direct read sat in `submit_bio_wait` 5.3 s until reinstate. Do not assert on `/sys/block/dm-N/inflight` (reads 0 0 for request-based dm; requeued requests are on `/sys/kernel/debug/block/dm-N/requeue_list`). `dmsetup remove` right after can report busy: use `--retry`. A lap aborting between create and cleanup must unmount and remove the map itself or the next prep fails with `/dev/sda already mounted or mount point busy`. [[trap-dm-delay-under-a-pr-registering-mount-conflicts-with-its-own-register-because-iterate-devices-lists-the-path-three-times]]

## Decoding an oops with no call trace

- 0.89.84 oopsed in `memmove+0x24` on `mxfs-worker`; netconsole lost the trace. RSI-RDI = 0x40 on a forward shift-down means `memmove(&a[i], &a[i+1], ...)` with a 64-byte element; `gdb -batch -ex 'p sizeof(struct X)' <obj>.o` over candidates picked `struct mxfs_node_lease` (64) at dlm/lease.c:669 (`struct v5_depart_req` = 48, ruled out). RDX/0x40 gave a garbage count; `node_count` sits at 0x1000 in a 5448-byte ctx (kmalloc-8192), whose SLUB freelist pointer lives at object_size/2 = 0x1000. A field garbage exactly there while neighbours are intact means the object was freed, not stomped. Page-aligned destination (R08 = ...000) = array at offset 0 of an 8 KiB object. The free-vs-use ordering in teardown names the race; prove it by holding teardown open with a one-shot knob (`dbg_teardown_lease_hold_ms`) plus a range check that logs instead of writing (fires every run, whereas a negative count only oopses ~50%). tests/concurrent_umount_lease.sh. `mxfs-worker` is the comm of EVERY `mxfs_pal_thread_create` thread (pal/linux/kern.c:1990), so it names no subsystem. [[technique-name-a-traceless-memmove-oops-by-stride-and-the-slub-freelist-offset]]

## Common rule

An instrument reading zero, absent, or PASS is evidence only after (a) the site is shown enabled, (b) the match is anchored to the field it means, (c) the log window is the build under test, and (d) a known-positive run showed the same counter non-zero or the workload's own verdict confirms it did work.
