Topic: how test harnesses on the MXFS rig lose or fabricate evidence (kernel-log capture, detached-process handling, lap design) and the tooling quirks that silently void a lap.

## Kernel-log capture: every channel loses lines

- **journald is not the kernel ring.** `journalctl -k` reads /dev/kmsg asynchronously and drops entries when the module prints faster than it drains. `DLM init: node_id=` was absent from `journalctl -k` while `dmesg` held it. A harness reading a kernel line reads `dmesg` ([[trap-a-harness-that-reads-a-kernel-line-through-journalctl-can-miss-it-and-a-rider-that-frees-an-inode-between-stages-confounds-the-next-stages-instrument]]).
- **The opposite failure also exists.** With thousands of held files the ring overflows before the harness reads it, so `dmesg | awk '/MARK/,...'` finds neither marker nor probe line, and journald dropped the marker in the same burst. For heavy-probe laps read `journalctl -k --since=@<lap start>` ([[trap-a-bare-wait-after-exec-tee-process-substitution-waits-forever]]). Neither source is universally right; verify the capture by hand once.
- **Userspace marks lose their `name:` prefix.** `echo '<5>mxfs-test: X start' > /dev/kmsg` appears in `journalctl -k -o cat` as `X start`, because journald takes the leading `word:` as syslog identifier and `-o cat` prints MESSAGE only. `dmesg` keeps the full text. Match marks without the prefix, and test a range extraction by hand before trusting a count of zero ([[trap-journald-files-a-name-colon-prefix-written-to-dev-kmsg-as-the-identifier-so-o-cat-drops-it]]).
- **`dmesg` costs >1 s on a 16 MB ring.** A per-iteration check must not call it. Use a background `cat /dev/kmsg > file`, note the byte offset after a mark, `tail -c +OFF | grep` after each step (~20 ms) ([[trap-a-join-lap-that-lets-the-incumbent-re-touch-its-objects-after-the-flip-measures-nothing]]).
- **Node journals are volatile.** The test VMs' journald is in `/run/log/journal` and `dmesg` wraps in ~15 min of chain activity; every `virsh destroy` discards the previous boot. A failed rejoin was unreadable 30 min later on both nodes. What survived was clyde's `/var/log/libvirt/qemu/<node>-serial.log` (root-only, `sudo -n cp`; monotonic timestamps; console-level lines only; anchor to wallclock using a harness-stamped copy of a line). Every harness step that can fail must save BOTH nodes' kernel window into its evidence dir at the time, with a negative filter that drops only known noise (ledger-page and bdev_io lines), never a positive filter naming expected lines. Same incident: `domain_admission_matrix.sh` defaults `MXFS_DEV=/dev/mapper/mpatha`; on the QNAP rig export `MXFS_DEV` and `MXFS_NODE_LIST` or every row fails rc=32 in 0 s against the wrong LUN ([[trap-node-journals-are-volatile-a-failed-rejoin-mounts-evidence-survives-only-in-the-libvirt-serial-log]]).
- **Netconsole had no listener.** Nodes always netconsoled to 192.168.120.1:6666; nothing listened, so a guest panic and a guest that "just rebooted" were the same observation. pstore empty (guests may have no pstore region), systemd pstore empty, crashing boot absent from `--list-boots`. An absent libvirt destroy/start event is a positive finding: the reset was initiated inside the guest. Fix: `tools/netconsole_listen.sh start|stop|status|tail`, run whenever the rig can kill a node. Guest `console_loglevel` is 1, so a plain `echo x > /dev/kmsg` (level 4) will not appear; only `<0>` panics-level lines do. Verify end to end with `echo '<0>PROBE' > /dev/kmsg` on a node then `tail`; a running listener receiving nothing looks like a healthy rig ([[trap-nothing-ever-listened-to-the-nodes-netconsole-so-every-guest-panic-was-discarded]]).
- **Mapping a panic to source.** The tree's `mxfs.ko` is rebuilt constantly; the crashed build is on the node as `/root/mxfs.ko.prep` until the next prep. Copy it out via `tools/mxfs_sshpass.sh`, confirm `modinfo -F srcversion` (name must end `.ko`). Frames `sym+0xOFF/0xSIZE` are return addresses; use `objdump -dr --no-show-raw-insn --disassemble=<sym>` for call targets and `objdump -dl` for source lines. A bare faulting address in freed module text: `.text` is page aligned, so low 12 bits equal the file-offset low 12 bits. Only reliable (non-`?`) frames order the calls. This named a double free in `mxfs_dir_sf_capture_base` and an unload panic in the thread wrapper's `schedule_timeout_interruptible` ([[technique-map-a-guest-panics-return-addresses-with-the-module-file-the-prep-left-on-the-node]]).

## Lap design that measures the instrument instead of the kernel

- **A join lap must not re-touch objects after the membership flip.** Incumbent loops that kept adding until `active_count=2` blocked ~0.7 s on the settle window after the flip and re-acquired under a real grant, masking the dirty never-multi image hazard (five laps read clean). The reproducing shape: adds round-robin over 96 objects (32 block dirs, 32 shortform dirs, 32 files), continuous modification up to the flip, no re-touch after. On a never-multi mount xfsaild lands a hot dir block every ~12 ms, so only the last tens of ms are dirty. The reproduction showed the incumbent's join-time flush not converging, force-shutdown, 34 objects losing entries. Verdict patterns must not collide with fixtures (`^b[0-9]`, not `^b`; `^A-[0-9]`, not `^A-`). An Edit that dropped the space before a grep path made grep read stdin and return 0 on every sweep: check the count expression on the node before trusting a zero ([[trap-a-join-lap-that-lets-the-incumbent-re-touch-its-objects-after-the-flip-measures-nothing]]).
- **Riders that free inodes confound later stages.** A rider unlinking stage N's file let stage N+1's create reuse the inode number with a pending bast, firing a release under the newly armed pause ("leaked 450 ms"); the FAIL stood since 2026-08-24 and was read as a kernel bug. No free between stages; run the rider after the ladder.
- **Fault-around bypasses `xfs_filemap_fault`.** A folio already in the page cache is served by `->map_pages`; `echo 3 > drop_caches` before the mmap racer makes the fault take the gated path.
- General rule: a healthy lap that FAILs on an instrument measurement is adjudicated by reading the kernel log around the instrument (who fired it, on which release) before it is a kernel finding; a real finding (held fd read the successor file's bytes) was proven by adding the missing measurement (a digest), not by trusting `rc=0` ([[trap-a-harness-that-reads-a-kernel-line-through-journalctl-can-miss-it-and-a-rider-that-frees-an-inode-between-stages-confounds-the-next-stages-instrument]]).

## Bounds on remote commands

- **`iscsiadm -m node --login` hangs after a healed iptables storage partition** whether or not the session survived (the comment "a surviving session makes login a no-op" is false). s123a died rc=124 at stage=capture after all MXFS verdicts had PASSed; s124a with `timeout 30` still hung, yet `DEV_READABLE=1`. Probe the LUN first (`timeout 10 dd ... iflag=direct`), log in only if it does not answer, wrap every call in a node-local `timeout`, take rc from the command not a pipeline, print `LOGIN_RC`. An outer bound (90 s `measure`) turns one node-local hang into an arm-wide ABORT discarding earned verdicts ([[trap-iscsiadm-node-login-hangs-after-a-healed-storage-partition-whether-or-not-the-session-survived]]).

## Process handling in shell

- **`$!` after `nohup setsid cmd &` is not the detached process.** setsid forks when its caller is a group leader (every `&` job is), so the parent exits at once and a `tail --pid` waiter returns in seconds. Use `nohup setsid bash -c 'echo $$ > PIDFILE; exec env ... cmd' > out 2>&1 < /dev/null &` and check with `ps -o pid,etimes,cmd -p $(cat PIDFILE)`. The release chain does not stop when window laps fail (8 laps failed ~1 s each, then full_verify ran): watch the first lap's `rc=` line before leaving it ([[trap-dollar-bang-after-nohup-setsid-is-not-the-detached-process-so-a-pid-waiter-returns-at-once]]).
- **A bare `wait` after `exec > >(tee log)` waits for the tee forever.** Collect `PIDS="$PIDS $!"` and `wait $PIDS` ([[trap-a-bare-wait-after-exec-tee-process-substitution-waits-forever]]).
- **A kill list from `tools/mxfs_pgrep.sh '<pattern>'` includes the Bash tool's own shell** (its command text carries the pattern), plus any older session shell that ever contained it. The self-kill returned 144, skipped the cleanup, and the harness died 2 min before its verdict. Record the PID at launch and `kill $(cat pidfile)`; or let a WANT= shape end the lap itself; put `kill` last or in its own call. See also `never-pgrep-f-on-clyde-mmap-lock-wedge`, `trap-killing-a-harness-run-midflight-leaks-the-module-refcount` ([[trap-a-kill-list-from-mxfs-pgrep-includes-the-shell-that-ran-it-and-kills-the-harness-mid-lap]]).
- **A detached lap queue outlives its session.** `tests/lap_queue.sh` runs under nohup setsid; a handoff saying "7 of 11 laps done" is a snapshot. A session started `make modules` with lap 8 live 41 s earlier; each lap re-preps and deploys `/src/mxfs/mxfs.ko`, so a relink mid-queue splits the sweep across two srcversions. Before any `make`: `tail -3 tests/evidence/lapq_<label>.log` (`QUEUE lap=N starting` with no `rc=` means in flight), and scan `/proc/[0-9]*/comm` for `*lap_queue*|*run.sh*` (never `pgrep -f`/`ps aux`). Bounds: `run.sh` does not build, so un-linked recompiles are inert; the queue file is read fully before lap 1 so editing it changes nothing, but editing a running harness script is dangerous (bash re-reads by byte offset) ([[trap-a-detached-lap-queue-outlives-the-session-that-launched-it-so-check-for-one-before-any-build]]).

## Tooling quirk

- **Awareness docs over 256 KB cannot be opened.** `dlm.md` (~270 KB), `xfs.md` (~312 KB), `pal.md` (~365 KB) are refused by Read regardless of offset/limit, so Edit cannot anchor. Append with `cat >> doc <<'EOF'`, fix a line with `sed -i` then `grep -c` to prove it, locate with `grep -n -B3 -A6`. `tests.md` and `tools.md` still take Read/Edit. Skipping the update leaves the docs stale ([[trap-an-awareness-doc-over-256kb-is-refused-by-read-and-edit-whatever-the-offset-so-append-with-a-heredoc]]).
