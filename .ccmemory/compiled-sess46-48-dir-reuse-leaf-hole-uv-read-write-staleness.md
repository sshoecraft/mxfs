## Compiled: sess46-48 — the 2/tcp dir-coherency flaky family (dir_reuse / cache_coherency-uv / crash_consistency)

Central topic: the recurring flaky failures of the `2 node dlm=tcp` ship criterion all share ONE root — a node's own committed-but-not-checkpointed dir mods **PIN** a shared dir block that has gone stale relative to the peer's concurrent mods. Read-path coherency serves the stale-pinned block (`DIR-STALE-SKIP`), and any naive fix hits a hard **merge dilemma** (neither the in-core block nor the LUN block is a guaranteed superset of both nodes' RMWs). sess46 diagnosed the root, sess47 refuted the read-side fix and shipped a write-side release-flush, sess48 fixed the remaining write-side lost-update and isolated the last residual to an **SCST per-initiator read cache** (storage layer, not FS).

### The unified root ([[sess46-UNIFIED-ROOT-pinned-shared-dir-block-merge-dilemma]], [[sess46-PROVEN-dir_reuse-leaf-hole-is-async-evictring-lag-stale-leaf-RMW]])
When two nodes concurrently modify the SAME shared dir, each node's own committed-but-not-checkpointed mods PIN the shared dir block in the CIL (`pin=1 has_bli=1 li_empty=1 undest=1 in_ail=0`, gen-stale `buf_gen=0 < inode_gen`). The read hook (`xfs_da_btree.c:3216-3229`) then hits `DIR-STALE-SKIP` (line 3261) and serves the stale block, missing the peer's mods. Same mechanism across the family:
- **cache_coherency (uv)**: node1's data block pinned by node1's OWN deletes → still lists `node2_file21..30` → `uv none remain got=10`.
- **dir_reuse**: node1's LEAF block (`blk=0x800000`) pinned → missing node2's last ~15 hash entries → `lookup_fail`.
- **crash_consistency**: same on small-file `.md5`.

PROVEN dir_reuse mechanism (dmesg capture, build EF006296 unchanged): (1) node1 creates under EX, RELEASE shows leaf CLEAN/destaged (`P34-LEAF-DRAIN CACHED=1 needs_flush=0 done=1 dirty=0 in_ail=0 pin=0` — release-side is NOT the gap; `mxfs_dir_flush_data_blocks` works). (2) node2 takes EX, adds `f36-50.md5`, destages → LUN leaf complete. (3) node1 RE-ACQUIRES EX; its CLEAN cached leaf (`XBF_DONE`, node1's OLD version) is served, not invalidated → node1 RMWs from the stale base → re-pins leaf missing node2's tail (`DIR-STALE-SKIP blk=0x800000 buf_gen=0 inode_gen=3 pin=1 undest=1`). (4) the peer-modify gen-bump arrives via **async `EVICT-RING-DIRMOD` heartbeat ~2s TOO LATE**, and by then the buffer is re-pinned so even the bump can't evict it. Root: **dir peer-modify invalidation is ASYNC (evict-ring), so node1's EX re-acquire does not SYNCHRONOUSLY invalidate its clean-but-stale cached leaf before RMWing it.** This is the sess43/44 "conversion/RMW divergence" at the BLOCK layer (NOT P43/P43B, which gate on `di_format==LOCAL`; a 200-entry dir is FMT_EXTENTS). Failure signature: `mxfs-drc-FAIL round=1 rank=1 readdir=200 lookup_fail=15 missing=[node2_f36.md5..node2_f50.md5]` — readdir sees all 200 (DATA blocks fresh, droppable→cold-read) but lookup ENOENTs node2's last 15 (LEAF pinned→stale). Verify lookup is `lock_flags=0` so it skips the slow-path acquire (no gen-bump, no eager drain-evict; sess43 comment `xfs_mxfs_dlm.c:5096`).

### The merge dilemma (why every direct fix is hazardous — mapped in [[sess46-dir_reuse-fix-vectors-and-hazards-map]])
node1's pinned in-core block = {node1 mods applied} + {node2 mods NOT applied}. node2's LUN block = {node2 mods} + maybe {node1 mods}. Neither in-core nor a naive disk re-read is a guaranteed superset; a block is a single unit and two divergent-base RMWs can't both survive one overwrite. Each intervention has a proven hazard:
1. **Refresh the pinned block** (clear XBF_DONE + re-read): blocked by the `!xfs_buf_ispinned` guard at `xfs_da_btree.c:3228` — sess64 PROVED relaxing it races writeback/unpin → `xfs_inode_buf_verify` corruption → FS SHUTDOWN (build C7BF9BFD). Pin guard MUST stay.
2. **Destage the pinned block** (force AIL/CIL push): writes node1's stale version over node2's superset → resurrects node2's deleted files (P-LEAFWRITE CLOBBER, write-side confirmed).
3. **Discard the pinned in-AIL leaf** (`xfs_buf_stale` + abort BLI): sess26 GPT — never manually abort a DIRTY/in-AIL BLI → log/AIL corruption. (sess26 fix only stales CLEAN ABA buffers.)
4. **Drain-then-evict on READ path** (log force + wait-unpin): sess97 RULE-0 perf — per-op drain = 5.5x unlink slowdown (28s→155s), reverted.
5. **force_block=1**: fixes dir_reuse but BREAKS dlm_fairness + cache_coherency (shutdown); REFUTED sess44. User forbids flag-flip.
6. **Write-side gen-arm suppress** (extend `mxfs_buf_xfsaild_skip_dir_write` tenure-mismatch arm, `xfs_mxfs_dlm.c:15778-15793`): DETECTOR-ONLY — `buf_gen=0`/unstamped on a LEGIT fresh leaf write → suppression drops the whole leaf (sess23 "suppression-was-corruptor"). Safe arms are NL-released + ABA (`b_mxfs_dir_incarn != live gen`); the failing case is CURRENT-incarnation EX-held → neither fires.

The write-side clobber is REAL, not just read staleness: a `dirwr=1` run fired **P-LEAFWRITE tag=CLOBBER count=2** (in rsync_paired before dir_reuse) — node1 about to write a leaf that drops the peer's committed hashvals ([[sess46-dirwr-confirms-writeside-leaf-clobber-and-fix-plan]]). But `dirwr=1` is NOT a clean repro vehicle: heavy FUA reads perturb timing → test1 SHUT DOWN on crash_consistency via `!(flags & XFS_DABUF_MAP_HOLE_OK)` at `xfs_da_btree.c:2814` → xfs_create → xfs_trans_cancel → Corruption(0x8) (the dir EXTENT-MAP hole — same family, more severe), and blows the rsync_paired 90s window. Use normal runs + the always-on `DIR-STALE-SKIP` probe.

### The suite is BROADLY FLAKY ([[sess46-CRITICAL-suite-is-broadly-flaky-never-17of17-clean]])
3 clean reboot+full `./run.sh 2 tcp` runs on EF006296 (zero code edits) gave 15/17, 16/17, ≤16/17 — each failing DIFFERENT tests (dir_reuse round-1 in two runs but ALL 24 rounds passing in the third; fence_during_write in another). NO clean run hit 17/17. Failures are TIMING/ALLOCATION-dependent races. Implications: the criterion "100% successful" is NOT met by one lucky 17/17; validating any fix needs 5-10+ clean full runs. The user's showstat "17/17" is ACCUMULATED `criteria.json` (single-test re-prep records 1 PASS, leaving stale PASSes) — NOT a clean run; always verify with no-arg `./run.sh 2 tcp` after clean virsh reboot of BOTH nodes and trust only the per-run log. `fence_during_write` is a SEPARATE root (self-fence/shutdown too slow, fired LATE outside the test window → test1 unmounted → contaminates tests 15-17), not dir-coherency. INFRA: `systemd-run --unit=dmesgcap --collect bash -c 'dmesg --follow > /tmp/dfollow.log'` works but /tmp is wiped on node reboot — COPY evidence to `/src/mxfs/tests/_cap/` (NFS=clyde) before any reboot (RULE 3).

### sess47 — read-side relaxation REFUTED, write-side release-flush shipped
Relaxing the read-hook pin guard (`xfs_da_btree.c:3228`) to evict a PIN-TAIL block (`pin=1` but `list_empty(b_li_list) && !dirty && !in_ail`) **REGRESSED uv 1/2 → 0/2 (BOTH nodes fail = data loss)** ([[sess47-uv-pintail-relax-REGRESSES-shared-medium-lacks-superset]]). This PROVES the shared LUN does NOT hold the superset: clearing XBF_DONE discards test1's undestaged (`wseq=0`) deletes and the cold-read returns a NON-superset. **The fix is WRITE-SIDE (get both nodes' dir mods onto the shared LUN), NOT read-side refresh.** Reverted.

Shipped KEEP fix, build **7ED2774139804E86CFD331F** (from EF006296) ([[sess47-FIX-release-flush-undestaged-DONE-dir-block]]): `mxfs_dir_data_durable` (`bad` ~L1069) and `mxfs_dir_flush_data_blocks` (`needs_flush` ~L1249) used `dirty||in_ail||pinned||delwri` and MISSED a dir block that is `XBF_DONE` + clean yet LOGGED-NEVER-WRITTEN (`b_mxfs_logged_seq != b_mxfs_written_seq`). Added `|| ((dbp->b_flags & XBF_DONE) && mxfs_dir_buf_is_undestaged(dbp))`, gated on XBF_DONE so an evict-invalidated stale image (!DONE, sess33) is never re-written. Safe at release (holder owns EX, block authoritative); xfs_bwrite snapshots `wseq=lseq`. Impact: crash_consistency + dir_reuse now PASS; uv still flaky (0/2→1/3 standalone). A `P47-NLSKIP-UNDEST` probe confirmed 0× (NL-skip is NOT the wseq=0 producer). The final sess47 KEEP build **CD292C045FDB4E8EDA0DE18** = EF006296 + this release-flush + a **stale-triggered acquire log_force** (`mxfs_dir_drain_evict_data_blocks` does `xfs_log_force(SYNC)` when `i_dlm_dir_gen != i_dlm_dir_loaded_gen`, not just the trylock-missable any_pinned scan) → reached 16/17 best, DIR-STALE-SKIP eliminated for crash_consistency/dir_reuse.

uv root refined (build CD292C045, always-on probes): uv reads from CACHE (no drop_caches). ASYMMETRY — node2 (LAST modifier) has the superset in-core → PASSES; test1 (earlier modifier) holds a stale pinned in-core block missing node2's later deletes → FAILS. Failing block: `DIR-STALE-SKIP ... pin=1 li_empty=1 dirty=0 in_ail=0 wseq=0 lseq=250` (never written to LUN). `P35-DIRHONOR=3` (test1 DID release), `evict-ring=9`, `P-TCPEX-REACQ=0 / P108=0` (NOT phantom-EX). The dilemma persists under lazy lock caching (`inode_mht_ms=300`, sess34 6s lazy release) + async EVICT-RING + per-op-destage banned (v0.5.1 = 60s on 8.7k rsync, RULE 0).

### sess48 — write-side lost-update FIXED (proven raw-disk), read-side residual = SCST read cache
Write-side root (PROVEN via raw O_DIRECT dir-block parse + cross-node P-WRACT active-count trace): durable WRITE-side lost-update — the outlier's/peer's deletes were committed to log+cache but NEVER destaged; the disk dir block stalled at intermediate active-count (`act=12` = 10 survivors), peer cold-read stale. TWO gaps fixed, build **8B767DA4** (KEEP) ([[sess48-uv-writeside-FIXED-readside-inode-cluster-stale]]):
1. **BLOCK-format deletes**: v0.5.1 had made `mxfs_dlm_dir_durable_signal` PUBLISH-ONLY (no I/O). Re-introduced contention-gated publish-before-notify: in durable_signal, `if (i_dlm_dir_gen>0 && fmt in {EXTENTS,BTREE}) { xfs_log_force(SYNC); mxfs_dir_flush_data_blocks(dp); }`. Caller holds dp `ILOCK_EXCL`+`i_lock` WRITE so mode==EX (NL-skip can't fire) and the block is authoritative. **Do NOT take i_lock (`mxfs_drain_ilock_read`) — caller already holds it WRITE → `down_read_trylock` spins forever = 150s `P132-ILOCK-STUCK` self-deadlock (PROVEN: D-state bash xfs_create→durable_signal→drain_ilock_read).** `gen>0` gate keeps solo rsync (gen==0) free.
2. **SHORTFORM deletes** (dir shrinks block→shortform; last ~10 deletes are fmt=LOCAL, durable_signal no-ops): `mxfs_dlm_dir_inode_durable` (shortform inode-cluster flush) was gated `!i_mxfs_self_created`; the uv dir is `mkdir -p`'d (self_created on one node) yet shared. FIX: gate `(!self_created || i_dlm_dir_gen>0)`.

PROOF write-side fixed: raw O_DIRECT read of the dir inode (both initiators BYTE-IDENTICAL = transport coherent) shows `di_format=01 (SHORTFORM) mode=0x41ed 0 files` — LUN durably correct; drop_caches on outlier → sees 0.

Read-side residual (the last blocker, ~1/3 prod flaky): outlier serves a STALE cached BLOCK-format inode (`incore_fmt=2`) after the peer's block→shortform conversion, cold-reads the freed data block (`act=12`) → "uv got=10". `P-DE-ENTER gen=21 loaded=19` (acquire KNOWS stale) but `loaded` never advances. Added reload-on-gen trigger (`mxfs_dlm_dir_consumer_refresh` + `xfs_dir2_readdir.c`): reload if `MXFS_IF_DIR_RELOAD || dir_gen>loaded_gen` (was flag/evict-ring, laggy); `reload_inode` sets `loaded_gen=dir_gen` on success (L7360, no loop) → uv 0/3 → 1/3.

REFINED to a STORAGE-layer cause ([[sess48-readside-refined-scst-per-initiator-readcache]]): the residual is a **stale SCST per-initiator READ cache**, NOT an FS buffer bug. Evidence (same live diverged dir, build 8B767DA4): raw O_DIRECT dd of the dir inode from BOTH initiators = byte-identical, `di_format=01`, 0 files (LUN correct); the outlier's `mxfs_dlm_reload_inode` read `di_format=2` DURING the test; **`P133-DINO-READSTALE` fired 0×** — P133 compares reload's buffer dip vs a `mxfs_pal_bdev_read_plain_bdev` coherent read, so 0× means BOTH the xfs_buf bio AND the plain-bdev read saw the stale image; the O_DIRECT dd that saw SHORTFORM ran SECONDS LATER. ⇒ SCST serves test2 a STALE cached inode-cluster block for a window after test1's durable write, then refreshes (cache-invalidation latency/TTL). **`fua_disable=0` did NOT help (uv 0/3)** — FUA reads do not pierce this cache (SCST may not honor READ FUA over iSCSI/TCP, or the buf is DONE-cached so the FUA gate at `pal/xfs_buf.c:4173` never runs); `mxfs_fua_disable=1` default (sess45). drop_caches on the outlier → sees 0 (SCST cache had refreshed by then). WHY dirwr=1 makes uv PASS: probe latency widens the window so the SCST cache refreshes before verify reads — pure timing artifact ("instr hides races"). ALWAYS validate uv in production (no dirwr/instr).
