### The real fix — GPT-5.5 whole-inode ACK-based EX handoff [[sess2-ccloop-GPT55-design-whole-inode-EX-handoff-ack-based]]
GPT-5.5 (RULE-5 consult) confirmed the diagnosis and that all single-sided fixes are expected to fail. The correct fix is a combination; four required invariants:
1. **Single-writer**: ≤1 node runs dir2-modifying txns on a dir inode at a time.
2. **Handoff visibility**: before EX moves A→B, every dir-metadata change A committed is on the LUN.
3. **No stale writeback**: after A releases/downconverts, A has NO dirty/pinned/delwri/async-writeable dir buffers that can later overwrite B.
4. **Whole-inode coherency UNIT** = ENTIRE dir inode (data-fork extent map + DATA + LEAF + NODE + FREE blocks + inode core + bmap-btree fork). NOT one dir data block — mxfs's per-block epoch/gen selective evict violates this, the root of the partial handoff.
- **Phantom-EX is a protocol bug — master must be ACK-based**: A owns EX epoch E; B requests → master QUEUES B and RECALL/BASTs A, A stays owner; A finishes bounded batch → freezes mutations → drains active txns → checkpoints ALL dir metadata to LUN → invalidates entire inode → sends DOWNCONVERT_ACK(E); master → epoch E+1 → grants B; B invalidates whole inode → rereads. A may modify after BAST only while master still regards A as owner (no grant to B); A must NOT modify after ACK; B must NOT modify before GRANT(E+1). **Gate dir-modify on an explicit per-lock grant epoch/token (mode==EX && epoch==current_ex_epoch && !draining && !released), NOT on i_dlm_mode==EX / mxfs_dlm_held_mode mirror — mirror is DIAGNOSTIC ONLY.**
- **Merge-at-bio-submit is fundamentally wrong** (explains use_free corruption + leaf holes): XFS dir2 create couples data bytes + free tags + bestfree[] + leaf hash + leaf stale counts + node/free blocks + inode size/extent map + bmap btree + log ordering. A "correct merge" = replaying CREATE/REMOVE/RENAME through XFS dir2 under EX = just serialization. Don't merge dir blocks at writeback; serialize via EX and let XFS dir2 be the only writer.
- **Make it FAST (RULE 0)**: EX delegation/LEASE — owner keeps EX for a bounded batch (max_ops≈128 or 5-20ms), peers queue at master, ~8 handoffs/round not 800. Native XFS also serializes same-dir creates; the win is amortizing cluster handoff cost. Existing mht-batching is this idea layered on a broken (non-ACK, mirror-trusting, selective-evict) handoff.
- **Impl sketch**: per-dir `mxfs_dir_coh{epoch, state(NL/EX_VALID/RECALL_PENDING/DRAINING/RELEASED), active_writers, dirty_dir_buffers}`. `mxfs_dir_write_enter/exit` around every dir2-modifying txn (enter validates epoch token + ++active_writers, blocks if draining). Recall: mark_recall → batch-window → mark_draining → stop new writers → wait active_writers==0 → checkpoint WHOLE dir to LUN (log_force SYNC + AIL push/wait + writeback&wait data/leaf/node/free/core/bmap + blkdev_flush + assert nothing dirty/pinned) → invalidate WHOLE inode → ACK. Acquire: new epoch → invalidate whole inode → reread → EX_VALID. Assert at dir-modify chokepoint (valid EX epoch token else shutdown) and at dir-buffer bio-submit (buffer_epoch==current_owned_epoch else stale-after-release write = fail loud, don't merge).
- The existing release fence (`mxfs_dir_data_durable` + writeback barrier, xfs_mxfs_dlm.c:9605) exists but has a residual gap (a peer add not destaged before handoff → the write-side loss). Audit GAPS next: (1) does the release fence flush LEAF/NODE/FREE not just DATA (write_merge left leaf holes ⇒ likely NO)? (2) does acquire evict drop the WHOLE inode or selective+keep-guarded? (3) is the master ACK-based or does it grant before drain/unlock completes? (4) gate modify on epoch token not mirror.
