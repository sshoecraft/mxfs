## sess18 (ccloop 8ddb16a2) — GPT-5.5 architectural consult (RULE 5: proven diagnosis + 4 refuted approaches + architectural Q) on the concurrent SAME-BLOCK dir RMW durable clobber [[sess18-CORRECTION-transition-redherring-sameblock-rmw-is-root]].

## GPT'S CORE THESIS: the DLM EX grant must be the AUTHORITY for the directory's XFS metadata BUFFER-CACHE ownership, not merely mutual exclusion around code. The forbidden state (= the bug): node A no longer owns the dir, peer B has modified the dir block on disk, but A still has a live dirty/in-AIL XFS buffer/log-item for the OLD image and can later write it (xfsaild/kworker → durable clobber). The KEEP-GUARD (keep undestaged buffer to avoid sess33 corruption) is LOCALLY correct for XFS memory-safety but ARCHITECTURALLY masks a protocol violation: a dirty dir buffer from an OLD dlm epoch must NEVER survive a real lock handoff.

## DO NOT pursue union-merge of stale buffers (GPT explicitly): dir mutations aren't a commutative CRDT (create/unlink/rename/bestfree/leaf-hash/nlink/log-replay ordering); and old committed log items still exist — merging peer dirents into the in-core buffer does NOT neutralize the older committed physical/logged changes (crash-recovery / AIL push can still write stale regions). Merging is only safe via a logical clustered directory-intent log (a much bigger architecture). => abandon the merge family (consistent with my perf-doomed finding).

## THE FIX (invariant + concrete steps):
1. **Epoch-tag every dir metadata buffer** read/dirtied under the dir EX grant: bp->b_mxfs_res = dir_res; bp->b_mxfs_epoch = dir_res->current_epoch. Track per dir-resource: active_tx_count, max_logged_lsn, dirty_buf_list, epoch.
2. **Checkpoint-on-revoke (BAST), STRICT**: freeze new local modifiers → drain active txns → xfs_log_force_lsn(max_logged_lsn, SYNC) → for each protected buffer wait until NOT pinned/dirty/delwri/in-AIL AND logged_seq<=written_seq → THEN xfs_buf_stale + drop → THEN epoch++ (publish in LVB) → THEN release DLM. The current sess97 release fence checks "data_durable" but GPT says that is NOT the same as "no live committed-but-uncheckpointed log item can later write this block" — verify ALL conditions, not just "xfs_bwrite returned".
3. **Epoch-CHECKED WRITE SUBMISSION (the backstop that catches the actual clobber)**: before xfsaild OR any metadata writeback submits a tagged dir buffer to the block layer, assert node_currently_owns_epoch(bp->b_mxfs_res, bp->b_mxfs_epoch); if we no longer own that epoch, BLOCK the write (it would be the silent stale clobber = comm=xfsaild/kworker in P17-CLOBBER-DROP). 
4. **Strict acquire**: cached buffer usable only if clean AND current-epoch; old-epoch dirty buffer = revoke-protocol bug (assert/shutdown rather than silent loss). The keep-guard should keep a dirty buffer ONLY if the lock never left the node (same epoch), NOT across a peer handoff.

## PERF (GPT, for the hot-dir ping-pong worst case): checkpoint-on-EVERY-handoff is fundamental cost IF two nodes ping-pong one block. Mitigations: (a) PR-prefetch then PR→EX convert (read peer block under PR, no I/O under EX — but PR→EX convoy/deadlock risk); (b) cache-to-cache clean-block transfer on demote (sender must have checkpointed); (c) **DIRECTORY-OWNER DELEGATION**: for a hot dir, one node owns the EX and peers FORWARD create/unlink intents to it over TCP (owner does native XFS txns, flushes only on ownership migration) — the scalable answer to satisfy both correctness and ~2x-native perf; make it adaptive (enter delegation when revoke-rate exceeds threshold). (d) pre-grow/index = mitigation not fix.
