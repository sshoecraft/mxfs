# dir_reuse_coherency (sess44-46): epoch signal is dead, loss is intra-block double-alloc, platter-lag + node-isolation are the two real failure modes

Central subject: the long-standing `dir_reuse_coherency` / `cache_coherency` ship blocker at **8/tcp**. The reused storm directory (`ino=131`, rm-rf'd and recreated every round of the barrier workload) loses dirents. Across sess44-46 the diagnosis moved from "acquire-side coherency signal" → "intra-block free-slot double-allocation" → "two distinct multi-modal failures: SINGLE intra-block + MASS node-isolation." Harness: `tests/drc_batch8.sh` (classifies PASS/FLAP/SINGLE/MASS), `tests/drc_detail8.sh` / `drc_cap8.sh` / `drc_cap4.sh` (mechanism capture). Criterion = full 1/2/4/8 tcp 100%.

## The proven loss mechanism: cross-node INTRA-BLOCK offset double-allocation
sess44's P13-NADD/LADD offset trace (build `5F0C1457`, clean reboot) is the decisive name-level instrument; the `dland` write-completion ring is BLIND to equal-count loss (a rising count MASKS the loss — refutes sess41's "no count regression ⇒ never durably added" discriminator). Round-19 dir DATA block `daddr=14652648` received FOUR distinct dirents all at the SAME physical offset `aoff=1600` (rank3 node3_f47, rank6 node6_f47 + node6_f20, rank8 node8_f31=victim), with massive offset-range overlap across nodes in one block. Last durable writer wins; the rest clobbered. The EX-acquiring node runs `xfs_dir2_*_addname` against a base whose bestfree/freespace does NOT reflect a peer's just-committed add → places its dirent at an already-used offset. A "two bursts per rank" pattern (same name added at two offsets in one round) signals a BAST revokes EX mid-create-wave → node re-acquires + re-addname on a fresh/stale base. See [[sess44-PROVEN-offset-collision-double-alloc-aoff1600-four-dirents]]. sess45 re-confirmed at 8/tcp with `P13-COLLIDE ino=131 daddr=14652640 off=2776 our=[node7_f8.md5] disk=[node8_f8.md5]` — node7 placed onto node8's durable dirent, NO doublegrant/stalemaster/flap → DLM serialized correctly; it is acquire-side stale-IN-CORE base while the platter is CURRENT ([[sess45-BREAKTHROUGH-8node-loss-is-intrablock-doublealloc-addname-coherent-fix]], [[sess45-WINNING-config-and-remaining-work]]). This confirms the older `sess11run` root-cause and supersedes the sess41/sess42 count-ring ambiguity.

## Triangulation: the bug is ACQUIRE-side, not release, not DLM serialization (sess44)
Three legs proven by elimination (RULE 4):
1. **DLM serializes correctly.** P44-MODGRANT (build `C532B4BF`→keeper `3062493A`, gated behind instr) logged all 38394 modifies of ino=131 at `mode=5(EX) held=1 exh=1`, zero cached-EX-held=0, monotonic cross-rank realns; the only "interleave" had 1.8-5.8ms deltas = legitimate rapid EX handoff at network-RTT scale, NOT sub-RTT concurrent modify. Refutes double-grant / cached-EX-stale-grant / MHT-window concurrency. MXFS_LOCK enum: NL=0,CR=1,CW=2,PR=3,PW=4,EX=5. (One residual rare `P-DOUBLEGRANT` fired 1× vs 38394 — noted, not the dominant path.) See [[sess44-FINAL-bug-is-acquire-side-stale-read-dlm-serializes-correctly]].
2. **Release durability is sufficient — NOT the gap.** Build `E5382150` added `dir_release_ail_all` (whole-AIL push-to-completion before DLM unlock, all AGs, 20000ms) — the MAXIMAL form of Architectural Invariant #1, closing the scattered-AG (agcount=50) grown-dir escape the per-AG `xfs_ail_push_ag_sync(d_agno)` misses. Still FAILED 0/2: round-1 single-entry loss (node8_f1, durable ENOENT all nodes) persists, clean loss. This redirects ~40 sessions that chased release-drain completeness (sess30/37/39/40/42/43/68/88/98). See [[sess44-DECISIVE-release-completeness-not-the-gap-bug-is-acquire-or-concurrency]].
3. ∴ **acquire-side**: node acquires fresh EX but its first addname reads its OWN STALE CACHED dir-data buffer. The acquire-side hole: `xfs/libxfs/xfs_da_btree.c ~3216` read-time revalidation is gated `((!owned_ex && dp->i_dlm_dir_gen != 0) || mxfs_ex_reval)` → during addname we hold EX (owned_ex=true) → revalidation SKIPPED → stale buffer served as RMW base.

Refuted acquire-side approaches (DO NOT repeat): `dir_coherent_modify=1` CORRUPTS (bmbt_scan/under-lock-disk-read side effects; round20 node6-wide 724/800 + xfs_corruption_error; P11-COHMOD-INVAL fired 0× so its passes were variance). `dir_tenure_evict=1 dir_tenure_stale_bypass=1` CORRUPTS (run3 readdir=500/800 from round1, xfs_dir2_sf_verify shutdown 5 nodes) — it invalidates an in-AIL buffer of UNCERTAIN durability (written_seq stamped at bio SUBMIT not COMPLETION unless `dir_wseq_at_completion=1`) → drops un-landed committed work → structural corruption, same class as sess40 dir_refresh_inplace v2. Per-block invalidation desyncs leaf-hash vs data-entries. Lesson: acquire-side invalidation of in-AIL buffers is fundamentally unsafe. See [[sess44-REFUTED-tenure-stale-bypass-corrupts-fix-must-be-release-side]].

## The epoch / grant_gen coherency signal is STRUCTURALLY DEAD for the reused inode (sess44)
The core sess44 finding: every acquire-side eviction fix (newtenure_evict, prior_tenure_evict, grant_evict, tenure_evict, dir_coherent_modify) is gated on a NON-ZERO `dir_epoch` or `i_dlm_cached_grant_gen` — and for the rm-rf-reused storm dir BOTH signals are 0, so all of them are structurally INERT (look correct in review, never fire on the failing inode). Evidence: P68-EVDECIDE (always-on, in `mxfs_dir_evict_data_blocks`) — the acquire-evict DOES run and examines 12000-24000 cached blocks/rank, but the dominant ~96000 decisions carry `cur_mep=0 valid_epoch=0 b_epoch=0`; `cur_mep = mxfs_v5_dlm_inode_dir_epoch(dlm, ino=131)` returns 0. `mxfs_dir_grant_evict=1` → P36-GRANTEVICT fired 0× because `i_dlm_cached_grant_gen` is also 0. See [[sess44-ROOT-epoch-and-grantgen-both-zero-for-reused-dir-inode-coherency-signal-dead]].

Why zero (design): `dg_grant_ex` (dlm.c:2583) advances the per-resource epoch ONLY on a cross-node OWNER CHANGE (`handoff = last_owner!=0 && last_owner!=owner`, epoch++ at 2667), sets 0 on a fresh/recycled slot (2701/2708), returns current epoch for an existing slot (2674). So epoch=0 on an EX grant = either (a) fresh slot granted before any cross-node handoff advanced it (first node to grab a fresh-each-round rm-rf'd dir), or (b) recycled slot. P44-GRANTDIREPOCH (build `EC24B20897`, dlm.c:2448) proved ~HALF of storm-dir EX grants carry epoch=0: best_mode=5(EX) epoch=15 ~10 samples, best_mode=5(EX) epoch=0 ~9 samples, PR grants epoch=0 (expected). NOT shadow-table overflow: enlarging `DG_SHADOW_N` 512→8192 did not fix it. See [[sess44-FINAL-epoch-unreliable-half-EX-grants-carry-zero-need-reliable-signal]].

The dominant zero source = the FAST-PATH MHT serve. Under `inode_mht_ms=300` batching a node holding CACHED EX serves modify after modify LOCALLY with no DLM round-trip, so `lk->dir_epoch` is never refreshed from the master's advancing epoch. The slow path that would refresh `cached_grant_gen`/`dir_epoch` (`xfs_mxfs_dlm.c:15006`, gated `mode > i_dlm_mode`) never runs on a cache hit. Also confirmed a genuine propagation gap: the MASTER computes epoch correctly (P64-MASTER-HANDOFF fires 128× for ino=131, epoch → 515) but the value isn't stored on the grantee node's local lock. Two sites to fix: (1) grantee LOCK_GRANT handler (dlm.c ~3150-3210, where `lk->grant_gen=grant_gen` at 3187/3204) must also do `lk->dir_epoch=resp.dir_epoch`; (2) master self-grant via local promote_waiters (dlm.c:704-709, stamps grant_gen at 707 but NOT dir_epoch) must call dg_grant_ex. See [[sess44-NEXT-fix-dir-epoch-on-local-promotion-grant-dlm-704]].

KEPT FIX (build `EBBC5A82`, keeper-safe, 2/tcp dir_reuse PASS, no regression): `dlm/dlm.c ~1842` — the lock DOWNGRADE→promote_waiters dispatch was the ONLY one of 4 dispatch sites (1684/1842/2065/3364) dispatching with just `pending_signal_resource` — no `dg_grant_ex` (EX grants got dir_epoch=0) and no `send_grant` to remote grantee (stranding it). Fixed to match the other 3. Genuine epoch-propagation correctness fix, but only MARGINAL (8/tcp run1 PASS run2 FAIL) — the downgrade-promote path is NOT the dominant grant path. See [[sess44-KEPT-fix-1842-dir-epoch-propagation-partial-next-is-fastpath-serve]].

Conclusion of the epoch line: need a RELIABLE per-dir "changed since I last coherently read it" signal that is (1) non-zero from the first grant, (2) advances on EVERY cross-node EX transfer incl fast-path, (3) survives inode rm-rf reuse, (4) does NOT over-fire within one continuous same-node tenure (sess35 trap: mid-tenure epoch 0→nonzero over-fires new_tenure → retires this tenure's own un-landed creates → readdir=0/resurrection). Candidates: a master-authoritative monotonic per-(ino) or per-(physical-daddr) grant counter queryable cross-node at fast-path-serve time; or drop the dir's cached EX entirely between create-wave handoffs (perf cost, correctness-first). Builds: keeper `3062493A` (P44 probe gated, all sess44 levers default-off; == baseline `5F0C1457` for 1/2/4; 2/tcp PASS), then `EC24B20897` (+DG_SHADOW_N 8192 harmless + P44 probe).

## sess45 PIVOT: the real root is FUA-PLATTER-LAG (resurrected from sess36)
sess45 discovered sess44 had chased the epoch theory while ~1 day earlier the project had ALREADY found the root and TWO working fixes ([[sess36-BREAKTHROUGH-platter-lag-target-flush-PASS]], sess36-HEAD-handoff) then lost the thread at a relay. THE PROVEN ROOT (~135 sessions): base-refresh fixes all reread from the PLATTER, which LAGS the shared LIO target write-cache where the releaser's just-drained dirent still sits. The release drain's bio-level `blkdev_flush` is DROPPED by LIO ("LIO target drops SCSI FUA bit"; "pwrite-O_SYNC zero not durable on LIO") → releaser's dir blocks never reach the platter before the peer's FUA read pierces to it → peer RMWs a base missing the entry → durable single-dirent loss on ALL nodes. sess44's "whole-AIL push still loses" did NOT refute this — AIL bio-writes and blkdev_flush both go through the LIO-dropped bio path; only an EXPLICIT SCSI command (WRITE16+FUA or SYNCHRONIZE CACHE) forces the platter.

THE FIX: `xfs/xfs_mxfs_dlm.c:4218` — `int mxfs_dir_release_fua_write = 1;` (was 0). At release-drain (~2428), after the synchronous `xfs_bwrite` of a released dir block lands (werr==0), re-issue the same block as explicit SCSI WRITE(16)+FUA (`mxfs_pal_scsi_write_fua_bdev`) before DLM unlock. Invariant-1 safe (already durably bwrite'd), scoped to released dir blocks. Build `1DD4B2F3`. Two independent 8/8 PASSes (only clean PASS 8/8 in project history): `cap_fw.log` writer-side dir_release_fua_write=1 (6m52s, within RULE-0 480s budget) and `cap_tf.log` reader-side `dir_modify_target_flush=1` (SYNCHRONIZE CACHE, xfs_mxfs_dlm.c ~6185). Chose writer-side (once per released block, not per reader-modify). See [[sess45-RESURRECTED-platter-lag-fix-dir-release-fua-write-default-on]].

Validation: `dir_release_fua_write=1` default → **4/tcp dir_reuse 3/3 PASS** (baseline ~2/24-fail). 2/tcp passes. This is the mode-A single-dirent platter-lag fix. See [[sess45-8node-residual-is-membership-splitbrain-not-platterlag]], [[sess45-progress-platter-fixed-8node-splitbrain-stochastic]].

GPT-5.5 consult (RULE-5) key insight: raw SCSI FUA at release makes the PLATTER current but leaves the XFS in-core buffer DIRTY/in-AIL/pinned (the BLI LINGERS in the AIL — sess37), and `addname_coherent` correctly SKIPS dirty/in-AIL blocks (protecting own work) → node still RMWs a stale base. Ranked fix: DLM EX RELEASE must be a synchronous XFS metadata checkpoint boundary — for every dir DATA/LEAF/FREE block: log-force → unpin → xfs_bwrite(+FUA) → wait IO → ensure NOT dirty/pinned/in-AIL → invalidate → THEN unlock. Enable BLI retirement at release: lever `dir_release_retire_bli` (xfs_mxfs_dlm.c:4143, default 0) now SAFE because the FUA forces the platter current (sess39 refuted retire_bli only because the platter was stale THEN, pre-FUA). DLM EX ACQUIRE = coherency boundary: cold-read current platter for dinode + every dir block before any free-space decision, UNLESS modified THIS tenure (per-tenure tag `bp->dirty_seq == grant_seq`). Sub-case: before `xfs_dir2_sf_to_block` converts, FUA-read dinode; if disk di_gen==in-core i_generation AND disk di_format!=LOCAL (peer already converted) → shortform fork STALE → reload+restart (di_gen disambiguates round incarnations; on-disk dir block header has owner but NO generation). DO NOT union-merge dir blocks or wholesale-adopt-disk-over-dirty. Unifying invariant: "the first modify of any dir metadata object in an EX tenure must be based on a coherent post-grant disk read, unless modified earlier this tenure." See [[sess45-GPT-consult-release-must-clean-not-just-fua-platter]].

WINNING 8/tcp config (build `C074A836` = dir_release_fua_write=1 default + membership beacon + run.sh convergence gate + self-fence): `dir_release_fua_write=1` + `dir_addname_coherent=1` (xfs_mxfs_dlm.c:5363 / xfs_dir2_data.c:1603, FUA-rereads target CLEAN dir block before first add, invalidate+restart if in-core != platter) + `memb_settle_ms=20000` → **3/5 PASS, 0 MASS** (was baseline 0/5). `dir_addname_coherent` was refuted in sess28 ONLY because the platter LAGGED then (no writer-FUA) — now COMPLEMENTARY (writer makes platter durable, reader rereads current platter); never tested together until sess45. See [[sess45-BREAKTHROUGH-8node-loss-is-intrablock-doublealloc-addname-coherent-fix]], [[sess45-WINNING-config-and-remaining-work]].

Two 8-node residuals after the winning config: (1) **dirty-block double-alloc (SINGLE)** — `dir_addname_coherent` SKIPS dirty/in-AIL/pinned blocks (xfs_dir2_data.c:1636); a dirty-stale-across-handoff block (sess61: bufgen < i_dlm_dir_gen) still double-allocs. Fix: extend coherent reread to dirty-stale (bufgen<dirgen) blocks via drain-AT-ACQUIRE, NOT mid-addname. (2) **host-load FLAP (MASS/empty)** — reduced by self-fence + memb_settle but not eliminated. Distribution progression: default `1DD4B2F3` 0/5 (3 SINGLE, 2 MASS) → +memb_settle_ms=20000 0/4 (reduces MASS) → +dir_modify_target_flush=1 combo 2/4 (0 MASS) → +convergence gate `8371542` high variance.

## sess46 REFRAME: 8/tcp is MULTI-MODAL, and MASS = node-isolation WEDGE, not double-grow
Build `A00D8CFE` = sess45 keeper `FB296422` + PROBE-ONLY (keeper-equiv; defaults intact: dir_release_fua_write=1, dir_addname_coherent=1, memb_settle_ms=20000, tcp_death_grace_ms=40000, dir_epoch_adopt=1, dir_epoch_convert_gate=1). Distribution ~20-50% pass, two roughly-equal fail modes:
- **MASS / node-isolation** (half the fails, loses MANY entries): a node goes UNREACHABLE >40s mid-create-wave → peers self-fence → "did not reconnect within 40000 ms — declaring dead, recovering locks" → its in-flight round work never publishes. Captured round 24: node5 lost ~54 (all 50 .md5 + tail f47-f50; f1-f46 present), node6 lost ~22. Membership HAD fully formed (active_count=8) before isolation.
- **SINGLE** (other half, loses 1): node4_f27, node7_f1 (classic FIRST-dirent loss, sess62 sf→block double-conversion family) — the intra-block/grow path. SINGLE loss is the LOSER'S OWN entry (node8 added node8_f49.md5 to its block, block lost the race, entry orphaned).

KEY sess46 corrections to sess45's model (all RULE-4 grounded), see [[sess46-REFRAME-8tcp-dominant-failure-is-node-isolation-wedge-not-doublegrow]]:
1. **Host NOT oversubscribed** — clyde 56 CPUs (load ~4.5), 70GB free, 8 VMs use 32 vcpu/32GB. The >40s unreachability is a genuine kernel-level WEDGE (unbounded sync drain / DLM-EX starvation), NOT CPU starvation. sess45's "host-load FLAP" assumption is WEAK; bumping tcp_death_grace MASKS.
2. **Release DOES drain the dir inode** — dir-EX release calls `mxfs_ail_drain_inode_sync(ip)` (xfs_mxfs_dlm.c ~8724) waiting `!in_ail && pincount==0` (checkpointed AND written-home). So SINGLE is NOT a release-side inode gap.
3. **LIO is WRITE-THROUGH and REJECTS FUA passthrough** (kern.c:502-514): `mxfs_pal_scsi_read_fua_bdev` / `mxfs_pal_bdev_read_plain_bdev` = plain bio read into a DISCARDED kmalloc temp (no buffer-cache effect) → causally INERT except LATENCY. ∴ sess45 `dir_release_fua_write` is likely REDUNDANT and any "FUA read fixes it" = TIMING-MASKING / RULE-0 debt. Masking experiment: a FUA/bio read at dir-grow raised pass rate (keeper ~4-7/8 → +1 read ~6/8 → +2 reads ~5/5) but read+discard is pure latency; removing the reads → failure back to ~75%.
4. **P13-COLLIDE off=64 = FALSE POSITIVE** (ourdir=0 = garbage disk bytes). P46-GROW ourdir=1 = ABA reuse (daddr held a PRIOR round's dir block, owner=131 because dir inode reused) — NOT a same-round double-grow. "Double-grow" is NOT proven; SINGLE is the older intra-block / first-dirent family.

Caveat: P46-GROW (`xfs_dir2_node.c` add_datablk) uses `pr_warn_ratelimited` → DROPS most grows under the 8-node storm → the double-grow-vs-ABA correlation is INCOMPLETE; cannot definitively rule out a same-round cross-node double-grow. NEXT: change P46-GROW to a CAPPED atomic counter (`if (atomic_inc_return(&n) <= 4000) pr_warn(...)`, like P28E) to log EVERY grow, then re-run failround cross-node correlation. See [[sess46-caveat-p46grow-ratelimited-and-single-mode-is-intrablock-loser]].

EXACT MASS death-timing chain (traced through peer.c + kern.c), see [[sess46-death-timing-chain-and-wedge-is-root-of-MASS-isolation]]:
1. A node STALLS (stops servicing/ACKing TCP) under the create storm.
2. **TCP_USER_TIMEOUT=25000ms** (pal/linux/kern.c ~1939, `icsk_user_timeout`) aborts the connection after 25s unacknowledged data (deliberately UNDER the 30s DLM lock-wait timeout, "Bug 105"). Keepalive (10s idle + 3×3s ≈ 19s) is the other detector.
3. Abort → -ECONNRESET → `peer_handle_disconnect` (peer.c:104,140). `mxfs_peer_send` retries 3× (1.7s), does NOT tear down on transient -ETIMEDOUT/-EAGAIN (sess40 flap-fix) — only a HARD error tears down, so the stall must exceed ~25s.
4. `v5_peer_disconnect_cb_tcp` marks SUSPECT + self-fence (freezes EX) + starts `tcp_death_grace_ms=40000` timer. Reconnect within 40s cancels death (but node was EX-frozen, couldn't do its creates).
5. No reconnect in 40s → declared dead, locks recovered → dead node's round work never published = MASS loss. Captured node 1992015415: disconnect t=48.5s → dead t=88.5s ≈ 40s wedge.

ROOT = a >25-40s NODE WEDGE (D-state in an UNBOUNDED synchronous wait). PRIME SUSPECT: `mxfs_ail_drain_inode_sync(ip)` at dir-EX release (xfs_mxfs_dlm.c ~8724) has deadline=0 = UNBOUNDED, waits `!in_ail && pincount==0`; if xfsaild is starved by the create storm it blocks indefinitely → wedge → false death. DO NOT just bound the release drain (sess32 v0.3.141-142 bounded ail_push + proceeded-to-release-on-timeout → violated Architectural Invariant #1 → stale peer reads → REVERTED). The wedge must be eliminated by making the drain PROGRESS (un-starve xfsaild / cheaper handoff), not by releasing early. self-fence + memb_settle(20s) + grace(40s) may AMPLIFY a brief wedge into a cluster-wide EX-freeze cascade. NEXT: LIVE per-node watchdog (dead node's dmesg is wiped on reboot) — kernel thread dumping the blocked task's stack (sched_show_task/dump_stack) when any mxfs DLM/drain op exceeds ~15s, or a survivor-side "last-heard-op from node X" log; confirm whether the wedge is at RELEASE-drain or own EX-ACQUIRE wait. `drc_detail8.sh` now sets `hung_task_timeout_secs=18` per node (catches >18s D-state before the 25s TCP_USER_TIMEOUT kills it) and captures [FAILROUND]+per-node grows+[MEMBERSHIP]+[DEATH/FLAP]+[HUNG-TASK]; hung-task only catches UNINTERRUPTIBLE tasks — for a busy-loop add an explicit in-mxfs "drain spinning >15s" probe in `mxfs_ail_drain_inode_to` (xfs_mxfs_dlm.c ~3164).

## Membership split-brain (sess45 line, feeds sess46 MASS)
master = `active_nodes[hash%count]`. During FORMATION ramp (beacon 5→6→7→8, workload starts before N-member convergence) and mid-run FLAPs, nodes hold DIVERGENT views → two masters → two EX holders → divergent RMW → loss (mostly MASS, early rounds 1-3). `memb_settle_ms=6000` (sess39 gate) is insufficient: it freezes EX for 6s after the LOCAL last-membership-change, but a node's view goes "stable" before it learns of a late-joining peer (lease UDP lag) → proceeds with a stale count. A starved-but-alive node declared-dead by PEERS sees NO change in its OWN view (deferred death) → never freezes → writes as stale master. `P-STALEMASTER-GRANT` (dlm.c:2649) DETECTS this but only LOGS and PROCEEDS to grant. Mitigations built (build `C074A836`): membership beacon (dlm.c update_active_nodes "MXFS-MEMBERSHIP active_count"), run.sh convergence gate (prep waits all N nodes report active_count==N), self-fence (dlm/v5_mount.c stamps `last_memb_change_ms` on BOTH peer disconnect AND reconnect → engages memb_settle EX-freeze locally). Candidate not-yet-done fix: make P-STALEMASTER-GRANT BAIL (return retry, don't grant as non-master) at dlm.c dg_grant_ex ~2643 — watch RULE-0 slowness from self-fence + 20s freeze per flap. See [[sess45-progress-platter-fixed-8node-splitbrain-stochastic]], [[sess45-8node-residual-is-membership-splitbrain-not-platterlag]].
