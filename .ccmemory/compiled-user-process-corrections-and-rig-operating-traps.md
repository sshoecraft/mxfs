Topic: how the user wants work run on MXFS (process fidelity, naming, time, repo hygiene, what is disposable) and the rig-operation traps that follow from ignoring it. Twelve notes folded; all stand as written unless marked superseded.

## Process fidelity

- Execute the user's stated steps, in their order, with their mechanism. Told "commit and push, then `git fetch && git pull` on each node and `make install OVERWRITE=1`", rsync'ing the working tree to "test first" skipped exactly the path under test. If a step cannot be done as stated (permission, rule, missing prerequisite, safety), STOP and report the specific conflict and what would unblock it. Never choose an alternative route. An interrupted instruction is not cancelled by default; confirm. [[feedback-follow-the-users-process-exactly-and-stop-on-a-conflict]]
- Do not propose commits mid-development or in handoffs; commit only when the feature/fix works or the user directs it. ("Why release something that doesn't work?") The global rule bans `git` unless directed anyway. [[Commits only when work is done/working]]
- Read a rule for its purpose before stretching it. "Never download kernel source" means no source trees/tarballs/clones (`/src/linux` exists); installing `proxmox-headers-*`, `linux-headers-*`, `kernel-devel` on a target VM or throwaway build container (`scripts/pve_kbuild_check.sh`) is how DKMS modules are built and is fine. The .deb depends on `proxmox-default-headers | linux-headers-generic | linux-headers-amd64 | linux-headers`. When unsure, ask in one line rather than proposing a workaround such as dropping the container build check. [[feedback-never-downloading-kernel-source-does-not-mean-never-installing-kernel-headers]]
- Do not wait for permission on lab VMs. test1..test32, pve9-1/pve9-2 (libvirt), vstest1/vstest2/alma-97 (vSphere via govc) may be reset, power-cycled, resized or reconfigured whenever a test needs it; report afterwards. Excluded: clyde itself, ESXi hosts, vCenter, the QNAP (its iSCSI service is never restarted). Still check for shared-LUN mounts first when evidence matters. [[feedback-lab-vms-are-disposable-reset-them-without-asking]]
- All libvirt operations use `sudo virsh` (qemu:///system), never bare `virsh`. Session libvirt runs QEMU with CapEff=0, so SCSI passthrough (CAW, PR) fails with "Aborted command, I/O process terminated" while plain reads/writes still work, which makes the failure deceptive. See docs/qemu_direct_caw.md and docs/qemu_tcm_loop_setup.md. [[feedback_sudo_virsh]]

## Naming, time, repo

- A configuration is named only by its full key `<nodes>/<class>/<method>/<attach>` (`2/net/mesh/direct`, `8/disk/caw/direct`); families as patterns (`{2,4,8}/net/mesh/direct`, `*/disk/caw/*`). A lock manager is `net/mesh` or `disk/caw`. Never "2-node TCP", "8-node CAW", "on TCP", or the retired codes `tcp`, `cawd`, `cawp`, `caw`, `tcpmp` (retired in `data/configurations.json`). Applies in chat, README, docs, CHANGELOG, defects, commits, queue files, harness output. Existing code identifiers (`force_transport`, `dlm_caw.c`) are not renamed unasked. Reason: the old codes fused lock manager and attachment and hid that releases were verified on `direct` only. [[user-never-use-the-old-naming-convention-name-configurations-by-their-full-key]]
- Times told to the user are clyde-local (America/Chicago, label CDT/CST), never UTC. Harness logs mix zones: `date -u`, chain logs and criteria.py stamps are UTC; platform round `[HH:MM:SS]` prefixes and `stat` mtimes are local. Convert with `date -d '15:30 UTC' '+%H:%M %Z'`. Internal artifacts keep their existing zone. [[feedback-give-the-user-times-in-local-time-never-utc]]
- `.ccmemory/` stays committed in the public repo; it is a feature (a clone with the ccmemory MCP gets every trap and correction). Never list its removal or gitignoring as hygiene. Consequence: no secrets or test passwords in a memory (they live in `~/.config/mxfslab/secrets`), no site specifics. Root launcher/scratch files remain an undecided hygiene item. [[user-ccmemory-stays-in-the-public-mxfs-tree]]
- Handoff is the ccloop relay (automatic) plus ccmemory, nothing else. Never put rolling state (build srcversion, blocker, findings, next steps) in CLAUDE.md (a ~34 KB awareness line once did, loaded every session), never invent STATE.md, never use CHANGELOG.md for troubleshooting notes. The original note says to write a new `sessNN-*` memory per session; that naming is superseded by the current rule that memories are named for the lesson, never a session or date. The no-CLAUDE.md/STATE.md/CHANGELOG part stands. [[feedback-handoff-state-via-relay-and-ccmemory-never-claude-md]]

## Rig traps

- Scratch-copy build chained `rsync … && cd "$B" && t0=…; make modules`: rsync exited 23 (root-owned `bench.json` and `.xfs_fio_baseline.tcp.scst-fio.json` left by a sudo'd bench), the `cd` was skipped, and the `;` let make rebuild the TREE's `mxfs.ko` mid-queue; one verification chain straddled two srcversions. Fixes: `make -C "$B" modules` or `( cd "$B" || exit 1; make … )`; gate on rsync (`|| { echo rc=$?; exit 1; }`, 23 is not success); `sudo -n chown steve:steve` root-owned leftovers; no command may write the tree's `mxfs.ko` while a queue is deploying it. [[trap-a-scratch-copy-build-chained-with-and-and-after-rsync-falls-through-to-the-tree-when-rsync-exits-23]]
- A `run_in_background` Bash task (and any `run.sh` under it) is killed when ccloop relays the session; the in-flight board row finalizes ABORTED and the crash-test victim is left shut off. Launch any rig chain longer than one turn as `nohup setsid <cmd> > tests/evidence/<log> 2>&1 < /dev/null &` (as `tests/lap_queue.sh` is). It counts zero toward the Stop gate, so keep working in the foreground. Before believing a handoff that says a chain is running, check the log tail and `/proc/<pid>/comm` for the pid in `/tmp/mxfs_run.lock`. After a killed board, start the VM and force a fresh prep. [[trap-a-background-bash-task-dies-with-the-session-at-a-ccloop-relay-so-a-rig-chain-must-be-nohup-setsid]]
- Killing a full_verify/packaged_round process group kills only local ssh clients; remote `apt-get install` of the mxfs .deb (postinst DKMS build) keeps running on every node. Rerun then fails on the dpkg lock in 10 s, POWER=1 powers off mid-DKMS, and `dpkg --audit` shows mxfs "half-configured" on all nodes. Before rerunning: power the set up; on every node check `dpkg --audit` (or `rpm -qa`/`dnf history`), apt/dpkg processes, `dkms status mxfs`; `apt-get -y purge mxfs` a half-configured package and confirm nothing remains. Never edit a script (packaged_round.sh, tcp_peer_freeze_death.sh, lun_pool.sh) that a running full_verify may still read; each step is a fresh bash reading from disk. [[trap-stopping-a-platform-round-leaves-its-remote-install-running-and-the-next-power-off-half-configures-the-package]]
