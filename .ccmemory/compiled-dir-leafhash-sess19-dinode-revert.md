## sess19 (ccloop 8ddb16a2) — 2/tcp shared-dir leaf-hash-vs-data inconsistency

Central blocker this session: `cc_blockdir_probe` (both nodes concurrently create N data + N md5 sidecars into ONE shared dir, `rm -rf`+`mkdir` reusing the inode/daddr each iter) durably "loses" entries under 2-node tcp. Official `./run.sh 2 tcp` PASSES 16/16 the whole session — the bug needs the harsher probe. `crash_consistency` is single-writer (no concurrent same-dir creates), so the official suite has a real coverage gap for this bug ([[sess19-handoff-leaf-hash-fix-plan]]).

### Root: it is a HASH-INDEX inconsistency, not data loss
The "lost" entries are present in READDIR (`ls` shows all 200 = 100 data + 100 md5) but FAIL LOOKUP (`stat`/`statx`/`[ -e ]` → ENOENT). Dirents are durable in the dir DATA blocks (readdir walks data blocks sequentially, sees them); the LEAF1 hash-index block (`xfs_dir3_leaf1`) is MISSING the hash entries for those names → namei hashes the name, searches the leaf, fails → ENOENT. The probe reported "loss" because its `ls … | wc -l` globs via readdir then statx's each; the failing statx drops the name. Verdict is durable/permanent (re-polled 0/10/20/40/60s with `drop_caches` both nodes; stays missing) but it is HASH-INDEX corruption, not dirent/data loss ([[sess19-ROOT-leaf-hash-inconsistency-not-data-loss]]).

Two manifestations, same root: (1) leaf-hash inconsistency (readdir>lookup; iter2/iter14), (2) genuine readdir data-block loss (iter9/iter16, ~164/200). Both from the same keep-vs-adopt tension ([[sess19-refine-clobber-is-content-divergent-not-count]]).

### Diagnosis progression (build order)

Concurrency confirmed via CLOCK_REALTIME (`realns`) ordering — the `[monotonic]` bracket timestamps are PER-NODE and NOT comparable across test1/test2 (different uptimes) ([[sess19-dinode-reverts-to-stale-shortform-confirmed]]).

That shortform-revert was later CORRECTED to a transient: the FINAL dinode is test2's BLOCK format (P133-DIRINO-WR size=8192 nx=3, intact). P62 shortform is a transient of the early concurrent-shortform phase. Inode-cluster-iflush clobber (`mxfs_iflush_cluster_merge_dirs`) exists but was NOT the cause here — P91-RELOAD-PROTECT and P133-DINO-READSTALE both fired 0× for the dir ino; the reload read the genuine coherent disk. The loss is purely the LEAF-block RMW ([[sess19-ROOT-leaf-hash-inconsistency-not-data-loss]]).

**F7911B10 → PROVEN in the act.** P-LEAFWRITECLOBBER detector (in `pal/linux/xfs_buf.c` submit chokepoint; reuses the sess56 coherent plain-bdev read of the same daddr, compares `xfs_dir3_leaf_hdr.count` buffer-vs-disk) caught: `owner=131 daddr=4186520 buf_cnt=140 disk_cnt=202 comm=xfsaild/sda`. **test1's XFSAILD (background writeback) flushed a STALE in-core 140-entry leaf OVER the durable 202-entry on-disk leaf, durably dropping 62 hash entries.** (Detector cosmetic bug: `owner` field read from `dir3_blk_hdr.owner` is garbage for a leaf which uses `xfs_da3_blkinfo`; paired P16-DIRBLK-SUBMIT `owner=131` is the correct dir ino. Why the existing sess17 guard misses it: `mxfs_buf_xfsaild_skip_dir_write` only suppresses a dir-block write when the owner dir is NL-released (`nl=1`) or (detector-only) tenure-mismatched. Here `nl=0` (dir held EX, mode=5) and `tmism=0` (buffer tenure == current EX epoch). The stale leaf is stamped with the CURRENT tenure yet holds STALE content — tenure stamp does NOT detect this; only a CONTENT compare does. How the stale leaf arises: DIR-STALE-SKIP (read keep-guard in `xfs_da_read_buf`) fires on the LEAF block (blk=0x800000) `pin=1 undest=1` — the read refuses to refresh test1's PINNED leaf (the sess64 pin-guard MUST stay, else CORRUPT_INCORE shutdown). So test1 keeps its pinned 140-entry leaf (its own adds, missing the peer's durable entries), then xfsaild flushes it → clobber ([[sess19-PROVEN-xfsaild-stale-leaf-reflush-clobber]]).

Refuted: the READ-side P-LEAFREADSTALE detector (buf<disk at leaf read, in `xfs_da_btree.c` before `*bpp = bp`) fired 0×. The clobber is WRITE-time stale reflush, not read-time count shortfall — the read-side detector was in the wrong place ([[sess19-PROVEN-xfsaild-stale-leaf-reflush-clobber]], [[sess19-handoff-leaf-hash-fix-plan]]).

**8B8D7499** — detectors matured (P16 logs dgen/lgen/pmp; `mxfs_dir_skip_info` extended with dir_gen/loaded_gen). Refinement: the clobber ALSO happens at EQUAL leaf count with CONTENT divergence — iter14 short 193/200, readdir=200, lookup-fail=7 on BOTH nodes, yet P-LEAFWRITECLOBBER fired 0×. A leaf can reach full 200 entries but have hash→data-offset mappings WRONG (hash points to a stale/wrong data-block offset → name mismatch → ENOENT). **A count-only detector/guard is INSUFFICIENT; need an entry-SET (hashval+address) compare.** `pmp` (peer-modify-pending = dir_gen>loaded_gen) is NOT a reliable discriminator (fired FALSE on a failing leaf); gen-based discriminators are weak because the reused ino resets i_dlm_dir_gen low (1-3) each incarnation ([[sess19-refine-clobber-is-content-divergent-not-count]]).

### Why: leaf↔data coherency unit is the WHOLE dir image
Concurrent creates land dirents at DIFFERENT data-block offsets on each node. A leaf RMW from a base with a different data-block LAYOUT writes hash addresses pointing to wrong/stale data entries → lookup ENOENT even at full count. The whole dir image (ALL data + leaf + free + node blocks together) is the coherency unit; piecemeal per-block gen-gated refresh is insufficient. The leaf is deterministically rebuildable from the data blocks — if data blocks are authoritative, rebuild the leaf rather than RMW a stale base ([[sess19-refine-clobber-is-content-divergent-not-count]]).

### GPT-5.5 consults (RULE-5)
Consult #1 (dinode framing): treat the dir DINODE + data fork (di_format, di_size, di_nextents, extent root, if_data) as ONE atomic coherency payload of the directory DLM lock, like a GFS2/OCFS2 inode glock. Protocol: drain dirty dir-inode metadata before unlock; on revoke mark in-core dinode/fork INVALID + invalidate the cached INODE CLUSTER BUFFER at/before unlock; on next EX grant authoritatively re-read the on-disk dinode uncached and rebuild i_df BEFORE any dir op (NO preserve-old-shortform, NO union); write-side allow log/iflush/sf↔block only when EX-held AND current-for-grant (a coherency ASSERTION, not tenure-stamp suppression). NO dirent merge; NO tenure-stamp write-suppression (both refuted). New lever #5: `xfs_iflush_cluster()` flushes MULTIPLE inodes from ONE cluster buffer and submits the whole buffer — when a node iflushes a NEIGHBORING md5-file inode sharing the dir's cluster, its cached buffer's slot for the dir holds the node's stale shortform image → durably writes stale shortform over the peer's block-format dinode. Fix candidates: re-read cluster buffer coherent before iflush submit and patch only this node's dirty inodes; or constrain `xfs_iflush_cluster` to granted inodes; or DLM-lock the cluster buffer ([[sess19-GPT-fix-dinode-coherency-and-cluster-iflush-clobber]]).

Consult #2 (DEFINITIVE fix spec): MXFS's per-buffer `b_mxfs_dir_gen` is a USE/TOUCH stamp (set on cache-hit/!XBF_DONE pre-read/post-read restamp), but correctness needs an IMAGE-ORIGIN epoch — `current-tenure ACCESS != current-tenure CONTENTS`. That is why the clobbering write showed tmism=0 over stale content. The fix ([[sess19-GPT2-dir-index-freshness-barrier-fix-spec]]):
1. Per-directory `epoch` (reuse i_dlm_dir_gen): increment on every peer-modified DLM grant (slow-path acquire); do NOT bump on continued local cached tenure.
2. Per-buffer `image_epoch` for dir DATA-fork index buffers (leaf/node/free AND data): set ONLY at read COMPLETION to the epoch captured at read SUBMISSION (`read_submit_epoch`); NEVER on cache-hit/verifier-success/buffer-lock/trans-attach/`xfs_buf_find`. CRITICAL for late readahead: a read submitted in epoch G that completes after the inode advanced to G+1 must stamp image_epoch=G (stale) so next tenure re-reads.
3. ENFORCE at three points: (a) `xfs_da_read_buf` — image_epoch != dir.epoch + CLEAN → `xfs_buf_stale`+cold re-read; + DIRTY/PINNED/in-AIL → INVARIANT VIOLATION → shutdown OR rebuild-from-data-blocks (NOT a silent keep — the current keep-guard keeping a gen-stale pinned leaf IS the clobber); (b) dirty/trans-join time — never let a stale-image dir index buffer become dirty; (c) bio write-submit chokepoint (final backstop) — stale-image buffer must NOT be written → force_shutdown/rebuild. Do NOT use `buf_cnt<disk_cnt` as policy — a legit REMOVE writes buf_cnt<disk_cnt legitimately and passes the epoch check (count is telemetry only). Remove-safe (policy is image-freshness not count), perf-safe (one cold read per peer handoff per accessed index block), no hot-path dirent merge, no extra DLM acquire, keep the pinned-buffer guard.

Two holes from the spec: **Hole A** (acquire eviction must cover the HIGH dir2 offsets — leaf at 0x800000 etc, walk data-fork extents not i_size) and **Hole B** (late readahead/read repopulates a stale image; stamp from read-SUBMIT epoch; simplest partial close = disable dir-index readahead) ([[sess19-GPT2-dir-index-freshness-barrier-fix-spec]]).

### Hole A RULED OUT; Hole B is the confirmed source
Hole A ruled out: acquire-side evict (`mxfs_dir_evict_data_blocks`, for_each_xfs_iext over the data fork) DOES reach the leaf. P-EVICT-SKIP fired for the leaf daddr (2093296) — MXFS walks extents not i_size, so the 0x800000 logical maps into a normal data-fork extent and coverage is fine. The evict skipped it as done=0/undest=1 (kept). The bug is the leaf getting re-populated/re-modified on a STALE base AFTER eviction, within the tenure. Therefore the fix is Hole B + the dirty/write enforcement, not eviction coverage: `b_mxfs_dir_gen` must be an IMAGE-ORIGIN epoch (set only at read submit/completion, never on touch/cache-hit — `xfs_da_btree.c` currently does touch-restamps, THAT is the bug) ([[sess19-holeA-ruled-out-fix-is-read-image-origin]]).

### NOREUSE proves it is fundamental, not ABA
Added NOREUSE flag to `cc_blockdir_probe.sh` (skips the per-iter `rm -rf`, so each iter's dir keeps a DISTINCT fresh inode — no inode/daddr reuse/ABA). `NOREUSE=1 cc_blockdir_probe 30 50` (build 8B8D7499, dirwr=1) FAILED at ITER 1 with a fresh inode (ino=132): readdir=200, lookup_fail=9 on BOTH nodes; P-LEAFWRITECLOBBER fired 0× (equal-count content divergence). Conclusions: the leaf-hash clobber does NOT require inode/daddr reuse — it is FUNDAMENTAL to concurrent same-dir create (do NOT pursue an incarnation/ABA-specific fix). Fresh dirs reproduce FASTER (iter1 vs reuse-mode iter9-16) because each fresh dir does a fresh sf→block→leaf CONVERSION under concurrency every iter — the conversion is the vulnerable window where the leaf is (re)built from THIS node's diverging data-block layout. The fix MUST be freshness/coherency based, NOT count based ([[sess19-noreuse-confirms-fundamental-not-ABA]]).

### Readahead-disable — partial fix (Hole B confirmed), default reverted to 0
**E99A445B** (deployed both nodes): added param `mxfs.dir_no_reada` making `xfs_da_reada_buf` a NO-OP for multinode shared dirs (S_ISDIR + m_mxfs_dlm + !single_node); defined in `xfs_mxfs_dlm.c` (EXPORT_SYMBOL), gated in `xfs/libxfs/xfs_da_btree.c`. KEEP but **default 0 / opt-in** (was briefly 1, REVERTED).
- POSITIVE — Hole B CONFIRMED: with no_reada=1, NOREUSE `cc_blockdir_probe` (reliably failed iter1 before, 155-198/200) ran 8/8 iters CLEAN. Late-completing dir-block readahead re-populating a stale XBF_DONE image past the acquire-evict IS a real stale-base source.
- INCOMPLETE: a longer reuse `cc_blockdir_probe 30 50` STILL shorted and `NOREUSE=1 15 50` STILL shorted (leaf-hash, lookup_fail>0, readdir=200). Readahead is ONE source, not the only one. Residual = equal-count leaf-ADDRESS divergence. Residual-run DIR-STALE-SKIP fired for blk=0 buf_gen=0 inode_gen=2 in_ail=1 undest=1 — mostly a freshly-ALLOCATED data block (buf_gen=0 = never disk-read) holding this node's unwritten entries during sf→block (benign keep). The subtle residual is the leaf hash→data-block-ADDRESS pointing to the wrong offset because the node's data-block layout diverged from the peer's durable layout during concurrent conversion.
- REGRESSION: `run.sh 2 tcp` with no_reada=1 = 15/16, crash_consistency FAIL (1/2) — single-file-write + node-kill + journal-replay, not obviously reada-dependent, likely flaky/timing but UNCONFIRMED → reverted default to 0 to guarantee no regression ([[sess19-readahead-disable-partial-fix-holeB-confirmed]]).
