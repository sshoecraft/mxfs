## sess22 (ccloop) — dir_reuse readdir=799 diagnosis, datascan leaf-hash heal, remove-reorder shutdown fix

Central topic: the sess22 ccloop attack on the `dir_reuse_coherency` criterion. Net result of the session is three banked keeper fixes in `xfs/libxfs/` that killed the shutdown *cascade* and healed the leaf-hash-hole read path, leaving one narrowed-but-unfixed residual — the `readdir count exp=800 got=799` durable dir data-block lost-update — plus a newly-surfaced flaky AGI-CRC shutdown. The three failed families of readdir799 fixes (write-side, release-side, acquire-side) are all refuted; do not re-try the obvious.

### FIX 1 — remove-reorder eliminates the dirty-cancel SHUTDOWN cascade (KEEP)
Proven (RULE 4) root of the sess21→sess22 8/tcp dir_reuse 0/8 cascade: test1 (rank1, sole rm-rf'er) hit `Corruption of in-memory data (0x8) at xfs_trans_cancel+0x15e (xfs_trans.c:1061)` via `xfs_remove -> xfs_trans_cancel`. `xfs_dir_remove_child` (`xfs/libxfs/xfs_dir2.c`) dirtied the trans (`xfs_trans_log_inode(dp,CORE)` + `xfs_droplink(ip)`) BEFORE calling `xfs_dir_removename`, which then returned -ENOENT (leaf-hash entry present but data-block dirent absent → node1's OWN in-core dir inconsistent, not a concurrent race) → dirty cancel → shutdown → EIO cascade. Fix: reorder the NON-DIRECTORY branch so `xfs_dir_removename` runs FIRST while the trans is CLEAN; a clean-trans -ENOENT cancel is benign. Log dp CORE + ichgtime + droplink only after removename succeeds. S_ISDIR branch keeps upstream ordering. Removed the now-wrong `ASSERT(error != -ENOENT)`. Result: 8/tcp went from 0/8-cascade to all nodes completing 24 rounds with structured FAIL, no EIO. This is THE active win of the session. [[sess22-FIX-remove-reorder-eliminates-dirty-cancel-shutdown]]

### FIX 2 — node/BTREE-format datascan leaf-hash-hole READ heal (KEEP)
`mxfs_dir2_datascan_lookup` (scans coherent DATA blocks when the leaf hash misses) was wired only into single-leaf `xfs_dir2_leaf_lookup` (`xfs_dir2_leaf.c:1814`) and itself bailed on any non-EXTENTS fork. dir_reuse's 800-entry shared dir grows to NODE/BTREE format → its leaf-hash hole was completely unhealed → stat ENOENT on a present file (`leaf-hash lookup_fail`). Three edits, all `xfs/libxfs/`: (1) `xfs_dir2_leaf.c` — relax the format bail, allow BTREE fork when extents loaded (`!xfs_need_iread_extents`), only bail for shortform/local/unloaded-BTREE; made non-static. (2) `xfs_dir2_priv.h` — declare `int mxfs_dir2_datascan_lookup(struct xfs_da_args *)` under `__KERNEL__`. (3) `xfs_dir2_node.c` — on `xfs_da3_node_lookup_int` -ENOENT (after releasing buffers, multi-node only) `return mxfs_dir2_datascan_lookup(args)`; added `#include "../../dlm/v5_mount.h"`. Result: 143/145, `lookup_fail` face ELIMINATED, no shutdowns. `P22-DATASCAN-HIT` fires on heal; `P26-DSCAN-MISS`=98 = genuinely-absent probed names (expected). Caveat: removename for node format still -ENOENT on a leaf-hash hole (no datascan fallback there) → could leave a +1 phantom; consider a datascan-based removename heal if phantom drift persists. [[sess22-FIX-node-format-datascan-leafhash-heal]]

### The residual: readdir=799 durable data-block lost-update — DECISIVELY CLASSIFIED
The dir_reuse verify does `sync; echo 3 > drop_caches` BEFORE the readdir (test line 91), so the failing readdir reads COLD from the shared LUN. drc-CLASS shows every missing entry = `LOOKUP_ENOENT REREAD_MISS` → the entry is **durably absent on disk**, not a reader stale-cache. Loss shape: sometimes a contiguous run of one whole data block's worth (round-2 got=787, missing node8_f40..f47 = 8 contiguous entries; round-1 got=700 = one node's 100 entries), sometimes a single entry (got=799, e.g. node6_f11 / node1_f19). A node durably wrote or KEPT a stale data block (missing a peer's recently-added run) over the peer's durable version = **durable data-block lost-update / whole-block clobber** = the sess11 "committed (rval=0) entry vanishes from the block" family. It is **content-divergent AND count-preserving** — the stale-base RMW REPLACES a peer's dirent, so `in-core < disk` and `disk_cnt > buf_cnt` are both FALSE → every existing COUNT-based guard is blind. [[sess22-readdir799-durable-datablock-clobber-diagnosis]] [[sess22-readdir799-is-content-divergent-clobber-count-guards-blind]]

Probe evidence (build `4E6BD15D`, reverted): P22-DATA-CLOBBER (release-drain bwrite `xfs_mxfs_dlm.c:1616`, count in-core vs disk) fired ONLY on test1 comm=rm (legit rm-rf removes, in-core 1 behind disk) and **0× during the create wave on all nodes** → the loss is NOT a count-reducing release-drain write. P-DATACLOBBER-SKIP (`mxfs_dir_ex_write_guard`, the xfsaild ABA guard at bio chokepoint `pal/linux/xfs_buf.c:2319`, predicate `dir_not_held_ex && disk_cnt>buf_cnt`) fired 0× → never matched (clobber is under-EX + count-preserving). Confirms the sess41 "240× bgen==dir_gen, both tenure tokens read current, write-side guard cannot catch" case.

### The genuine difficulty (sess16/sess69 synthesis)
The loss is a cross-node stale READ-CACHE HIT (fua=0) that poisons the RMW base, but you cannot reliably invalidate it: (a) at acquire the peer's durable write may not be on the LUN yet (racy); (b) at release you can't tell which blocks a future peer will need; (c) at write you can't tell clobber from legit. The in-AIL-undestaged "keep our own uncommitted work" exception is what preserves the stale base, but removing it causes resurrection. Novel directions NOT yet tried (for a future session): (1) EX-handoff barrier ordering — make the release drain provably LAND on the LUN before the DLM grant is handed to the peer, and hard-invalidate by daddr at grant-receipt (tie invalidation to the DLM grant message, not local buffer state) to close the racy-LUN window; (2) per-block durable epoch stamped on the shared LUN so staleness is self-describing (read finds in-core epoch < shared marker → forced miss); (3) re-instrument the exact daddr the clobbering RMW reads its base from on THIS build, confirm the sess69 fua=0 cache-hit is still the mechanism before assuming it. ### Free-slot double-alloc hypothesis — RULED OUT structurally
GPT-5.5 confirmed the "count-preserving content clobber = free-slot double-alloc" diagnosis and gave a false-positive-free structural fix. Mechanism (refined): node-format `xfs_dir2_node_addname` picks the target data block from the FREEINDEX `xfs_dir2_free_t.bests[]` summary (not by scanning data blocks). If that summary is STALE-overlarge (kept in-AIL-undestaged from this node's prior EX tenure while the data blocks WERE refreshed), addname selects a block lacking room; production XFS only ASSERTs `bestfree[0].length>=need` (debug), so it proceeds to `xfs_dir2_data_use_free` and carves the small free region PLUS adjacent live peer dirents = count-preserving overwrite. Fix L3 (structural, no content/count compare, no ghost trap): in `xfs_dir2_node_addname` (`xfs/libxfs/xfs_dir2_node.c` ~1966), after reading the chosen data block + before `xfs_dir2_data_use_free`, verify `data_bestfree[0].length >= need` AND `free->bests[findex] == actual`; if inconsistent, `xfs_dir2_data_freescan` to rebuild bestfree, repair `free->bests[findex]` + `xfs_dir2_free_log_bests`, and if still short RESTART the free-space search — NEVER call `use_free` on a stale summary. Invariant: never `use_free` unless freshly-read `data_bestfree[0].length >= need`. [[sess22-GPT-fix-design-freeslot-doublealloc-readdir799]]

**RESULT — RULED OUT (build `8948C889`, KEEP as harmless):** the Layer-3 guard (`P22-FREESLOT-STALE`) fired **0× on all 8 nodes**, still FAILED. `bf[0].length >= length` was ALWAYS true at addname — the chosen data block always had genuine room. So the stale-freeindex-summary mechanism is NOT the cause; addname writes into a genuinely-free region (no overwrite at add time). Therefore the loss is a **POST-ADD stale-block DESTAGE**: node X adds its dirent to data block B at a real free slot (durable-able), then later a STALE cached copy of B (from before X's add, or a peer's older view) is DESTAGED over durable B → X's dirent erased. Most likely path = xfsaild async writeback flushing a lingering dirty/in-AIL stale copy (sess16 "flushes a backlog of stale shrink" / sess40 "dir-block ABA writeback skip" / sess55 M3 family) at a moment count/EX-gate misses. Next probe (unbuilt): at the single dir-DATA bio chokepoint (`pal/linux/xfs_buf.c`), for EVERY dir-data write (xfsaild AND release), coherent-read the on-disk block and log if the in-core block being written is MISSING any inumber present on disk — a CONTENT non-superset (not a count compare), same-incarnation gated (`b_mxfs_dir_incarn == i_generation`) to dodge the rm-rf ghost — identifying comm (xfsaild vs releaser) and EX-hold state. Likely fix: a dir DATA/LEAF block may only be destaged by the current dir-EX holder (mirror P126 AG-meta / P60 bmbt suppression), with a CONTENT-superset check the missing piece over the incomplete `mxfs_dirskip` / `mxfs_dir_ex_write_guard`. [[sess22-freeslot-guard-0x-loss-is-postadd-stale-destage]]

GFS2/OCFS2 reference (GPT): coherence via glock/DLM lock state, NOT write-time content compare — on demotion flush/invalidate ALL metadata of the locked domain (incl allocator/index blocks); next holder revalidates from disk. → MXFS must treat data+leaf+node+free as ONE coherent dir-mutation domain.
