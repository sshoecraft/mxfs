# dir_reuse_coherency 2/tcp — stale in-core dir inode-fork flush + phantom-EX + iflush-cluster fence

Single failing ship criterion: `dir_reuse_coherency` on the **2-node TCP** transport (16/17, everything else PASS). Repro loop throughout: `MXFS_EXTRA_MODARGS='inode_mht_ms=300 dirwr=1' bash tests/drc_cap2.sh` (clear `dmesg -C` first; logs in `tests/_cap/test{1,2}.log`). **`inode_mht_ms=300` is NOT the code default and must be made default before any real criterion run** — timing depends on it. Marker never written across this whole arc. The workload: each round rank1 `rm -rf D` (frees dir ino=131 + 100 child files) then `mkdir D` + repopulates; ino=131 is reused every round with a fresh incarnation.

## The two-layer bug

This investigation peeled a phantom-EX (mutual-exclusion) bug off the top and then hit the real, deeper root: **a node flushing a STALE in-core dir INODE FORK over the canonical dinode**. They are distinct; the first masked instrumentation of the second for ~90 sessions.

## Layer 1 — Phantom-EX, root-caused to a TCP no-op held-check (build 972D4319)

[[sess-tcp-PHANTOM-EX-root-fix-held-check-was-tcp-noop]] — The decisive infra bug explaining why 90+ sessions missed this on TCP: `mxfs_v5_dlm_inode_held()` (`dlm/v5_mount.c:1350`) returned **1 (held) UNCONDITIONALLY on TCP** (`if (!ctx->dlm_caw) return 1`). TCP keeps grants in the `dlm.c` local mirror, not the CAW slot table, so every phantom-EX probe/fix built on it (sess107 P106/P108, sess8 "double-grant" conclusion) was **inert on the exact transport the criterion tests**. sess8's "P108 fired zero times" was because `held` always == 1.

- **FIX 1 (landed, KEEP):** real TCP held-check — new `mxfs_dlm_held_mode(ctx, resource)` in `dlm/dlm.c` (highest mode this node holds in its local mirror, else `MXFS_LOCK_NL`; read-only, cheap), declared in `dlm/dlm.h`; `mxfs_v5_dlm_inode_held` (via `mxfs_v5_dlm_is_tcp`) now uses it on the TCP path. With the working check, broadened P106 probe fired **45× on node1** for ino=131: `cached_mode=EX on_disk_held=0 unpub=1 pin=0` — node1 RMWs the dir under a locally-granted UNPUBLISHED EX (invisible to DLM) while node2 acquires the empty slot cleanly → both modify → durable lost-update.
- **FIX 2 (landed, KEEP):** broadened the sess107 unpublished-EX backstop (`xfs_mxfs_dlm.c ~8309`) to divert EVERY unpublished dir EX-modify (`pin==0`) to slow-path real acquire, dropping the `(reused_create || !self_created)` gate (an unpublished inode gets no BAST, so `self_created` never clears). **Result: P106-STALE-EX → 0 on both nodes; phantom-EX eliminated.**
- **FIX 3 (landed, KEEP):** un-throttled TCP dir-EX held-verify + re-acquire (`xfs_mxfs_dlm.c ~8246`, "P-TCPEX-REACQ"): published dir, held<EX → demote in-core, slow-path re-acquire.

[[sess-tcp-HANDOFF-phantom-ex-fixed-residual-incarn-aba]] — Handoff at build **6E20D7F9** confirming P106-STALE-EX → 0 and P-TCPEX-REACQ → 0: **phantom-EX (mutual-exclusion violation) ELIMINATED**. All three fixes are real bugs, KEEP. Diagnostics P-DWR/P-DRD (per-block `node1_f` dirent counts in `xfs/libxfs/xfs_dir2_data.c`) now gated `mxfs.dirwr=1`, off by default.

## Layer 2 — the residual: false framings before the real root

Two intermediate framings, both later superseded:

[[sess-tcp-drc-residual-is-divergent-block0-cache-writeside]] (build 5E18ACAA) — framed the residual as a **divergent block-0 cache**: block 0 lives at daddr 112 or 120 (reused across rm-rf+recreate); on-disk content OSCILLATES 83↔100 (`cnt=83` = node2's view missing node1_f1..f18; `cnt=100` = complete), ALL writes by `xfsaild/sda` (the release-fence synchronous `xfs_bwrite` in `mxfs_dir_flush_data_blocks` effectively never fires — block already clean). Concluded failing runs read `cnt=83` durably from disk, i.e. durable on-disk loss. Proposed a GFS2 `go_inval`-style release-side data-block eviction. **Flaky 2 PASS / 2 FAIL with instruments live.**

[[sess-tcp-HANDOFF-phantom-ex-fixed-residual-incarn-aba]] also carried a **prior-incarnation buffer / incarn_aba** framing: node2's round-N buffer at daddr 112 lingers into round N+1 (daddr reused); the `xfs_da_btree.c ~3212` incarn_aba read-hook (`b_mxfs_dir_incarn != i_generation`) is the right catch but (a) TRYLOCK fails (node2's own xfsaild destaging the buffer holds the lock) and/or (b) the invalidate is SKIPPED when the buffer is dirty/pinned/delwri (3220/3228/3229). Candidate: `xfs_buf_stale()` even-if-dirty for owner_aba||incarn_aba, skip only PINNED — but flagged AIL-corruption risk (sess64).

**Both of these were then refuted** by better forensics — the disk is NOT durably divergent; the in-core extent MAP is.

## The real root — STALE IN-CORE EXTENT MAP / inode fork (breakthrough, build 2045BCE9)

[[sess-tcp-ROOT-stale-incore-extent-map-getdents-blk0-daddr]] (2045BCE9 = 6E20D7F9 + P-GROW0 instr in `xfs_dir2_grow_inode`) — **the novel insight 38+ sessions missed: the corrupting object is the dir INODE FORK's extent map, not the dir DATA block.** The signature (readdir=183-188/200, missing EXACTLY node1_f1..f12-17 first data files, no .md5, `lookup_fail=0`) is a map/leaf split:

- `getdents`/`xfs_readdir` iterates the dir's **in-core data-fork extent map** → reads logical blk0 at node2's STALE daddr **112** (cnt≈88) → short listing.
- The leaf/lookup path reads the CORRECT blk0 @ daddr **120** → every listed name IS lookup-able → `lookup_fail=0`.

Decisive forensics: **node1 ALWAYS allocates blk0 @ fsb=15 = daddr 120** (P-GROW0, 24×/run every round); **node2 NEVER allocates blk0** (P-GROW0=0 even on FAIL). Disk @ 120 is CORRECT (P-DRD cold reads = node1_cnt=100) — **refutes the "divergent block0 cache writeside" durable-loss framing** of [[sess-tcp-drc-residual-is-divergent-block0-cache-writeside]]. node2's blk0@112 is a stale prior-incarnation daddr it never reconciles; node2's xfsaild destages that stale buffer during the failing round. P62-RELOAD-FORK-SHRINK shows `incore_gen ≠ disk_gen`, `incore_nx=3 vs disk_nx=1`.

Why the map stays stale: `getdents`/`xfs_readdir` reloads the inode ONLY for SHORTFORM dirs (`MXFS_IF_DIR_RELOAD` consumer ~`xfs_mxfs_dlm.c 11941`); for BLOCK/LEAF dirs it uses the in-core map with NO coherent reload. And `mxfs_dlm_reload_inode` (`xfs_mxfs_dlm.c ~6629` sess33 DIR-GROWTH-REVERT-GUARD) either bails on the bounded `down_write_trylock(&ip->i_lock)` under create contention (~6717, leaves `i_dlm_stale` set) or never runs for getdents. Also: evict-ring dir-modify notify is ASYMMETRIC (node1 receives 0, node2 338) via a producer dedup bug (`disklock.c ~1037`: node2 only ever modifies ino=131 so every DIR_MODIFY after the first is permanently deduped).

## FIX DESIGN — the DLM must fence writeback authority, not just mutual exclusion (GPT-5.5, RULE 5)

[[sess-tcp-FIX-DESIGN-fence-stale-dir-inode-fork-flush]] (2045BCE9) — Root restated: **DLM protects mutual exclusion but NOT writeback authority over the inode fork.** The in-core dir inode fork is a dirty cache line not owned/fenced by the DLM. A node can checkpoint an OLD data-fork extent map (via ANY inode-dirtying: timestamp/size/nlink/dirent/AIL push/undrained release) into the home dinode — it need not allocate blk0, only flush an inode whose cached fork still says blk0→112. Then both nodes reload the now-stale canonical dinode → self-sustaining 112↔120 oscillation.

**Invariant needed: no stale in-core fork may ever reach the on-disk dinode.** A shared dir inode fork may only be flushed if it was VALIDATED under the currently-held DLM lock epoch (GFS2/OCFS2 model: DLM = cache-coherency lock — demote writes-back+invalidates, promote validates/reloads, stale metadata may NOT be written back). Priority plan:

1. **Reload must NOT bail silently** (`mxfs_dlm_reload_inode ~6717`): on contention, block or `-EAGAIN`/restart — never proceed with a possibly-stale fork.
2. **Validate/reload from DLM, not the heartbeat ring** on dir-lock acquire (stamp fork with an epoch; blocking-reload if `local_epoch != current`). Remove correctness dependence on the asymmetric/lossy evict-ring; keep it as an optimization only.
3. **Release/demote flushes the inode FORK HOME** (`mxfs_dlm_dir_inode_durable ~4858`): synchronously iflush+bwrite the dinode/bmbt to its home block before bumping gen/unlock (`log_force` alone is NOT publication for FUA-cold-reading peers).
4. **FENCE the inode flush (the key fix):** for a shared multi-node DIRECTORY inode, refuse to serialize the fork to the dinode unless this node holds the current valid DLM epoch. Else skip/requeue (`-EAGAIN`, AIL-safe) + mark need-reload.
5. **Bump map_epoch ONLY on bmap/incarnation change** (dir block alloc/free, sf↔block convert, extent ins/del, bmbt split, inode reuse) — NOT per-dirent-insert — to avoid the always-reload perf wall (24s→500s flush storms that killed prior attempts).

**Critical caveat (RULE 4):** a naive "holds EX" fence won't work — node2 holds EX during its own release-flush. The fence MUST require the fork was VALIDATED under the current epoch (reloaded since the peer's last write), not merely "holds EX". The Step-2 epoch stamp is what makes Step-4 correct.

## Proving the stale flush is UNDER EX (builds C180A702 → AFE4E833)

[[sess-tcp-FINDING-stale-iflush-is-under-EX-not-NL]] (C180A702 = 2045BCE9 + P-STALE-IFLUSH-NONEX detector in `xfs_iflush` before `xfs_inode_to_disk`) — DECISIVE FAIL run: **P-STALE-IFLUSH-NONEX = 0 on BOTH nodes**. node2's stale fork (blk0→112) is serialized to the canonical dinode **WHILE node2 holds EX** (release-drain / publish-before-notify path), NOT by a background xfsaild flush in NL. => a "forbid flush unless holding EX" fence is INSUFFICIENT. The hard core (circularity): disk oscillates 112↔120; node1 ALWAYS writes 120 (allocator), node2 NEVER allocates blk0 but writes 112 (stale in-core map). To break it, node2 must STOP ever writing 112 → its fork must be reconciled to 120 and an epoch fence must forbid serializing a fork whose loaded epoch != canonical, even under EX.

[[sess-tcp-P-DIRIFLUSH-detector-build-AFE4E833]] (AFE4E833 = C180A702 with P-STALE-IFLUSH upgraded to **P-DIRIFLUSH**, in `xfs_iflush` just before `xfs_inode_to_disk`; logs ino, dlm_mode, incore_blk0_fsb, incore_nx, disk_nx, dir_gen, loaded_gen, relflush, comm; gated dirwr/instr, capped 3000). 3 PASS runs (detector overhead masks the flaky race): node2 P-DIRIFLUSH ino=131 ~90-110× ALL `mode=5 fsb=15`; node1 ~3000× `mode=5 fsb=15`. **dlm_mode=5 = EX on ALL dir iflushes** confirms the stale fork is serialized under EX; a simple "flush requires EX" fence is USELESS. On a PASS node2's fork is CORRECT (fsb=15/daddr 120) — so the fix target: keep node2's in-core blk0 fsb = 15 always. NOTE: the P-DIRIFLUSH iext-scan perturbs timing and masks the race — to CONFIRM the stale flush, run a FAIL and grep node2 for `fsb != 15` under mode=5; consider moving the scan behind a cheaper gate (only log when incore_blk0_fsb differs from recorded canonical). Caution: cannot naively skip only the fork (core `di_nextents`/`di_size` must stay consistent) — skip/requeue the WHOLE inode flush.

## Why the existing merge doesn't catch it, and the CORRECT fence location

[[sess-tcp-WHY-merge-misses-it-EX-held-stale-incarnation-fork]] (AFE4E833) — `mxfs_iflush_cluster_merge_dirs` (`xfs/xfs_inode.c:5071`, sess61) IS the right area. The cluster-false-sharing mechanism: dir ino=131 shares its 64-inode cluster buffer with its regular-file children; node2 creating 50 files constantly flushes dirty CHILDREN via `xfs_iflush_cluster`, which writes the WHOLE cluster — carrying node2's dir slot. That's why the stale dir-fork flush is "under EX of a child" (P-STALE-IFLUSH-NONEX=0; the dir isn't the flush target, a child is). The merge overlays FOREIGN inode slots with the durable on-disk image, but its authority gate (line 5149-5152) treats a slot as authoritative (NOT overlaid) iff `MXFS_IF_DLM_RELFLUSH || (i_dlm_mode==EX && i_mxfs_dirty_seq==i_mxfs_ex_grant_seq)`. node2 IS holding the dir EX and modified it this tenure → its slot is treated authoritative → its stale fork (blk0→112) is written, reverting node1's 120. The gate is "correct" by its own logic but node2's fork is a STALE PRIOR INCARNATION. **Therefore the fix is the RELOAD, not the merge.**

[[sess-tcp-FENCE-correct-location-iflush-cluster-not-iflush]] (refines [[sess-tcp-FIX-entrypoints-inode-flush-fence]]) — **DO NOT fence inside `xfs_iflush` (`xfs_inode.c:4298`)**: returning an error there makes its only caller `xfs_iflush_cluster` ABORT the whole cluster flush and FORCE-SHUTDOWN the FS — `xfs_iflush` has no safe "skip just this inode" return. The P-DIRIFLUSH detector living there is fine for LOGGING, wrong for enforcement. **CORRECT fence point: `xfs_iflush_cluster` (`xfs/xfs_inode.c:5325`), at inode selection BEFORE `error = xfs_iflush(ip, bp)` (~5470)** — skip the stale dir inode (leave it dirty/in-AIL) when its in-core blk0 fsb is not canonical, alongside the existing per-inode skip logic (XFS_ISTALE, lock failures). CRITICAL ADVANTAGE: `xfs_iflush_cluster` is the COMMON path for BOTH the background AIL push AND the EX release-drain (`mxfs_dlm_dir_inode_durable → mxfs_inode_cluster_durable → imap_to_bp → xfs_iflush_cluster → bwrite`), so it covers the actual failing (under-EX) path. **PAIR WITH RELOAD** — skipping a stale flush must trigger/leave a reload (`i_dlm_stale`) that adopts node1's canonical blk0 (fsb=15/daddr 120), else the dirty stale inode lingers in AIL forever (wedge). Alternative deferral point: `xfs_inode_item_push` (`xfs_inode_item.c:740`) can return `XFS_ITEM_LOCKED` to defer the AIL-driven flush, but does NOT cover the release-drain path — so `xfs_iflush_cluster` is more complete.

## Seed synthesis and a self-correction

[[sess-tcp-SEED-ROOT-ino131-free-lost-to-evict-ring-overflow]] (AFE4E833) — stitched the end-to-end chain and proposed a ring-INDEPENDENT primary fix: `grep EVICT-RING-FLAG test2.log | grep ino=131` → **0** (node2 receives INODE_FREE for the 100 file inodes 2097303..2097312 but NEVER for dir ino=131). Proposed mechanism: evict-ring OVERFLOW (`MXFS_EVICT_RING_ENTRIES = 28` in `dlm/disklock.c`; ~101 frees/round ≫ 28). **Primary fix: incarnation-verify on dir-EX acquire (fast AND slow path) and dir lookup/readdir** — compare in-core `VFS_I(dp)->i_generation` vs on-disk `di_gen`; mismatch ⇒ inode reused ⇒ force full reload (`xfs_idestroy_fork` + `xfs_inode_from_disk`) + invalidate cached EX grant + cached dir buffers before any modify. This is GPT-5.5's "validate on DLM acquire, not the heartbeat ring." Entry points: dir-EX fast-path grant (`xfs_mxfs_dlm.c ~8558` P-DIRFASTEX, currently NO incarnation check), slow-path acquire, readdir (`xfs_dir2_readdir.c:631`), lookup.

[[sess-tcp-SEED-correction-notification-not-acted-on]] — CORRECTION to the above: the **conclusion (node2 keeps a stale incarnation of reused dir ino=131) and the fix (incarnation-verify on dir-EX acquire, ring-independent) are CORRECT and unchanged**, but the specific "28-entry ring overflow drops 131" cause is UNPROVEN and probably WRONG: `rm -rf D` removes the 100 files FIRST then rmdir's the dir LAST → ino=131's INODE_FREE is the NEWEST ring entry → overflow would KEEP it (drop oldest = the files). `mxfs_dlm_note_inode_freed` (`xfs/xfs_inode.c:3499`) has NO dir/file guard so 131 IS published. `EVICT-RING-FLAG ino=131 = 0` more likely means the consumer's flag action didn't fire — gated (`xfs_mxfs_dlm.c:11986-11990`) on cached ino=131 being live AND `i_mode != 0` AND `(uint32_t)i_generation <= gen` — so node2 may have cached a LATER incarnation than the freed one, or 131 wasn't cached, or dispatch was missed. Optional next-session probe: capped log in the INODE_FREE consumer (~11981) for ino=131 showing received gen vs in-core i_generation vs the flag conditions. **The fix does not need this — the on-disk incarnation (di_gen vs i_generation) is the reliable signal regardless; the evict-ring is latent, conditional, and asymmetric and cannot be the correctness mechanism.**
