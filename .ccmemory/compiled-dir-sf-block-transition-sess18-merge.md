# sess18 (ccloop 8ddb16a2) — 2/tcp durable directory-entry loss

Central subject: the `crash_consistency` / `cache_coherency` **durable dirent lost-update** on a 2-node TCP-DLM mount. Reproduced live all session via `tests/cc_blockdir_probe.sh` (dir starts SHORTFORM, both nodes concurrently create from empty). Ship marker NOT written — criterion genuinely unmet. Cluster left HEALTHY at baseline (final build `F13B9FB0`, `dir_merge=0 force_block=0 dirwr=0`, both mounted RW_OK). Canaries to watch on any fix: `cache_coherency`, `zero_silent_loss`, `rename_visibility`, `unlink_visibility`, `cross_write_read`.

## Root cause — narrowed, corrected, then reconciled (read in this order)

1. **Write-side, not read-side** [[sess18-readside-ruled-out-writeside-clobber-confirmed]]. Setting `fua_disable=0` (FUA reads pierce SCST cache) STILL lost at iter4 — even faster. The entry is genuinely absent on the LUN; not a stale cold-read (refutes the sess96 read-side theory).
2. **Release path does NOT escape** [[sess18-readside-ruled-out-writeside-clobber-confirmed]]. On isolated failing iters (dmesg cleared at iter start) NONE of the always-on release-escape detectors fired: no `P35F-STALE-RETRY-EXHAUSTED`, no `P-SF-DURABLE-FAIL`, no `P97-RELFENCE-WEDGE`, no `P-DIRREL-DIFFERS`, no shutdown/corrupt. The release fence (`xfs_mxfs_dlm.c` ~3980-4375: drain-until-`data_durable` + flush→stale-loop publish-and-discard) completes CLEAN — the block is written DURABLE-but-STALE (on disk, but content missing peer's entries).
3. **Mechanism**: the ACQUIRE-side keep-guard (`mxfs_dir_evict_data_blocks` ~2044: undurable = `in_ail && !incarn_aba && undestaged`) PRESERVES an undestaged block (our committed-but-unwritten logged entries) that never adopted the peer's entries. Can't drop it (loses logged local work → sess33 `CORRUPT_INCORE` when `XBF_DONE` cleared on a dirty buf); can't write it (clobbers peer).
4. **Narrowed to the shortform→block FORMAT-TRANSITION window** [[sess18-ROOT-NARROWED-shortform-to-block-transition]]. Discriminator experiment `tests/cc_pregrown_probe.sh`: test1 pre-grows a fresh dir to BLOCK format single-node (40 files, sync, dirsize=4096) BEFORE concurrency → **0/15 (then 0/30) iters lost**. The sf-start probe on the SAME build loses ~1/8 iters. Steady-state block-format concurrent create is SAFE; the loss is the sf→block conversion race. Corroborated by `P62-RELOAD-FORK-SHRINK` adjacent-gen format divergence on failing iters (e.g. test2 incore fmt=2/block gen433 vs disk fmt=1/shortform gen434, and the reverse).
5. **Precise fix locus** [[sess18-FIX-LOCUS-reload-selfskip-sf-block-format-upgrade]]: `mxfs_dlm_reload_inode` (`xfs/xfs_mxfs_dlm.c` ~5490), the SELF-SKIP at ~5659-5722. `peer_modified_since_load = i_dlm_dir_gen > i_dlm_dir_loaded_gen` (~5639). In the concurrent race `i_dlm_dir_gen` does NOT advance (it only bumps on OUR BAST-release/reacquire, per sess37/43 — no clean serialized BAST between peer's conversion and our next modify). So `mxfs_dir_disk_superset=FALSE`, and because our shortform dir has in-flight mods the self-skip KEEPS our stale SHORTFORM base → create RMWs it → durably writes a SHORTFORM dinode over the peer's BLOCK dir. `P62-RELOAD-FORK-SHRINK` showed `incore_fmt=1(sf) disk_fmt=2(block)` on ino=131. Proposed test: since a dir never reverts block→sf in a create-only workload, `incore LOCAL while disk di_format >= EXTENTS` is DEFINITIVE proof the peer converted — make `mxfs_dir_disk_superset` also true on that condition (read disk `di_format` before the self-skip decision).

### CORRECTION — the transition framing is a RED HERRING; same-block RMW is the root [[sess18-CORRECTION-transition-redherring-sameblock-rmw-is-root]]
Built fix #1: force new multinode dirs to BLOCK format at mkdir via `xfs_dir2_sf_to_block` (`module_param dir_force_block` default 0; build `F13B9FB0`; wired in `xfs_create` after `xfs_dir_create_child` + resblks bump). Sanity: fresh mkdir → dirsize=4096. But with `dir_force_block=1` the sf-start probe STILL lost durably (run1 iter15 195/200; runA iter2 199/200; runB iter2 199/200 — worse, loses earlier). So sf→block was NOT the root. The pre-grown probe was clean not because the dir was block-format but because test1's 40 single-node entries spread it across MULTIPLE data blocks before concurrency (creates landed in DIFFERENT blocks) AND the vulnerable single-block phase ran single-node. `force_block` makes the dir block-format but EMPTY, so both nodes still hammer the SAME first data block.

**REAL ROOT: concurrent SAME-BLOCK RMW durable clobber during the single-data-block phase.** When all entries live in ONE data block, two nodes concurrently RMW it; one writes a stale base (kept-undestaged block missing peer's entries) over the peer's → durable lost update. Once the dir grows to LEAF format (multiple hash-spread blocks), same-block contention drops and loss stops. `force_block` code is in-tree, GATED OFF (default 0), INEFFECTIVE — do not enable.

### FINAL reconciliation — loss is at INSERT time [[sess18-FINAL-insert-time-loss-reconciliation-and-path]]
Decisive prior evidence (`P35E-DIRWR` with `dirwr=1` on the actual failing iter, from sess17): the lost entry was `node1_f1` (the FIRST file) and it was ABSENT FROM THE EARLIEST captured block image on BOTH nodes; ZERO `nl=1` (NL-released) dir-block writes in the trace. → the dirent is lost AT INSERT TIME (shortform / sf→block-conversion / concurrent-RMW), NOT a stale xfsaild/kworker reflush over a good image. This means the "stale-writeback clobber" framing AND GPT's epoch write-submission guard target a vector that is NOT firing here. Best-synthesis vector: node2 acquires EX with a shortform base MISSING node1_f1 — because shortform dirents are INLINE in the dinode and the sess97 data-block release fence flushes DATA blocks but a shortform dir HAS NONE (dinode-cluster durability is a separate path that can lag) — then node2 adds node2_f1, converts sf→block, and writes a block image without node1_f1. This is the shortform concurrent-insert lost-update family (sess9/13/14), supposedly fixed but still reproducing.

### LIVE THREAD to resolve FIRST next session — maybe transient, not permanent [[sess18-MAYBE-transient-visibility-lag-not-permanent-loss]]
New doubt: the "durable loss" MAY be a TRANSIENT visibility/durability LAG, not permanent loss. With `dirwr=1`, `cc_blockdir_probe` iter2 (ino=1962) reported 199/200 and both recovery probes (pureLUN drop_caches+reread, direx touch+reread) failed at that instant — but minutes later the dir listed 200/200 with NO corrective action. All earlier "durable/unrecoverable" verdicts this session checked pureLUN+direx ONCE at the failure instant and never re-checked seconds/minutes later. If transient, the fix target shifts to COHERENCY PROMPTNESS (dir-EX handoff / writeback-visibility latency) per [[feedback_timing_is_failure]] — still a fail, but not corruption, and it would partly misdirect the whole merge/clobber framing. Verification task `be4d24oir`, `/tmp/transience_test.sh` (relocate to `tests/` per RULE 3 if kept): on first short count, re-polls every 4s for 32s with no further writes — climbs to 200 ⇒ TRANSIENT; still short after 32s + forced dir-EX touch cycle + test2-view ⇒ PERMANENT. **Resolve this before continuing the insert-time path.**

## The merge family — every variant exhausted (do NOT re-try without solving perf)

Progression across builds `B0C5862` → `F5F46A31` → `AA741B4E` (all in-tree, `dir_merge` default 0 = dormant/safe):

- **v1** (per-entry fresh txn+ilock at pre-lock): FS SHUTDOWN — extra dir-EX DLM acquire churn → timeout (sess17).
- **v2** (single-tenure `xfs_trans_roll_inode`, ONE ilock at pre-lock 1305; build `B0C5862`, `dir_merge=1`): SAME SHUTDOWN at iter 1 on ino=131 (hot shared dir) [[sess18-merge-v2-single-tenure-REFUTED-dlm-timeout]]. dmesg: `DLM inode lock failed: ino=131 mode=5 rc=-35` (EDEADLK, handled) then `mode=3 rc=-110` (ETIMEDOUT) ×3 → `unrecoverable ... shutting down` at `mxfs_dlm_ilock_begin+0xbc6` (`xfs_mxfs_dlm.c:8159`, `SHUTDOWN_CORRUPT_INCORE`). Root of failure is NOT txn churn — it is an EXTRA dir-EX acquire on the HOTTEST inode; `mxfs_dlm_ilock_begin` (8146-8161) force-shuts-down on ANY non-EDEADLK acquire failure, and 2-node contention times the TCP acquire out. **Merge-via-separate-lock-tenure is a DEAD END** — the merge, if done at all, must reuse the create's already-held grant.
- **v3 fold-into-create-tp — BREAKTHROUGH (no shutdown) but PERF WALL** [[sess18-foldtp-merge-no-shutdown-BREAKTHROUGH-perf-wall]]. New `mxfs_dir_merge_peer_into_tp(tp, dp, max_ents)` in `xfs_mxfs_dlm.c`: snapshots peer's durable dir DATA blocks from the LUN (caller holds ILOCK_EXCL, no ilock taken), then `xfs_dir_lookup`+`xfs_dir_createname` re-adds ≤max_ents missing peer dirents INTO the caller's tp. Gen-gated: early-return unless `i_dlm_dir_evicted_incarn != i_generation || i_dlm_dir_gen != i_dlm_dir_evicted_gen`. Wired in `xfs_create` (`xfs/xfs_inode.c` ~1571) immediately AFTER `xfs_trans_ijoin(tp,dp,0)`, BEFORE `xfs_dir_create_child`; dp ILOCK_EXCL + ijoin'd + dir-EX grant CACHED → **NO new DLM acquire** (the v1/v2 killer). Removed the old pre-lock `mxfs_dir_merge_peer_blocks(dp)` call. resblks bumped by `MXFS_DIR_MERGE_MAX(=16) * XFS_DIRENTER_SPACE_RES`. **Result: NO shutdown** — proves folding into the create's grant avoids the acquire-timeout. **Blocker is now PERF (RULE 0)**: the merge does DISK I/O (snapshot reads) WHILE HOLDING the create's dir-EX grant → lengthened hot-dir critical section → cross-node EX-handoff starvation (SESS50-STARVE family) → 40s+ stalls, iters 1-2 fast then iter 3 empty. `F5F46A31` (ungated, full-dir read every create) was worse; `AA741B4E` (gen-gated) helped iters 1-2 then wedged.
- **v4 split-snapshot** (I/O at pre-lock, fast re-add under EX): BLOCKED — the create pre-lock hook (`mxfs_dlm_dir_modify_reload_prelock`, `xfs_inode.c` ~1309) runs with NO ILOCK held, so a snapshot there must walk `dp->i_df` extents lock-free (crash-racy) or take its own ILOCK_SHARED (→ PR→EX upgrade churn = same acquire hazard). No clean placement.

**Why merge is perf-doomed** [[sess18-merge-perf-doomed-pivot-to-format-transition]]: the fix burdens the HOT create path (per-create dir-block I/O). RULE 0 = ≤2× native XFS, which does ZERO cross-node coordination. Any per-create peer-state read either crashes (extra acquire) or starves the handoff (I/O under grant). **GPT also refuted merge architecturally**: dir mutations are NOT a commutative CRDT, and old committed log items persist — union-merging peer dirents into the in-core buffer does NOT neutralize older committed physical/logged changes (crash-recovery/AIL push can still write stale regions). Merge is only safe via a logical clustered directory-intent log (much bigger architecture). Merge code stays in-tree, GATED OFF.

**Unexplored perf-viable idea (INVERSE / snapshot-ours merge)** [[sess18-CORRECTION-transition-redherring-sameblock-rmw-is-root]] [[sess18-candidate-fixes-ranked-force-block-format]]: at acquire refresh (`mxfs_dlm_dir_modify_refresh`, `xfs_inode.c:1374`), BEFORE evicting our stale undestaged block, SNAPSHOT OUR in-core entries (a MEMORY read, NO disk I/O), THEN evict (so createname cold-reads the peer's fresh durable image — I/O the create does anyway), THEN re-add our snapshotted entries via createname into the create's tp. Union with NO extra disk I/O. Risk: bounded by count of our entries in the undestaged block; plus sess33 in-flight-log-item tension on evicting an undestaged block (must handle our log items).

## GPT-5.5 architectural consult (RULE 5 satisfied: proven diagnosis + 4 refuted approaches + architectural Q) [[sess18-GPT-architecture-epoch-ownership-checkpoint-on-revoke]]

Core thesis: the DLM EX grant must be the AUTHORITY for the directory's XFS metadata BUFFER-CACHE ownership, not merely mutual exclusion. Forbidden state (the bug): node A no longer owns the dir, peer B modified the block on disk, but A still holds a live dirty/in-AIL buffer for the OLD image and can later write it (xfsaild/kworker → clobber). The keep-guard is LOCALLY correct for XFS memory-safety but ARCHITECTURALLY masks a protocol violation — a dirty dir buffer from an OLD dlm epoch must NEVER survive a real lock handoff. Prescribed invariant + steps:
1. **Epoch-tag** every dir metadata buffer read/dirtied under the EX grant (`bp->b_mxfs_res`, `bp->b_mxfs_epoch = dir_res->current_epoch`); track per dir-resource `active_tx_count`, `max_logged_lsn`, `dirty_buf_list`, `epoch`.
2. **Checkpoint-on-revoke (BAST), STRICT**: freeze modifiers → drain txns → `xfs_log_force_lsn(max_logged_lsn, SYNC)` → per protected buffer wait until NOT pinned/dirty/delwri/in-AIL AND `logged_seq<=written_seq` → `xfs_buf_stale`+drop → `epoch++` (publish in LVB) → THEN release DLM. The sess97 fence checks `data_durable`, which is NOT the same as "no committed-but-uncheckpointed log item can later write this block."
3. **Epoch-CHECKED WRITE SUBMISSION** (backstop): before xfsaild/any metadata writeback submits a tagged dir buffer, assert `node_currently_owns_epoch(bp)`; if not, BLOCK the write (the silent stale clobber = comm=xfsaild/kworker in `P17-CLOBBER-DROP`).
4. **Strict acquire**: cached buffer usable only if clean AND current-epoch; old-epoch dirty buffer = protocol bug (assert/shutdown, not silent loss). Keep-guard should keep a dirty buffer ONLY if the lock never left the node (same epoch).

**Reconciliation caveat** (why this may not fire, per [[sess18-FINAL-insert-time-loss-reconciliation-and-path]]): MXFS ALREADY HAS epoch/tenure write-submission machinery — `P16-DIRBLK-SUBMIT` (`pal/linux/xfs_buf.c`) logs owner/daddr/tenure/epoch/tmism/would_skip/enforce/comm, and a prior "enforce" arm was REFUTED (sess17: tenure-mismatch arm corrupts on tenure=0 fresh/conversion blocks, and `would_skip` fired 0× in the real suite). Since the P35E evidence shows insert-time loss with ZERO NL-released reflushes, the epoch guard targets a vector that is NOT firing. Enforcing the write-skip corrupts legit fresh-block writes ([[sess23-ccloop-suppression-was-corruptor-3of4]]). If `would_skip` fired 0× yet the clobber happened, either epoch tagging is WRONG (not capturing the real handoff) or the clobber carries the CURRENT tenure.

**GPT perf guidance for hot-dir ping-pong**: checkpoint-on-every-handoff is fundamental cost. Mitigations: (a) PR-prefetch then PR→EX convert (convoy/deadlock risk); (b) cache-to-cache clean-block transfer on demote; (c) **DIRECTORY-OWNER DELEGATION** — one node owns EX, peers FORWARD create/unlink intents over TCP; owner does native XFS txns, flushes only on ownership migration (the scalable answer for RULE-0 ~2×-native perf; make it adaptive on revoke-rate threshold); (d) pre-grow/index = mitigation not fix.

## Ranked candidate fixes carried forward [[sess18-candidate-fixes-ranked-force-block-format]]

- **#1 (originally recommended, since undermined by the CORRECTION)**: force multinode dirs to BLOCK format at mkdir to kill the sf→block transition race. Cost is one extra block + a once-per-dir conversion (NOT hot-path). NOTE: `force_block` was BUILT (`F13B9FB0`) and PROVEN INEFFECTIVE — the same-block RMW still loses on an empty block-format dir. Do not re-pursue as-is.
- **#2 (riskier fallback)**: format-upgrade-forces-adopt in `mxfs_dlm_reload_inode` self-skip (~5659) — make `mxfs_dir_disk_superset` also true when incore `if_format==LOCAL` && disk `di_format>=EXTENTS` (block never reverts to sf in create-only = definitive peer-convert proof, independent of the laggy `i_dlm_dir_gen`). MUST handle the in-flight tension: replay our pending dirent onto the adopted block image (a bounded transition-only merge), else lose our own entry / sess33 CORRUPT_INCORE. Regression-prone — the self-skip protects unlink/rename/cross_write_read in-flight work (sess14/49/58/59).
