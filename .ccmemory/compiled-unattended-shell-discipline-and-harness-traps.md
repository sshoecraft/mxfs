Shared topic: what makes an unattended session (or a delegated subagent) stall, mislead, or leak when it drives the shell and the rig. Corrections come first, then traps, then two standing directives.

## Permission prompts stop unattended runs

- Claude Code's safety checker cannot resolve what an inline `bash -c` program executes. A grind subagent ran `bash -c` with a function `run() { local name="$1" cmd="$2"; bash -c "$cmd" ... }` and the run stopped on "This shell -c script runs rm and could not be checked". User: "dont do this again ... write it to a script or something". [[feedback-multi-step-shell-logic-goes-in-a-repo-script-never-an-inline-bash-c-program]]
  - Shell logic beyond a plain command or short pipeline (functions, eval-building loops, `"$@"`, `run()` wrappers) goes in a script under `tests/`, `tools/` or `scripts/`, written with Write and run by path.
  - Every subagent prompt delegating shell work must carry verbatim: "Do not write shell functions or `bash -c` programs; run each command as its own plain Bash call, or write a script file under the repo's tests/ or tools/ and run that." Subagents do not see mid-session corrections.
- Same checker, narrower case: `nohup setsid bash -c 'step() { ...; "$@"; ...}; step scripts/drbd_rig.sh x'` was refused because `"$@"` could be `rm`, and an unattended session cannot approve it. Never execute a variable as the command; use a fixed command with variable arguments (`for s in "self-outage-test" "takeover-test self"; do scripts/drbd_rig.sh $s; done`) and an `if` branch for an env-prefixed variant. Also `cmd && L=x && nohup ... &` backgrounds the whole && list, leaving `$L` unset in the parent; separate with `;`. [[trap-a-bash-c-chain-that-runs-a-function-with-dollar-at-is-refused-by-the-rm-safety-check]]
- The project allowlist matches each command piece on its FIRST word. On it: `tests/:*`, `tools/:*`, `scripts/:*`, `./run.sh:*`, `python3`, `grep`, `timeout`, `virsh`, `make`, `chmod`, `cat`, `ls`. NOT on it: `cd`, `sleep`, `export`, inline `VAR=value cmd`, `( ... ) &` subshells, `zcat`, `strings`, `ps`, `sudo`, `systemctl`. In one session 55 of 57 Bash calls began `cd /home/steve/src/mxfs; ...` and the user, furious, had to approve them by hand. [[feedback-every-bash-command-starts-with-an-allowlisted-program-never-cd-sleep-or-an-env-prefix]]
  - The shell already starts in the repo root; never `cd`. Use absolute scratchpad paths.
  - Rig launches via `tests/mpath/lap_chain.sh laps|row ...`; kernel logs (plain or .gz) via `tools/kgrep.py`, not `zcat | sed | grep | cut`; processes via `tools/mxfs_pgrep.sh`, never `ps`; binary strings via `grep -ac`, never `strings`; no `sudo` for the cold-audit log (world-readable now).
  - Anything multi-step or env-dependent is a script called with arguments. This is distinct from the ccloop delegate hook that refuses an 8th consecutive Bash call.

## Timeouts, parallelism, waiting

- Never reuse a prior session's timeout; derive each as measured infra + 2x native workload. Reusing a 590 s timeout for a cluster reset drew the user's anger. `cluster_reset_n.sh 16` is about 180 s ceiling; tighten after each healthy pass and record it in `tests/criteria/TIMEOUT_BUDGETS.md`. Per-node loops run as backgrounded subshells plus `wait`; audit a script for a serial per-node loop before running it; independent diagnostics run concurrently (parallel Bash calls, background tasks, subagents). [[feedback-parallelize-and-derive-timeouts]]
- Never wait by polling: no `until ... sleep` waiter, no `TaskOutput block=true`, no watching `tasks/*.output`, no backgrounding a batch and polling for a tally. Each poll costs a full request, and `TaskOutput` on a local agent dumps raw JSONL (~15K tokens). Backgrounding itself is fine since the Stop gate counts only an `.output` file held open by a live process, and it blocks (without counting against max continues) while one exists. Fire the Agent or background Bash and do independent work. Ending the turn to wait is valid only for locally live tasks; rig work (32-node `run.sh`, ssh/nohup launches) counts zero and gets the session re-fed "continue". Outside ccloop there is no gate and ending the turn hands control to the user. Nothing required may be in flight at a relay boundary; a task exiting is not a task succeeding, so validate output. [[feedback-never-background-wait-poll]]
- An in-flight Workflow is invisible to the Stop gate (13 of 13 samples read zero live) and dies at the relay: the watcher SIGTERMs the child plus descendants, SIGKILL after 5 s, and auto-compact is disabled in ccloop sessions. Size a workflow to remaining token headroom, have its agents write findings into the repo as they go, and read the durable record with `tools/workflow_journal.py`. Workflow agents inherit the session model, so a 10-agent run costs ~134 requests, not fewer than steering by hand; override `model`/`effort` on mechanical stages. A genuine `run_in_background` Bash task was NOT measured by that probe and does count. [[trap-a-workflow-is-invisible-to-the-ccloop-stop-gate-and-dies-at-the-relay]]
- An outer timeout below the wrapped operation's own bound kills it just before it explains itself. The DRBD boot program ran `mount` under `timeout=180` while the module's own refusal was due at ~184 s (scan ~64 s + fence 120 s). The kill raised `TimeoutExpired` out of `cmd_boot`, bypassed the 6-attempt step-down-and-retry loop, and left the node Primary needing an operator. Sum the inner bounds and set the outer past the sum, say so in a comment, catch the timeout as a failed attempt inside the retry loop, and drive the retry to its second attempt in a test (`SELF_OUTAGE_PEER_PRIMARY=1 scripts/drbd_rig.sh self-outage-test`). [[trap-an-outer-timeout-below-the-wrapped-operations-own-bound-kills-it-just-before-it-reports-why]]

## Shell and process traps

- `grep` in the Bash tool and every subagent is a function over ugrep. `grep -avq PAT` on EMPTY input exits 0 (GNU grep: 1), so a watcher stop condition `grep '^LAP ' summary | grep -avq ' rc=0 '` fired with zero laps and abandoned a 78-minute chain. Counts agree; only `-v -q` exit status differs. Decide on a count (`n=$(... | grep -avc PAT); [ "$n" -gt 0 ]`) or call `command grep`. Scripts run as their own `#!/bin/bash` and do not inherit the function, so test pasted conditions on empty input. sed back-references stop at `\9`. [[trap-grep-in-the-tool-shell-is-a-ugrep-function-and-its-v-q-exit-code-on-empty-input-is-zero]]
- Never edit a shell script while bash is executing it: bash reads by byte offset, so an insertion can resume mid-token and run text nobody wrote. It bit twice (a trap added to `tests/fence_lost_response.sh` mid-lap). Stop the run (`TaskStop`), edit, re-run with a new label; a lap that overlapped an edit is untrustworthy even if it completes. Applies equally to a script being run by a subagent or a `run_in_background` Bash. [[trap-editing-a-shell-script-while-bash-is-executing-it-shifts-the-interpreters-byte-offset]]
- A `call_usermodehelper` child starts with fds 0, 1, 2 closed. `tools/mxfs_lu_reset_witness.py` died on `sys.stdout.write` (CPython leaves `sys.stdout` None), so every upcall timed out at 45 s with `no-report-within-bound` although exec had succeeded. Worse, the first `os.open()` gets fd 0 and the next fd 1; there the first open was the block device being reset, so a later stdout write would have landed inside the LUN. In any program a kernel may exec: fill 0/1/2 first (`os.fstat`, else `/dev/null` + `dup2`), write the load-bearing report channel before the console, each in its own try/except, and treat `UMH_WAIT_EXEC` success as only meaning `execve` worked. Fixed as `secure_fds()` and verified by `tests/lu_reset_witness_probe.sh`. [[trap-a-kernel-upcalls-child-starts-with-fds-0-1-2-closed-so-a-helper-dies-on-its-first-print-and-its-first-open-becomes-stdout]]

## Standing directives

- `state.md` is a deprecated pre-ccloop handoff artifact. Do not read, maintain, or write it at relay boundaries even when a run prompt says "read state.md"; handoff is ccloop's resume summary, durable knowledge is ccmemory, build history is `CHANGELOG.md`, defect state is the defect queue. Deleting the file is the user's call. [[state-md-deprecated-do-not-maintain]]
- The lab node root password lives only in `~/.config/mxfslab/secrets` (mode 600), never in prose, docs, comments, tables, examples, awareness docs, memory bodies, handoffs or commit messages. The repo is PUBLIC and four doc files had leaked it, three of them sentences asserting it was never committed; prose is where the leak lives, not code. Write "password from the lab secrets store" and point at `tools/mxfs_secrets.sh passfile`. Before each commit grep the tree and `git diff --cached` for the password and for sshpass litter (directories with spaces or shell metacharacters in the name). A separate defect, calling `mxfs_sshpass.sh` without the passfile arg writing password files named after the command, is already fixed by a guard in `secrets_passfile()`. [[feedback-never-write-lab-password-into-any-file-in-tree]]
