## dir_reuse single-dirent loss (readdir 799/800): the sess32-33 diagnosis arc

Central subject: the lone ship blocker for `dir_reuse_coherency` at **8 nodes / TCP** (1/2/4 nodes = 100% PASS). The `rm -rf` + recreate churn on a NODE-format directory intermittently (~1 of 2 iters) drops exactly one dirent: `readdir=799/800`. Two sessions chased the mechanism through a false "duplicate/ghost buffer" theory to the proven root: a **clean, in-AIL, canonical dir-DATA buffer carrying a STALE BASE, reflushed by xfsaild while the node holds EX**, clobbering a peer's durable add. `owned_ex` disables the read-time gen/epoch staleness machinery, so the stale base is served to the RMW and never refreshed.

### Proven mechanism (final, sess33)
On a losing iter the loss-write is the CANONICAL dir buffer (not a ghost), state:
`DONE=0 in_ail=1 dirty=0 pin=0 delwri=0 lseq==wseq bgen=0 held_mode=5(EX) comm=dd/bash kind=data disk_extra=1 incore_extra=1 — MERGE-NEEDED`.
`mxfs_dir3_disk_has_extra_inum(incore,disk)` counts disk inums absent in-core: `disk_extra=1` = disk holds a peer's dirent we lack; `incore_extra=1` = we hold a dirent disk lacks. Writing our in-core block reverts the peer's dirent. Symmetric across nodes → ping-pong, last writer wins, the other's dirent is the durable 799. Sequence ([[sess33-PROVEN-clean-inAIL-stale-reflush-not-ghost]]): tenure N addname (POST-RMW superset, durable at release) → BLI written (wseq=lseq) but LINGERS in the AIL clean → peer acquires EX, adds its dirent to disk, releases → we re-acquire EX → xfsaild reflushes our lingering STALE clean buffer → clobbers the peer's add. The release fence's `data_durable` check waits for durability/!pin/!dirty but does NOT RETIRE an already-written clean BLI from the AIL.

### Why owned_ex is the enabling root cause
The stale base survives to the RMW because the entire read-time staleness machinery is gated OFF under EX ([[sess32-PROVEN-owned-ex-disables-gen-mechanism-wmerge-root]]): `xfs_da_btree.c:3154` bumps `dir_gen 0→1` only `!owned_ex`, so an EX holder keeps `dir_gen=0`; a stale cached base has `bgen=0`; `bgen==dir_gen==0` → treated FRESH → served. Consequences observed: `DIR-STALE-SKIP` (xfs_da_btree.c:3427) fires **0×** under EX; acquire-evict SKIP branch (`mxfs_dir_drain_evict_data_blocks`) sees only `done=0` blocks (342/342), so no kept-stale `done=1` block at acquire. Design premise "EX grants authority, not freshness" (xfs_da_btree.c:3176 gate `!owned_ex`) is exactly wrong for cluster coherency; GPT-5.5 framing: EX acquisition must be a cache-coherency boundary (GFS2 glock model), revalidating cached metadata under EX using FUA reads (LIO target: plain bio is per-initiator-stale; FUA is coherent — xfs_mxfs_dlm.c:17904).

### sess32 progression (what was ruled OUT with evidence)
Chronology of refuted leads — DO NOT retry:
1. **NOT mechanism A (stale RMW base at create).** POST-RMW probe (right after `xfs_dir_create_child`, `mxfs_dir_postrmw_probe` ~xfs/xfs_mxfs_dlm.c:5723) shows the in-core block is ALWAYS a superset of disk (`disk_extra=0`) on losing iters, all 8 nodes ([[sess32-DECISIVE-A-vs-B-late-destage-toctou]]). The RMW base at create time is fresh; the block goes stale AFTER release, and xfsaild re-flushes it.
2. **v2 reconcile gen-filter INERT** ([[sess32-reconcile-v2-inert-gen-filter-dropped]]): build 8E4B6D08 `dir_stale_reconcile=1` → `P31-RECONCILE` fired 0× while the SKIP flag-set (`P-DE-BLK disp=SKIP`, sets `MXFS_IF_DIR_DATA_STALE`) fired 160-270×/node. Cause: between acquire-SKIP and reconcile the block is re-read and re-stamped `b_mxfs_dir_gen=i_dlm_dir_gen` (xfs_da_btree.c:3426), so `bgen==dir_gen` even though disk carries a peer add. Dropped the `b_mxfs_dir_gen != i_dlm_dir_gen` clause → broad reconcile of every DONE data block (build F36166BE) — still `P31=0` at acquire-SKIP (SKIP blocks are `done=0`, flag-set needs `XBF_DONE`). Note: `P31-RECONCILE` print gates on `dirwr=1`, NOT `dir_writeprobe`.
3. **EX-side epoch revalidation REFUTED — REGRESSED to 798** ([[sess32-ex-epoch-reval-REFUTED-798-regression]], [[sess32-FIX-ex-side-epoch-revalidation-build-5BD1CE5F]]): build 5BD1CE5F wrapped the read-time invalidation with a new gate `((!owned_ex && dir_gen!=0) || mxfs_ex_reval)` where `mxfs_ex_reval = dir_tenure_evict && m_mxfs_dlm && !single_node`, needing BOTH `dir_tenure_evict=1` + `dir_evict_prior_tenure=1`. It PROVABLY fired under EX (`P16-PREREAD-EPOCHSTALE ino=131 buf_epoch=131 master_epoch=137`, previously 0×) but `dir_evict_prior_tenure`/epoch_stale BYPASSES the in-AIL undestaged keep-guard (xfs_da_btree.c:3373) → invalidated a block holding OUR OWN un-destaged dirent → re-read from disk dropped it while the AIL item still destages → readdir=798 (TWO lost) at round 1. This is the sess43 hazard. RULE: do NOT bypass the in-AIL keep-guard under EX.
4. Other sess32 refutations: read-side/acquire-refresh (base already fresh at RMW); create-time reconcile/`dir_merge` FUA (FUA reads lag platter, miss the add); destage byte-graft (bnobt double-free SHUTDOWN, no txn leaf/freeindex update); suppress MERGE-NEEDED (loses OUR entry); all param tuning (full proven config still loses).

### The "mechanism B" red herring (sess32 → refuted sess33)
sess32 leading hypothesis was duplicate/ghost `xfs_buf` per daddr ([[sess32-mechanismB-duplicate-dir-buffers-per-daddr]], [[sess32-HEAD-handoff]]): `P-POSTRMW-BP` logged **8 DIFFERENT bp pointers for the SAME daddr (12559416) in ~100ms** (one per create), all `disk_extra=0 done=1 lseq=0 wseq=0`. Interpretation was that a stale prior buffer INSTANCE destages while we hold EX on a fresh one. CAVEAT flagged immediately: the heavy per-create probe (xfs_buf_incore + full raw disk read) AMPLIFIED loss to 786/800 (vs keeper 799) = timing perturbation. sess33 built the decisive low-perturbation probe `P-WGHOST` (`mxfs_dir_canonical_buf_ptr()`, RCU-only rhashtable lookup, pointer compare) at the write chokepoint: **P-WGHOST = 0 on all 8 nodes** on losing iters ([[sess33-PROVEN-clean-inAIL-stale-reflush-not-ghost]]). The destaged bp IS the canonical rhashtable buffer. Mechanism B REFUTED — the "8 bp in 100ms" were different buffers across TIME/rounds, never two simultaneously for one daddr.

### sess33 progression (writer proven, 5 more fixes refuted)
- **DECISIVE writer identity** ([[sess33-HEAD-handoff]]): `P-WMERGE-STACK` (dump_stack at the loss-write) shows the durable-loss write IS the EX-RELEASE FENCE DRAIN's synchronous bwrite: `xfs_buf_submit_bio ← xfs_buf_submit ← xfs_bwrite ← mxfs_dir_flush_one_daddr+0x201 (xfs/xfs_mxfs_dlm.c ~1751) ← mxfs_dir_flush_data_blocks ← EX release path, comm=dd`. Gemini correctly predicted the release-fence drain as the writer. This satisfies Invariant #1 (drain before unlock) but drains a STALE BASE.
- **5 fixes REFUTED** ([[sess33-fixes-refuted-zombie-bli-reenters-after-evict]]):
  1. `dir_write_merge=1` (write-chokepoint union graft `mxfs_dir3_data_writemerge`, pal/linux/xfs_buf.c:2215, build C0F7D69E): WORSE — round1 `readdir=803/800` over-count on all nodes, round2 `readdir=0` + `lookup_fail=58` ([[sess33-REFUTED-dir-write-merge-overgrafts-803]]). Over-grafts a stale prior-incarnation name, leaf hash desyncs. Matches sess21 offset-collision / sess26 dir_merge rc=-110 family. DO NOT enable.
  2. write-chokepoint reflush-skip v1 (EX+clean+destaged, no !DONE key): INERT, gated `mxfs_dirskip_enabled` (default 0), P33=0; the iter-3 fail was flaky variance.
  3. reflush-skip v2 (+`!XBF_DONE` key, enforced): CATASTROPHIC `readdir=0/1` (empty dir). Legit dir writes are frequently `DONE=0` at submit (FUA/`_XBF_FUA_FRESH` read cycle + acquire-evict clears DONE every tenure) so !DONE-skip drops needed writes. **Write-side suppression of dir buffers corrupts in ALL forms (sess23 confirmed).**
  4. release-side GFS2 demote-stale (`dir_release_stale`: `xfs_buf_stale` clean dir buffers at EX release after data_durable): FIRED (`P33-RELSTALE` 18-115×/node) but loss PERSISTS — wrong boundary, the stale buffer re-enters cache+AIL during the NEXT tenure.
  5. acquire-evict zombie-retire (`dir_zombie_retire`: `xfs_buf_item_done` the in_ail+destaged BLI in `mxfs_dir_evict_data_blocks` !undurable branch): SAFE but fired 0× (`P33-ZOMBIE-RETIRE=0`); `P68-EVDECIDE` never shows `in_ail=1` at evict time.
- **Key narrowing** ([[sess33-fixes-refuted-zombie-bli-reenters-after-evict]]): the zombie BLI's `in_ail=1` arises BETWEEN acquire-evict (which soft-clears `DONE=0`) and the write. During the EX tenure a `DONE=0` soft-cleared buffer is RE-LOGGED (BLI→AIL) on its STALE content WITHOUT a fresh re-read, then written = clobber. This contradicts sess32 POST-RMW superset and must be reconciled. Candidate re-log sites: (a) freescan/bestfree/leaf re-logs an existing block via `get_buf` (no read); (b) modify re-reads a different block while the soft-cleared one is re-logged stale by freescan; (c) BLI lingers across release because `data_durable` bmap-walk misses the block (stale in-core extent list).

### Why write/drain-side union-merge is a fundamental dead end
([[sess33-union-merge-ambiguous-acquire-refresh-is-root]]) `dir_reuse` does concurrent CREATE **and REMOVE**. A "disk-only dirent" (on disk, absent in-core) is AMBIGUOUS: either a peer's ADD we never saw (graft it) or OUR REMOVE the peer's disk copy hasn't caught up to (do NOT graft). Name/inumber alone cannot distinguish — so ANY write-side merge over-resurrects removed dirents (the observed 803 + leaf desync). Merge/graft at write is architecturally unfixable.

### The convergent root fix (both sessions agree): acquire-side stale-base refresh
Because the node holds EX for the whole tenure, the peer's missing dirent (`disk_extra`) was necessarily added in a PRIOR tenure, before our acquire. The acquire path MUST FUA-refresh every dir DATA block from the coherent LUN BEFORE the first RMW, so our adds graft onto the peer's CURRENT image → block becomes a true superset (`disk_extra=0`) → the release drain write is correct, no merge, no ambiguity. The refresh machinery EXISTS (`mxfs_dir_evict_data_blocks` soft-clear + `xfs_da_read_buf` gen-invalidation, gated by `i_dlm_dir_gen`/epoch/`owned_ex`) but MISSES this block. Open investigation for next session: instrument WHY `disk_extra>0` survives to the drain — is `i_dlm_dir_gen` not bumping on the relevant handoff? is read-path invalidation gated off under ILOCK_EXCL/`owned_ex` on the modify path? is the bmap stale so the block isn't enumerated? Add `P-RMWBASE` (disk_extra of the base right before addname) at the FIRST RMW of each block to catch the stale base at its source. This is the sess20-26 dir-gen/epoch coherency family.

**Complementary release-side backstop** ([[sess33-PROVEN-clean-inAIL-stale-reflush-not-ghost]], [[sess32-DECISIVE-A-vs-B-late-destage-toctou]]): at EX release after `data_durable`, RETIRE every dir data/leaf BLI for the inode from the AIL (not just wait for durability) so no clean already-written buffer can be reflushed after a peer supersedes the block (GPT-endorsed, mirrors sess26 clean-ABA detach+stale). Since all bad writes are `dirty=0`, the release fence's durability wait is insufficient — it must remove the clean BLI. Option B alternative: chokepoint suppress+invalidate of CLEAN divergent reflushes SYMMETRIC on all nodes (each node's active-tenure release already made its dirent durable), preferred over A to avoid release-path deadlock — but heed sess32's "suppress relocates loss" (verify not asymmetric, don't suppress active dirty writes). Deadlock caution per RULE 2: push/retire AIL not holding buffer locks/txn/ILOCK; default-off param, validate then default.
