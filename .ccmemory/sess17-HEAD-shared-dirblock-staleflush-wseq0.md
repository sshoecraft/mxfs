## sess17 HEAD (ccloop). `./run.sh 2 tcp` = 15/16 (FULL clean run), crash_consistency SOLE fail (1/2). Marker NOT written. Build F605BA70D8FBE572C257831 deployed both nodes (= baseline coherency logic + new dir-block detector tooling, dirskip default 0). Functional fallback = sess16 baseline 895603D7.

## THE CRITERION TEST: tests/suite/crash_consistency.sh (category=suite, NOT tests/criteria/*). Each node writes 50 data files + 50 md5 into ONE shared dir, sync, drop_caches, then EVERY node re-reads EVERY node's md5 from the LUN. A durably-lost dirent → FAIL. Reproducer = tests/cc_blockdir_probe.sh (faithful; fails in <6 iters w/ dirwr=1). NOTE: crash_consistency PASSES in isolation (4/4) but FAILS in the full suite — the failure needs CUMULATIVE cluster state (prior tests free+reuse daddrs/inodes), which the probe forces with mkdir+rm-rf per iter.

## ROOT (RULE 4, PROVEN via P-EVICT-SKIP + P35E-DIRWR, build F605BA70, dirwr=1 dirskip=0):
- Loss = 2 ADJACENT data dirents (e.g. node2_f15+f16, test2's OWN), durably gone from BOTH nodes. md5 sidecars all survive. => a durable WRITE of a stale dir-DATA-block image dropped them.
- SMOKING GUN: the shared dir data block **daddr=496** shows `lseq=24/26 wseq=0 undest=1 in_ail=1 done=1` on BOTH nodes (P-EVICT-SKIP ino=131). i.e. the block was READ (done=1) then logged ~25× locally but **written_seq NEVER advanced (wseq=0)** = never destaged. `mxfs_dir_buf_is_undestaged` = (lseq!=wseq) = true → the refresh keep-guard (mxfs_dir_evict_data_blocks ~2043, `in_ail && !incarn_aba && undestaged`) KEEPS each node's stale base.
- MECHANISM: under the tight 50-file loop both nodes accumulate un-written logged mods to the SAME block 496. The cross-tenure refresh (mxfs_dlm_dir_modify_refresh / consumer_refresh) correctly refuses to discard a node's own un-written mods (undest=1) — but that base is ALSO missing the PEER's committed entries (never merged). The node then DURABLY FLUSHES its stale base (release drain or xfsaild) over the peer's durable f15/f16 → durable lost update. This is the continuous-churn trap [[sess10-gpt-verdict-serialize-tenure-not-epoch]] (sess10 REFUTED a naive FUA-compare-reload for exactly this reason).

## WHY wseq=0 (the key open sub-question): mxfs_dir_flush_data_blocks (release drain, ~1184) DOES xfs_bwrite each needs_flush block (which would set wseq=lseq at the chokepoint). Yet block 496 shows wseq=0 at refresh. So either the release drain is NOT running for this tenure/dir, OR block 496 is not cached/needs_flush at drain time, OR the un-written mods are added POST-release (cached-lock window). sess16 P16-RELEASE-UNDESTAGED claimed undest=0 at release — CONTRADICTED here; re-verify. **NEXT decisive instrument**: per-daddr name-set superset detector at the bio chokepoint (sess16-NEXT idea) — track max dirent-name-set written durable per daddr; if a new write DROPS a previously-durable name, log P-CLOBBER w/ comm/lseq/wseq/undest. comm=xfsaild vs comm=release-drain vs comm=dd identifies the clobber vector. Then fix: either (a) ensure release drain truly destages (wseq=lseq) ALL dir blocks so next acquire cold-reads clean, or (b) block-level 3-way merge (analogue of sess14 shortform sf_merge) when a node's base is undestaged AND peer advanced the gen.
