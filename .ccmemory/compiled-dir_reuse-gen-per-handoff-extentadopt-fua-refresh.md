## sess26 (ccloop) — dir_reuse_coherency 8/tcp durable lost-update

Single remaining blocker for `./run.sh {1,2,4,8} tcp` 100%: **dir_reuse_coherency at 8/tcp**, ~50% flaky in the keeper. 1/2/4 tcp always PASS. Symptom: durable lost-update in a shared reused directory — `readdir=799/800` (single-entry loss) or whole-block loss (~16-20 contiguous dirents = one dir DATA block), all `LOOKUP_ENOENT + REREAD_MISS` (durable, not transient). This article traces the sess26 hunt from evict-side refutations through the read-side dead-ends to the working two-lever fix, plus the residual.

### 1. Evict is NOT the problem — the RMW base is cold-read stale post-evict [[sess26-DECISIVE-evict-always-evicts-base-is-postevict-stale-read]]
Always-on P68-EVDECIDE instrumentation on a real keeper loss run proved the modify-path evict (`mxfs_dir_evict_data_blocks`, `dir_force_evict=1` default) **ALWAYS evicts cached DONE blocks including in-AIL**: `undurable=0 (evicted)=2559`; every `undurable=1 (kept)=3441` was `in_ail=0 dirty=0 pin=0 delwri=0 done=0` (a no-op keep of an already-uncached block). **ZERO `undurable=1 in_ail=1`.** This REFUTES sess25's "stale base is a kept in-AIL-undestaged block" read-side keep-guard theory. The RMW base is cold-read AFTER eviction. Two new candidate loci: (1) FUA-platter-lag, (2) write-side re-dirty then xfsaild destage. Refuted band-aids/dead-ends: MHT tuning (`inode_mht_ms` 600/1200 pass 1× then fail — reduces race-window frequency, never 100%); `dir_tenure_evict` (readdir=0, syncs valid_epoch mid-tenure, evicts un-drained work); `dir_newtenure_evict` (readdir=0 — clearing XBF_DONE on an in-AIL-UNDESTAGED block corrupts in-core; the keep-guard is load-bearing for buffer integrity, not merely conservative).

### 2. FUA-platter-lag refuted; clobber locus = xfsaild push of invalidated buffer [[sess26-target-flush-refuted-clobber-is-xfsaild-push-of-invalidated-buffer]]
`dir_modify_target_flush=1` (build A04C8631): after the modify-path evict, `blkdev_issue_flush` (SYNCHRONIZE CACHE) the shared target so a peer's release-drained dirent reaches platter before the post-evict FUA read. → STILL FAILS (readdir=799, 353s). The peer's release-drain DID land on platter; staleness is not FUA-vs-write-cache lag. Converging mechanism (sess25 PROVEN + sess26): the clobber WRITE is the EX holder's own xfsaild AIL-push of a dir buffer whose XBF_DONE was cleared by the modify-evict (invalidated, stale b_addr) while its BLI lingers in-AIL (mode=5/EX, in_ail=1, bdirty=0, comm=dd/bash, stale=0, EQUAL-count DIFFERENT-fingerprint). sess33 trap: clearing XBF_DONE on a dirty/in-AIL buffer lets xfsaild bwrite the stale invalidated image over the peer's newer durable block. AVOID the sess25 defer (`XFS_ITEM_LOCKED` pins log tail → DLM starvation shutdown).

### 3. FUA-refresh-destaged candidate: PASS-8/8 but not durable [[sess26-CANDIDATE-FIX-fua-refresh-destaged-dir-block-lingering-bli]]
Proven finer root: `mxfs_buf_read_fua` (pal/linux/xfs_buf.c:2741) **P91-FUA-SKIP-LOGGED** skips the FUA SCSI pierce whenever `b_pin_count>0 || !list_empty(b_li_list) || b_log_item`, returning existing in-core b_addr as authoritative. For a DESTAGED multinode dir block (pin==0 && `b_mxfs_logged_seq==b_mxfs_written_seq`) the BLI merely LINGERS (no un-checkpointed work) yet P91 serves the stale prior-tenure RMW base AND keeps the stale b_addr xfsaild later destages. FIX (`dir_fua_refresh_destaged`, build FD17BF68): before the P91 skip, if lever && dir3 data/block/leaf1/leafn ops && destaged → `goto do_fua_read`. pin>0/undestaged still hard-skip (protects un-checkpointed work, the sess90 bnobt lost-removal concern). Result: PASS 8/8, 352s (== keeper speed).

### 4. LEAF refresh causes DABUF_MAP_HOLE shutdowns; DATA-only is shutdown-safe but loss persists [[sess26-fua-refresh-data-only-no-shutdown-but-loss-persists-base-is-undestaged-or-plainbio]]
`dir_fua_refresh_destaged=1` LEAF+DATA (FD17BF68): 1st run PASS, validation FAIL with **140× XFS_DABUF_MAP_HOLE (xfs_da_btree.c:2876)** — FUA-refreshing a fresh LEAF exposes data-block offsets the STALE in-core data-fork extent map can't resolve → hole → shutdown (sess20 family). DATA/BLOCK-only (build 8B331267): **SHUT=0** but durable lost-update PERSISTS (readdir=798/799). So the stale base at the clobber is NOT a destaged-lingering-BLI block. It is either (a) in-AIL-UNDESTAGED (this node already stacked its own un-checkpointed entry on a stale base — the destaged-gate correctly refuses to refresh it; too late, the stale read happened before the first modify), or (b) served by a PLAIN BIO reading SCST's per-initiator stale read cache, never entering `mxfs_buf_read_fua`.

### 5. PIVOTAL — loss is WRITE-side; FUA-piercing every read still loses [[sess26-PIVOTAL-loss-is-write-side-not-read-fua-pierces-still-loses]]
Build BDD8DDD9: P26-FUAREFRESH fired 8000× (capped) — all dir DATA base reads redirected to real FUA SCSI pierce (fresh-from-LUN, bypasses SCST read cache), most `has_bli=0` plain-destaged. P91-FUA-SKIP-LOGGED fired only 4×, ALL `ops=xfs_inode` → P91 essentially NEVER skips dir DATA/LEAF (the "P91 keeps stale dir base" theory is WRONG). **Loss STILL occurs** (readdir=799). Definitively eliminates the entire read-side family (re-read/evict/FUA). The read gets the peer's fresh image, the create adds correctly, then a STALE in-core copy is DESTAGED (xfsaild background push) over the peer's fresh disk. Re-confirms sess25's write-side clobber. Proposed next fix: SUBSET check at the bio write chokepoint (skip+invalidate, not defer).

### 6. dataclobber detector: create-phase loss is INVISIBLE to write-time disk compare [[sess26-dataclobber-detector-catches-only-legit-removes-creastage-loss-invisible]]
`dataclobber=1` detect-only run (CA135E9C) on a real whole-block loss (round1 node2_f13..f32.md5 = ~20 entries = one DATA block, detected at round-1 verify BEFORE any rm). P-DATACLOBBER-SKIP: ALL 13 hits were `comm=rm` legit round-END removals (buf_cnt=disk_cnt-1, a single-entry remove, NOT a clobber) — this is the false-positive that makes dataclobber≥2/subset-guard catastrophic. ALL had `bufgen==dirgen (379==379) stale=0` → **`i_dlm_dir_gen` does NOT advance across a fast-path EX handoff**, so any gen-based (bgen<dirgen) guard is BLIND. ZERO create-phase (comm=dd/bash) clobbers logged despite inspecting every write. Decisive: when the clobbering node submits its stale block, the peer's about-to-be-lost entries are NOT yet on the LUN → disk_cnt not > buf_cnt → not flagged; entries land, then the stale image destages over them in a later interleave the one-shot read can't see. This is why ALL write-side submit-time guards fail (racy disk read) AND all gen-based read-side guards fail (gen frozen). The only non-racy point is the SYNCHRONOUS RELEASE FENCE while the node holds EX and disk is quiescent.

### 7. Subset-guard refuted — suppression is the corruptor [[sess26-subset-guard-refuted-racy-false-positive-fix-must-be-release-side]]
`dir_subset_guard` (build CA135E9C): `mxfs_dir3_disk_has_extra_inum()` (pal/linux/xfs_buf.c) real dirent subset test wired into the dir write chokepoint — for a CLEAN (bdirty=0) in-AIL xfsaild push, same-incarnation, if disk has an inum the in-core lacks → suppress write + mark read-path refresh (gen=0, KEEP XBF_DONE; v1 that CLEARED XBF_DONE hung ioend → 110s barrier-timeout abort). v2: ran 24 rounds, no shutdown, 199s, STILL FAIL 0/8 AND caused **readdir=0 on test5 rounds 16,18** (whole dir read empty) — the guard fired and SUPPRESSED LEGIT WRITES. Structural (matches sess16/sess23): comparing in-core to a plain disk read at bio-submit is RACY — a peer's concurrent/in-flight write makes disk look like it has "extra" inums, false-positive-suppressing a needed write. **Suppression is the corruptor.** The fix is NEITHER async read NOR async write chokepoint — it must be the synchronous release fence (bast_process / `mxfs_dir_flush_data_blocks` before DLM unlock). Concrete release-side direction (for later): at EX→NL release, after draining each dir DATA block durable, DETACH/complete its BLI so xfsaild can never re-push it (P126/P60 `xfs_buf_stale` pattern, xfs_buf_item.c:608/638 — GPT verdict: safe ONLY on a clean !dirty !undestaged !pinned buffer, gate strictly).

### 8. PROGRESS — dir_gen_per_handoff: whole-block loss FIXED, single-entry + extent-map hole residual [[sess26-PROGRESS-dir-gen-per-handoff-wholeblock-to-single-but-dabuf-hole]]
PROVEN root of the frozen-gen bug: the fast-path EX-grant epoch-handoff gen-bump (sess64 `mxfs_dir_epoch_adopt`, xfs_mxfs_dlm.c ~12119/12156) is CAPPED by `if (i_dlm_dir_gen <= i_dlm_dir_loaded_gen) i_dlm_dir_gen++`. After a reload sets loaded_gen=dir_gen, the FIRST handoff bumps to loaded+1, but 2nd..Nth intra-round handoffs fail the cap → NO further bump → cached blocks stay `bgen==dir_gen` and alias a peer-superseded image as fresh (the proven `bufgen==dirgen==379` whole-block clobber). FIX (`dir_gen_per_handoff`, DEFAULT 0, build 965BDBD3): uncap at BOTH fast-path sites (grant_handoff + epoch_adopt) — `if (mxfs_dir_gen_per_handoff || dir_gen<=loaded_gen) dir_gen++`. Now `i_dlm_dir_gen` advances on EVERY cross-node handoff → read-path pre-read invalidation (bgen<dir_gen, xfs_da_btree.c:3363) fires every handoff. SAFE: master epoch advances only on real cross-node handoff, never while holding EX continuously (no spurious mid-tenure re-read). Result 8/tcp: whole-block loss (~20 entries) → SINGLE-entry (readdir=799). SIDE EFFECT: **511× `!(flags & XFS_DABUF_MAP_HOLE_OK)` (xfs_da_btree.c:2876)** — per-handoff re-reads visit dir offsets beyond this node's STALE in-core extent map (a peer grew the block count; gen-bump refreshes CONTENT but not the extent map / if_nextents). Non-fatal but trips dmesg_clean; slower 497s.

### 9. BREAKTHROUGH — dir_gen_per_handoff + dir_modify_extent_adopt fixes whole-block AND hole [[sess26-BREAKTHROUGH-genperhandoff-plus-extentadopt-fixes-wholeblock-and-hole-residual-single-entry]]
Working combo (build 965BDBD3, both levers as `MXFS_EXTRA_MODARGS="dir_gen_per_handoff=1 dir_modify_extent_adopt=1"`, both still DEFAULT 0):
- `dir_gen_per_handoff=1` — fixes whole-block + most single-entry data-block clobber (per-handoff read invalidation).
- `dir_modify_extent_adopt=1` (existing, was default 0 / sess68 "MAPDIVERGE=0 at modify-prelock"): on an epoch-advanced modify, FUA-check dinode + adopt peer's grown extent map. With per-handoff re-reads now pulling NEWER leaves, the map DOES diverge → adopt closes it → **DABUF_MAP_HOLE 511→0**. (Without adopt, gen_per_handoff alone gives 511× holes.)
- **DO NOT add `dir_modify_extent_reload`**: gen_per_handoff + adopt + reload → HOLE=0 BUT round-14 BLOWUP (readdir=501/800 lookup_fail=229). extent_reload (sess14-flagged) reverts blocks. Use extent_ADOPT only.

Results (clean reboot each): Run A **PASS 8/8, 354s** (normal speed, HOLE=0, all 24 rounds, 0 failrounds). Run B **FAIL** — single round-13 `readdir=799/800` durable single-entry loss on ALL nodes, HOLE=0, 355s. So whole-block clobber + DABUF hole are FIXED; **residual = occasional SINGLE-entry lost-update (the long-standing readdir=799 deepest face). NOT 100% yet.**

### Residual single-entry — open hypotheses (RULE-4, next session)

Needs the FREE-SPACE accounting stale for one node (data-block bestfree[] OR the node-format FREE block, `xfs_dir3_free_buf_ops`) OR an epoch-handoff-detection MISS (a rapid same-pair handoff whose epoch granularity under-fires so one handoff isn't invalidated).
