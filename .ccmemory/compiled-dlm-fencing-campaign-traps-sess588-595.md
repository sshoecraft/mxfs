Continuation of [[compiled-dlm-fencing-campaign-traps-sess578-586]]: the join/takeover/recovery/fallible-acquire campaign, sess588-595. Defects touched: D-0953 (departure-worker vs unmount race), D-0958 (fallible acquires + transport repair), D-0960 (joiner racing a dead-authority takeover pass) / D-0352, D-0961 (ledger-grant precondition), D-0962 (recovery-completion pacing), D-FOREIGN-REPLAY-UNGATED-IMAGES.

## sess588 — two consult rulings, one harness-shape correction

**D-0960/D-0352 ruling** ([[ruling-joiner-during-authority-takeover-priority-service-progress-aware-wait-staged-mount-abort]]): a joiner's root-inode request can land on a page whose dead-incarnation authority a live bootstrap is mid-takeover on (~15k pages, minutes); the 60-retry loop exhausts in ~18s and the XFS classifier fail-stops the node. Verdict: ship all three fixes together, not A alone.
- A — priority takeover of the requested page, only where page order is incidental; re-validate authority/incarnation per request; dedupe/bound/fair-schedule; receive thread only enqueues.
- B — a distinct retryable "authority transition" outcome (not a blanket REMASTER exemption), gated on a validated dead/settled predecessor + live certified bootstrap, progress causally tied to servicing THIS page (stable pass identity + monotonic completed-transaction count, never heartbeats/ACKs/max-index), 30s no-progress watchdog classified as retryable stall, never corruption.
- C — explicit mount-abort lifecycle state covering all acquisition paths: not-VFS-published does not mean no distributed effects (heartbeat membership, slice/PR registration, replay may already be on the LUN); staged abort in protocol order; never unregister protection while writes/recovery obligations remain.

**D-0958 remainder ruling** ([[ruling-transport-repair-reconnect-protocol-and-the-remaining-non-fallible-acquire-class]]), after open/getattr/read/readdir were made fallible: a per-peer transport-repair worker triggers on no-receipt-for-15s while membership says live (a QUEUED acquisition is not a broken-socket signal). Reconnect must NOT be "close socket, redial, replay pending" — messages already in the receiver's workqueue survive a socket close, so a naive receiver can double-grant; requires stable logical identities, an idempotent master state machine, grant identities on release/convert/recall, coordinated stream cutover, bidirectional reconcile, watermark-retired tombstones (never TTL). K consecutive NOT_FOUND is diagnostic/rate-control only, never authorizes a new identity. Remaining fallible boundaries enumerated: write path's initial IOLOCK ride, a namespace op that has only reserved (not logged) a transaction, writeback-before-I/O (retain/redirty, never clear dirty as success), AG acquires only on a clean unwindable prefix.

**D-0953 harness-shape trap** ([[trap-a-peer-death-takeover-runs-inside-recovery-and-put-super-waits-for-it-so-it-cannot-reach-the-worker-teardown]]): a virsh-destroy-then-unmount repro put the ledger takeover inside the peer's `recovery-complete` path (`put_super` waits it out), which proved nothing about the actual race — the departure WORKER's takeover passes run OUTSIDE recovery, in three shapes: `v5_settled_incarnation` (sole survivor's own-predecessor takeover on lone remount, ~13s/1000 pages), clean peer goodbye/handoff, and the post-departure orphan sweep. Deterministic repro: `tests/depart_takeover_unmount.sh DEATH=ghost`. Found downstream: a joiner mounting during the orphan sweep exhausts root-inode retries and self-shuts-down (feeds D-0960); every departure queues a sweep, so the first full sweep is followed 2s later by an empty one — read the sweep lines' `tail -1`, not the first, or leftover pages score as never taken.

## sess590-592 — three sequential D-0960 harness traps

- [[trap-a-control-laps-recovery-step-deploys-the-trees-build-and-destroys-the-control]] (sess590): the death-arm control lap re-formed the fleet via `module_swap_deploy.sh`, which installs the TREE's `.ko` (the fix) — one lap destroyed the only old build available for a control, and the single iteration didn't even reproduce the recorded shape (locality is a hash of per-incarnation node ids; A-mastered vs B-mastered are different code paths, `LOCALITY=` must be named and repeated to `WANT=`). Fix: run the control before building the fix, or save `mxfs.ko.backup` first.
- [[trap-a-refused-mounts-command-return-time-includes-its-unwinds-cluster-acquires]] (sess591): a refused mount's command wall-time includes its unwind (`xfs_log_mount_cancel → …→ xfs_log_quiesce`), which itself takes a non-fallible cluster acquire (SB summary cover) that can be parked behind the very takeover the mount was refused for. A harness asserting on refusal must time the dmesg refusal line, not the command return, separately from the unwind's own bound. Same shape hits the D-0959 join path: the bootstrap's join-install freeze quiesces through the same summary lock.
- [[trap-a-lone-mount-takes-no-grants-so-it-writes-no-ledger-pages-for-a-takeover-harness]] (sess592, D-0960/D-0961): the TCP authority ledger records GRANTS; a lone mount with no peer modifies everything at NL with no grant, so nothing it creates leaves a ledger record. A harness precondition of "many ledger pages under node X" requires taking the grants under two members, then a clean peer departure (handoff) with X leaving last — creating/reading files alone proves nothing. Check `cand=` on the first lap of a fresh filesystem before trusting an in-flight window measured on an aged one.

## sess593 — five traps in one session (D-0960, D-FOREIGN-REPLAY-UNGATED-IMAGES, rig ops)

- [[trap-a-lap-window-opened-before-the-incarnation-under-test-counts-the-previous-laps-pass]]: the harness's kernel-log window opened at the lap marker, not the incarnation under test, so it counted ~7000 activations and quoted the summary line of the PREVIOUS takeover pass still finishing. General rule: a count's window must open at the boundary of the thing measured (incarnation/pass/mount), never the lap start. Fix: a second marker written just before the mount under test.
- [[trap-a-gate-fail-closed-against-a-different-report-is-open-to-no-report-and-a-zero-is-a-report]]: the settle gate was fail-closed only against a peer beaconing a DIFFERENT view; a peer beaconing view `{0,0}` ("none installed" — a real, deliberate statement) was filtered out by two layers as "no report" (hash-0 treated as unset), so the gate opened unconfirmed at 18-20s and every subsequent acquire got DEFERred until the retry budget or 30s watchdog killed the mount. Pattern: a sentinel value the SENDER emits deliberately is data — audit every filter between sender and predicate for a sentinel drop before trusting a "nobody objected" gate.
- [[trap-a-kill-list-from-mxfs-pgrep-includes-the-shell-that-ran-it-and-kills-the-harness-mid-lap]]: `for p in $(tools/mxfs_pgrep.sh 'pattern'); do kill $p; done` matched the Bash tool's own `sh -c` chain (its command text contains the pattern) and killed the invoking shell first, skipping cleanup and losing a scored verdict 2 minutes from completion. Fix: record the lap's PID at launch (`echo $! > …pid`) and `kill $(cat …pid)`, or just wait for the WANT= match to end the lap.
- [[trap-a-cleanly-released-tenures-image-is-outside-the-replay-window-assert-the-marker-not-the-redundant-count]] (D-FOREIGN-REPLAY-UNGATED-IMAGES): measured that a cleanly released tenure's directory-block image is never inside the victim's replay slice window — the release drain writes the block, the AIL delete moves the tail, the marker's forced commit carries that tail past the image, by construction. `REDUNDANT_CLEAN >= 1` cannot be a pass requirement for a clean release; assert the marker was seen (`relmarks >= 1`) and nothing refused, report REDUNDANT_CLEAN as information only. Also: `P-RMAN-EVAL hits >= 1` is vacuous on this window (no image consults the manifest); `mxfs_relmark_publish` prints only on FAIL, success is a counter only visible on the survivor.
- [[trap-a-recovery-completion-that-lands-after-the-watch-window-reads-as-never-completes]] (D-0962, spans into 594): a 60s restore-wait and 96s capture were both shorter than the actual ledger-page takeover inside recovery-complete (~13ms/page × 7984 pages = 103.8s), so D-0962 was filed as "recovery never completes." Reading the survivor's live dmesg past the watch window showed `P163-RECOVERY-COMPLETE` at +104.5s, and the two PASSING laps logged the identical "cause" event before their (shorter) replays. Lessons: read `P-COMPLETE-TIMING` and the takeover-quartet count before calling a hang; a probe present only in the failing lap is a cause only if ABSENT from the passing laps — diff timelines first; pull the survivor's dmesg to a file before the next lap, its ring buffer rolls within ~2 laps.

## sess594 — technique, and a rig-infra trap

- [[technique-pin-the-victims-log-tail-to-put-a-released-tenure-image-in-front-of-the-replayer]] (D-FOREIGN-REPLAY-UNGATED-IMAGES): to actually get a released-tenure image inside the replay window, pin the AIL: `mxfs.dbg_ail_pin_ino=<ino>` makes `xfs_inode_item_push` answer XFS_ITEM_LOCKED for that inode (skipped by the cluster-buffer flush a sibling push would otherwise trigger), holding the tail. Harness handshake via a go-file touch after the knob is set remotely. Never pin a node meant to survive (exhausts its log). Editing a running harness script is safe only after the byte offset bash has already read.
- [[trap-the-tool-host-kills-a-long-background-rig-task-under-its-own-memory-threshold-mid-deploy]]: a `run_in_background` `module_swap_deploy.sh` was killed by the Claude Code TOOL HOST's own memory threshold ("system is running low on memory") with 62GB actually available (`free`'s cache-heavy accounting misread) — not a clyde problem. The deploy had already brought both nodes down and died mid-step, leaving both with no module loaded and nothing else announcing it. Prefer the foreground for deploys/laps (module_swap_deploy is 3-5min, within the 600s Bash cap); after any killed background rig task, check both nodes' srcversion/mount count and the script's log tail before the next step — never assume the marker.

## sess595 — two D-0958 items closing out this arc

- [[trap-a-directory-holders-own-upgrade-takes-the-self-demote-release-drain-so-a-release-pause-armed-first-parks-the-holder]] (D-0958 control): for a DIRECTORY target, a harness that arms the release-pause knob before re-dirtying can park the HOLDER's own create — a peer's listing upgrade (PR→EX) can hit -EDEADLK, self-demote through the release drain, and land the holder's own subsequent acquire behind its own pause. Directory grants cache PR/EX at the last holder (a peer listing leaves the previous EX holder at PR, not NL) — unlike a file, where the holder holds nothing after being read and its own next write takes EX cleanly. Fix: for `TARGET=dir`, re-dirty first, arm the pause after; the release-pause knob fires on ANY release drain including self-demote, and `clear_knobs` mid-pause does not shorten an already-started msleep — wait for the END marker.
- [[technique-an-unaligned-dio-exclusive-retry-follows-an-attempt-that-submitted-nothing]] (D-0958 reference): confirmed from `/src/linux/fs/iomap/direct-io.c` and `pal/linux/xfs_iomap.c` that under `IOMAP_NOWAIT | IOMAP_OVERWRITE_ONLY` the -EAGAIN driving `retry_exclusive` is decided at the FIRST `iomap_begin`, before any bio exists — so the retry never follows a partial submit and is a clean fallible boundary (refusal is -EIO, nothing landed). Converted in 0.84.13 as `unaligned-excl-retry` / `atomic-cow-retry`; the atomic arm is unmeasurable on the lab LUN (no atomic-write support), the unaligned arm is measured with a 512-aligned/block-unaligned 4096-byte pwrite into an unwritten fallocated region.
