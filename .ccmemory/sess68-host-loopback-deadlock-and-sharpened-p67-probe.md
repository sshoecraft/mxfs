## (1) zsl FIX — build 2D460CA3 (RULE 4 step 2b, patch at proven cause)
sess67 P34B FUA-readback PROVED (measured): at consume `xfs_iread_bmbt_block` (xfs/libxfs/xfs_bmap.c:~1136) the cached bmbt LEAF is STALE (cached_recs=14 < disk_recs=18) while the ON-DISK block is CORRECT (disk_recs==di_nextents) and the buffer is CLEAN (bflags=0x20, no uncheckpointed mods = "STALEREAD" not "AHEAD"). It survived reload eviction (mxfs_dir_evict_bmbt_blocks) — the (a)walk-miss/(b)transient-pin question is still open but the FIX is INDEPENDENT of it. Consuming the stale leaf → ir.loaded<if_nextents → EFSCORRUPTED → 1600-dirent cascade.
**Fix:** in `xfs_iread_bmbt_block`, the former dirwr-gated P34B probe now RUNS ALWAYS for multi-node dir data-fork bmbt consume: FUA-read the daddr, and if the cached leaf is `stale && !ahead`, `memcpy(bp->b_addr, fua_buf, len)` (refresh the clean stale leaf in place from the proven-correct on-disk image) then re-read `num_recs` so the record-copy loop consumes the peer's committed map. `!ahead` guard (`mxfs_buf_has_uncheckpointed_mods`) protects our own un-destaged work (release-side path owns that). Logs `P68-BMBT-REFRESH` (gated dirwr). Reuses the proven-safe P34B FUA mechanism (already ran under ILOCK_EXCL in sess67). Cost: 1 FUA read/leaf/(re)load (xfs_need_iread_extents gates caller) — bounded, concentrated on large/contended dirs; single-node & non-dir excluded.
**Belt-and-suspenders:** still carries the sharpened P67 evict probe (`P67-BMBT-EVICT-ENTER ino nheld nseen_bmbt nthisino ncapped need_iread`) so if the fix is insufficient the eviction-miss case is still diagnosable.
**Risk (unverified — needs cluster):** (i) RULE-0 perf of FUA-per-reload could regress timing — measure; (ii) could in principle affect other passing criteria with dir-bmbt reloads (posix/rsync) — watch those in the post-reboot verify.
**Self-review (adversarial, code-traced — CONFIRMS correct for proven case):** `xfs_btree_visit_blocks(...,VISIT_RECORDS)` calls the callback ONLY for level-0 leaf blocks (xfs_btree.c: level>0 `continue`s without VISIT_LEAVES; level==0 proceeds with VISIT_RECORDS), so the memcpy refresh only touches leaves. For the proven zsl case (di_nextents=18 → broot_lvl=1): cur->bc_nlevels=2, level-1 root = in-inode `if_broot` (ALWAYS fresh post-reload), level-0 leaves = on disk. Descent uses the FRESH broot ptrs → correct leaf daddrs; each stale-cached leaf is refreshed in place as consumed (and its bb_rightsib comes fresh from disk, so multi-leaf sibling-walks also self-correct) → ir.loaded reaches if_nextents → no shutdown. `block` ptr stays valid after memcpy (points into bp->b_addr; num_recs re-read). `ahead` clean⟹disk-authoritative so no committed local data lost. Held ILOCK_EXCL; FUA-under-ILOCK proven-safe (P34B ran there in sess67). **KNOWN LIMITATION:** broot_lvl≥2 (huge dirs) has on-disk INTERNAL blocks at level≥1 that the fix does NOT refresh (callback skips internal levels) — if a stale internal node is hit, descent could follow stale ptrs. Not the observed bug (dir bmbt here is broot_lvl=1). If post-reboot zsl still fails with broot_lvl≥2 in P59, extend the refresh to internal blocks (use VISIT_ALL or a separate pointer-block refresh pass).
**Why the EXISTING read-time invalidator misses it (static analysis — explains the (a)/(b) survival):** `mxfs_dir_bmbt_invalidate_stale` (sess133) IS already called per bmbt block read at `xfs_btree.c:1432` (xfs_btree_read_buf_block, TYPE_INODE branch), need_iread-gated. BUT it uses `xfs_buf_incore(...,XBF_TRYLOCK)` — **TRYLOCK can FAIL** (buffer momentarily locked by writeback/peer-grant/the cursor) → returns without clearing XBF_DONE; and even when it locks, it SKIPS dirty/in_ail-undestaged/pinned/delwri buffers (the transient-pin case b). When it DOES clear XBF_DONE, the subsequent `xfs_trans_read_buf` re-read can still repopulate stale from SCST's per-initiator cache if not FUA (case c). So the read-time invalidator has three escape hatches; sess67 proved at least one fires. **My sess68 consume-side fix sits at the RIGHT layer past all of them:** it runs in the xfs_iread_bmbt_block callback on the buffer the cursor ALREADY holds (no TRYLOCK to fail), reads FUA into a private buffer, and memcpy-refreshes — robust to the lock/pin/reread races upstream. They are complementary (read-time invalidate is the fast path; consume-refresh is the guaranteed safety net). This also means a gen-gate on my fix would be WRONG: the surviving-stale leaf's b_mxfs_dir_gen state is exactly the unresolved escape-hatch question, so gating the FUA on gen could re-introduce the miss. Keep the consume FUA UNCONDITIONAL (scoped to multi-node BTREE-format dir data forks only — small EXTENTS-format dirs never reach xfs_iread_bmbt_block, so posix/rsync perf is not impacted).
