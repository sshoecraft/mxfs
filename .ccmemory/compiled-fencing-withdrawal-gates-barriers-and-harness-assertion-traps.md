Common shape across these notes: a predicate, barrier, assertion or verdict is written against the one state/producer/arm/caller that the author observed, and silently misjudges every other one. Some are product defects, some are harness attribution errors that look like MXFS defects in the RESULT line.

## Product-side traps

**Multi-producer state read through one producer's flag.** `v5_lease_member_state_cb` (dlm/v5_mount.c, 0.89.68) answered WITHDRAWN only when `ctx->disklock->auth->state == MXFS_AUTH_CLOSED`. A mount withdraws two ways: (1) authority CLOSED (lease expiry, PR conflict, revocation) via `P290-AUTH-CLOSED` -> withdraw pump -> `mxfs_v5_dlm_withdraw`; (2) forced shutdown (`xfs_do_force_shutdown`, `dbg_dialloc_shutdown`, log I/O error) via `mxfs_v5_dlm_withdraw` -> `mxfs_v5_dlm_poison`, which sets `ctx->withdrawn` and stamps the slot WITHDRAWN but never moves the authority off ADMITTED. Renewals kept saying MEMBER and the peer promoted SUSPECT back to ACTIVE 546 ms after reading the stamp. Fixed in 0.89.69 by reading both (`ctx->withdrawn` / `mxfs_v5_dlm_is_withdrawn`). A lap that drives the other producer measures the consumer's blind spot as the defect. See [[trap-a-withdrawn-predicate-that-reads-only-the-authority-object-misses-the-forced-shutdown-withdrawal]].

**NULL pointer as permission.** 0.89.20 gated five mutating producers with `if (v5 && !mxfs_v5_dlm_write_admitted(v5))`, and `write_admitted(NULL)` returned true ("not a clustered mount"). `xfs_fs_put_super` sets `mp->m_mxfs_dlm = NULL` before the log cover and unmount record, so the gate answered itself on a node that had stopped proving liveness; `tail_admit=1` on every ordinary unmount. A predicate on pointer liveness answers "is there a context", not "may this proceed". Comments like "NULL it so a queued X no-ops" mean the pointer is being used as a flag with an unplanned third state. Do not move the NULL; make the question answerable for the work's whole life via a property that is never cleared (`mp->m_mxfs_clustered`) plus a refcounted state object that outlives all holders. See [[trap-a-gate-that-reads-a-pointer-the-teardown-clears-reads-the-absence-of-the-reference-as-permission]].

**Lease-bounded wait is unbounded for a slotless caller.** `mxfs_v5_dlm_lu_reset_barrier` (dlm/v5_mount.c, 0.89.32) exits on `dl->auth->last_ok_ms > reset_issued_ms` or `!mxfs_disklock_authority_ok(dl)`; both derive from a claimed heartbeat slot. The whole-cluster bootstrap owner has no slot by design and beats only the bootstrap record (`v5_boot_hb_fn`), so the loop never exits; `mount` hung and `timeout 240` could not reap it (evidence 20260921T025611Z_bootfull, last line `P307-LURESET-CONVERGE converged=1`). Diagnosable because `P307-LURESET-BARRIER` is logged unconditionally after the loop on both outcomes: its absence proved "never left". Before reusing a wait justified by "the lease is the timeout", enumerate callers and check each holds what each exit reads. Fix: for a slotless owner exit on a bootstrap beat after `reset_issued_ms` or `ctx->boot_hb_lost`. The barrier predates the bootstrap and nothing re-drove the bootstrap through it. See [[trap-a-barrier-whose-two-exits-are-both-slot-derived-hangs-forever-for-the-one-caller-that-has-no-slot]].

## Harness and measurement traps

**Arm-specific durable state asserted unconditionally.** `tests/fence_crash_cuts.sh:645` asserted `flags=ACTIVE` on the victim slot at cut 1 regardless of arm. The silent arm parks the heartbeat (`dl_inject_hb_pause_ms=150000`); the 30 s authority lease expires, the victim self-fences (`P131-SELF-FENCE`, `AUTHORITY_LEASE_EXPIRED`) and stamps WITHDRAWN. ACTIVE is only what the destroyed (power-cut) arm can leave. The real subject was "prover died before the intent CAS, no RECOVERY_GUARD and no descriptor"; read the resting state per arm, never a single literal. Second instance in two days of a harness naming one node/state as the expected one. Also: never edit a harness script while a sweep is executing it (bash reads by byte offset); the fix waits for the sweep. See [[trap-an-expected-durable-state-that-only-one-victim-arm-can-produce-must-not-be-asserted-unconditionally]].

**Capture set wider than count set.** `fence_crash_cuts.sh` silent arm captured `P131-SELF-FENCE` and `P236-SELF-FENCE` into `B_contain.txt` but its `contain=` count omitted both, so a working self-fence read `contain=0` (lap s108a cut 7) while every later fsync returned rc=1. The predicate judging a property must read the same family the capture collects. `wait_for_into` sets its variable to the poll index on success (`0` = first-poll hit) and to the string `timeout` on failure, so a bare `resumed=0` is a hit. A cumulative-fails gate (`[ $fails = 0 ] || ABORT`) names the stage it sits in, not the stage that failed; read the FAIL lines. See [[trap-a-containment-assertion-that-counts-a-narrower-pattern-set-than-its-own-capture-fails-a-containment-that-worked]].

**Control reproduced outside the defence window.** D-0945 positive control (sess582): with the victim-side poison gate off, the ungated release reached the master 2.65 s after shutdown, but the fence sealed at 2.4 s, so `mxfs_dlm_process_remote_release` refused it (`P-TAUTH-SEALED-RELEASE-REFUSED`) and the manifest held the grant. Reading "gate off, no harm" concludes the gate is unnecessary. When a defect has several lines of defence, a control that reproduces the cause at the wrong time is caught by the next line. Before scoring: (1) measure the primary defence's window with timestamps on both nodes; (2) put the actor inside it deliberately (`echo 2 > /proc/sys/vm/drop_caches` right after the trigger) and prove it with the second-line counter at zero (`sealed_owner_refusals=0`) plus a direct effect (manifest 3 vs 4 entries); (3) report which line answered per arm. Evidence: 20260911T193709Z_d0945ctl_s582a, 20260911T194213Z_d0945ctl_s582b. See [[trap-a-cause-reproduced-outside-its-timing-window-lands-in-the-second-defence-and-reads-as-unreachable]].

## Planning trap

**A "route closed" verdict expires when the capability is built another way.** `D-FENCE-CRASH-MATRIX-UNTESTED` said route 1 (witnessed SCSI LU RESET) was closed because `scsi_ioctl_reset` is unexported and `try_*_reset` are static on 6.8. True for in-kernel reach only. 0.89.33/34 built it through `mxfs_pal_lu_reset_witness()` -> `call_usermodehelper` -> `ioctl(SG_SCSI_RESET ...)` with `retire_basis = completed-target-op`, called from the dead-peer prover; the record was never updated. A feasibility judgement phrased "there is no X" outlives someone building the capability without X. Check whether the capability (grep `lu_reset`, `LURESET`, the fence-kind enum) has an implementation, not whether the named symbol is still missing; when a route is built, sweep the queue for records whose next step was written while it was closed. Mirror of withdrawing a mechanism expiring banked passes (`trap-banked-lap-evidence-stops-describing-the-build-when-an-intervening-change-withdraws-the-mechanism-the-lap-depended-on`). See [[trap-a-records-next-step-can-declare-a-route-closed-on-reasoning-a-later-version-made-obsolete-by-building-it-another-way]].
