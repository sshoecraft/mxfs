## sess13 (ccloop 4cb2d0a2) — dir_reuse 4/tcp: 0/400 → 399/400, residual = in-transaction dir-DATA-block RMW

Single-session campaign on the `dir_reuse_coherency` criterion (the `cache_coherency` ship blocker) at 4 nodes over TCP DLM. Cluster test1-8, `virsh -c qemu:///system` reset. 7 builds, ~14 cluster runs, 2 GPT-5.5 consults, 17 memories. **Criterion NOT met** — best result 399/400, 8/tcp never run.

### The winning config (the headline result)
`MXFS_EXTRA_MODARGS="fua_disable=0 fua_always=1 dir_epoch_adopt=1 dir_epoch_convert_gate=1"` on `./run.sh 4 tcp dir_reuse_coherency` → **399/400 on all 4 nodes, ZERO shutdowns**. Progression [[sess13run-WINNING-CONFIG-fua-plus-epoch-adopt-399of400]] [[sess13run-BREAKTHROUGH-FUA-removes-corruption-readdir-divergence-remains]]:
- default (fua_disable=1, epoch off): readdir 0/400 & 306/400 + ~150 `DABUF_MAP_HOLE` shutdowns/node.
- FUA only (`fua_disable=0 fua_always=1`): NO shutdown, readdir 306/400 (rank1=0).
- FUA + epoch_adopt + epoch_convert_gate: NO shutdown, **399/400** all nodes. `P65-EPOCH-ADOPT` fires adopt=1 ~52-58×/node.

**Both levers are required and neither alone suffices:** FUA gives LIO-cache-piercing coherent reads; epoch_adopt gives level-triggered (sess64) cross-node handoff detection so a node adopts the disk superset on every real EX handoff. FUA alone = 306; epoch alone = sess10-refuted. `dir_force_evict` is also **ESSENTIAL** — force_evict=0 → 374/400 (26 lost); it prevents ~25 of 26 losses but is NOT the residual cause [[sess13run-HANDOFF-FINAL-state-residual-likely-in-transaction-revert-next-instrument-addname]].

RULE-0 caveat: `fua_always=1` ≈ 16s/round = too slow to ship. Once residual=0, scope FUA to dir-meta-on-handoff (GPT #3: `XBF_MXFS_COHERENT_READ` flag in `xfs_dir3_data_read/leaf_read/free_read`, `xfs_da_read_buf`, DLM-epoch-driven → REQ_FUA). `prep_node.sh` passes NO params, so the winning combo must become source DEFAULTS (currently `dir_epoch_adopt`/`dir_epoch_convert_gate` default 0, `fua_disable` default 1).

### What FUA proved about the corruption (build 40AC2A0C)
The baseline `DABUF_MAP_HOLE` shutdown (`!(flags & XFS_DABUF_MAP_HOLE_OK)` at xfs_da_btree.c:2817, via xfs_dabuf_map, comm=dd) is **read-coherency stale-base RMW corruption** — the LIO per-initiator read cache served stale dir blocks under fua_disable=1; SCSI READ(16) FUA piercing the cache eliminates it (165→0). `fua_disable=1` on LIO is unsafe for 4-node dir contention. But readdir divergence persists with same dirino=131 on all nodes (intra-inode content divergence, not inode-incarnation mismatch) [[sess13run-BREAKTHROUGH-FUA-removes-corruption-readdir-divergence-remains]].

Machinery confirmed **fully built but gated off**: grant_gen (sess61, `mxfs_dlm_grant_gen@dlm.c:2263`), handoff-bit (sess63, `grant_was_handoff@2299`), dir_epoch (sess64, `grant_dir_epoch@2339`) + v5_mount.c wrappers + xfs_inode.h fields (`i_dlm_cached_grant_gen`, `i_dlm_handoff_acted_gen`, `i_dlm_dir_valid_epoch`, `i_dlm_dir_valid_epoch@138`) + `xfs_mxfs_dlm.c` probes (`P65-EPOCH-ADOPT@7758`, `P63-HANDOFF@7774`). Handoff IS detected; adopt was suppressed only because without FUA the reads were stale anyway.

### Characterizing the residual (robust, deep, invariant)
Exactly **1 durable `.md5` dirent lost / run** (rounds vary 1-26 lost, contention-scaled — earlier "always 1" was just the last failround sampled) [[sess13run-CORRECTION-dir-is-LEAF-format-probe-belongs-in-data_log_entry-loss-varies]]. Always the **2nd create wave** (.md5 sidecar, dir fuller/multi-data-block → more free-slot contention). `LOOKUP_ENOENT REREAD_MISS` clusterwide = **durable DATA-block loss (bytes overwritten)**, NOT a leaf-hash hole (so `dir_leaf_rebuild` won't recover it) [[sess13run-HANDOFF-residual-is-data-block-RMW-release-durability-or-concurrency]]. 2/tcp PASSES, 4/tcp fails → contention-scaled. 8/tcp unrun.

The dir is **LEAF format**, not node: probe `P13-NADD` in `xfs_dir2_node_addname_int` fired 0×; addname routes `xfs_dir2_leaf_addname` → `xfs_dir2_data_use_free` → `xfs_dir2_data_log_entry`. Any per-format probe must go in `xfs_dir2_leaf_addname` or common `xfs_dir2_data_log_entry` (xfs_dir2_data.c:1212, where P11-DATALOG lives) [[sess13run-CORRECTION-dir-is-LEAF-format-probe-belongs-in-data_log_entry-loss-varies]].

**The test is an ABA daddr-reuse + inode-reuse stressor:** each round after verify, rank1 `rm -rf "$D"; sync` frees the WHOLE dir (inode 131 + leaf + data daddrs), next round `mkdir -p` recreates it (dir_reuse_coherency.sh:142-147). DIRID probe shows dirino=131 every round. mxfs's ABA defense is `b_mxfs_dir_incarn` (= dir i_generation, checked xfs_da_btree.c ~3246) — only works if di_gen changes on rm/re-mkdir. Decisive unverified check: does ino 131's i_generation differ between consecutive rounds? If XFS recycles the inode with same gen, a peer's cached prior-incarnation buffer (same daddr, same di_gen) passes the incarn check and is served stale [[sess13run-RELAY-test-does-rm-rf-each-round-ABA-daddr-reuse-verify-digen]].

3. Fast-path level-triggered epoch check (see refuted list above) [[sess13run-FASTEPOCH-inert-four-fixes-exhausted-residual-not-staleread-not-doublegrant]].
4. `dir_coherent_modify` / `mxfs_dir_refresh_stale_data_blocks` (xfs_mxfs_dlm.c:1311, called from `mxfs_dlm_dir_modify_refresh` ← xfs_create:1499 / remove:3845 / rename:4295-97): plain-bdev-reads each cached dir DATA block, and if disk count STRICTLY > cached count, invalidates so addname re-reads coherent (GPT-5.5 #D). `P11-COHMOD-INVAL` fired **0×** across 20 rounds × 4 nodes [[sess13run-FINAL-residual-is-concurrent-sameblock-rmw-cohmod-skips-own-undestaged]].

### Why the fixes are inert — the sharpened diagnosis
The release-invalidate and coherent-modify refreshes both **SKIP any block that is `undestaged || _XBF_DELWRI_Q || !XBF_DONE`** (xfs_mxfs_dlm.c:1370, "KEEP our own committed-unwritten work"). At release the dir blocks are almost never clean-XBF_DONE — they are **DIRTY-but-durable** (`XFS_LI_IN_AIL` set for log-tail tracking, but written_seq ≥ logged_seq). That is exactly the buffer GPT said must be discarded, but clearing XBF_DONE on an in-AIL/dirty buffer is the sess96-refuted force-evict-on-release that resurrects/corrupts — so the safe version can't touch the culprit [[sess13run-FIX-ATTEMPT-release-invalidate-inert-culprit-is-dirty-durable-AIL-buffer]].

In the heavy create wave the LOSER's target block is THIS node's own recent in-flight (undestaged) add → correctly skipped — but that same block is also missing a PEER's durable add at a different offset. So the loser's bestfree (from its own in-flight image) sees offset X free, peer durably used X → collision → 1 dirent lost. COHMOD also deliberately ignores equal-count-different-content divergence [[sess13run-FINAL-residual-is-concurrent-sameblock-rmw-cohmod-skips-own-undestaged]].

**Decisive inference:** coherent reads everywhere + no buffer surviving a handoff does NOT recover the lost dirent ⇒ the entry's BYTES are durably overwritten on the LUN by another node's dirent at the same (daddr, offset). No read-side/buffer-lifetime fix can recover a durably double-written slot. **The fix must prevent the double-PLACEMENT at write/addname time** [[sess13run-CONCLUSION-readside-buffer-fixes-exhausted-residual-is-write-placement]].

### Two competing root models for the residual
Both surviving candidates share directionality (sess11run, PROVEN): the LATER writer's just-placed dirent reverts to the disk image and is dropped.

**(A) In-transaction / commit-path revert (strongest lead, single-node-tractable).** sess11run FINAL proved (PRELOGF: single thread comm=bash, ILOCK_EXCL held continuously, NO split, NO evict, NO peer-BAST) the lost dirent is logged (P11-DATALOG rval=0, commit OK) then VANISHES from its own in-core cached data block within ~250µs between addname and durable_signal — INTERNAL to the create transaction. Combined with P13-COLLIDE clean of real names (no peer overwrites at the same offset), the entry disappears from ITS OWN block. Already ruled out as the revert source: the read-time XBF_DONE-invalidation hook (xfs_da_btree.c ~3173, guarded skip of dirty/in-AIL/pinned/delwri per sess43/64) and the `mxfs_buf_read_fua` P91 guard (skips pinned/log-item buffers). Candidates: (a) `xfs_dir2_node_addname` xfs_trans_roll commits an intermediate tp then re-reads a source missing the entry; (b) a freespace path adds count++ but bytes land in a region reused later in the same txn; (c) an mxfs commit/CIL hook (note_dir_modified bumping i_dlm_dir_gen → next addname's force-evict re-reads/reverts the prior addname's not-yet-durable entry). **NEXT (the never-completed sess11run step): instrument xfs_dir2_node.c `xfs_dir2_node_addname` + xfs_dir2_leaf.c — log the target (db/daddr/off) and whether xfs_trans_roll runs between data-write and return, storm dir ino≤256, correlate with PRELOGF. SAFE method: walk `tp->t_items` or add log lines IN the xfs_dir2 functions — NEVER a fresh `xfs_buf_incore` in-txn (drops the txn buffer lock → corrupts).** This is likely single-node-reproducible given the right dir-growth + i_dlm_dir_gen state — far more tractable than the 4-node race [[sess13run-FUAWRITE-inert-platter-hypo-weakened-next-is-intransaction-trace]] [[sess13run-HANDOFF-FINAL-state-residual-likely-in-transaction-revert-next-instrument-addname]] [[sess13run-P13-STALEREAD-mostly-normal-need-correlate-specific-lost-name-with-probes]].

**(B) Release-durability hole (peer add committed in-core but not on the LUN when the adopting node reads).** Proper EX-serialize-then-adopt would give B a base including A's add; B's base missing it ⇒ A's add to that block wasn't durable on the LUN when B acquired+adopted, so the disk B adopted was NOT a strict superset (Invariant #1 gap for ONE block under the 2nd-wave burst). One sub-variant (LIO write-back vs FUA-platter): mxfs marks a block destaged/durable once SUBMITTED to the LIO target (lands in target write-back cache, not platter); a same-node force-evict then FUA-re-reads the platter which LACKS the just-written E1 → in-core reverts → E1 lost. This explains why FUA fixed read-stale but left a write-not-on-platter revert, and why coherent_modify/release-invalidate (which see the block as "durable" by mxfs's LIO-submit notion) don't catch it [[sess13run-MHT-invariant-residual-leading-hypo-LIO-writeback-vs-FUA-platter-revert]] [[sess13run-FINAL-residual-is-concurrent-sameblock-rmw-cohmod-skips-own-undestaged]]. **NEXT: instrument the bast_process release drain (xfs_mxfs_dlm.c ~6164 loop) to log per-dir-DATA-block dirty/pin/undestaged at unlock for the storm dir — find the ONE block released not-yet-durable; and/or at force-evict, log whether the FUA-read content count < in-core count (platter behind us). Fix direction: make a dir block's "durable" mean PLATTER-durable (add blkdev_issue_flush after per-block xfs_bwrite before marking destaged), or make publish-before-handoff a true durability fence so the master doesn't grant B EX until A's committed dir-block add is on the LUN.**

### A strong but not-yet-proven correlation (stale LEAF freespace)
Placement probes (build B2FAE263) show multiple nodes' `xfs_dir2_leaf_addname` converging on the SAME use_block index (=1, same daddr): test3 placed node3_f1 at use_block=1 daddr=10468032; test2 placed node2_f16.md5 at use_block=1 daddr=10468032. In a multi-block leaf dir nodes should spread across blocks; converging on block 1 implies the LEAF `bestsp[]`/`ltp->bestcount` free-space table (read in xfs_dir2_leaf_addname ~L1005-1048) is STALE — every node believes block 1 is most-free and piles in, then the per-block `xfs_dir3_data_read` (L1168) serves a near-empty image (`P13-STALEREAD` bf0len~3984) → low-offset placement → clobber. Ties to `P21S-EVICTSKIP-LEAF ino=131 daddr=1912 leaf_count=402 dirty=0 in_ail=0 pin=0 delwri=0 done=0 dir_gen=6 loaded_gen=6`: the clean cached leaf-block coherent re-read is SKIPPED because the gen-gate sees dir_gen==loaded_gen (too conservative — real handoff occurred). Caution: `P13-STALEREAD` fires 150-200×/node = MOSTLY NORMAL fresh-round fill (dir freed/recreated each round, each wave fills its own block from empty, daddrs reused across-rounds not concurrent) — the 1 loss/round is a rare race buried in ~750 normal placements [[sess13run-LEAD-nodes-converge-same-use_block-stale-leaf-freespace-bestsp]] [[sess13run-MHT0-refuted-residual-is-cached-clean-stale-buffer-evictskip]] [[sess13run-P13-STALEREAD-mostly-normal-need-correlate-specific-lost-name-with-probes]]. Candidate fix: on a genuine dir-EX handoff evict/invalidate ALL the dir's clean cached data+leaf+free-index bufs (not just block0/extent-map) + scoped FUA re-read; stamp buffers with di_gen incarnation; NEVER evict dirty blocks (own uncheckpointed mods = resurrection, sess36/50).

### Methodological lessons carried forward
- Bulk probes (P11-DATALOG, P13-NADD, P13-COLLIDE, P13-STALEREAD) all show NORMAL high-volume dir activity and do NOT isolate the single loss. MUST correlate the SPECIFIC lost name: from a node's `/root/drc_failrounds.txt` + `drc-RDMISS round=N` get the exact lost name (e.g. node3_f19.md5) and round, then `dmesg | grep '<lostname>'` on each node across the probes to reconstruct which node placed it at which (daddr,off), whether read stale, and whether a peer wrote the SAME (daddr,off). Cross-node correlate by (daddr,off) — the true double-alloc vs the daddr-reuse-across-rounds false positive. Probes are already in the builds, storm-dir scoped, always-on [[sess13run-P13-STALEREAD-mostly-normal-need-correlate-specific-lost-name-with-probes]].
- SAFE in-txn instrumentation idiom: `mxfs_pal_bdev_read_plain_bdev` into a kmalloc temp (buffer-cache-untouched, what `mxfs_dir_refresh_stale_data_blocks` uses) — NEVER `xfs_buf_incore` inside a live transaction.
