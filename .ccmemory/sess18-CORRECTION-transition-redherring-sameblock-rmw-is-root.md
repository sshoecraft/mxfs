## sess18 (ccloop 8ddb16a2) — IMPORTANT CORRECTION to [[sess18-ROOT-NARROWED-shortform-to-block-transition]].

## WHAT HAPPENED: built fix #1 (force new multinode dirs to BLOCK format at mkdir via xfs_dir2_sf_to_block; module_param dir_force_block default 0; build F13B9FB0; wired in xfs_create after xfs_dir_create_child + resblks bump). Sanity confirmed fresh mkdir → dirsize=4096 (block). BUT the sf-start probe with dir_force_block=1 STILL lost durably: run1 iter15 (195/200), run A iter2 (199/200), run B iter2 (199/200). force_block does NOT fix it.

## CORRECTION: the shortform→block TRANSITION was a RED HERRING. The pre-grown probe's 0/30 (tests/cc_pregrown_probe.sh: test1 pre-creates 40 files single-node, then concurrent) was clean NOT because the dir was block-format, but because test1's 40 single-node entries spread the dir across MULTIPLE data blocks BEFORE concurrency — so the two nodes' concurrent creates landed in DIFFERENT data blocks (low same-block contention) AND the vulnerable single-data-block phase was done single-node. force_block makes the dir block-format but EMPTY, so both nodes still hammer the SAME first data block → loses (even worse, iter 2).

## REAL ROOT (back to the core, now sharper): concurrent SAME-BLOCK RMW durable clobber during the SINGLE-DATA-BLOCK phase. When a small/empty dir has all entries in ONE data block (block format, pre-leaf), two nodes concurrently RMW that block; one writes a stale base (kept undestaged block missing peer's entries — the keep-guard) over the peer's → durable lost update. Once the dir grows to LEAF format (multiple data blocks, entries hash-spread), same-block contention drops and loss stops. This is the original block-format lost-update [[sess18-readside-ruled-out-writeside-clobber-confirmed]] [[sess14-cc-root-blockdir-concurrent-create-dirent-loss]] — write-side, release-fence-clean, merge-needed, and the per-create merge is PERF-DOOMED [[sess18-merge-perf-doomed-pivot-to-format-transition]].

## NEW UNEXPLORED FIX IDEA (perf-viable merge candidate — "INVERSE merge"): the perf-doomed merges read the PEER's block from DISK (extra I/O under the grant). Instead: at the acquire refresh (mxfs_dlm_dir_modify_refresh, xfs_inode.c:1374), BEFORE evicting our stale undestaged block, SNAPSHOT OUR in-core entries (a MEMORY read of the cached block — NO disk I/O), THEN evict the block (so createname cold-reads the PEER's fresh durable image — I/O the create does ANYWAY), THEN re-add our snapshotted entries via createname into the create's tp. Union = peer's fresh image + our entries, with NO extra disk I/O (only the unavoidable cold-read + bounded re-adds). This sidesteps the I/O-under-grant wedge that killed the disk-reading merge. Risk: bounded by how many of OUR entries are in the undestaged block (could be many); and the in-flight-log-item tension on evicting an undestaged block (sess33 — must flush/handle our entries' log items so evict doesn't corrupt). Needs careful design + the in-flight handling.
