# Same-node waiter-cancel / lreq-registry campaign — sess111–125

Campaign to fix the same-node CAW reconcile corruption family in `dlm/dlm_caw.c`. Ledger defects served: **D-SAMENODE-WAITER-CANCEL-COLLISION** (critical, ledger #16 — carries the implementation design), **D-RECONCILE-SLOT-IDENTITY-UNCHECKED** (critical), **D-RECONCILE-EXHAUSTION-SILENT** (high), **D-TRACK-PUBLISH-ORDERING** (high). Ledger stood at 29 open of 68, 17 critical throughout. Fleet stayed on 0.11.440 (srcversion `DF0E1ABC1CEA16331E2DF6C`) the entire campaign; every landing below is build-only.

## Root cause (sess111)

`caw_drop_own_waiter` (`dlm/dlm_caw.c:2318`) is the post-giveup reconcile — 3 call sites (grant-wait timeout :3346, claim-exhaustion :4990, convert-exhaustion :6479), looping ≤1000× clearing `waiters`, `waiters_ex`, and the holder bit in `giveup_mode`. The adopt arm (:2823) writes nothing (pure recognition). Core problem: the on-disk image is identical for "handoff landed, unadopted" and "adopted and live" — node identity is ONE bit, so multiple local attempts share it and one attempt's reconcile can clear a bit belonging to another live local attempt. Same-node concurrency exists by design: the demoter is exempt (`!mxfs_is_demoter(ip)`) from the `MXFS_DLM_ISTATE_ACQUIRING` park (`xfs/xfs_mxfs_dlm.c:28138/28141/28415`). sess111's 32-node census: `P6H-ABORT-RECONCILE`, `P3A-DEMOTER-SLOWACQ`, `P-CAWEXH`, `P91-CLAIMEXH` all 0 vs ~970 `P6H-ADOPT`/node — **the reconcile arm never runs under a healthy board, so a green board can never close these defects (RULE 6)**; the closure test is the sess113 debugfs exerciser (scenarios A/B/C + negative control asserting a lone give-up DOES clear). GPT rejected the initial `ctx->held` mode-guard (observe-to-track window; shared node bit), ruled "lease expiry is a failure detector, not a fence" (dead-node WAITER bits clearable unfenced, holder bits never), and required a per-(node,resource) local registry — the ruling that minted the defect set: [[ccloop-c7ee71c6-sess111-GPT-ruling-blocker6-REJECTS-held-table-guard]].

## Registry v1 and its rejection (sess112–113)

sess112 landed the registry (0.11.441, srcversion `750BDB5F2A229A3B8438947`): `struct mxfs_caw_lreq`, chained (not direct-mapped — a missing entry reads as "no other attempt", the false statement that authorizes the clear) off `ctx->lreq[MXFS_CAW_LREQ_BUCKETS=1024]` under `lreq_lock`; `lreq_join/plan/finish/release_all`; alloc failure refuses the acquisition (`P247-LREQ-NOMEM`); probes P244 (guard hits), P245-RECONCILE-EXHAUST, P246-LREQ-OWED, P248-LREQ-LEAK. En route it found the 4th defect: `caw_drop_own_waiter` validated only `magic == MXFS_CAW_MAGIC` at a remembered slot index — a tombstoned/re-claimed slot for a DIFFERENT resource passes; the function didn't even take a `resource` arg (fixed via memcmp) — [[ccloop-c7ee71c6-sess112-lreq-registry-LANDED-0.11.441]].

sess113 GPT ruling: **STOP-SHIP** — counter-sampling (`attempts`/`tenure`) cannot authorize a clear; three corruption paths: (A) the deferred owed pass passes `e=NULL`, bypassing the tenure guard; (B) the plan is snapshotted once across a 1000-iteration I/O loop; (C) passing `e` to the deferred pass mis-subtracts a post-decrement joiner. Structural items: single `owed_slot` overwriteable, identity-mismatch is not debt discharge (`-ESTALE`, not `rc=0`), exhaustion must escalate, GC needs `pin==0`, registry alloc failure must fail the mount — [[ccloop-c7ee71c6-sess113-GPT-ruling-lreq-registry-STOP-SHIP]]. The companion facts note verified: FACT 1 — adoption runs on the attempting thread (`P6H-ADOPT` at `dlm_caw.c:3348` inside `caw_wait_for_grant`), so adopt/cancel of one attempt is one thread and full ADOPTING state is unnecessary; FACT 2 — `waiters_ex` setters (:5292, :6921) match `mxfs_mode_can_write()` exactly; FACT 3 — `recompute_waiter_mode()` is a pure derivation — [[ccloop-c7ee71c6-sess113-lreq-verified-code-facts-and-design]].

## The cached-lock model correction (sess115)

Proof work, no edits: **FACT A — `tenure[]` is NOT a refcount.** CAW locks are per-mount cached grants with no per-acquire release; `lreq_finish` increments `tenure[held_mode]` (:2736) on every acquire including memory-only shortcuts (:4680-4722, :4790-4828); only decrements are convert's `tenure[conv_from]--` (:7020) and `lreq_release_all`'s memset (:2816); unlock is BAST-driven whole-node eviction. `refs>1 ⇒ no clear` would permanently wedge the cluster. FACT B: AG eviction already excluded by `pag_dlm_demoting` (`xfs_mxfs_dlm.c:39483`, `mxfs_ag_dlm_wait_demote` :32531-32544). FACT C: 1:1 inode covered by the `i_dlm_state` park; residual exposure is **ICLUSTER** (one resource per 16KB cluster, up to 32 inodes — different demoter threads on one resource). FACT D: the adopt arm has no natural CAS ordering against unlock (prebump lands only when locally noticed; the :5661-5670 guard does not cover grant-lands-mid-unlock) — [[ccloop-c7ee71c6-sess115-cached-lock-model-invalidates-blockers-2-3]]. GPT accepted FACT A: **blockers 2 and 3 WITHDRAWN**, snapshot-subtract withdrawn (blanket retirement correct under proven exclusion), blocker 1's linearization requirement stands; `tenure[]` renamed conceptually to epoch-scoped historical accounting (the fail-closed `tenure[giveup_mode]>0` holder guard remains sound). Two NEW blockers: ICLUSTER resource-granularity quiescence (a DLM RELEASING state cannot fix it — the exclusion must cover protected-drain lifetime), and adoption must be PROVISIONAL against a release epoch. Governing invariant: **"No post-boundary grant/adoption publication may become usable across a successful destructive clear"** — [[ccloop-c7ee71c6-sess115-GPT-ruling-blockers-2-3-WITHDRAWN-two-new]].

## Clear-window linearization (sess116–118)

sess116 proved sess113 path (A) end-to-end: `lreq_finish`'s owed pass calls `caw_drop_own_waiter(..., NULL, m)` (:2781/:2784); `lreq_plan(e=NULL)` returns the legacy clear-everything plan; a granted thread's fresh EX holder bit is stripped after `mxfs_dlm_caw_lock` returns 0 — unfenced writer — [[ccloop-c7ee71c6-sess116-owed-run-passes-NULL-real-corruption]]. The design response: only THREE memory-only publications (already-held shortcut ×2, adopt arm :3337) plus `lreq_release_all` lack CAS linearization — so a validation protocol suffices: `clr_active`/`clr_seq`/`pub_seq` on the entry, `lreq_clr_begin/end/snap/still_good`, per-iteration plan re-derivation, `release_all(pub_seq0)` keeping tenure on a moved `pub_seq` — [[ccloop-c7ee71c6-sess116-clear-window-linearization-design]].

sess117 landed the clearer half (srcversion `3C6F0BF4547E9A22C95A0ED`): `e=NULL` fixed (pinned entry passed), `lreq_plan` gained `self_joined`, windows on `caw_drop_own_waiter`/`unlock_gen`/`force_release_self`, `P248-LREQ-REL-KEPT`, bounded 50ms CLRWAIT park (`P249-LREQ-CLRWAIT-TO`) — publication half unwired — [[ccloop-c7ee71c6-sess117-clear-window-HALF-LANDED-do-not-deploy]]. sess118 wired it (srcversion `AC44AC4FAF6EF5DA0C24299`): snap/validate at all 3 arms (`P250-LREQ-CLR-REFUSE arm=held|held-hi|adopt`), **snapshot armed BEFORE the read it protects** (the sess116 "after" was wrong), missing-entry validation FAILS CLOSED (ruling item 4), tenure saturates at `UINT32_MAX` (item 6) — [[ccloop-c7ee71c6-sess118-publication-half-LANDED-still-stop-ship]]. The sess118 ruling confirmed snapshot-before-read and issued the 8-item checklist: (1) post-validation demotion race stays IN SCOPE (three dispositions only — XFS quiescence / `use_begin`/`use_end` API / prove all callers quiesced; RULE 0 buys no exemption), (2) 50ms fail-forward NOT acceptable ("there may be no next attempt"), (3) `committed` = MAY-have-changed, (4) entry ABA, (5) ENOMEM fail-closed ("an ENOMEM fallback that proceeds without registry coverage is a correctness defect"), (6) tenure latch/saturate + named reconciliation, (7) force-release precondition, (8) multi-step clears — [[ccloop-c7ee71c6-sess118-GPT-ruling-clear-window-8-blockers]].
