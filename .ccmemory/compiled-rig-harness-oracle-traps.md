Compiled from a topic group: MXFS rig/harness traps where a lap's verdict (FAIL, FLAKY or PASS) did not measure the filesystem. One loosely related user note on platform priority is folded in at the end. Before treating any verdict as a defect or as proof, establish that the subject actually ran.

## Verdicts produced by a lap that never measured anything (false FAIL / FLAKY)

- **FLAKY can be an oracle that refused to start.** A board FLAKY means one FAIL sits in the 11-run window (`tools/flake_laps.py` gives k and laps needed). Read that FAIL's evidence directory before spending laps. 2/disk/caw/direct crash_audit read FLAKY on 0.90.107 from a FAIL whose `oracle.log` was only `ABORT: test15 srcversion != tree` (exit 2, no I/O; the tree was rebuilt under the run). `tests/death/crash_audit.sh` scores any non-zero oracle exit as a failed death oracle and the reason matches none of `criteria.RIG_NOISE`. Clear it with `tools/criteria.py amend --at <cfg> --iso <iso> --detector-defect "..."` only if a detector fix is already in the tree (editing a script after evidence was gathered opens a new version and voids that evidence); otherwise run laps `LAPS="<cfg>:<row>:<10-k>"` on `tests/release_verify_chain.sh`. Open record: D-CRASH-AUDIT-SCORES-AN-ORACLE-THAT-REFUSED-TO-START-AS-A-FAILED-DEATH-ORACLE. See [[trap-a-flaky-rows-window-fail-can-be-an-oracle-that-refused-to-start]].
- **A row failing right after a budget-killed row is collateral.** 4/tcp (0.90.14/16): chk_clean was killed at its 180 s budget (umount wedge, a real fault) leaving every node unmounted; the next host-coordinated row, crash_audit, aborted at its own "member not mounted" check and the board counted two genuine crash-recovery failures. `tools/criteria.py` excludes only reasons matching `pre-assert|NO_TERMINAL_RECORD|run was killed|prep fail`; a precondition abort phrased otherwise counts as genuine. When a row FAILs in the same run as a preceding killed row, read the earlier row's evidence first (`tests/evidence/run_<row>_<RUN>/*.rc` all 124 = killed). Fixed in 0.90.17: `run.sh` `run_host` does the same mount-and-readdir pre-assertion as the coordinated runner and records "pre-assert"; the two collateral FAILs were annotated with `criteria.py amend`. See [[trap-a-row-that-fails-right-after-a-budget-killed-row-is-collateral-until-the-earlier-row-is-read]].
- **At 3+ nodes the prover and the replayer can be any survivor.** 4/cawd crash_audit FAIL (0.90.10): test3 fenced and snapshotted the victim while test1 replayed, and the oracle read only W=test1's log; 1198 files verified OK. Fencing is a race among all survivors, the replayer is elected separately. Rules for any N>2 death/fence harness: pass every mounted member (`TDR_MEMBERS`, `MXFS_NODES`, `MXFS_NODE_LIST`); read prover and replay lines from a merged capture of every survivor (keep W's own for workload/verify only); arm "prover" injections (`fence_gate_inject_refuse`, `blocked_after_ms`) on every survivor, find the prover by `P238-FENCE-BLOCKED`, clear on all; unmount peers before the last member so the cold audit does not read counters a mounted peer holds; a 2-node PASS says nothing about N-node validity. See [[trap-at-three-or-more-nodes-the-prover-and-the-replayer-can-be-any-survivor-so-a-death-oracle-must-read-every-survivors-log]].
- **A racing thread's coverage is not an oracle.** `tests/delalloc_dirty_tail_race.c` expected every odd page stored by the toucher; the toucher never reached pages 1..N-1 after the pass restarted, so holes were graded as lost data. Ordered by cost: native XFS control on the same kernel (loop device, `tests/delalloc_dirty_tail_loop_control.sh`, 14 s) gave the identical verdict; kprobes on the folio's per-block bitmaps (`tests/delalloc_dirty_tail_kprobe.sh`) showed all blocks dirty/submitted/written; the reproducer stamping progress into `trace_marker` named the cause. Fix: record coverage in a per-page manifest and verify only covered pages, reporting the rest UNTOUCHED (`tests/ddtr_verify.py`; native XFS 3/3, MXFS 2/2, P313 x60). Side facts: a loop device cannot host a single-node MXFS mount on 0.89.60 (needs `fence_capability_override=1`, `single_node_exclusive=1`, and COMPARE AND WRITE, `P304-CAS-NOCAW` -95), use the real LUN; in 6.8 `xfs_iomap_found` DELAYSTARTBLOCK is -1, HOLESTARTBLOCK -2; `iomap_iter` tracepoint fires before the iterator advances; `mm_filemap_*` print ino as bare hex and filter on `i_ino`. See [[trap-an-oracle-that-assumes-a-racing-thread-covered-every-page-grades-the-holes-it-skipped-as-lost-data]].
- **Fixed-instant capture picks the wrong branch.** `tests/fence_partition_reconnect.sh` ARM=network captured after `sleep "$PART_S"`, ending 24 s before `P236-FENCE-CERTIFIED`; `fen_a=0` took the "nobody fenced" branch, graded by the inverse rules, printing three FAILs against a correct resolution. Select the branch on the pipeline's START (`P-PR-FENCE preempt-and-aborted`, `P236-FENCE-INTENT`, `P309-DEATH-FENCE-QUEUED`), then hold the condition (do not heal the partition) and wait bounded for the end, with the bound derived from the pipeline (~2 s I/O bounce + 62 s disklock dead window + 5 s fence/reset/certify/seal = 69 s, bound 100 s). A settle timeout is a finding: a fence that proved exclusion and never certified consumes the victim's key (`P236-FENCE-CERTIFY-FAIL`). When branches are graded by opposite rules, the selector must be early and monotone; the late signal becomes an assertion. See [[technique-discriminate-a-multi-stage-pipelines-verdict-on-its-start-then-wait-for-it-to-settle-never-on-one-fixed-instant]].

## Verdicts produced by a lap that measured the wrong thing (false PASS / vacuous)

- **A refused mount leaves the mountpoint a writable local directory.** `tests/fence_crash_cuts.sh` cut 7 (0.89.19): B's recovering mount was refused (`MOUNT_RC=32`, `NOT_MOUNTED`), the post-recovery section ran anyway, wrote 16 files and read back 16 checksums on B's root filesystem, and printed PASS. Any write-and-read-back oracle keeps working with the filesystem absent. Assert `mountpoint -q` first, on the node the workload runs on and after the event that could lose the mount; report NOT MEASURED if it fails. Separately, reading back through the same mount that recovered cannot distinguish platter state from that kernel's caches: "am I mounted" and "is it on the platter" are different claims. See [[trap-a-refused-mount-leaves-the-mountpoint-a-writable-local-directory-so-the-post-recovery-workload-check-passes-on-the-wrong-disk]].
- **A `sync -f`'d oracle is not a replay workload.** `tests/fence_crash_cuts.sh` cut 7 (0.89.18): the oracle files were synced, the only live load was one fsynced append per 500 ms (one dirty inode), so the foreign replay queued one buffer and the module declined the cut (`P-DRAIN-PEAK ... queued_buffers=1`, `P-DBG-REPLAY-CUT-VACUOUS`). A partial-replay cut needs continuous metadata churn (creates, renames, unlinks, directory fsynced per batch) up to the fence. The acknowledged batches are then a strong oracle for what recovery owes. Read `P-DRAIN-PEAK queued_buffers=N` before choosing a prefix; single digits mean the workload is wrong, not that the prefix should be 1. See [[trap-a-synced-dirty-death-oracle-is-not-a-replay-workload-and-leaves-the-cut-one-buffer-to-divide]].
- **An injector ending in withdrawal removes the caller under observation.** A withdrawn mount is shut down and `mxfs_sb_summary_final_sync` (`pal/linux/xfs_super.c:1786-1797`) returns on `xfs_is_shutdown` with `P-SB-SUMMARY-FINAL-SKIP`, taking no cluster lock; the lap reads as a clean unmount. `recov_complete_inject=1` (withdraws at 120 s, `P234-COMPLETE-DEADLINE`, `dlm/v5_mount.c:9040-9067`) and `=2` withdraw; `rman_inject=1` (`P-RMAN-INJECT`, `dlm/v5_mount.c:9230`) parks at SNAPSHOTTING with a healthy mount and is the right shape. Ask what state the injector leaves the observer in, not only the subject; related named skips: `P960-REFUSED-MOUNT-NOCOVER` (`xfs/xfs_log.c:2367`). Built with `tests/nonfallible_transition_stall.sh` (0.89.47). See [[trap-an-injector-that-ends-in-withdrawal-removes-the-very-teardown-caller-the-lap-was-built-to-observe]].
- **A knob lap that changes what reaches the platter must end in `chk_mxfs -v`.** `tests/d0946_disklive_knob_vs_aging.sh` A/B on `partial_iwrite_sole` (0.75.128) stranded a directory core (`P56-NL-LOGGED-DIR-SKIP`, `pub_skip_rearm=0`) and reported clean; it surfaced 20 min later in another harness's cold chk as "inobt-allocated agino 128 has a FREE core" (D-0957). Probes count decisions, name walks see dirents, only the offline check compares an inode's two records. Alternating arms hide damage (a knob=0 round can rewrite the buffer); one stranded object in N rounds is the expected shape. A dmesg capture starting at the last mark is not the lap's dmesg. Epilogue `COLDCHK` added in 0.85.2 (`MXFS_D0946_COLDCHK=0` skips); board row `tests/criteria/chk_clean.sh`. See [[trap-a-knob-lap-that-toggles-a-publication-filter-must-end-in-the-offline-structural-check]].

## Laps lost to the harness, not the rig

- **Delegated rig steps that fail before the rig still cost the lap.** (1) `tools/mkfs_mxfs` etc. are untracked build products: `./run.sh 2 tcp` aborted `PREP FAIL (mkfs)`; `make tools`, and `ls tools/mkfs_mxfs tools/chk_mxfs` beforehand. (2) A script written with Write has mode 664: both arms hit rc=126 after the fleet was prepped; `chmod 775` and `bash -n` first. (3) Bash auto-backgrounds a foreground command at 600 s; a ~13 min board always trips it and the agent returns while the board runs on as an orphan (flock `/tmp/mxfs_run.lock` protects it). Split the wait onto `/proc/<run.sh pid>/comm` or read the log afterwards; never re-launch. The reader is `python3 tools/criteria.py 2 tcp`; FLAKY is cross-run (last 11), not rows of the board just run. See [[trap-a-delegated-rig-step-that-fails-before-the-rig-costs-a-lap-check-tools-mode-and-the-600s-cap-first]].
- **Do not arm a fleet that is still rebooting.** `tests/sess482_chain130_affine_audit.sh` aborted twice `armed on only 30 of 32` with ssh rc=255 on test6/test7 and `mounted: 0/32`; its control lap `node_death_replay` reboots nodes by design. The nodes were fine and the sequencing was the fault. Any chain whose earlier stage kills, reboots, fences or unmounts nodes needs a positive readiness gate (all answer ssh and `/mnt/shared` mounted, ceiling 240 s from 60-90 s guest boot doubled, exit at 32/32), like `tests/rig_wait_free.sh`; a row PASS does not mean its nodes are back. Before filing "two nodes are bad", check whether the chain made them bad. See [[trap-arming-a-fleet-that-is-still-rebooting-from-the-previous-lap]].
