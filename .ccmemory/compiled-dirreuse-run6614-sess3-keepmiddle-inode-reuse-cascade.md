### The reframe (build 5240351B): force_block conflict + divergent extent map
Criterion = full `./run.sh {1,2,4,8} tcp` recorded in criteria.json. criteria.json's recorded 4/8 PASSes are STALE (older builds); current build must RE-validate — do NOT trust recorded PASSes without a current-build re-run.
- `dir_force_block=1` (compiled default, sess67, `xfs_mxfs_dlm.c:6560`) is the trigger for the cache_coherency regression: CRC error on ROOT dir block, `xfs_dir3_block_read_verify` → deterministic shutdown. `dir_force_block=0` → cache_coherency 2/tcp PASSES 2/2, but dir_reuse 4/tcp FAILS 0/4 (sess67 set force_block=1 to fix the sf→block conversion divergence). CONFLICT: force_block is GLOBAL and `mxfs_dir_should_force_block()` (`xfs_mxfs_dlm.c:6577`) can't distinguish the two fresh-shared-shortform cases — it just shifts WHICH test fails. Disabling `dir_addname_epoch_refresh=0` does NOT fix cache_coherency (epoch refresh gate is not the cause).
- UNIFIED ROOT: both tests fail with the same signatures — `P13-COLLIDE` (in-core dir-data buffer for a daddr holds a DIFFERENT incarnation's content), `P-IFLUSH-GAP-DETECT` (in-core dir data fork has a HOLE between data blocks; DABUF_MAP_HOLE source), `P49-STALEBASE` (whole-block writeback clobbers durable peer dirents). The dir's DATA-FORK EXTENT MAP diverges across nodes when two nodes grow the same shared dir. Per-block epoch/gen coherence is insufficient — coherence unit must be the WHOLE inode (extent map + bmbt fork), not one dir block (GPT-5.5 gap #4). For fresh-mkdir'd inodes the epoch gate is inert (master_ep=0).
- Fix locus identified: `mxfs_dlm_reload_inode` adopt-vs-keep (`mxfs_dir_epoch_adopt`, `xfs_mxfs_dlm.c:5328`, default 0). adopt=1 rereads whole disk extent map but adopts STALE-SMALLER disk when our grow isn't destaged → shrinks fork → hole → AG double-free (sess49 measured 8/8 FAIL). adopt=0 keeps in-core when dirty/grant_held (correct for our uncommitted grow; wrong when a peer durably grew). THE FIX: make adopt-vs-keep EPOCH-GATED — adopt disk when peer's master-handoff epoch is AHEAD of our last-commit epoch; keep in-core only for our own uncommitted-under-current-epoch work (GPT ACK-based whole-inode handoff).

### Breakthrough (build 5726D17A): keep-middle-block fix
`mxfs_dir_keep_middle_block` (module_param, DEFAULT 1) in `xfs/libxfs/xfs_dir2_leaf.c`, `xfs_dir2_leaf_removename` ~line 2252. Param defn in `xfs_mxfs_dlm.c` ~line 5465. Stock removename calls `xfs_dir2_shrink_inode` to free a now-empty data block; for a NON-LAST (middle) block that removes the extent but leaves di_size unchanged → GAP in the data-region extent map (sess49b's proven DABUF_MAP_HOLE torn-map root). FIX: under MULTI-NODE, if `dp->i_disk_size > xfs_dir2_db_off_to_byte(geo, db+1, 0)` (a block exists after db = it's a middle block), do NOT shrink — leave a valid EMPTY mapped data block (bests[db] all-free), `dbp=NULL; return xfs_dir2_leaf_to_block(...)`. No extent removed → no gap → no cross-node tear. The block is reused by later adds and freed normally once it becomes the tail.
- MEASURED (force_block=0): `dir_reuse_coherency` 4/tcp → 4/4 (was 0/4 torn-map FAIL); 8/tcp → 8/8 within the 480s run_coord budget at DEFAULT mht=300 — satisfies both correctness AND RULE-0 (no slow mht=1500 stopgap needed).
- WINNING CONFIG: `force_block=0 + keep_middle_block=1` makes BOTH conflicting tests pass (force_block=0→cache_coherency; keep_middle→dir_reuse). Removes the need for sess67's force_block=1.
- If 8-node dir ever hits NODE format (~800 entries), apply the same keep-middle to `xfs_dir2_node.c:1387` — but 8/8 PASS suggests the storm dir stayed LEAF, so not needed.

### Residual #1 — inode-reuse cascade (root proven; FIXED in build 24EDC1F3)
After the keep-middle fix, full 2/tcp = 14/17. Three fault tests (`fence_during_write`, `fault_netpartition`, `tcp_dlm_scaling`) FAIL 1/2 in the full suite but PASS standalone — a CASCADE after `dir_reuse_coherency` runs first. Cheap repro: `./run.sh 2 tcp dir_reuse_coherency fence_during_write` → dir_reuse PASS, fence FAIL. A/B CONFIRMED not caused by keep_middle (repro with `dir_keep_middle_block=0` too); pre-existing, regressed since sess58 (build 60EFBE5E had 2/tcp 17/17).
- PROVEN ROOT (probe build 94342F7: P-CR3-CANCEL + P-CREATE-ERR1 + P-CR62 in `xfs_create` out_trans_cancel @ `xfs_inode.c:2107`): dir_reuse's create+rm-rf churn frees an inode number, it's immediately reallocated; `xfs_dialloc` hands out the inode (dirties the trans), then `xfs_icreate`→`xfs_iget(XFS_IGET_CREATE)` returns **-ENOENT** for an inode that is FREE on disk (di_mode=0, `verdict=DISK-FREE=>incore-struct-stale`). du.ip stays NULL; trans already DIRTY → `out_trans_cancel` → `xfs_trans_cancel:1061` "Corruption of in-memory data (0x8)" → SHUTDOWN → cascades downstream fault tests. Ruled out as the ENOENT site: `xfs_iget_check_free_state`, XFS_INACTIVATING→out_skip, cache-hit P-IGET-ENOENT@`xfs_icache.c:772`. The ENOENT is from cache-MISS new-inode coordination (cf. sess127 durable-before-visible).
- THE FIX (`mxfs_create_needinact_flush`, default 1): `xfs/xfs_icache.c`, `xfs_iget_cache_hit` ~line 866 (the ENOENT site was line 869). When an IGET_CREATE finds an in-core inode still `XFS_NEED_INACTIVE` with `nlink==0`, upstream returns -ENOENT ("unlinked inodes cannot be re-grabbed") and fatally cancels the dirty create trans. Fix: for a multi-node CREATE, `goto out_inodegc_flush` (queue inodegc + return -EAGAIN → retry) so the pending inactivation completes and the inode recycles cleanly. Param defn in `xfs_mxfs_dlm.c` after dir_keep_middle_block. PROVEN (RULE 4): probe P-CR3-NEEDINACT fired 10× (the race DID occur) but was handled gracefully → NO P-CR3-CANCEL, NO shutdown; `./run.sh 2 tcp dir_reuse_coherency fence_during_write` → BOTH PASS.
- Related but distinct mechanism noted earlier (same cascade, DLM side): a freshly-dialloc'd inode's peer EX lock LINGERS (cached-until-BAST); the reuse EX acquire returns rc=-35 (EAGAIN, mode 5=EX) from `dlm/v5_mount.c:1286` (`mxfs_v5_dlm_inode_lock`, flags=0/NOQUEUE). The slow-path acquire loop (`xfs_mxfs_dlm.c:15255`) retries only 3×/50ms but the peer's BAST-release takes >150ms (P34-ACQ-SLOW = seconds) → gives up too early → dirty-trans cancel shutdown. Candidate: a freshly-dialloc'd inode CANNOT be legitimately held EX by a peer (any peer lock is a stale prior incarnation, different di_gen) → the new-inode EX acquire must retry/block/force-grant, e.g. via `mxfs_v5_dlm_inode_lock_retries` (`dlm/v5_mount.c:1311`, sess58, TCP-only, ABBA-safe because it keeps calling `mxfs_dlm_yield_basted_cached_ags`). Unused retry infra: `mxfs_v5_dlm_inode_lock_retries` (no callers). The needinact_flush fix (above) is what actually closed the cascade.
