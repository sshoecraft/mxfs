## Compiled: 8/tcp `dir_reuse` `readdir=799` single-dirent loss (sess38→sess40)

Central subject: the `cache_coherency` / `dir_reuse_coherency` ship-criterion blocker on an 8-node TCP-DLM cluster. `1/2/4 tcp` PASS; **8/tcp intermittently loses exactly one committed dirent** (`readdir=799` of 800; sub-modes `785`, `796`, whole-block ~49-entry), all nodes agree (`LOOKUP_ENOENT REREAD_MISS` = durable on-disk, not cache staleness), cascading to `DABUF_MAP_HOLE` / `xfs_dir3_block_verify` CRC-shutdown in later rounds. It is a RACE: round 1 usually passes; fires ~1–2× per 24 rounds. Across three sessions the diagnosis moved: **stale-EX/split-brain DLM grant (sess38) → membership split-brain formation+flap, FIXED (sess39) → residual async-writeback overlap across the EX handoff, with a TCP-flap detour that was refuted (sess40)**. Criterion still NOT met at end of sess40.

### sess38 — "stale-EX grant / split-brain" root (later superseded as the *mechanism*, but the split-brain half was real)
[[sess38-HEAD-handoff]] [[sess38-DECISIVE-loss-is-stale-EX-grant-bufepoch-eq-masterep]] [[sess38-DECISIVE-clobber-is-inail-clean-nonstale-subset-genblind]]

Decisive measurement (`P-DATACLOBBER-SKIP`, filter `comm!=rm`): the loss clobber is `kind=data daddr=120` (dir block 0), `buf_cnt=154 disk_cnt=155` (buffer one dirent behind durable disk), `bufgen==dirgen`, `buf_epoch==master_ep` (e.g. 329==329), `in_ail=1 bdirty=0 in_txn=0 stale=0 comm=xfsaild`. The buffer is a STRICT SUBSET of disk and reads **fully current by both the gen token and the node's own held grant dir-epoch, yet content-stale** — so every read-side gen/epoch heuristic is structurally blind (37 prior sessions of dir-block heuristics failed because the freshness tokens `b_mxfs_dir_gen`/`b_mxfs_dir_epoch` LIE). Mechanism named "zombie in_ail buffer surviving a tenure handoff": node committed 154 (in_ail), released+drained, peer added 155th, node re-acquired but the stale 154 BLI was never retired, and xfsaild background-reflushes it over the peer's add.

Why the epoch lies: `mxfs_v5_dlm_inode_dir_epoch` (dlm/v5_mount.c:1190) returns the node's *cached* grant dir_epoch, not a live master query. Master advances epoch only on cross-node handoff (`dg_grant_ex` dlm/dlm.c:2601). `P64-MASTER-HANDOFF` fired ~1100×/node so handoffs are detected — yet test1 held epoch 329 across a peer's EX-modify = it **retained a stale EX grant / never observed the handoff** = a BAST-delivery / mutual-exclusion failure. Corroboration: `P-STALEMASTER-GRANT` fired (split-brain mastership: transient membership divergence → two masters grant EX from independent `dg_shadow` tables); `P-DOUBLEGRANT` = 0× (single-master table internally consistent; the violation is cross-master). `active_nodes` is sorted+deduped (dlm/dlm.c:2144) so masters are consistent for the SAME set — the divergence is a transient membership window under the 8-node storm.

GPT-5.5 architectural verdicts (RULE 5 consults):
- [[sess38-GPT-architectural-fix-inail-survives-handoff-release-retire-genbump]]: MXFS treats the XFS AIL as if the node still owns metadata after the DLM lock is dropped. Strengthened Invariant 1: "flush dirty buffers before release" is INSUFFICIENT — the bad buffer is `dirty=0` but still an AIL checkpoint item. Correct rule: before EX→PR/NL demotion the dir resource must have ZERO in_ail/dirty/pinned/delwri/under-writeback buffers; **drain AND retire all AIL BLIs**, not just dirty ones. Two fixes: (1) release-side synchronous write+retire of every resource BLI while still holding EX (never skip-write+emulate-ioend; never `ail_delete` an uncheckpointed item; retire-without-write only with proof `mxfs_dir_buf_is_undestaged==false`); (2) gen-bump driven by DLM grant-seq/LVB on every EX re-acquire following any peer EX (Policy A). Existing code's release path `mxfs_dir_flush_data_blocks` (xfs_mxfs_dlm.c:7992) is best-effort — `mxfs_dir_flush_one_daddr` BAILS on lock contention (`P-FLUSH-LOCKWAIT-BAIL`); the `!DONE`-only retire gate (xfs_mxfs_dlm.c:1683+4090) misses the measured DONE-destaged zombie.
- [[sess38-GPT2-DLM-fix-design-split-brain-mastership-write-authority]]: stateless `master = active_nodes.nodes[hash % count]` is split-brain-prone. Full design: (1) recovery barrier on membership change (`DLM_RECOVERING`, freeze grants → fence → remaster state transfer → resume); (2) version every DLM message with `{cluster_view_gen, lockspace_recover_gen, resource_master_gen, sender_incarnation}` and reject grants on mismatch; (3) **blocking BAST** (master must not grant EX to B until RELEASE_ACK from holder A or A fenced — a late BAST after peer-grant is the correctness bug); (4) local **write-authority token** `{granted_mode, resource_data_seq, grant_cookie, write_authority, revoking, atomic io_refs}` that xfsaild must hold (`mxfs_begin_metadata_writeback`) before ANY metadata submit; on `-ESTALE` a CLEAN stale buffer is DROPPED (never written), a DIRTY/pinned stale buffer after EX loss is FATAL; (5) optional on-LUN owner record (PR-fenced, TOCTOU-prone alone). Smallest piece to kill the measured loss: reject-stale-grant + write-authority token gating xfsaild dir-metadata writeback.

Refuted in sess38 (all default-off levers): `dir_subset_guard=1` (write-suppress → round-2 fail → shutdown by round 10 — confirms "write-side DROP/suppress of dir DATA = corruptor"); `dir_release_retire_done=1` (retire-without-write → round-1 shutdown); `dir_tenure_evict=1` (BEST read-side lead, 0%→~67%, but INSUFFICIENT — the epoch the buffer carries EQUALS the held grant epoch); `dir_tenure_evict+dir_evict_prior_tenure`; `dir_refresh_inplace` (memcpy disk→buffer → `xfs_dir3_block_verify` corruption — disk image is not a drop-in for the in-core buffer's CRC/log/verifier state). [[sess38-refuted-tenure-stale-bypass-keepguard]]: `dir_tenure_stale_bypass=1` (bypass the read-path `!in_ail||!undestaged` keep-guard for tenure-stale buffers) → round-21 loss + **11 CRC shutdowns**. Lesson: the in_ail-undestaged keep-guard MUST be honored — you cannot distinguish "my un-landed work" from "a stale base that looks un-landed" by clearing it on a flag heuristic; the read side cannot safely refresh an in_ail-undestaged stale base by invalidation.

Test/env facts (sess38): `dirwr=1`/`instr=1` MASK the race (logging slows the storm → false PASS) — use `dataclobber=1` (does not mask). `MXFS_EXTRA_MODARGS` → insmod needs the BARE param (`dataclobber=1`, NOT `mxfs.dataclobber=1`); always verify `cat /sys/module/mxfs/parameters/<p>`. Reboot ALL 8 VMs (`virsh -c qemu:///system destroy/start test1..test8`) before each run (they wedge rmmod after CRC-shutdown). Repro needs full 24 rounds (`DRC_ROUNDS=24`); 2–3-round runs falsely pass.

### sess39 — MEMBERSHIP split-brain root-caused and FIXED (keeper `8CC09D97`)
[[sess39-ROOTFIX-membership-splitbrain-formation-and-flap]]

Root-caused + fixed the 8/tcp CATASTROPHIC (0/8, `readdir=0/163/796` → `DABUF_MAP_HOLE`) failures = membership split-brain (PROVEN). Inconsistent `active_nodes` → `master=nodes[hash%count]` diverges → two nodes grant EX for the same dir. Two triggers, same mechanism: (1) **formation ramp** — 8 nodes converge 1→8 holding divergent views (`P-STALEMASTER-GRANT ino=128 active_count=5/6` at t=47s when workload round-1 started before convergence); (2) **mid-run TCP flap** — under storm a peer's TCP stalls ~7s, all 7 peers drop then reconnect, and `v5_peer_disconnect_cb_tcp` (dlm/v5_mount.c) IMMEDIATELY purged locks + unregistered lease + refreshed active_nodes (8→7), bypassing the cooldown in dlm/mount.c ("membership changed" logs at DEBUG → invisible in dmesg).

The fix (both in dlm/, DEFAULT-ON, kill-switchable, KEEP):
1. **Deferred TCP-death** (`tcp_death_grace_ms=15000`): disconnect marks peer SUSPECT, not immediate purge; grace-checker `v5_tcp_death_worker_fn` declares death only if no reconnect within grace; `v5_peer_connect_cb_tcp` cancels on reconnect; genuine death still caught by `v5_lease_expire_cb`.
2. **EX-grant membership-settle gate** (`memb_settle_ms=6000`): `dlm_lock_impl` BLOCKS an EX acquire (bounded 60s) while `dlm_membership_settling()` (active set changed within window; new `ctx->last_memb_change_ms` stamped in `update_active_nodes`). Single-node + steady-state never gate (zero perf impact).

Evidence it works: `P-STALEMASTER-GRANT` → **0** on fresh-boot 8/tcp; catastrophic `readdir=0/163` GONE; 2/tcp dir_reuse 3/3 PASS. Harness `tests/drc_loop8.sh <iters> [modargs]`.

Residual after the membership fix (the criterion blocker): rare steady-state xfsaild ZOMBIE reflush — `stale=0 disc=0` cluster-wide, `P-DATACLOBBER-SKIP kind=data daddr=120 buf_cnt=154 disk_cnt=155 in_ail=1 comm=xfsaild` → `readdir=799`. Traced: on a handoff EX acquire the fast-path (xfs_mxfs_dlm.c ~13760) does eager `mxfs_dir_drain_evict_data_blocks` but SKIPS blocks it can't evict (`left>0` — block 0 LOCKED by this node's own xfsaild mid-reflush) → the skipped stale block-0 buffer is reflushed stale. RACE: acquire-side evict vs xfsaild-flush of the same buffer.

Refuted in sess39 (all on top of the membership fix, so genuinely the wall, not split-brain-confounded): `dir_tenure_reflush_skip=1` (round-1 `readdir=0` — skip catches fresh writes); `dir_release_retire_bli+dir_release_retire_done` (`readdir=796` — over-lost 4; the `lseq==wseq` destaged check is unreliable); `dir_force_evict+dir_tenure_evict` (`readdir=268 lookup_fail=161` — force-evict creates zombie BLIs); `dir_refresh_inplace=1` (`xfs_dir3_block_verify block 0x78` corruption — disk not a drop-in for the in-core buffer). Conclusion: EVERY buffer-layer intervention (skip/drop/retire/force-evict/refresh) corrupts or over-loses — the residual needs an ARCHITECTURAL fix (candidate options: abort the in-flight xfsaild write at acquire-evict instead of skip; write-through FUA dir DATA blocks so xfsaild never holds one to reflush; GPT's write-authority token).

### sess40 — TCP-flap detour (built, then REFUTED) and the writeback-completion-barrier direction
Sequence of reframes within sess40 (ccloop `4cb2d0a2`):

1. [[sess40-FIX-dir-writeback-completion-barrier-readdir799]] — build `E12A35EE`, GPT-5.5 consult #1 design. Diagnosis: single committed dirent (`node3_f46`, `dirino=131`) durably lost; creator added it (`P13-NADD`), verified absent (`P26-DSCAN-MISS`), in-core extent map == disk exactly (`P33-DSCAN-ONDISK` — NOT bmbt staleness); DECISIVE NEGATIVES `P-DATACLOBBER-SKIP` + `P25-RELVERIFY-MISMATCH` both SILENT. Root (GPT): a dir DATA/leaf write bio submitted in a PRIOR EX tenure COMPLETES AFTER the node released EX and a peer cold-read+RMW'd+rewrote the block → the late bio lands an older image, reverting the peer's dirent. Detector-blind because at the stale write's SUBMIT disk lacked the entry. `daddr` REUSE (rm-rf+recreate) makes a freed-block bio land on the reallocated daddr. Fix (canonical clustered-FS invariant — EX tenure owns the writeback LIFETIME, GFS2 glock / OCFS2 lock): `m_mxfs_dir_wr_inflight` atomic (inc at `xfs_buf_submit_bio` for multi-node dir data/block/leaf/free/da3_node writes, dec at `__xfs_buf_ioend`, per-buffer `b_mxfs_dir_wr_counted`), and the dir EX release fence (xfs_mxfs_dlm.c ~8799) WAITS `m_mxfs_dir_wr_inflight==0` before releasing. No write dropped — only the handoff delayed. `mxfs.dir_wr_barrier` kill-switch.

2. [[sess40-REFRAME-799-is-tcp-flap-not-buffer-barrier-noop]] — the mount-wide barrier (`E12A35EE`) was REFUTED as a NO-OP: `P40-WRBARRIER` never fired — the counter is ALWAYS 0 at release because publish-before-notify already writes dir blocks SYNCHRONOUSLY (zero in-flight dir bios at handoff). This memo then (temporarily) reframed the 799 as CORRELATED with a transient TCP DLM flap: failing iter test7 showed `TCP peer … disconnected — deferring death 15000 ms` at t=46.344 then `reconnected — transient flap absorbed` at t=46.846 (~500ms gap), sess39 deferred-death absorbed it but the entry was still lost. Proposed unified root "both 8/tcp modes = TCP flap under load" (mass-fail = flap >15s → split-brain; 799 = flap <15s → one in-flight DLM grant/release message lost in the socket gap). Likely flap mechanism: a node blocked in a long synchronous DLM op (drain / CAW poll / blocking `msg_cb`) stops servicing its TCP recv socket → peers' `mxfs_pal_tcp_send` 16MB buffer fills → 5s sndtimeo+3 retries → `mxfs_pal_tcp_shutdown`. **This TCP-flap unified-root theory was subsequently REFUTED — see #4/#5 below.**

3. [[sess40-FIX-tcp-flap-prevention-send-no-teardown]] — build **`A985424B`** (KEEPER, dlm/peer.c `mxfs_peer_send` ~914): a TRANSIENT send failure (`-ETIMEDOUT/-EAGAIN/-EWOULDBLOCK` = slow receiver / full sndbuf, not dead) no longer `mxfs_pal_tcp_shutdown`s + fires disconnect_cb — it returns `-EAGAIN`, keeping the connection up (caller retries; TCP still holds the bytes). Only HARD errors (ECONNRESET/EPIPE/ENOTCONN) tear down. True death still caught by keepalive (~19s) + UDP lease (~75s). Effect: 8/tcp 3/6→**6/8**, 2/tcp 3/3 (no regression) — helps the MASS-FAIL / membership-flap mode. REVERTED dead-end (do NOT repeat): changing `mxfs_pal_tcp_send` in kern.c to return `-EAGAIN`(nothing sent)/`-ECONNRESET`(partial) instead of uniform `-ETIMEDOUT` (build `5A98FD22`) REGRESSED 2/tcp to 0/3 — `mxfs_pal_tcp_send` has many callers (discovery/lease/journal/md_request) that retry-loop on `-EAGAIN` → infinite retry → hang. Flap-prevention must live ENTIRELY in dlm/peer.c; pal keeps returning `-ETIMEDOUT` uniformly. **`A985424B` is KEPT as a correctness improvement but does NOT fix the 799.**

4. [[sess40-CORRECTION-799-is-concurrent-add-not-flap-bmbt-extent-fork]] — CRITICAL CORRECTION: on `A985424B` the 8/tcp still lost a dirent at ROUND 1 with ZERO flap events in dmesg (no "deferring death", no "reconnected", no "slow peer"). The test7-flap↔loss correlation was COINCIDENTAL — a flap often co-occurs under the storm but does not cause the loss. The 799 is a concurrent multi-node dir-block lost-update (the ~130-session core bug): durable, all nodes agree, happens even at round 1 on a FRESH dir (NOT cross-tenure/daddr-reuse). Sub-modes: single dirent (`799`, data-block content) and whole-block (~49 entries) → `DABUF_MAP_HOLE` (xfs_da_btree.c:2876). KEY UNEXPLORED LEAD: `dataclobber` and `dir_relverify` only inspect dir3 DATA/LEAF block CONTENT — they do NOT cover the dir INODE buffer (di_size/di_nextents/inline extents) or bmbt (data-fork btree) writes. A dir-GROWTH race (node A allocates a new dir data block + adds extent record N; B's stale inode/bmbt write reverts extent N) would lose block N's entries, unmap the leaf's target → `DABUF_MAP_HOLE`, and be INVISIBLE to dataclobber. NEXT: add a write-chokepoint detector for the dir INODE extent fork + bmbt blocks (analogous to dataclobber; `P60-BMBTWRITE` probe already exists xfs_mxfs_dlm.c ~982); check `mxfs_submit_partial_inode_write` for the shared dir inode.

5. [[sess40-REFUTED-countregress-799-is-cross-node-concurrent-overwrite]] — added `P-COUNTREGRESS` (build `B17141DA`, instrumentation-only): at `xfs_buf_submit_bio` (pal/linux/xfs_buf.c) compute active-dirent count via `mxfs_dir3_data_fingerprint` vs new per-buffer high-water `b_mxfs_dir_wrcnt_max` (reset on `xfs_buf_stale`); fires when a write's count drops below the buffer's own high-water = a per-node stale-base RMW. RESULT: `P-COUNTREGRESS` did NOT fire on a failing iter (round 20, `readdir=785`, no flap, no dataclobber, no relverify). So the loss is NOT a per-node count regression — each node's buffer is internally consistent (monotonic count); the lost entry was added by a PEER and this node's buffer simply never held it. = a CROSS-NODE concurrent/overlapping dir-block write: two nodes write the same block, each consistent with disk-at-its-own-submit, net one entry lost (dataclobber blind because at each submit disk also lacked the other's entry).

6. [[sess40-PROVEN-799-is-release-drain-gap-async-writeback-overlap]] — PROVEN BY ELIMINATION (the standing sess40 conclusion). On no-flap failing 8/tcp iters (build `B17141DA` = keeper `A985424B` + detectors), ALL of these are SILENT at the failure: no flap; no `MX-DOUBLEGRANT` (dlm.c:601 single-master audit); no `P-STALEMASTER-GRANT`; no `P-COUNTREGRESS`; no `P-DATACLOBBER-SKIP`; no `P25-RELVERIFY-MISMATCH`. CONCLUSION: **the DLM lock layer serializes correctly (one EX holder at a time), but the WRITEBACK of a dir-data block crosses the EX handoff boundary = async-writeback overlap / release-drain gap** (Architectural Invariant #1 violated in a way the release fence doesn't catch). Why the release fence misses it: it decides "durable" via `mxfs_dir_buf_is_undestaged(dbp)` = `b_mxfs_logged_seq != b_mxfs_written_seq` (xfs_mxfs_dlm.c ~15715), but `written_seq` is snapshotted at write SUBMIT, not I/O COMPLETION — a block whose bio was submitted-but-not-completed reads `logged==written` = "destaged" and the fence releases EX before the bio lands. The mount-wide `dir_wr_barrier` was a no-op because it counted bios at SUBMIT and most dir writes are synchronous; the PROBLEM block is an ASYNC xfsaild write the fence wrongly passes.

FIX DIRECTION (end-of-sess40, the surviving plan — GPT consult #1 was right idea, wrong granularity/mount-wide-submit-count; do it PER-INODE with completion-stamped state):
1. Per-DIR-INODE in-flight dir-bio counter (not mount-wide) so the release wait has something real to wait on;
2. At release, for each cached dir data/leaf/free block: take a BLOCKING buffer lock (waits out any in-flight bio), then if dirty/in_ail/not-written-to-completion → synchronous `xfs_bwrite`+wait UNCONDITIONALLY — do NOT trust the `lseq==wseq` `mxfs_dir_buf_is_undestaged` heuristic; either stamp `written_seq` at I/O COMPLETION or add a separate `b_mxfs_io_inflight` flag (set at submit, cleared at ioend, waited on);
3. Acquire-side: `mxfs_dir_drain_evict_data_blocks` must NOT LOCKED-SKIP a block with an in-flight write — wait it out, then evict + cold-read.

Caveat: `dir_reuse` only ADDS within a round, so any in-round count loss is the bug (a genuine multi-dirent remove also regresses count, but that is not this test). The mass-fail membership-flap mode is SEPARATE (helped by `A985424B`).

### Consolidated lessons / recurring failure modes
- **Freshness tokens lie under stale-EX**: `bufgen==dirgen` and `buf_epoch==master_ep` can both read "current" on a content-stale buffer → every read-side gen/epoch invalidation is structurally blind. Writeback/freshness authority must come from the DLM, not a local epoch or a disk-compare (acquire-side `mxfs_dirrefresh` disk-compare is REFUTED-racy: the peer write isn't on the LUN yet at evict-time).
- **Write-side DROP/suppress of dir DATA = corruptor** (repeatedly proven: `dir_subset_guard`, `dir_refresh_inplace`, `dir_tenure_reflush_skip`, retire-without-write). Never suppress the physical write; fix the BASE before the modify, or delay the handoff — never drop data.
- **The in_ail-undestaged keep-guard must be honored** — a flag heuristic cannot distinguish "my un-landed work" from "a stale base that looks un-landed."
- **`written_seq`/`lseq==wseq` (`mxfs_dir_buf_is_undestaged`) is unreliable** as a durability proxy — it stamps at SUBMIT, not COMPLETION; a submitted-not-completed async bio reads "destaged."
- **AIL-empty / disk==incore-at-sample is NOT a proxy for "no in-flight bio."** The release fence proves a sample instant, not "no already-submitted bio can still land."
- **Flap↔loss correlation was coincidental** — under the 8-node storm a transient TCP flap co-occurs but does not cause the single-dirent loss.
- **pal `mxfs_pal_tcp_send` must keep uniform `-ETIMEDOUT`** — many retry-looping callers hang on `-EAGAIN`. Flap-prevention belongs in dlm/peer.c only.
- **Instrumentation masks the race**: `dirwr=1`/`instr=1` slow the storm → false PASS; `dataclobber=1` does not mask. Full 24 rounds + all-VM reboot required to repro.
- **Unexplored root candidate carried forward**: the dir INODE extent fork / bmbt btree writes are NOT covered by `dataclobber`/`dir_relverify`; a concurrent dir-GROWTH extent-map clobber remains a live hypothesis for the whole-block loss + `DABUF_MAP_HOLE` cascade.

Harnesses (RULE 3, in-tree): `tests/drc_loop8.sh <iters> [modargs]` (reboot-clean 8-node loop); `tests/drc_cap8.sh <iters> [modargs]` (breaks on first FAIL, pulls `drc_fail_r*.dmesg` before reboot wipes it). Key probe modargs: `mxfs.dataclobber=1`, `mxfs.dir_relverify=1`, `mxfs.dirwr=1` (P40). Always re-verify 1/2/4 tcp before any criterion claim.
