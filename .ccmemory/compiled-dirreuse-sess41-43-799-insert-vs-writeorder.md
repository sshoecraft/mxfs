## Compiled: dir_reuse `readdir=799` durable dirent loss — sess41→43 (ccloop 4cb2d0a2)

Central subject: the `cache_coherency`/`dir_reuse_coherency` ship-blocker. 8 nodes concurrently grow one shared dir (ino=131) 0→800 entries over 24 rounds (rank1 `rm -rf` the dir at each round end → new i_generation + reused daddrs). ~33% of iters durably lose ONE (sometimes many) just-added dirent → `readdir=799`, LOOKUP_ENOENT, all nodes agree, no flap. The three sessions walked the diagnosis through three successive framings — **insert-time drop → post-submit write-ordering → stale-base RMW clobber** — refuting each fix class with instrumented evidence. Criterion NOT met at end of sess43.

### Standing invariants (proven, carried across all three sessions)
- **EX is correctly serialized.** `MX-DOUBLEGRANT` silent; `P42-STALEEX-SERVE`=0 (held=1 at every serve); `P63-FASTEX-HANDOFF`=0 for ino=131. No simultaneous double-grant. The storm dir is always contended → state≠CACHED → every EX modify diverts to the SLOW path; fast-path handoff machinery never runs for it. Coherency rests entirely on slow-path acquire-reload + release-drain.
- The lost dirent IS added in-core under a valid held EX (`P13-NADD`/`P13-LADD` fire, leaf_count increments), then durably vanishes on a handoff, absent from disk after (DSCAN-MISS).
- `mht=1000` (long holds, few handoffs) STILL fails → NOT handoff-frequency driven.

### sess42 — the "stale-base RMW clobber" framing (corrects sess41)

Victim `node2_f23.md5` in daddr=16745864: node2 wrote it up to count 112, **then test6 wrote it up to count 132 WITHOUT the victim** — a count-INCREASING stale-base RMW that fools BOTH the count-regression detector AND the sum=801 discriminator. So the loss is a stale-base RMW clobber, not insert-loss; the sum discriminator is ambiguous. Kept (correct but insufficient alone): **`b_mxfs_written_seq` stamped at SUBMIT was wrong** — deferred to `__xfs_buf_ioend` (gated `b_mxfs_dir_wr_counted`, real-bio only) so `mxfs_dir_buf_is_undestaged` no longer reports in-flight/skip-emulated writes as durable; `dir_wseq_at_completion` default 1 (NOT re-verified on 1/2/4). Refuted: `dir_write_merge` (inert dko=0), `dir_release_flush_all_done`, BTREE-vacuous bail (`P42-VACUOUS-DURABLE`=0×), prior-tenure-evict. Smoking-gun path: `P-TCPEX-REACQ ino=131 (cached EX, mirror !held → re-acquire)` → `P63-HANDOFF post_release=1 disk-superset adopt` → `P62-RELOAD-FORK-SHRINK` → creator reload-adopts disk WITHOUT its own un-checkpointed add. - [[sess42-CONFIRMED-stale-WRITE-not-base-grantevict-plus-wseq-both-insufficient]]: A/B with BOTH `dir_grant_evict=1` (acquire reads current/fresh base) AND `dir_wseq_at_completion=1` STILL fails 8/tcp → the RMW node is NOT reading stale; a node durably WRITES an image missing a just-added entry → the loss is a **stale WRITE, not a stale base**. grant_gen machinery covers READ/base side but not the write. Proposed a content-superset (NOT count) `P-STALEWRITE` name-set probe at the dir-data write chokepoint.
- [[sess42-ELIM-fua-write-plus-grantevict-fail-broken-path-bypasses-release-flush]]: `dir_release_fua_write=1` (creator SCSI-FUA to platter, bypass LIO/SCST write-back cache) + `dir_grant_evict=1` BOTH ON still fail. Cumulative elimination — every release/durability/base lever refuted. Conclusion: the broken path NEVER reaches release-flush machinery; the creator's add is DISCARDED from in-core (cached-EX demote → reload-adopt) WITHOUT ever being written — the cached-EX / master-grant DIVERGENCE.
- [[sess42-SMOKINGGUN-cached-EX-stalegrant-demote-discards-uncheckpointed-dir-work]]: precise site = `xfs/xfs_mxfs_dlm.c` ~13485-13516 (TCP-only cached-EX stale-grant demote). Fix directions: (1) verify grant held BEFORE each modify under cached-EX even mid-batch → divert to slow-path re-acquire; (2) fail-closed if un-checkpointed work at demote. Deeper root = where the master releases this node's grant while its in-core `i_dlm_mode` stays EX without callback (lease expiry / peer steal / `mxfs_dlm_purge_stale_for_resource` / acquire-timeout-retry win path).
- [[sess42-REFINE-reload-always-adopts-disk-superset-no-shrink-loss-is-block-never-durable]]: `P62-RELOAD-FORK-SHRINK` shows **shrink=0 in EVERY instance** (disk_nx≥incore_nx, node adopts disk superset) → candidate A (reload orphans a block by shrinking the dinode extent map) REFUTED. The release-drain (`mxfs_dir_data_durable`/`mxfs_dir_flush_data_blocks`) iterates `for_each_xfs_iext(&ip->i_df)` = CURRENT extent map — a block dirtied this tenure but no longer in the current (or reloaded-smaller) map is never drained. ### Net state at end of sess43 (the actionable frontier)
Serialization is correct. The loss is a **durable single-/multi-dirent stale-base RMW clobber**: a node RMWs a dir DATA block on a stale base (its OWN cached/pinned buffer that lagged a peer's durable adds, or across a growth conversion / handoff), and writes it durably. Both release-side durability flush AND acquire-side evict are PROVEN insufficient; the write-submit union-merge chokepoint is structurally inert (decoupled from the EX txn). The remaining architectural fix is GPT's **per-tenure checkpoint fence** (flush all tenure-dirty dir metadata — tracked via `xfs_trans_log_buf`/`xfs_trans_log_inode`, incl freed/converted blocks + dinode + bmbt — home BEFORE any EX downconvert/handoff; cached-EX impossible without a valid grant; reload never discards undestaged local work / fail-closed), and/or a coherent rebase at MODIFY time on the buffer the addname RMW uses. Decisive next experiment: `tests/drc_trace.sh` at an early/mid round with the 64K dland ring, trace ONE victim end-to-end (P13 add daddr → dland count trajectory for that daddr in that round, real-ns ordered) to pin the exact clobbering write's node/comm/incarn, then fix at THAT path.
