## Root cause (proven, native-timing dmesg)
Dir coherency on TCP is **eventually-consistent via a LOSSY/LAGGY async EVICT-RING-DIRMOD heartbeat** (`note_dir_modified` → `mxfs_v5_dlm_note_dir_modified` → DIR_MODIFY, bumping per-node `i_dlm_dir_gen`), NOT strongly-consistent via the DLM lock. Concrete trace: dir `ino=17313366` (`.tcp_dlm_scaling`, shortform fmt=1); test1 (failing rank1) stuck at `EVICT-RING-DIRMOD gen->4` while test2 reached `gen->13`. test1 reloaded when `n2_rK.done` existed (gen 4), RMW'd its own entry onto that base, and NEVER got the heartbeat for test2's REMOVAL (gen 5+). So `i_dlm_dir_gen (4) == loaded_gen` ⇒ "fresh" ⇒ stale-base detector never fires ⇒ test1 durably re-publishes a fork still containing `n2_rK.done` ⇒ **peer's removed dirent RESURRECTED = durable split-brain** (survives a node1-EX-op BAST that should force peer reload). The test: each node does 150 rounds of create→rename→remove its OWN entry in one shared dir; rank1 asserts empty. The ~1/30 loss is when heartbeat convergence loses the race vs rank1's check. [[sess10-tcp-dlm-scaling-heartbeat-gen-lag-root]].

Framed as double-grant: dirs are kept **cached-EX on BOTH nodes** and reconciled via the lossy heartbeat instead of a real DLM BAST. That "cached-EX-on-both + async reconciliation" scheme is the bug for RMW metadata. [[sess10-double-grant-mht-grant-before-release-hypothesis]].

This validated `tcp_dlm_scaling` 2/2. grant_gen is stamped every grant episode and delivered over **acked TCP = RELIABLE**.
- TCP dir modify takes a REAL per-inode DLM EX (`mxfs_v5_dlm_inode_lock` → `mxfs_dlm_lock` on `ctx->dlm`). Release/`bast_process` sets `i_dlm_mode=NL` before unlock (2869/3545/8346/8369).
- `mxfs_dlm_reload_inode` (xfs_mxfs_dlm.c ~4799) is RELIABLE when reached: `xfs_buf_stale`+clear `XBF_DONE` (~4997) → fresh FUA re-read from the coherent LUN; only skips if the buffer carries THIS node's uncheckpointed mods (P91-RELOAD-PROTECT); shortform self-skip disabled (sess49).
- **CRITICAL GAP:** `mxfs_v5_dlm_inode_held` (dlm/v5_mount.c:1350) **RETURNS 1 (no-op) on TCP** — it only queries CAW (`ctx->dlm_caw`). So slot-ownership detectors P106-STALE-EX / P108-REACQUIRE silently do NOTHING on TCP (why P106 never fired). The XFS layer currently has NO reliable way to query TCP DLM grant state. CAW does NOT exhibit this bug (atomic slot mutual-exclusion). [[sess10-FIX-PLAN-use-dlm-grant-gen-not-lossy-evictring]], [[sess10-SYNTHESIS-handoff-and-final-target]].

## Concrete fix plan — use reliable TCP DLM grant_gen (preferred implementation)
[[sess10-FIX-PLAN-use-dlm-grant-gen-not-lossy-evictring]]: use the authoritative, already-existing TCP DLM `grant_gen` as the dir staleness signal instead of the lossy eviction-ring.
1. Add `mxfs_v5_dlm_inode_grant_gen(ctx, ino)` (dlm/v5_mount.c + .h): for `ctx->dlm` (TCP) look up the inode resource under `table_rwlock`, return THIS node's current GRANTED `grant_gen` (0 if not held); mirror `make_inode_resource`. CAW returns 0/unsupported.
2. xfs/xfs_mxfs_dlm.c: add per-inode `i_dlm_cached_grant_gen`, set when a slow-path acquire completes (~7200-7330, where grant published / `i_dlm_mode` set EX).
3. On the dir-EX fast-path serve (~6520 dir-strict gate else-block / ~6809): query current grant_gen; if `!= i_dlm_cached_grant_gen` the lock changed hands (a peer was granted) → force slow-path reacquire + `mxfs_dlm_reload_inode` BEFORE the RMW.
4. MHT preserved: within one continuous tenure grant_gen does NOT change → fast path keeps serving (no starvation); changes only when a peer actually got the lock = exactly GPT's once-per-tenure reload. First read: dlm/dlm.c lock-table lookup (`resource_hash` + bucket walk + `resource_equal` + `owner==local` + `state==GRANTED` → grant_gen).

## Correction — a LOCAL grant_gen check is insufficient
[[sess10-CORRECTION-local-grantgen-insufficient]]: a purely-local `mxfs_dlm_local_grant_gen` walking THIS node's table cannot detect "a PEER got the lock since I cached it" — when node B fast-paths a dir-EX MODIFY without touching the DLM, its local entry is UNCHANGED (gen==cached), exactly as stale as `i_dlm_mode`. Authoritative current-holder/grant_gen lives on the resource MASTER; if node B isn't master it needs a network round-trip = a real reacquire (the thing the fast path avoids). No cheap reliable purely-local signal exists. So the fix is inherently GPT's: a REAL DLM reacquire (round-trip) when tenure may have changed, MHT-bounded (per-tenure, not per-op). The reliable "tenure may have changed" trigger is a **BAST received** (reliable, acked TCP). The bug therefore narrows to ONE of:
- **(a)** node B keeps fast-path-serving EX MODIFYs DURING the MHT-defer window (state stays CACHED), RMW'ing on a base a peer is invalidating → fix: do NOT serve EX-modify while a BAST is pending for a CONTENDED dir (reads OK / drain current batch then honor); OR
- **(b)** after honoring the BAST + release + later reacquire, the reacquire does NOT reload because `i_dlm_mode` wasn't actually demoted to NL on some release path → fix: ensure release/demote sets `i_dlm_mode=NL` and clears cached state on EVERY path incl. MHT dwork honor.

## Coherency-model synthesis (read FIRST next session)
[[sess10-SYNTHESIS-handoff-and-final-target]]: the coherency model is **DLM-based, NOT heartbeat-based** (proven from `mxfs_dlm_dir_durable_signal` comment, xfs_mxfs_dlm.c:9984-10001): a peer that reads the dir acquires PR/EX → forces OUR BAST release drain (invariant #1) → blocks durable BEFORE peer reads. The eviction-ring is only an EVICTION OPTIMIZATION, not the primary coherency mechanism. So the intended flow is reliable IF the BAST demotes; the bug is **necessarily a BAST that did NOT demote this node** (deferred and never honored, or a dropped/reordered TCP BAST), leaving a stale cached grant the fast path trusts. Where to look: trace BAST end-to-end on TCP — `process_remote_request` (peer EX) → send BAST → `mxfs_dlm_bast_notify` → branch (ACQUIRING/pinned/MHT-defer/immediate/active-holders) → is demote ALWAYS eventually run? Prime suspect: **MHT-defer** keeps state==CACHED + arms `i_dlm_bast_dwork`; if the dwork's early-out (`mxfs_dlm_bast_dwork_fn` ~4370: `if(!i_dlm_bast_pending) return`) fires wrongly, or the dwork is cancelled by a re-acquire, the BAST is DROPPED → stale cache persists.
