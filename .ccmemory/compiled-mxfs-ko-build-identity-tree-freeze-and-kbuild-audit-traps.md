# mxfs.ko build identity, the frozen tree, and what Kbuild actually compiles

Central topic: the module the rig measures is whatever `mxfs.ko` the nodes loaded, and the tree's `mxfs.ko` is the reference every harness compares against. Most traps below are one of three confusions: which build is this, did the build move under a running experiment, and does this code exist in the build at all. Two further notes (slab-merge zombies, a repair at the measurement point) are measurement-integrity traps from the same debugging area.

## 1. Identifying the build: srcversion is weaker than it looks

- `srcversion` hashes sources, not linked objects, and modpost hashes only dependencies in the SAME directory as the object. A prototype added to `pal/pal.h` rebuilt the module (size and mtime changed) with an identical srcversion; `include/mxfs/*.h` and `compat/` are equally invisible. After a header-only change in `pal/`, `include/` or `compat/`, compare `sha256sum mxfs.ko` (nodes keep the loaded file as `/root/mxfs.ko.prep`) and force the prep; a harness that checks fleet-vs-tree by srcversion will accept a stale fleet. [[trap-modpost-srcversion-hashes-only-same-directory-sources-so-a-pal-h-change-keeps-the-srcversion]]
- A srcversion that differs from the tree's proves nothing about the linked objects either (see the scratch-compile trap below). Verify a change landed by `strings -a mxfs.ko | grep <marker unique to the change>`.
- `mxfs.ko` declares no `MODULE_VERSION`, so `/sys/module/mxfs/version` does not exist and `modinfo -F version` is empty; the package version lives only in VERSION, dkms.conf and tool `-D` flags. Identify a DKMS build by three agreeing srcversions: `/sys/module/mxfs/srcversion` (loaded), `modinfo -F srcversion mxfs` (installed), `modinfo -F srcversion /var/lib/dkms/mxfs/<V>/$(uname -r)/$(uname -m)/module/mxfs.ko*` (built for V), plus `dkms status` saying `installed`. Corollary: srcversion does not move when only VERSION changes; a container build check for the same kernel reproduces the DKMS srcversion exactly, a cheap cross-check. [[trap-mxfs-ko-has-no-module-version-identify-the-loaded-build-by-srcversion]]
- A scratch compile made by `rsync -a /src/mxfs/ $S/` copies `mxfs.mod` (kbuild's object list of absolute paths). On a later incremental rsync the tree's `mxfs.mod` overwrites the scratch one while the excluded `.mxfs.mod.cmd` still matches, so it is not regenerated and the link uses the TREE's old `.o` files. Symptom: marker strings absent from the scratch `.ko` although the scratch `.o` has them. After every rsync into a scratch copy, remove `mxfs.mod`, `mxfs.mod.c`, `mxfs.mod.o`, `Module.symvers`, `modules.order` (or add the matching `--exclude`s), then verify with `strings -a`. Never rsync the other way. [[trap-scratch-compile-rsync-copies-mxfs-mod-links-tree-objects]]

## 2. The tree's mxfs.ko is frozen while any rig run or lap chain is live

Preps (`MXFS_FORCE_PREP=1 ./run.sh N tcp prep_cluster`, one per sweep arm) insmod the tree's `mxfs.ko` over the NFS-shared tree, and every harness derives its precondition from `modinfo mxfs.ko` of the tree, compared against each node's `/sys/module/mxfs/srcversion`. So a `make modules` mid-run is not queued for later; it reaches the next arm. Observed failures:

- A loop harness's lap 8 died `ERROR: cluster is prepped for 2/tcp (srcver=BE2A...), you requested 2/tcp (srcver=3DDE...)`, recorded `NO_TERMINAL_RECORD(rc=1)` / `infra=1`; nodes were healthy, the reference moved. The precondition check is load-bearing: it refused a verdict instead of measuring a stale module. Keep the srcversion+mounted precondition in every `tests/` harness. [[trap-never-rebuild-mxfs-ko-while-a-rig-harness-run-is-in-flight]]
- A rig-runner dispatched for two A/B arms, then a one-line fix and rebuild: the arms can land on different srcversions, or a node can read a truncated `.ko` mid-relink. [[trap-never-rebuild-mxfs-ko-while-rig-run-in-flight]]
- A "just compile-check the next site" `make modules -j8` during a delegated chain (deploy, 2 fault laps, 2 control laps) made `tests/tcp_lockreq_blackhole.sh` and `tests/live_holder_wait.sh` print `ABORT: <node> srcversion != tree` in 1 s on laps 2-4; ~25 min of rig time plus an extra deploy lost. When a chain reports that ABORT, first suspect the parent rebuilt, not the fleet. [[trap-a-make-in-the-tree-during-a-delegated-lap-chain-moves-the-srcversion-and-aborts-every-later-lap]]
- Sweep `s123a`: a rebuild between arms gave the storage arm `0EA7...` and the network arm `5E4A...`. Each arm's own `ck "prep deployed the tree build"` PASSed because each reads the tree at its own start, so nothing in the harness catches it; it shows only as two differing prep lines. The result is two half-matrices, not one matrix. [[trap-rebuilding-the-module-while-a-rig-lap-runs-splits-the-sweep-across-two-builds]]

Rule: source edits are fine; `make modules` (anything rewriting the tree's `mxfs.ko`) and edits to a shell script being executed (bash reads incrementally) are not. Compile-check BEFORE the deploy or after the chain reports DONE. If a build is unavoidable, build in a scratch copy (mind section 1) and never into the path prep reads. Always cite the per-run srcversion the harness reports (test1 `/sys/module/mxfs/srcversion`), not the tree's modinfo.

## 3. A control whose recovery step deploys the tree destroys the control

D-0960: the fix was built into the tree before the control lap ran on the old fleet build, and the control lap's re-form via `scripts/module_swap_deploy.sh` installs the tree's `mxfs.ko` (the fix); no old `.ko` remained. The single control iteration also landed the B-mastered root-page shape, which the old build already survived, not the recorded A-mastered shape. Run the control BEFORE building the fix, or copy the old `.ko` aside as `mxfs.ko.backup` (the only permitted name). A two-node lap on a per-resource path must name its locality (`LOCALITY=A|B|none`) and repeat until it gets the recorded shape (`WANT=`, `ITER_MAX=`). When a control cannot be re-run, prove the detectors against recorded evidence directories and say so in the changelog instead of claiming a control. [[trap-a-control-laps-recovery-step-deploys-the-trees-build-and-destroys-the-control]]

## 4. The tree is a superset of the product: check Kbuild before naming a site

Of 236 `.c` files under `xfs/ dlm/ pal/ mxfs_clayer/`, Kbuild compiles 129; 107 are not built. Not all are upstream leftovers: `dlm/mount.c`, `dlm/net2_*.c`, `mxfs_clayer/invalidate.c`, `pal/linux/xfs_hooks.c`, `pal/linux/xfs_drain.c`, `xfs/xfs_mxfs_dentry.c` are MXFS's own and uncompiled. A blocking-waits audit (309 raw matches, 44 sites) named `dlm/mount.c:1225` `bast_worker_fn`'s untimed cond_wait as unbounded; it is not in the module (`nm mxfs.ko | grep -c bast_worker_fn` = 0). `xfs_mxfs_dentry.c` defines a `mxfs_drevalidate` that looks live; the used one is in `pal/linux/xfs_super.c`. [[trap-a-source-sweep-over-counts-call-sites-by-every-file-the-kbuild-object-list-leaves-out]]

D-0958: a plan listed FS_IOC_FSSETXATTR and the ACL read as acquire sites; `make` then reported nothing to do. `xfs_ioctl.o` is absent from Kbuild, `xfs/xfs_stubs.c:98` stubs `xfs_fileattr_get/_set` to -EOPNOTSUPP, and `xfs_acl.o` and `xfs_handle.o` are excluded (also quota, realtime, zones, DAX/pNFS, compat ioctl, dahash test, fsmap, `xfs_sysctl.o`). The 0.84.19 CHANGELOG claim was corrected in 0.84.20. [[trap-a-call-site-read-from-the-tree-may-not-be-in-kbuild-check-the-object-list-and-xfs-stubs-before-making-it-a-boundary]]

Check before a source sweep becomes a work list or a site becomes a boundary:
1. `grep -n '<basename>\.o' Kbuild`
2. `grep -n '<symbol>' xfs/xfs_stubs.c`
3. `ls <dir>/<file>.o` and `nm mxfs.ko | grep <symbol>`

A symbol absent from `nm` cannot execute and owes no disposition. Presence in `nm` is also not sufficient (a branch can be compiled out); see `technique-ask-the-built-module-which-probes-exist-before-trusting-any-harness-that-counts-one`.

## 5. Two evidence-integrity traps from the same area

- Slab zombie: `kmem_cache_destroy` with live objects leaves a refcount-0 cache on the slab list that is still mergeable; the next `insmod`'s same-shape `kmem_cache_create` adopts it and re-reports the stranded objects at its own unload, repeating for the rest of the boot. D-0924 ("six xfs_buf objects leak at every unload", critical) cost ~10 sessions: three different builds showed the same six hashed addresses at the same offsets, even on an idle mount, which was read as corroboration instead of as one echoed object. The build that "fixed" it had merely grown `struct xfs_buf` by 16 bytes, so it stopped merging; 14+ clean laps accumulated against that confound. `/sys/kernel/slab/<name>` being an alias symlink (`:a-0001216`) means merged. Create caches with `SLAB_NO_MERGE` (via `mxfs_cache_create`, `pal/linux/xfs_super.c`; `slab_merge=1` is the control arm), prove with a positive control (`dbg_leak_bufs`, `tests/d0924_zombie_cache_ab.sh`), and ask which load's cache any "objects remaining" report belongs to. [[trap-an-unload-slab-leak-report-is-not-evidence-about-the-load-that-printed-it]]
- Repair at the measurement point: D-0496's record names two masks (`mxfs_dir2_datascan_lookup`, `mxfs_dir2_leafless_removename`, knob `dir_datascan_heal`), but a third, `mxfs_dir_rebuild_leaf_from_data` (knob `dir_leaf_rebuild`, default 1, fired from `xfs_dir_createname` on `MXFS_IF_DIR_LEAF_STALE` before a tenure's first mutation), sat exactly where an incoherent acquisition is observable and overwrote it silently. When hunting a producer that never reproduces, enumerate every repair that can touch the object, not just those the record names. Do not remove the repair; make it report: snapshot pre-repair state, diff, emit both divergent and clean outcomes (`P496-ACQ-DIVERGE` / `P496-ACQ-CLEAN`, 0.79.0). Census count must equal repair count or the instrument is blind. First run: 36 censuses = 36 repairs, zero divergence, but 81 rebuilds declined on directory format and the diff ran against in-core data, so a clean result is a bounded negative. [[trap-a-repair-sitting-at-the-measurement-point-destroys-the-evidence-it-would-have-produced]]
