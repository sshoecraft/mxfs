Common thread: a death, fence or survivor test that grades the wrong thing, never reaches the state it claims to test, or runs on a platform where the precondition does not exist. Most are DRBD-rig traps; a few are neighbours (QNAP PR keys, install path, teardown ordering, allocator floors). Newest first within each cluster where timing matters.

## Death and fence tests must reach the state under test

- **Hold the lock across the death.** `drbd_rig.sh death-test` passed every session because the victim always died between CAS swaps; `crash_audit` killed it holding its bakery ticket and the survivor's swaps EIO'd after 10 s, heartbeat failed, survivor self-withdrew (`P163-WITHDRAW-STAMP`). For any lock/lease a peer can hold across its death, test death WHILE held, deterministically (`mxfs.dbg_drbd_cas_hold_ms`, `DEATH_HOLD_TICKET=1`), and check clearance by proof (`P-DRBD-CAS-PEER-EXCLUDED`). [[trap-a-death-test-whose-victim-dies-between-swaps-never-tests-a-lock-held-across-death]]
- **Power-off hides every release path that needs an answer.** A powered-off peer answers nothing, so the guard's release-on-answer path was dead code in `self-restart-test`. On pve1 the peer was UP with DRBD unconfigured; the guard released it 65 s in, under the survivor's own startup fence, giving `P-DRBD-STARTUP-FENCE-UNPROVEN` and a refused mount (fix 0.90.69, `own_mount_pending`). Add a variant where the excluded peer is up and answering without the service. [[trap-a-survivor-test-whose-peer-is-powered-off-never-sees-the-guard-release-a-peer-that-answers]]
- **Do not release a fenced peer before the survivor's witness confirms.** `drbd_rig.sh fence-test`/`split-test` released the loser's inhibit 1-2 s after the fence; the peer rebooted and reconnected before the witness saw "off AND inhibited under the receipt's episode" (`P-DRBD-EXCL-NOT-YET`, `P238-DRBD-FENCE-NOT-YET link Connected` forever). Survivor stayed fail-closed with grants frozen and its unmount blocked forever (on 0.90.106 also the put_super UAF). Fix 0.90.107: `wait_mxfs_recovered` gates every release on `P163-RECOVERY-COMPLETE` + `P238-DRBD-FENCE-WITNESSED` (~12 s). Diagnose with `journalctl -t mxfs-rig-fence` on clyde. [[trap-a-drbd-test-that-releases-the-fenced-peer-before-the-survivors-witness-confirms-freezes-the-survivor]]
- **A platform pass says nothing about another platform.** The QNAP purges a frozen initiator's PR key ~40 s after freeze (PRgen unchanged); death lands ~60 s, so PREEMPT AND ABORT never has a key. The only certifying fence is the witnessed LU reset, admitted only on audited kernels; on 0.89.79 a hung PVE node froze its cluster (`verdict=kernel-unaudited`) while the Ubuntu rig recovered at +78 s. Run the freeze test ON the platform (PREP=pve); test key-present fencing on a conforming target (LIO); check `scripts/pve_libiscsi_crosscheck.sh` for new PVE kernels. [[trap-the-qnap-drops-a-frozen-nodes-pr-registration-40s-after-freeze-so-every-fence-there-is-key-absent]]

## Grading must follow evidence, not hard-coded roles

- **Symmetric fault: derive winner/loser first.** `fence_partition_reconnect.sh ARM=network` named A survivor and B partitioned; B won, and all six FAILs were attribution errors against a correct resolution. Grade roles from `fen_a`/`fen_b` (`P236-FENCE-CERTIFIED` counts), never hostnames; give the loser an instrument too. `bad_lines()` has two different bodies in two harnesses; a fence-notify shutdown is expected containment on the loser, `BUG:`/`Oops` never acceptable. A harness whose INFO says an outcome is legitimate and then counts it FAIL has two disagreeing graders. [[trap-a-two-node-arm-that-names-one-node-the-survivor-grades-every-assertion-against-the-wrong-side-when-the-other-one-wins]]
- **Assertions that encode the observed behaviour pass on the defect.** Live-prover mode 3 asserted the hang; the real defect was a retry gate that read only the platter. `scsipr` returned before PROUT when `arm_submit` failed (PRECOMMAND, retry armed), then `retryable()` saw `FENCE_CMD_MAY_HAVE_RUN` and disarmed, leaving FENCING + MAY_HAVE_RUN, no latch, no block, waiters hung. A durable arm can only say "may have"; whether it was issued is in-memory knowledge of the writing incarnation. Fix 0.89.63: per-slot witness `fence_boundary[slot]={victim,epoch,term}` keyed on all three fields (terms restart at 1), `retryable()` returns 2 for ours-and-armed, `P304-FENCE-RETRY-ARMLANDED`, `P238-FENCE-BOUNDARY-HELD`. Mode 3 now requires re-drive, a certificate after a completed command, and a served stat. [[trap-a-retry-gate-that-reads-only-the-platter-disowns-the-arm-its-own-node-made-under-a-lost-answer]]
- **A coverage floor ruled from harness shape demands what the design forbids.** The allocation-coverage witness floors (same-AG carving by both nodes, overlap, >=1 chunk release) failed at 2/tcp because `xfs_dialloc_pick_ag` pins files and dirs to the affine AG, `mxfs_ag_inode_owned` keeps nodes in their stride, and `mxfs_inode_chunk_may_delete` is false on clustered mounts. Read the allocator path and list what the design FORBIDS before ruling a floor, and put those facts in any consult prompt. Re-scoped: partition integrity, per-node >=2 carves in affine AG, span overlap, releases == 0 as invariant plus a live empty-retain-reuse lifecycle. [[trap-a-coverage-floor-ruled-from-the-harness-shape-alone-can-demand-what-the-module-is-designed-to-forbid]]

## Harness mechanics that fake or hide results

- **Proxmox `/run` is noexec.** A slow-witness wrapper staged there failed `P-DRBDW-NOEXEC rc=-13` at once and the arm tested nothing. Stage executables in `/dev/shm` or root fs, and assert the helper actually ran; a fast verdict with empty reasons is an exec-failure signature. [[trap-proxmox-mounts-run-noexec-so-a-usermode-helper-staged-there-fails-eacces]]
- **Unmount the survivor before destroying the peer** when the lap's subject is the next mount. Unmount inside the 62 s dead-confirm window (31 beats x 2000 ms) hit rc=124 at a 60 s bound. Staging is identical either way. If a harness must unmount inside the window, derive the bound from window plus unmount work. [[trap-unmounting-a-survivor-inside-the-peer-death-confirm-window-costs-the-whole-window]]

## Product-side lessons surfaced by these tests

- **Teardown: NULL-then-free protects only re-readers.** `put_super` cleared `m_mxfs_dlm`, `synchronize_rcu()`, freed the ctx while `xfs_log_worker` sat in a 20 s acquire holding it; Oops, reproduced by `tests/rig_unmount_cover_race.sh`. Cancel every worker that can be inside a call (`cancel_delayed_work_sync(&m_log->l_work)`) ABOVE the free on every path including error/skip paths (0.90.106). A directed repro must park AFTER the pointer read, or it resumes into NULL and looks like "no bug". [[trap-clearing-m-mxfs-dlm-does-not-stop-a-worker-already-inside-an-acquire]]
- **DRBD victim records carry no identity.** `mxfs_disklock_set_identity()` runs only under `if (ctx->pr_key)`, and DRBD registers none, so victim host/boot UUIDs are all zero (`P-BOOT-SCAN-NOIDENT`). Treat zeros as "not recorded", never compare them as "another host". The bootstrap-owner record does carry real UUIDs. A DRBD victim is bound by get_tree_bdev uniqueness, exclusive backing-device hold, and exactly two endpoints. [[trap-a-drbd-victim-record-carries-no-identity-block-so-its-host-and-boot-read-as-zeros]]
- **`make && make install` is the user's path.** At 0.90.42 it installed only `mxfs.ko` (no current mkfs, witness, fence-peer handler, modprobe.conf, man pages, udev); a stale 0.11.39 mkfs formatted the volume and the unfenced DRBD pair lost pve2. The node file list lives only in `mxfs_stage_node_files` (`packaging/common.sh`), shared by `install_source.sh` and `mkdeb.sh`; `mkrpm.sh` has its own copy to keep in step. Install refuses over existing .deb/.rpm/DKMS. Release claims need a clean-clone install-mkfs-mount; safety instructions must be reachable from the README and enforced by the module. [[feedback-users-install-by-git-clone-and-make-install-so-that-path-must-produce-a-working-node]]
